# 第二轮：统一歧义规则，让回答忠实使用证据

状态：待审阅。依赖第一轮离线检查通过。此轮先做开发和离线检查，不运行正式模型测评。

## 1. 统一何时追问

拟采用同一句业务规则，并同步到产品规范、Skill、题目和评分：

> 用户需要单一范围的结论，现有证据不能确定该范围，而且不同选择会改变结果时，先提出聚焦澄清。用户明确要求比较、允许多范围，或问题本身要求分别分析时，才并列给出结果。

允许先查目录、候选身份和必要事实来判断是否真的有歧义；不要求看到同名就问。已有明确引用或前文确认时直接完成。不能先计算并合并多个区域，再用结尾的可选邀请代替必要澄清。

例子：

| 用户要求与证据 | 应怎样做 |
| --- | --- |
| “看北区可用资源”，确有两个北区且结果不同 | 问港口侧还是山麓侧，得到回答再给该区结果 |
| 明确引用港口侧区域后问“这里有哪些资源” | 直接分析，不重复确认 |
| “两个北区分别有哪些资源” | 分别给结果，不强迫选择一个 |
| “把两个北区合起来统计” | 明确联合范围并去重；边界按联合几何或用户指定口径处理，不直接相加 |

旧A08/P03不重写分数；新版本按新规则评分。固定脚本答案只有实际追问匹配时才发送，不用隐藏偏好判错。结构化与普通文本澄清分开记录，不要求必须采用某一种API才算业务成功。

## 2. 工具怎样改

继续扩展现有资源结果的公开投影，不另造“模型必须填写的完成证明”。优先复用已有事实、来源和时间字段，只补目前缺少的明确原因及适用对象。

| 当前容易误解的地方 | 拟调整 | 不能做什么 |
| --- | --- | --- |
| `unknown`原因不直观 | 在相应资源上说明条件未核实、证据过期、来源冲突或缺少报告，并带原依据 | 未收到回执不能改成未放行 |
| 多种时间并列 | 区分来源快照时间、固定版本时间、本次查询时间、事实生效/上报时间 | 不把旧asOf字段直接改名为查询时间 |
| 每组数量范围不同 | 类别、单位、数量含义和scope随每组数量一起返回 | 不用第一组scope概括全表 |
| 缺实体键统一警告重复 | 区分单体身份未知、汇总成员覆盖不足、已知成员重叠与位置未知 | 没有单个entityId不等于汇总成员未知 |
| 平台引用和分配证据混淆 | 明示引用只支持关联，分配/支援各自引用实际有效证据 | 不把建引用说成调配或可用性确认 |

状态原因可有多个，不能为给一句简短原因而丢掉同时存在的冲突或过期。具体字段名在实施前核对既有契约，避免平行维护重复状态。

如公开投影改变已持久化回执正文或校验，沿用第一轮确定的版本兼容策略；不静默改旧版本渲染与哈希。

## 3. Skill与回答怎样改

- `spatial-analysis`：收紧“独立解释即可给条件答案”的宽泛出口；保留纯图形任务直接计算和已明确范围无需追问的能力。
- `map-annotations`：保留显式引用、受控导入、保存和采用规则；只在涉及新结果含义的地方同步，不增加新Skill。
- 回答先给用户所问的名单、数量与状态，再说明直接影响结论的未知、覆盖缺口和冲突。用户问依据或方法时须完整回答，不能靠省略必要信息提高分数。
- 版本ID、算法细节及内部接口过程不默认扩写；已有结果卡片保留可追溯依据。前台过程说明同样不得无据断言“未查询”“已保存”“必须先关联”等。
- 宿主只保留少量稳定规则，不堆长提示词；不强制每次读取Skill，不新建自由文本拦截器或付费裁判Agent。

主要修改位置预计为资源服务与结果投影、现有两份Skill，以及 `.trellis/spec/backend/task-resource-query.md` / `task-resource-experience.md`。确需展示新字段时才修改现有卡片；不改地图点选与引用行为。

## 完成标准

两轮形成的工具、规则、Skill和评分口径一致，历史兼容检查通过；必要事实没有因“简洁回答”被隐藏。新评分器能区分产品失败、测试基础设施失败、解释错误与表达建议，并保留独立审阅及裁决版本。再冻结版本，进入单独审核的验收阶段。

本轮不实现任意自然语言消息自动改资源字段，也不修改关系覆盖为全量；用户口述与来源确认继续分开。模型是否仍误读证据，留给新实例验收判断。
