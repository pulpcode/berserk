# 第一批：先把任务资源的业务含义讲清楚

2026-11-02｜默认范围已确认，第一批已获准实施｜[四批总览](README.md)

实施进展：本批已完成并通过离线及独立检查，详见[第一批完成报告](../../11-02-task-resource-contracts/results.md)。正文保留获准实施的范围与标准；第二、三、四批尚未执行。

## 1. 本批目标

把“哪些算本任务资源、是否可用、在哪里、为什么这样判断”写成统一规则和受校验的数据定义。这里的“数据定义”就是后端、工具和界面共同遵守的字段含义与填写规则。

**本批完成后，给定一组结构化样例，不调用模型也能判断应纳入哪些记录、哪些可以合并、哪些必须待核验。** 自动查询、地图交互和 Agent 完整回答分别在后续批次完成。

用户于 2026-11-02 确认默认范围，并授权按本方案实施第一批。默认同时考虑任务相关来源、有依据的支援、当前草稿明确资源和可核实会话补充；未知状态单列，用户明确限定优先。其余业务与数据规则作为本批实施依据；本文件不表示后续三批已获准开工。

## 2. 为什么先做这一批

当前代码已具备固定版本、来源引用和空间计算，但还缺少下列业务定义：

| 缺口 | 容易出现的误解 | 本批处理 |
| --- | --- | --- |
| 草稿没有受校验的“实际资源”字段 | 消防车图标被当成真实可用消防车 | 明确对象代表什么 |
| 任务引用与分配关系未分开 | 资料提到某辆车，就说已分配给任务 | 分开记录关联与分配证据 |
| 来源资源数量主要限定为“辆” | 车辆、船、设施及对象条数混算 | 明确类别、单位和数量含义 |
| 引用资料不等于同一实体 | 同名合并，或副本重复计数 | 明确实体关联及其建立依据 |
| 图形位置不一定是实际位置 | 用计划停靠点回答船现在在哪里 | 区分实际、计划、估计位置 |

现有代码依据见总览末尾。无需为这些缺口另建任务系统、知识库或空间服务。

## 3. 本任务资源默认从哪里找

先遵守用户明确限定；用户未限定时，按下面的默认范围查询。**可访问不等于与本任务相关；进入候选范围也不等于确认可用。**

| 数据 | 默认如何处理 | 纳入依据 |
| --- | --- | --- |
| 本任务已关联的资源 | 纳入，保留实际任务关系 | 任务记录、关联资料或可核实业务引用 |
| 有依据的潜在支援资源 | 纳入，单列为可申请支援 | 来源提供的支援关系，或已配置且可解释的支援查询规则 |
| 当前会话绑定草稿中的明确资源 | 纳入补充信息，未知状态保留 | 草稿属于当前任务，且对象明确标为资源 |
| 已正式纳入任务的发布信息 | 使用其固定发布版本 | 任务采用记录或明确的任务资料关联 |
| 当前会话中仍适用的用户明确信息 | 作为带出处的补充 | 具体消息、资源身份、时间和适用范围 |
| 其他会话的实时草稿 | 默认不纳入 | 用户明确引用后，仍检查读取权限 |
| 能查询到但没有任务关联依据的外部资源 | 不自动纳入 | 可按用户明确要求另查，不能把“附近”当成已关联 |

补充说明：

- “只数这个草稿图层的点”是图形统计，不要求每个点都认证为业务资源。新规则不能破坏此类明确请求。
- 任务关联资源可能在区域外。先确定资源范围，再按问题判断位置，不能用任务区域标签提前排掉可能的支援资源。
- 当前草稿中的实际资源可以标为“任务相关”，但不能据此说“已分配”。
- 未配置支援查询能力时，明确说明这部分未覆盖；不扫描全部可访问系统后自称取得全部支援资源。
- 没有当前任务或会话绑定时，不能退回“查询全部资源”；返回缺少任务上下文，必要时请用户明确范围。

## 4. 一个对象需要分清哪些信息

### 4.1 对象代表什么，与记录性质分开

拟增加一组可选、受后端校验的资源字段。旧对象未填时保持“未注明”。

| 信息 | 通俗含义 | 示例 |
| --- | --- | --- |
| 对象含义 | 实际资源、拟定部署位置、普通标注，或未注明 | 实际救援船；拟定停靠点 |
| 资源类别 | 这是什么资源 | 消防车、救援船、消防栓 |
| 记录粒度 | 表示单个实体，还是一组资源的汇总 | 一辆车；某站可用车辆汇总 |
| 记录身份 | 定位某条来源记录或固定草稿对象 | 来源系统＋对象 ID；草稿集＋版本＋对象 ID |
| 实体关联 | 经核实，这条记录代表哪个实际资源 | 受控关联到来源资源 R1 |
| 数量及单位 | 数了什么、多少、什么单位 | 对象条数；可用车辆 3 辆 |
| 任务关系 | 它为什么参与当前任务分析 | 已分配、潜在支援、仅相关、未确认 |
| 可用状态 | 在所述时间和条件下能否使用 | 可用、不可用、未知；附条件 |
| 位置含义 | 几何表示实际位置、计划位置还是估计位置 | 当前报告位置；计划部署位置 |
| 证据与时间 | 上述信息从哪里来，何时成立 | 来源版本、固定草稿、用户消息；业务有效时间 |

标为“实际资源”表示这条记录声明自己代表资源，不单凭这个字段认证现实存在或当前可用；仍须保留声明来源和相关事实依据。

继续保留 `informationRole`：现场记录、研判、拟定方案。它描述信息性质，不能代替对象含义。

例如：一辆真实消防车出现在部署方案中，仍可关联该实体；图上的位置却可能是计划位置。不能把所有 `plan` 对象排除，也不能把其中的坐标当作车辆当前位置。

首版规范先覆盖车辆、船舶和设施的计数及未知类别。类别由受控映射提供，不靠模型根据名称造类别；本批不建设完整行业分类库。

### 4.2 任务关系与可用状态分别保存

| 任务关系 | 表示什么 | 不能推出什么 |
| --- | --- | --- |
| 已分配 | 有具体记录证明已分配给本任务 | 不能推出设备正常、已经到场 |
| 潜在支援 | 符合有依据的支援范围 | 不能推出已获调配批准 |
| 仅相关 | 被任务资料或当前草稿明确关联 | 不能推出已分配或可用 |
| 未确认 | 资源身份已知，但任务关系不足或冲突 | 不能计作已分配资源 |

可用状态另设“可用／不可用／未知”，同时记录时间、条件和依据。存在尚未满足的条件时，不能计入“已确认可直接使用”。冲突是额外的信息问题，不用一个状态值覆盖所有证据。

“本任务可用资源”的回答要区分：已分配且确认可用、可申请支援但调配待确认、状态或位置待核验。设备可用不等于任务有权立即调度。本轮只报告事实，不生成调度决策。

### 4.3 数量、单位和位置不能省略含义

- 对象条数、实体数量、来源报告的可用数量分别表达。读到 1 条记录，可能代表 3 辆车。
- 只有类别、单位、数量含义、统计范围和时间可比，且不存在重叠计数时才能合计。消防车与救援船分别列出，不合成“4 辆”。
- 数量未知与数量为 0 分开；计数不接受负数、非整数。首版不做重量、面积库存等单位换算。
- 汇总记录与其中单体明细，缺少覆盖关系时不相加，也不把汇总记录当作另一个实体。
- “某站有 3 辆可用车”加上站点坐标，不证明 3 辆车此刻都在站点。只有位置确实适用于所统计资源时，才参与相应空间结论。
- 缺位置、仅有计划位置、位置已过期或冲突，都不等于区域外；可以计算位置已知的部分，但须保留未判断部分。
- 沿用现有经纬度约定与几何校验，不借本批改变空间算法。点在边界线上时保留“边界上”分类，不暗中算入内部或外部。

## 5. 同一个资源、多种证据如何处理

### 5.1 区分三种关联

| 关联 | 它证明什么 | 它不证明什么 |
| --- | --- | --- |
| `sourceRefs`：资料引用 | 记录引用过哪些来源 | 不保证始终代表同一个资源 |
| `originFeatureRef`：派生记录 | 图形从哪个固定对象派生 | 不保证复制后仍是同一真实实体 |
| 拟新增的实体关联，例如 `represents` | 该标注明确表示某个业务实体 | 不证明状态或位置仍然最新 |

实体关联只能由受控导入、用户明确关联或已验证的实体映射建立；后端核对目标权限并保留建立依据。单凭同名、图标、坐标接近或模型填了一个有效 ID，不能建立受信关联。

普通复制不能一概继承实体关联。明确作为同一资源的另一种展示时可保留；用户新建另一辆车或关系无法确定时，保持独立，不自动合并。

有可靠实体关联时，业务实体计数只计一次，但保留所有来源。没有关联时保留独立记录，必要时标注“是否重复待核验”；不能把尚未去重的记录数包装成确定的实体总数。

### 5.2 不建立“来源系统永远优先”或“草稿永远优先”

每个关键事实保留自己的来源、时间和适用范围。同一实体的实际位置、计划位置可以同时成立；它们不是二选一冲突。

对同一事实的不同说法，按以下方式处理：

1. 同一来源明确提供替代关系或后续有效版本时，按其契约读取，并保留原固定结果。
2. 不同来源相互矛盾且没有明确优先依据时，保留冲突，相关结论待核验。
3. 已过期的信息不继续作为当前确认结论；只知道查询时间，不代表知道业务生效时间。
4. 尚未定义有效期的来源，注明“截至某时的报告”，不自行设统一的过期时长。
5. 用户明确补充可以作为用户报告保留。它不自动变成外部系统事实、正式调度回执或已保存标注。

会话补充复用 Pi 原生消息与已有引用，不建立第二套记忆库。首版只接受能定位到具体资源、具体消息和适用范围的补充；模糊陈述留给 Agent 定向核对或澄清。程序验证引用与权限，不声称能自动证明所有自然语言都被理解正确。

## 6. 数据交接需要约定什么

本批定义下表内容；第二批实现实际查询和固定结果。字段名可以在实现时收敛，业务含义不能自行改变。

| 交接部分 | 必须说明的内容 | 缺失时怎么办 |
| --- | --- | --- |
| 资源记录 | 稳定记录身份、粒度、类别、数量及含义；关联实体如有则提供 | 无法识别实体时保留独立记录，不认证同一性 |
| 事实证据 | 任务关系、可用状态、位置分别对应来源、版本、时间和条件 | 不影响身份的缺项保留为未知 |
| 任务相关查询 | 支持哪些关系、任务 ID 如何映射、支援范围如何定义 | 能力不足明确返回，不能退回全域后宣称完整 |
| 来源能力 | 可查询的类别、单位、筛选能力、分页和固定快照规则 | 不支持的筛选报能力不足，不静默忽略 |
| 覆盖情况 | 哪些来源已读完、哪些只有局部、哪些不可用 | 查询成功不自动表示“任务资源全集” |
| 空间可判断性 | 哪些资源有适用几何，哪些缺失、计划位置或冲突 | 对未判断资源保留清单和原因 |
| 合并依据 | 哪些记录代表同一实体，为何只计一次 | 依据不足不合并 |

特别区分两件事：**清单是否读完**与**清单中的位置是否都能判断**。例如完整读到 5 项，2 项缺位置，仍只能对另外 3 项给出空间分类。

现有 `availableCount` 数据继续可读，但不能补造“已分配”等新事实。其统计粒度、类别及时间由来源映射明确；映射不够时保留旧数量和限制，不把旧数据强制改成新实体清单。

第一批用模拟来源验证上述定义。真实外部系统的接口、字段映射和接入权限，仍须逐个核实；没有真实接入，不宣称已经覆盖中澳实际资源。

## 8. 用具体样例确认规则

以下全部是**拟构造的开发数据**，不是历史实测，也不是第四批封存题。位置“内／外”由独立几何预期给出。

### 样例一：同一个问题应得到什么资源清单

用户已明确选中区域 A，问：“区域内，本任务有哪些可用资源？”样例已明确 R1、R2、R3、R4、R5 各表示不同的单体车辆，每项 1 辆；数量不是从记录条数猜出。

| 记录 | 输入事实 | 应如何处理 |
| --- | --- | --- |
| R1 来源消防车甲 | 已分配本任务、确认可用、实际位置在 A 内 | 纳入已确认资源，1 辆 |
| D1 草稿消防车甲 | 受控关联到 R1，画的是 A 外的计划位置 | 与 R1 只计一个实体；不覆盖 R1 的实际位置 |
| R2 来源消防车乙 | 有潜在支援依据、设备可用、调配待确认、实际位置在 A 内 | 单列可申请支援，1 辆，不说已分配 |
| D2 草稿救援船丙 | 明确资源、单体 1 艘、当前任务草稿、报告位置在 A 内、可用性未知 | 纳入待核验，不能称确认可用 |
| D3 草稿停靠点 | 拟定部署位置 | 不计为实际船舶 |
| D4 旧草稿船形图标 | 没有资源语义 | 保持未分类，不据图标计作资源；说明存在未分类记录 |
| R3 来源消防车丁 | 有读取权限，但仅属于无关任务、位置在 A 内 | 不纳入本任务默认范围 |
| R4 来源消防车戊 | 已分配本任务、故障、实际位置在 A 内 | 纳入分析清单，列为不可用，不计确认可用 |
| R5 来源消防车己 | 已分配本任务、可用、缺实际位置 | 纳入待核验，不能判断在 A 内或外 |

预期资源清单为 R1、R2、D2、R4、R5，共 5 项；D1 关联到 R1，不重复计数。A 内已分配且确认可用 1 辆，潜在支援 1 辆，可用性待核验 1 艘，不可用 1 辆；另有 1 辆位置待核验。D4 只形成未分类提示，不计入这 5 项资源。

### 样例二至十二：需要明确通过的边界情况

| 编号 | 输入与请求 | 应纳入／排除及预期结论 |
| --- | --- | --- |
| B1-S02 明确数图形 | 用户指定草稿图层，其中 4 个点都没有资源语义 | 回答 4 个点；不因未认证资源拒绝图形统计 |
| B1-S03 同名记录 | 两系统都有“救援车一号”，记录 ID 不同，缺少跨系统实体映射 | 保留 2 条独立记录，不按名称合并；是否重复待核验，不声称确定有 2 辆 |
| B1-S04 引用不等于实体关联 | 手工点的 `sourceRefs` 指向 R1，未建立受控实体关联 | 保留引用；不据此合并或继承可用性 |
| B1-S05 信息冲突 | 同一船的两个有效来源，一个可用、一个故障，无优先规则 | 身份可合并，状态保留冲突；不计确认可用 |
| B1-S06 单体与汇总 | 一条记录报告某站 3 辆可用车，另有其中一车的明细 | 不得算成 4 辆；有覆盖依据才能合并统计，没有则分别报告 |
| B1-S07 混合单位与未知 | 车辆 2 辆、船 1 艘、另一船数量未知 | 分类给出已知数量及未知项，不能说共 3 辆或未知为 0 |
| B1-S08 只有计划位置 | 一辆实际车关联的草稿点在 A 内，但只是计划位置 | 纳入资源清单；当前位置待核验，不计确认在 A 内 |
| B1-S09 归属与几何相反 | 资源登记属于 A，实际位置在 A 外 | “属于 A”与“位于 A 内”给出不同结果；登记关系不能替代几何 |
| B1-S10 空结果与失败 | 一来源完整返回空；另一来源不可用 | 前者在其范围确认为 0，后者未覆盖；不能说任务没有资源 |
| B1-S11 其他会话与发布版 | 当前任务采用了其他会话发布的固定版本，原草稿后来改变 | 读取被采用版本，不跟随读取另一会话的新草稿 |
| B1-S12 会话补充与时效 | 用户明确报告某车于指定时间故障；后文只重复旧助手“可用”说法 | 保留用户报告及时间；旧助手自述不是新证据，不自动改外部系统或草稿 |

样例一编号为 B1-S01。B1-S02—12 都应有对应的具体 ID、字段、依据和独立预期文件；本次只审阅其业务要求，实施时再落成测试数据。

## 9. 兼容与权限边界

- 新资源字段可选；旧点、线、面、文字继续读取和编辑，不批量认证或迁移成资源。
- 旧草稿、发布版、空间结果、composer 历史正文和哈希保持原样。若新持久格式需要版本升级，增加版本读取，不改旧版解释。
- 新字段中涉及来源或私有对象时，沿用现有授权及公开投影规则。不得通过实体关联泄露其他会话私有引用。
- 创建资源语义、建立实体关联、保存草稿、发布、任务采用都是不同动作；查询不自动执行这些写操作。
- 历史评测保持原规则、原分数。新业务规则以 `task-resources-v1` 单独记录，不倒改旧失败。

## 10. 第一批验收标准

| 验收项 | 通过标准 | 提供的证据 |
| --- | --- | --- |
| 规则可判断 | 12 个开发样例的纳入、排除、合并、状态、数量和缺口均有明确预期，无互相矛盾规则 | 业务预期表及审阅记录 |
| 字段可校验 | 非法关系、负数/小数计数、无依据实体关联等被拒绝；合法未知值可保留 | 离线契约与服务检查 |
| 不混淆事实 | 任务引用不升级为分配；计划位置不升级为实际位置；未知不改为 0 | 对应反例检查 |
| 兼容可证明 | 旧数据可读、原哈希不变；旧未分类对象不自动补字段；旧数量解释不变 | 固定历史样本与兼容记录 |
| 权限不扩大 | 新字段、复制和公开投影不绕过原权限；模型不能填身份字段授予权限 | 授权与公开投影检查 |
| 可交给第二批 | 数据字段、来源能力和失败含义都有明确约定；真实来源缺口单列 | 数据定义和交接清单 |

本批验收以离线、确定性检查为主，不需要付费模型。通过只证明业务定义和数据承载可用，不证明 Agent 已能正确完成任务。
