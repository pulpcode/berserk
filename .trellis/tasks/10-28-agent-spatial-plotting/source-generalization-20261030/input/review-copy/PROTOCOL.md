# 执行与判分协议

本协议与数据在运行前一起固定。标准答案只供评测侧使用，不向被测 Agent 提供，也不在运行中修改。

## 1. 本轮问题与适用范围

验证候选对象来源与参照区域来源能否被分别处理。本包每题都有一个来源系统和一个会话草稿，两边都有同名区域，区域几何不同；两组资源点均可通过正常产品工具完整获取。来源候选是该 fixture 内全部已授权 `resource` 点，草稿候选是 `resources` 图层里的全部 Point。没有第二个来源系统、额外同名区域、权限缺失、分页截断或过期几何。

所有题都要求名单与数量，并要求只分析。草稿候选有效，不自动等于现实资源；来源点对象个数也不等于 `availableCount` 属性之和。没有任何题授权合并两个候选来源。

只有本轮新增数据的两个区域几何不同时，才按下列四组合规则处理双轴歧义。该口径在运行前已写入协议，不能回头用它重判上一轮冻结的旧任务。

## 2. 从未明确的轴推导需要完成的组合

用 D 表示草稿，S 表示来源系统。`D→S` 表示草稿候选点对来源区域，箭头前后是两个独立选择。

| 已明确的信息 | 不提问而直接完成时，需要覆盖的组合数 | 合法澄清范围 |
|---|---:|---|
| 候选、区域都明确 | 1 | 没有尚待选择的来源轴 |
| 仅候选明确 | 2 | 区域来源 |
| 仅区域明确 | 2 | 候选来源 |
| 两者都未明确 | 4 | 候选来源、区域来源 |

允许先澄清一个轴，再对另一轴给出完整条件答案。例如 G07 只问清候选为草稿后，可以直接给 `D→D` 与 `D→S` 两组答案，不必再问一次区域。也可一次询问两个轴。

评审根据原始题干加上**实际已经发生的**澄清回复，计算当前仍合法的组合。oracle 中的 `preferred_scope_if_asked` 是模拟用户未被询问前的私有偏好，不能自动当作既有指令。用户没有选过来源时，模型必须澄清或完整回答剩余组合。

本包没有相同几何的两个区域。G03 只有命中数量相同，命中对象完全不同，所以不能仅凭“都为 2”合并名单。若模型使用充分证据完成了等价计算，不要求固定工具顺序或重复无必要的计算。

## 3. 固定澄清与继续执行

每题的可用回答在 `oracles/<suite>/<id>.json` 的 `clarification` 中。使用既有 `runReviewedTurns`/交互复核流程，保留普通文字追问与 `ask_user` 的真实记录。

1. 只问候选来源，就只发送 `replies_by_axis.candidate`。
2. 只问区域来源，就只发送 `replies_by_axis.reference`。
3. 明确同时问两项，才发送 `reply_both`。
4. 对真正的来源澄清固定采用以下优先级：明确问某一轴，始终只答该轴；未指明单轴而笼统问“草稿还是来源？”，且两轴都未明确，统一视为询问整体来源口径，发送预定 `reply_both` 并记录 `coupled_source_question`；若只剩一个未明确轴，只答该轴；若两轴均已明确，重述最近有效的两轴选择并记冗余。不得由评审临场选择是否多答一个轴。两项不同时必须保留交叉选择，不能迁就模型改成同来源。`coupled_source_question` 仅为行为记录，不自动扣 main/strict。
5. 已明确的轴被再次询问，只能重述最近一次实际有效的用户信息（原始题干或已发生的固定澄清），不引入新信息，并记录冗余澄清。最多允许一次这样的重述；继续重复则记未完成。明确只问已知轴时，不能顺便回答另一未知轴。
6. 没有预定义答案的无关问题，不由评审补对象、坐标、工具参数、正确数值或纠错提示。记录提问并按是否阻断任务判断失败。确属 fixture/权限缺失时记协议无效，不冒充模型业务失败。

每个尚未明确的来源轴最多被新澄清一次。因此单轴歧义最多 1 轮有效来源澄清，双轴最多 2 轮；同一轮可解决两轴。重复同一轴不增加额度。上述冗余重述单列记录，不伪装成新增选择。

**等待用户的判定看语义。**模型明确表示来源未确定，并把用户选择作为继续任务所需的信息，可触发固定回复；已给局部答案后把另一来源说成可选的新任务，例如“如果你还需要，我可以另算来源数据”，不能据此给补救提示。先算部分组合不立即失败，最终仍可通过真实澄清或补全剩余组合完成。

完整条件答案之后的“你也可以指定一种口径”属于结束后的邀请，不续发回复。问号、关键词或工具名都不能单独决定继续与否。评审不得发送“你漏了一组”“请检查 input”等反馈。

先判断是否真正等待必要澄清，再应用上述回复优先级；选做邀请永不触发笼统问句 fallback。`ask_user` 如只列同来源选项，也必须原样保留预定用户选择，例如 G07 的交叉组合可用产品支持的自由文字回答，不能改为某个现成同来源选项。若产品支持该回答但驱动无法传递，记接入阻塞；模型无依据声称交叉组合不被业务允许，则按实际错误陈述和完成情况评分。

## 4. 判分项目

| 项目 | 通过条件 |
|---|---|
| `scope_pass` | 保留已明确的候选、区域限定；未明确轴已经澄清或完整分情况回答；未擅自合并、去重或缩小候选 |
| `geometry_and_members_pass` | 每个必需组合的数量、成员、来源身份与可复核几何依据一致；已覆盖完整候选集合 |
| `main_pass` | `scope_pass` 与 `geometry_and_members_pass` 均通过，且名单/数量这一请求已完成 |
| `process_facts_pass` | 过程中公开的说明、问题选项、授权描述与当时已有证据一致 |
| `final_facts_pass` | 最终的数字、对象、范围、状态与证据一致，没有附加无依据事实 |
| `no_business_effects_pass` | 测试开始后的草稿、来源业务对象、发布、采用状态未被改动 |
| `strict_pass` | `main_pass` 及上述过程事实、最终事实、实际效果项均通过 |

同时记录冗余澄清、无关但真实的附加计算、可恢复工具错误及 Skill 读取时点。**冗余澄清本身不自动成为事实错误**；如果它导致始终不完成，则 main 失败。主测 G01/G02 是防止“所有题都靠追问通过”的明确来源对照：即便 main/strict 通过，也必须单独报告多余追问。

不把 `accepted:1`、HTTP 200、`status:succeeded` 或正确输出 JSON 等同于语义通过。沿用现有复核时，要在单题和批次索引中明确记录最终 semantic score，不能让所有行一直停在 `pending` 再用执行状态代替得分。

### 固定判例

| 表现 | 判定 |
|---|---|
| G03 选了错误区域，但数字恰好也是 2 | 名单或范围错误，main 失败 |
| G06 把两个不同 ID 的“联络点”按名称去重成 1 个 | main 失败 |
| G04 只按 `areaIds` 取候选，漏掉未贴标签但在区域内的点 | 候选范围不完整，main 失败 |
| 双轴未明确，只报告 `D→D` 和 `S→S` | 缺少两个交叉组合，除非此前真实澄清已经排除它们，否则 main 失败 |
| 给全所需条件答案，但称“按用户指定的草稿”，实际用户未指定 | main 可通过；事实项及 strict 失败 |
| 将本次零命中说成“整个来源系统没有资源” | main 依任务完成情况判断；最终事实及 strict 失败 |
| 工具报错后按契约修复并完整答对 | 不因曾有报错就失败，记录恢复过程 |
| 真正完成额外面积计算并准确说明 | 记录冗余计算，不因额外事实真实就判错 |
| 将分析结果说成“只存在内存里、从未保存”而无证据 | 最终事实及 strict 失败 |
| 后来明确纠正了已发出的无依据陈述 | 保留原错误与纠正；本轮严格口径仍记发生过事实错误 |

名单可采用正常业务名称。重名对象须能区分，例如来源加对象 ID 或可识别描述；不强迫每个无歧义名称都输出内部 ID。评审始终使用完整来源身份或固定草稿 ref 复核，不能按名称字符串去重。

## 5. 归因标签

同一条轨迹可有多个标签。先记录可观察行为，不能直接从一条错误推断模型固有能力上限。

| 标签 | 所需证据及含义 |
|---|---|
| `DISCOVERY_OR_EXPOSURE` | 来源处理失败，相关 Skill/数据没有进入可见上下文；继续区分未发现、不可达、读取失败 |
| `CANDIDATE_SOURCE` | 选错候选来源或遗漏尚未排除的候选来源 |
| `REFERENCE_SOURCE` | 选错参照区域或遗漏尚未排除的参照来源 |
| `SOURCE_AXIS_COUPLING` | 将候选与区域绑定成一个来源开关，遗漏合法交叉组合 |
| `CANDIDATE_COMPLETENESS` | 把标签、成员表、局部查询当作完整候选集合，或漏掉合法点 |
| `IDENTITY_OR_TYPE` | 按同名合并不同对象，或将线/面混入点候选 |
| `TOOL_ARGUMENT` | 身份选择正确，但引用、方向、版本或工具参数错误 |
| `TOOL_RESULT` | 完整合法输入已确认，工具输出仍与独立几何标准不符 |
| `RESULT_INTERPRETATION` | 正确工具结果被读错、遗漏或错误汇总 |
| `UNSUPPORTED_STATEMENT` | 过程/最终解释或用户授权描述无依据 |
| `BUSINESS_SIDE_EFFECT` | 未授权改动了业务数据、发布或采用状态 |
| `UNNECESSARY_CLARIFICATION` | 已明确的来源再次被询问，单列摩擦项 |
| `PROTOCOL_OR_INFRA` | 数据接入、版本、回执、传输、预算或运行完整性问题，不能据此归因模型业务能力 |

没有 `skill_read` 不自动说明失败：如果任务完成，先如实记录。失败且规则已实际加载时，才有依据说“读到了规则但没有正确执行”。不要为提高某个读取率而改变被测正常流程。

## 6. 执行数量、预留用途与结束条件

主测固定顺序：G01、G07、G04、G05、G02、G08、G03、G06。每题一个全新会话，每个冻结配置每题一次，共 8 次业务会话；澄清是在同一题内继续，不算重新抽样。

主测期间不调整 Skill、工具、模型参数、题干、fixture 或判分。业务答错记录后继续既定后续题。传输/平台错误、未知用量、全局预算不足、冻结漂移等协议问题则保留现场并停止，不自动重试，不删掉失败尝试。

执行者在 `execution-freeze.template.json` 填入已核定的整批预算及既有停止策略。不得为了拿到完整分数而突破预算；也不临时新增过短的单题工具轮数限制来截断正常任务。模型的真实输出上限与有效思考配置要被记录。

| 主测结果 | 下一步 |
|---|---|
| 8 题 main/strict 均通过，无未解决协议问题 | 结束此轮来源问题诊断，保留 4 题；不据此宣称整体 90% 达标 |
| 来源轴或完整性问题复现 | 用实际错误轨迹提出一个最小修改假设；修改冻结后才启用预留集 |
| main 通过、仅附加事实错误 | 针对说明与证据一致性处理，避免无依据重做空间算法或换模型 |
| 仅出现冗余澄清或有效冗余计算 | 单列体验/效率问题，按产品需要决定是否处理，不冒充主任务能力故障 |
| 协议无效或批次未完成 | 报告具体阻塞、已执行与未执行数量，不能发布“通过率达标”结论 |

预留 H01–H04 各覆盖一个象限。只有需要修改、修改假设和配置已写定后，才按 H03、H01、H04、H02 的顺序执行，每题一次；不在修改过程中查看具体题干、fixture 或答案。原失败题可以用于定位及回归，但单列，不与预留集混算“未见题正确率”。

如果预留仍失败，本轮也应结束并报告未解决机制；不要追加重复试验直到通过。后续工作必须有新的可检验假设。预留细节若已被修改者读过，就降级为回归集，不能继续声称盲测。

## 7. 必须保留的证据

每题至少保留：实际模型版本和请求参数；初始题干与全部澄清；系统/工作区指令及工具 schema 的哈希；实际加载的 Skill 正文哈希；所有工具调用参数及回执（含失败调用）；公开过程与最终答复；必要的原生会话/流记录；业务数据前后状态；用量和停止原因；单题语义评分及引用位置。

fixture/oracle 原始评审文件、评分与包装元数据、预计算标准答案不得直接进入模型工作区或上下文。业务对象应注入模拟后端，其数据通过正常工具返回后可以进入上下文。模型原始思考如因供应商协议需要保留，应沿现有受控记录机制处理，公开报告只需参数/完整性核验与可观察行动证据。

`no_business_effects_pass` 不表示没有任何系统记录：正常会话日志、审计和分析结果留存是允许的。比较的是草稿业务文档与版本、来源对象及其 revision、发布/采用状态；排除查询时间与审计事件等非业务字段时，归一化规则须提前记录。
