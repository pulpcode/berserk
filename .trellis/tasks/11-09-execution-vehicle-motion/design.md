# 车辆动态展示方案

2026-11-09 · v0.3（通俗说明版）· 已于本日确认实施

**导演点一次“推进”，故事里的时间和车辆一起往前走；到下一条事件时停住，等待导演再点。**

本版保持v0.2的方向，补充例子、刷新规则和职责说明。采用的是“推进过程中移动”，不是先确认到场再播放过去的动画。

## 1. 现在为什么会跳到终点

模拟系统已经算好了车辆应该走的路线，但地图主要使用少量位置记录：

| 当前机制 | 带来的问题 |
| --- | --- |
| 导演推进后，场景时间直接跳到目标时刻 | 车辆可能从站内位置直接变成到场位置 |
| 行驶时约每60个场景秒安排一次普通位置更新 | 35秒就到场的车辆，途中还没到下一次更新就结束了 |
| 地图每15个现实秒查询一次，并连接位置记录 | 既看不到连续移动，又容易把轨迹画成穿楼的直线 |

已有服务器证据：V01在09:19出发、09:19:35到场，路线有7个点、约416.208米，但位置记录只有3条。V06按同车组行驶。这些时间是故事时间，等待地图刷新不会让车自行前进。

## 2. 导演以后怎样操作

导演仍使用现有“推进”按钮，每次只推进到下一条事件。

**例如：车辆09:19出发、09:22到场，假设中间没有其他来报或变化。**

- 当前机制：09:20位置更新、09:21位置更新、09:22到场，可能需要导演分别点击。
- 新方案：导演点一次“推进到到场”，模拟系统在几秒内让场景时间从09:19走到09:22，地图连续显示车辆行驶；到09:22由来源确认到场，然后停住。
- 09:20、09:21以及它们之间的位置由系统自行计算，不再单独要求导演确认。这就是“普通位置更新作为内部计算”。

如果09:20还有一条既定来报，就必须先到09:20处理来报后停住，不能越过它直接到场。下一条事件包括既有来报、道路变化，以及系统根据实际指令算出的出发、到场、受阻等；无需AI再判断哪些事件“重要”。同一时刻有多项变化时，继续按现有确定顺序处理。

用目前旧路径举例：

| 点击时的场景时间 | 下一条事件 | 这次推进怎样展示 |
| --- | --- | --- |
| 09:18 | 09:19出发 | 车还在等待，直接到09:19，更新出发状态后停住 |
| 09:19 | 09:19:35到场 | 用几秒展示沿途行驶，到09:19:35确认到场后停住 |
| 09:22 | 09:23中轴桥封闭 | 展示途中行驶，到09:23处理封桥及受阻变化后停住 |

停止后不会自行继续下一条事件。导演不需要为每一分钟的位置变化点击，也不需要逐帧控制动画。

## 3. 怎样决定是否展示移动、展示多久

由模拟系统按已有执行记录计算，不靠AI猜测：这段时间内，只要至少一辆车会沿有效路线实际增加行驶距离，就按有运动处理。

等待、受阻、到场停留和取消之后通常不移动；被任务占用也不等于正在行驶。期间若有出发或恢复行驶，按实际生效时刻分段计算。不能只比较起终点是否相同，因为车辆绕行后也可能回到同一点。

本期只用两条规则：

- **没有运动：**直接到下一条事件，不让观众空等。
- **有运动：**统一压缩成几秒展示，建议每次上限约4个现实秒；更短的区间不刻意放慢。具体统一时长在桌面验证中核对。

倍速只改变观看节奏，不改变车在故事里的速度、路程、等待时间和到场先后。不细分很多内容类型，不给每辆车单独设倍速，也不增加倍速选择按钮。

例如下一条来报20分钟后、车辆3分钟后到场，系统应先把“3分钟后到场”作为下一条事件，用几秒展示后停住，而不是跳过到场去等20分钟后的来报。

## 4. 各席位地图怎样一起更新

模拟系统统一维护“故事现在几点、正在向哪个事件推进、这段展示多久、什么时候开始”。各席位读取同一套进度，不各自从头播放。

1. 导演启动推进，来源开始走时并更新车辆事实。
2. **可见的演示地图统一每1个现实秒查询一次，即使暂时没有运动也保持这个简单规则。** 页面隐藏时停止查询，恢复可见时马上读取。
3. 地图拿到来源给出的路径和共同计时依据，平滑画出两次读取之间的移动。若读取时已走到09:19:10，就加入这个进度，不从09:19重新播放。
4. 只有模拟系统到达相应业务时刻，才能确认到场、改变占用或生成通知；浏览器动画结束不能作为到场回执。

本期不增加“轻量版本探测＋另取详情”两套请求，也不新建通用推送服务。版本没变化时不重复更新地图；如果实际多席位测试证明有负载问题，再针对证据优化。

目标是近同步，不保证每一帧完全相同。浏览器会参考服务器时间校正自身计时偏差；每一帧的位置只用于显示，不写回来源，也不作为Agent查询到的事实。资源有效期按故事时间算；网络超时、登录有效期仍按现实时间算。

首次打开地图或从后台回来，直接加入来源当前进度，不补播过去全过程。网络断开或计时依据失效时停止自行推算，保留最后可信显示和错误提示；恢复后重新读取。地图是否打开不影响模拟系统走时。普通席位只读其有权查看的态势，不获得控制席下达权限，也不显示轮次选择或控制备注。

## 5. 怎样避免查询过程中前后时间不一致

走时以后，一次查询可能要翻几页，Agent也可能连续查车辆、道路等资料。不能第一页是09:19、第二页变成09:20，却把它们当作同一时刻的完整资料。

因此，**同一次查询使用同一个时刻的数据副本（快照）；下一次刷新再取新时刻。**

- 地图每秒发起一轮新的读取；这一轮里各页、各项资料按同一时刻读取，下一轮可以更新。
- 同次Agent分析作业或前台请求中的业务资料读取也固定依据时刻，结果注明这个时刻；重新发起查询/分析可以取得更新资料，不把整个会话永久锁在旧时间。
- 控制指令真正受理时，仍核验当时最新条件和版本。旧资料快照不能代替当前受理检查；控制指令和执行回执沿用实时接口，并说明时点。
- 数据副本已不可用或重启后无法恢复时，应明确提示重新读取，不能悄悄混用新旧资料，也不能无限重试。

优先复用现有查询证据、版本和翻页机制，补最小的固定时点读取能力；不复制模型会话。原有权限、轮次隔离、200 KiB来源分页和256 KiB宿主响应上限继续保留。动画计时等显示参数不塞进普通Agent工具结果。

## 6. 怎样保留真实路线，避免穿楼

模拟系统已有实际行驶路径（path/segments），应按已经走过的距离保留全部拐点，地图不再只拿几个采样点直接连线。

- 原位置记录（executionTrack）仍表示带时间和来源版本的定位记录；计算出来的道路拐点不冒充新的GPS上报。
- 地图每画一帧，不需要新增一条历史或通知；来源按有限频率保存进度和必要记录。
- 改道前走过的旧路保留，再从实际位置接续新路；受阻就停止，取消后不画尚未发生的行驶。位置修正或路线接不上时保留断开，不能强行连直线。
- 未来计划路线不能画成已经走过的轨迹。

现路径只经过R03的一部分，其余大多是明确配置的模拟接入通道；指定R03不等于沿它的全长行驶。另外L01当前坐标在仓库屋顶，最后一段通道延伸到这里，仅补动画仍可能让车开进建筑。

获批后先把站点出口、R03接入/离开点、仓库外围可停靠点叠加到底图核对。保留L01作为事件地点，另给车辆配置与它对应的可达到场点。不能由前端另画一条“看起来贴路”的线来美化结果。

确需修正路径或到场点时，由模拟来源发布新场景版本（拟v7），重新计算路程和到场时间，因此不承诺修正后仍是09:19:35。先用冻结旧路径确认仅改变演示节奏不会改变业务结果，再单独记录新路径的差异。当前只完成代码与既有证据核对，尚未证明每段接入线都符合实景通行条件。

## 7. 操作异常和页面边界

- 推进过程中按钮显示简短“推进中”，避免重复启动；同一操作重复提交只执行一次。丢失响应先查原操作结果，不另起一段掩盖未知状态。
- 若控制席在行驶期间发来改变路线等有效操作，来源先算到当前时刻，再处理变更，结束这一次推进并更新下一事件，等导演继续；不能继续沿过期路径走，也不能丢弃业务指令。原权限和人员确认保留。
- 模拟服务异常或重启后，回到最后可信保存的进度并停住；不按宕机期间现实时间自动补跑，不重复投放事件。
- 结束或切换演示时先停止旧推进，旧回调和旧页面请求不能继续写入；地图也清掉旧动画。内部轮次标识不进入业务页面。
- v4/v5/v6历史定义、回执和轨迹保持可读，不回写旧结果；旧数据缺少运动依据时仍显示静态资料，不补造动画。

页面沿用现有“推进”、下一事件及地图时间区域，只增加必要的状态文字。不增加常驻播放面板、手动暂停或倍速选择，也不堆叠说明。

## 8. 怎样验证、什么时候实施

批准后在服务器隔离目录验证：路线折点、到场点、多车运动/等待/受阻/改道/取消、同刻事件顺序、长间隔、无运动跳转、查询翻页/跨工具时点、重复点击和丢响应、断连/重启、结束/切换演示，以及导演和至少两个业务席同时观看。保留短录像、截图及来源时间/版本证据。

分别检查“画面是否连贯”和“来源事实是否正确”，不能只凭动画流畅宣布可靠。先实现与验证，再按明确授权发布。

本期包含模拟来源时间推进和查询一致性改造，不只是前端动画；不修改LLM研判策略、不增加自动调派或通用导航服务，也不恢复已搁置的SIM-MAP-001。本版已获用户确认，实施与验证结果另见复验记录。
