## 怎样理解结果

“主任务正确”是用户要的名单、分类、数量和范围处理正确。“解释正确”还要求公开过程说明和最终答复没有无据断言或事实错误。“严格正确”要求主任务、解释和四项关键约束都通过。

一次任务可以清单正确，却因为附加说明出错而严格失败；也可以被产品错误中断，而不是模型算错。本轮分别记录这些情况。没有最终答复的 A06-2，其解释项标为不适用，不能靠空回答得到解释成功。

本轮只有一个产品版本、一个模型和正常按需加载方式。两遍是同题独立重复，**不能据此证明比旧版提高了多少，也不能把这 8 类诊断题的命中率当作全部真实业务的正确率**。

### A06-2 的产品问题

模型的请求合法：查询两个指定来源，并按任务关系整理。来源返回 1 条关系未确认的记录；按任务关系筛选后，选中记录为 0 条。

产品生成总数时检查了“原始记录是否为空”，因此写成 `entityCount: 0`；校验器检查的是“筛选结果是否为空、关系覆盖是否不完整”，因此要求保留未知，即 `null`。两者不一致，产品拒绝了自己的结果并中止会话。

只读验证已复现：原始结果校验失败；在内存副本中只将 `0` 改为 `null`，校验通过。没有修改冻结产品或原始审计数据。详见 [诊断证据](records/A06-2-integrity-diagnostic.json)。问题仍待后续修复，本轮没有补测。

## 有争议的判断如何处理

- **A02-1 的“换一轮对话后不保证还在”**：第一审认为是无据的留存说明；第二审认为结合“本次会话”可理解为另开会话。最终按表达不清处理，不把“不保证”硬判为确定丢失，也不拿后续答对为前述补证。两份原判保留。
- **A05-1 的舟组重复问题**：最终采纳具体来源证据，判解释失败。A05-2 则明确说“清单注明”，属于准确引用工具给出的限制；它因另外的统计范围误述而失败。两次错误不能混为一谈。
- **A07 的含边界合计**：表格明确区分内部与边界，合计式也明确列出两项；“边界总数”“区内合计”等标签不够清楚，记表达建议，不另判算错。
- **A04-2 的关键约束**：第一审把它限定为解释错误，第二审同时判状态证据约束失败。根复核起初漏掉这一分项差异，现按冻结口径采用第二审；初始根决议保留，不改原始两审。是否已放行本身是需要证据的状态，不能因可用清单恰好保守正确而放过。
- **A08-1 是否必须追问**：不能用从未告诉模型的“港口侧偏好”判错。它开头说明有两个区域，并逐行标出归属，最终按并列条件答案认定主任务完成，与公开 P03 同口径；第二审原本认为合并标题使范围仍未解决，该意见保留。若采用第二审的更严主任务判定，主任务将为14/16（87.5%），严格仍为9/16；整批未通过验收的结论不变。

- 20 次执行的业务状态前后均相等。P04 的来源更新是控制器预设动作，不是 Agent 写入。

没有验证真实生产来源系统、线上部署、真实救援决策或底图加载质量。浏览器测试阻断了外部底图瓦片，避免把外部加载问题混入资源回路验收；因此截图不作为底图显示验收证据。

## Skill 读取怎么理解

正式16次中，6次实际调用过Skill读取工具，共8次成功读取：空间分析6次、标绘2次。公开4次中，2次有读取，共3次。未调用读取工具记0，不能推导为没有收到宿主规则。

这些是诊断记录，不是正确率。存在没有额外读Skill但正确完成的题，也存在读取空间Skill后仍解释错误的题。本轮没有预加载对照，不能将失败直接归因于Skill未读，也不能证明当前Skill修改产生了净提升。
