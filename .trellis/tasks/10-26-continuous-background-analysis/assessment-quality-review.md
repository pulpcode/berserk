# 后台研判质量改进方案（审阅稿）

2026-10-28｜用户已批准“提交git，然后开始实施”；本文件作为本轮批准基线。

**目标：让后台持续分析既能说清“当前怎么看”，也能可靠地说明“具体哪项变了、依据是什么”，减少事实被改写、推测逐轮固化、计算错误和重要变化漏提醒。**

## 1. 当前是什么样，准备改成什么样

当前已经具备任务关联、空间计算、原始资料读取、多轮记录和有限补做。缺口主要出现在模型如何解释证据、保存判断及接续历史。本轮是在这些能力上补齐约束。

| 环节 | 当前实现 | 本轮拟调整 |
| --- | --- | --- |
| 记录粒度 | 每个任务保存一个变化标记、一段理由和是否重要；具体条件写在理由中 | 保留总体判断，另外逐项记录关键条件的前后状态、依据和重要性 |
| 事实与推断 | 来源和消息身份可区分，提示词要求不混淆；判断内部主要靠文字表达 | 将来源陈述、模型推断和行动建议明确区分，关键判断绑定具体证据 |
| 历史接续 | 复用 Pi 会话，可读取上次已发布结果和原始资料 | 在现有读取能力中按任务组织上次条件记录、当前任务版本、本轮输入及可回查依据 |
| 关键计算 | 空间已有工具；时间、数量等仍可能由模型口算或转述错 | 补有限的只读计算能力，关键数值直接引用计算结果 |
| 正文与提醒 | 最终正文与变化元数据分别生成；按任务的重要标记投递 | 当前研判、变化展示和提醒使用同一份已保存结果，减少相互矛盾 |

本轮依据是[方舟回归中已确认的问题](research/ark-regression-results.md)：道路恢复却漏提醒、总重2.5吨被重新怀疑、工具坐标被抄错并沿用、旧推测及历史判断被转述变形。六次运行均未触发原生压缩，不能把这些错误归因于压缩丢失。

## 2. 谁来组织和判断

| 责任 | 负责什么 | 边界 |
| --- | --- | --- |
| 程序 | 按权限取数，标明任务和来源版本，提供上次结果，执行计算，保存并展示记录 | 能核对引用、版本、数值等明确规则，不能自动证明所有自然语言判断都正确 |
| Agent | 理解任务，识别关键条件，判断新信息影响哪些条件，解释变化并提出建议 | 推断须标明推断；建议不能直接更新为实际安排 |
| 用户 | 查看变化和依据，继续讨论，决定业务行动 | 无需逐条点击“继续分析”；讨论中的假设不自动成为共享事实 |

条件由实际任务及证据决定，不预设所有任务都必须检查道路、车辆或载重，也不把每条建议都变成“尚未满足的必要条件”。Agent 识别条件后，程序赋予稳定标识；后续沿用同一条件记录，避免改了名字就被误认为新增问题。

## 3. 一轮后台分析如何运行

**新信息进入 → 找到候选任务 → 读取各任务基准和证据 → Agent 判断、工具计算 → 保存并检查 → 更新研判和必要提醒。**

1. **准备材料。** 沿用当前任务发现与权限范围。按任务提供当前任务说明、该任务上次已发布结果、本轮新增资料；历史证据保留确切引用，原文较长时按需读取，不把全部历史重新复制一遍。
2. **逐项判断。** Agent 复核已有条件，更新受影响项；确有新依据时新增条件，撤回或纠正旧条件时说明理由。每项至少保留：条件标识与名称、前后状态、判断性质、证据引用、变化理由及是否重要。行动建议单独记录。
3. **核算关键值。** 时间差、时间窗口关系、数量及单位比较交给只读工具，空间计算复用已有工具。计算输入也须指向来源；工具算对不能弥补模型选错输入。业务发生时间、有效时间和系统更新时间分别处理，关键数值按工具结果展示。
4. **形成统一结果。** Agent 给出总体判断和说明；程序保存总体判断与各条件记录。当前研判、前后变化、提醒摘要均由这份结果展示，不再从另一段自由答复重新提取判断。Pi 原生答复和工具过程仍完整保留供追溯。
5. **检查后更新。** 检查任务覆盖、版本、基准、证据引用及可客观验证的计算一致性。记录缺失或明确字段错误沿用 Pi 工具反馈与最多2次补做；业务依据不足可以如实记录为不确定，不为了凑出确定结论反复重试。取消、超时、权限变化及补做失败继续遵循现有停止或恢复规则。

来源引用应能定位到当时的原文片段、结构化字段或工具结果。引用存在，只能证明“材料可找到”，不能单独证明“这句话受到材料支持”；后者仍要核验语义。

### 历史与有效依据怎样处理

- 每轮主要对照**同一任务、同一权限范围内的上次已发布判断**；首次分析标为首次。继续保留历史，不另设“最近N轮记忆库”。
- 上轮判断用于回答“之前怎么看”，原始资料用于回答“当时依据是什么”。旧推断不能作为新的业务来源。
- **本轮没有再次提到某项事实，不代表它自动失效。** 明确过期、撤回、被更新版本替代或不再适用时才重新处理；新证据冲突时同时保留双方依据。自然语言的适用性仍由 Agent 解释，程序不凭空给资料设置有效期。
- 如果发现上一轮说错，本轮明确标记为“纠正旧判断”，与“外部情况发生变化”区分；不修改历史原文。

## 4. 用一个场景看最终效果

假设任务A需要4辆车经过东桥；车辆报告明确只有2辆可用，后续变化均有来源报告。

| 轮次与新增信息 | 道路条件 | 车辆条件 | 总体判断与提醒 |
| --- | --- | --- | --- |
| 第1轮：东桥封闭 | 不满足 | 不满足 | 已知两项阻碍，提醒影响 |
| 第2轮：东桥恢复 | 不满足 → 满足 | 仍不满足 | 仍有车辆缺口；提醒道路阻碍解除 |
| 第3轮：另外2辆修复，报告确认4辆可用 | 保持满足 | 不满足 → 满足 | 这两项已知阻碍均解除；提醒车辆条件改善 |

第2轮是本轮重点：**总体仍受阻，也必须保存道路条件的改善，不能把它遗漏。** 第3轮只能说明已核验的阻碍解除，不能外推为任务已完成或所有未知条件都已确认。

提醒以对任务有实质影响的条件变化为依据：新增重要阻碍、重要阻碍解除及影响行动的重要纠错需要提醒；重复信息、同义改写和无实质影响的核对静默更新。Agent 判断业务重要性并说明理由，程序汇总已标记的重要变化；不得以总体结论没变覆盖条件级的重要标记。未归属任务的重要变化继续按现有机制处理。

在现有任务“当前研判”中展示“总体判断、本轮变化、条件与依据”，历史入口仍固定到当时轮次；不另建看板，也不让用户维护两套任务信息。

## 5. 本轮范围与实施顺序

拟分三步完成，均在审阅通过后开展：

1. **记录和接续。** 扩充现有研判记录与读取工具，保存条件、判断性质和具体依据；同一任务各范围仍独立，条件记录不写回正式任务或业务来源。
2. **计算、展示与检查。** 补只读计算，统一当前研判及提醒的数据来源，接入现有 Pi 反馈机制；页面只增加理解变化所需的内容。
3. **对照验证。** 冻结实现和样本后完成下述回归，单独报告机制正确性与研判质量。

兼容已有历史：保留原文与原引用；没有条件记录的旧轮次按旧格式显示，首次进入新格式时由 Agent 回读证据并明确建立基准，不后台批量把旧文字猜成事实。所有数据变更采用可迁移、可回滚方式，正式切换前完成兼容验证。

继续复用 Pi 会话、原生历史、现有队列、候选发现、空间服务和权限机制。本轮不新增另一套 Agent 循环、通用代码执行权限、向量库或业务调度能力；不更换压缩机制。现实6—8小时运行与压缩后保持能力另行安排，不能用短时回归代替。

## 6. 如何验证是否改善

| 验证场景 | 必须观察到的结果 |
| --- | --- |
| 道路恢复，车辆仍不足 | 道路条件更新且重要解除被提醒；车辆缺口保留 |
| 总重明确2.5吨，限制为超过3吨；后续多轮不再提重量 | 不无故怀疑仅为货重，不凭空增加确认事项 |
| 建议借车，连续多轮没有调配通知；随后才有正式通知 | 建议一直保留建议身份；有正式依据后才更新实际资源状态 |
| 09:50到达、10:30截止；09—12时限制取消，任务14时通过 | 余量40分钟；取消通知不能证明14时所有通行条件满足 |
| 工具返回坐标120.025，模型解释或下一轮复述 | 关键数值与原结果一致，不能改写后继续传播 |
| 同地点不同任务、同资源不同需求；任务修改或出现新条件 | 各任务比较自身基准；允许更新条件，不串用另一任务的状态 |
| 来源撤回、相反新证据、旧版晚到、重复推送 | 按来源版本和适用范围重评；保留冲突或撤回依据，不重复提醒 |
| 引用缺失、旧记录读取、取消、版本冲突、越权读取 | 按现有规则明确处理，不能把执行失败当无变化，历史和权限不退化 |

验证安排：

- **程序与桌面验证：** 覆盖记录保存与回读、条件身份、计算、失败反馈、旧数据兼容、权限、当前/历史展示及提醒一致性。
- **真实模型对照：** 旧版以当前已提交的 `2321f72` 为基准，旧新版本使用同一方舟配置和实际模型版本。原文本、空间两组样本，各版本各运行3次，共12次独立运行；正式开始前核验请求实际走方舟。模型版本或输入条件发生变化时单独说明，不混作代码效果对照。
- **独立变体：** 补时间与重量变化、来源冲突、同对象不同任务三组变体，冻结逐轮输入和独立预期后再运行；答案不交给 Agent，不只验证原错误措辞。
- **结果判定：** 分别统计任务覆盖、条件变化正确性、事实误写/推测固化、关键计算、提醒漏报/误报，以及耗时和用量。关键场景任一失败须列出原文和失败轮次，不能仅凭发布成功宣称通过；保留全部运行，不挑选最好结果。
