# 后台研判漏记录：修复方案（已批准）

2026-10-27｜用户已批准实施；以下为批准的方案基线

**建议：保留现有检查；发现漏记录时，先让 Agent 自动补做，最多2次，仍失败才暂停。用户无需点击“继续”。**

## 1. 当前问题

多任务测试中，Agent写出了分析结论，也声称“已记录”，却没有调用记录工具。系统发现没有真实记录，拒绝更新当前研判并暂停。

现有检查已经生效，缺少的是检查失败后的自动补做机会。[实际失败记录](research/multi-task-results.md)

## 2. 拟修改的流程

1. **分析结束，先检查。** 程序核对本轮变化记录与工具成功回执，不采信正文中的“已记录”。
2. **发现漏记录，自动提醒。** 利用Pi原生接续能力，将明确反馈送入同一会话，让Agent补调记录工具。
3. **补做后，再检查。** 记录、输入引用、任务版本及最终答复通过现有检查，才更新“当前研判”，按需提醒。
4. **最多补做2次。** 仍不满足要求，就保留旧研判和待处理输入，暂停并说明原因。

正常完成的轮次不增加模型调用。补做期间，中间答复不能作为新的当前研判，也不能提前发出重要提醒。

## 3. 如何提醒，如何判断成功

系统反馈示例：

> 本轮尚未成功保存研判变化记录，当前结论未发布。请根据已获取的资料，调用 `information_record_analysis_update` 完成记录；若调用失败，请依据工具错误处理。仅在正文中声明“已记录”不能完成此步骤。

**提醒由系统发送，具体判断和工具参数仍由Agent生成；系统不提供测试答案，也不代写记录。**

| 检查 | 成功条件 |
| --- | --- |
| 真的保存了吗？ | 本轮存在有效记录，且与真实工具成功回执一致；不能用旧轮次的记录充数 |
| 记录对应当前任务吗？ | 输入引用合法，任务版本仍有效，明确要求重评的任务没有遗漏 |
| 可以更新界面了吗？ | 本轮正常结束，最终答复可追溯，执行未取消或中断 |

这些是程序检查，保证执行完整性；**不等于证明研判内容正确。** 时间、数量、任务归属等仍须通过样本测评。

## 4. 实现边界

- **复用Pi。** 优先使用公开SDK的follow-up机制，不另建Agent循环。实施第一步验证接续时机及请求归属，确保补做完成前本批次不被标记为最终完成；此衔接尚待验证。
- **限定补做范围。** 针对正常生成答复后缺少有效变化记录的情况。取消、超时、权限失效、原生记录损坏不通过补做绕过；任务版本冲突沿用现有重评机制。
- **控制次数与影响。** 每批次累计最多2次补做，沿用本轮时间预算，不因补做重置超时。保持同一配置串行，新消息留待后续批次处理。
- **保留证据。** 保存遗漏、反馈、补做调用和最终结果；不删除失败原文，不重放已执行的业务操作。借鉴结束前检查与有限接续，不引入看板或多Agent派工。

## 5. 如何验收

| 验证 | 预期 |
| --- | --- |
| 正常记录；漏调后补做成功 | 正常路径无额外调用；补做成功后只更新一次、按需提醒一次 |
| 虚称已记录；引用旧回执；连续漏调 | 均不能误判成功；达到2次补做上限后暂停，旧研判与待处理输入保留 |
| 补做期间取消、超时、任务修改或新消息到达 | 取消和超时立即遵循现有终止规则；版本变化正确重评；新输入不混入当前批次 |
| 腾讯云真实模型复测 | 使用原3任务、12次更新样本，新开独立测试；分别报告流程完成情况与判断正确性，保留首次失败作为对照 |

**已批准采用：“程序检查 → Pi自动补做最多2次 → 再检查 → 成功更新／失败暂停”的方案。**
