# 任务关联与空间分析接入后台研判方案

2026-10-27｜用户已批准实施，本文件保留批准方案

**建议：复用已有空间计算工具，让系统找全候选任务，Agent结合任务条件判断影响，再沿用现有后台机制自动接续和记录变化。** 目标是减少任务漏检，并让每项影响都有可核验的依据。

## 当前已有能力与缺口

| 环节 | 已有能力 | 需要补齐 |
| --- | --- | --- |
| 任务关联 | 任务可保存业务对象引用、关注区域和时间；工具可分页查询活动公共任务 | 明确对象与任务的用途关系，补齐完整查找和覆盖检查 |
| 空间计算 | 前台已有 `spatial_analyze`，支持包含、相交、距离、缓冲和筛选，并保留原始依据 | 适配后台服务身份，将空间结果关联回任务 |
| 后台接续 | 来源推送触发分析，同一配置持续接续，逐任务保存判断、比较变化、按重要性提醒 | 接入空间候选和证据；补上没有历史研判的任务首次触发 |

任务查询尚不能发现不同编号对象的地理重叠；空间工具目前依赖前台席位与会话，需要补后台适配。

## 完整流程与使用效果

**信息进入 → 确认变化对象及版本 → 工具查找关联任务并计算空间关系 → Agent逐任务判断影响 → 检查覆盖与记录 → 更新当前研判。**

例如，来源系统推送“区域Z在09:00—12:00禁止车辆进入”，并提供可查询的区域对象。任务正文都没有写区域Z：

- A绑定路线R1，预计10:00经过；工具查出路线与Z相交，Agent判断通行受到影响。
- B也使用R1，但预计14:00经过；空间上相关，计划时间与本次封控不重叠。
- C绑定作业区域W，与Z仅部分重叠；先确认重叠部分涉及哪些作业，不直接判定整个任务停摆。
- D只写起终点，未提供路线；保留为“关联待核实”，说明缺少实际路线。

用户在任务“当前研判”中查看影响、相对上次的变化和依据，并可打开对应路线与区域。后台继续接收后续修订，用户无需逐条点击“继续分析”。

## 拟补齐的五项能力

1. **任务关联真实对象。** 复用现有业务引用，明确路线、车辆、执行地点、作业范围等用途。优先导入或选择已有对象；模型提取的关联保留为待核实。关注区域不能直接代表实际作业区，起终点也不能替代真实路线。

2. **完整找候选，并检查覆盖。** 程序分页取得获准的活动公共任务，由直接对象关联和空间计算共同生成候选；Agent用语义理解补充线索。任务分别标记“已核验关联／已核验无关联／资料不足待核实”。文字查询明确整段匹配规则，空结果不能代表没有相关任务；尚未检查、缺页和超限必须明确暴露。

3. **后台复用空间计算。** 补服务身份、来源授权、工具注册和历史结果读取，首期使用获准来源及本分析流的可信结果。保留对象版本、几何、时间和计算依据；相交包含边界接触，距离阈值须有业务依据。沿用现有几何类型与计算上限，缺页、数据变更和计算失败不返回虚假的“零命中”。

4. **变化能重新找到任务。** 来源修订经现有推送入口触发重评；以前相关、现在不再相关的任务也须检查，以撤回旧影响。新建或修改的公共任务，按启用分析流的授权及关联范围检查首次评估需求，不再要求先有历史研判。没有推送的来源变化，本期不承诺自动发现。

5. **逐任务比较与记录。** Agent结合空间结果、执行时间和业务限制判断影响，各任务比较自己的上一已发布研判。现有记录补充关联依据与覆盖情况；程序检查必查任务、证据及版本，漏项复用Pi有限补做。假设调车、建议改线保留条件，只有新业务依据才能成为实际安排。程序检查不能替代语义测评。

后台继续遵守来源权限和分析流边界，不获得私人标绘、地图编辑或业务调度权限。

## 怎么测试

先冻结任务、地图对象、逐轮推送和独立预期。采用易核算的几何样本与核验表，答案不提供给模型，也不用被测工具自证正确。

| 测试场景 | 预期判断 |
| --- | --- |
| 正文无区域关键词；不同区域编号但路线实际穿过 | 能通过对象与空间关系找到任务；改名不改变结果 |
| 同名地点或同区域编号，但实际不相交 | 不因名称或标签相同直接判为受影响 |
| 同一路线、不同执行时间；同一信息影响多个任务 | 分别判断，既不漏掉真正受影响任务，也不把影响复制给所有任务 |
| 区域局部重叠、边界接触、孔洞及现有距离阈值 | 按工具定义给出关系；关系不足以确定业务影响时保留条件 |
| 封控范围扩大／缩小／撤销，任务改线，旧版本晚到及重复消息 | 正确增减候选、撤回旧影响；不由接收顺序覆盖新事实，不重复提醒 |
| 新建任务；没有历史研判的任务被修改 | 能进入首次评估，不再因缺少历史基线静默跳过 |
| 缺路线、缺几何、任务分页、来源故障或计算超限 | 分清待核实与执行未完成，不报告“全部无影响” |
| 越权对象、运行中版本变化、假设调车连续出现 | 拒绝越权与失效证据；假设不能逐轮变成事实，任务资源不串用 |

验证分三步：

1. **程序验证。** 复用现有空间、任务查询和后台接续测试，补服务权限、候选完整性、首次触发、取消和历史证据回读；几何关系按独立预期核对。
2. **真实模型验证。** 原3任务文本样本回归，新增约5任务、12轮更新的空间样本，两组各固定运行3次。模拟业务来源HTTP接口提供带固定坐标的地图对象，走正式后台链路；保留所有运行和失败。
3. **桌面界面验证。** 核对当前研判、前后变化、重要提醒和地图依据；打开历史轮次时显示当时对象，不能被当前地图资料替换。此阶段验证综合链路，现实6—8小时稳定性另设长时测试。

分别报告任务漏检、影响漏报／误报、假设固化、待核实与未完成数量，以及耗时和用量。验收要求程序检查通过、必查任务无遗漏、预期重要变化正确识别、没有虚构的调度事实。未执行轮次不算通过。

## 首期范围

首期打通任务关联、后台空间分析、证据展示和多轮回归。精确裁切重叠路段、重叠比例、自动绕行、影像识别和复杂扩散暂不纳入；展示原对象与可靠关系，不编造重叠长度。复用现有Agent，不新建向量库、全局知识图谱或另一套运行循环。

用户已要求提交本方案并开始实施；实施顺序为“任务发现与首次触发 → 后台空间适配与证据 → 综合测试”。
