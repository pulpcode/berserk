# Axon 导演台整合方案 v0.1

日期：2026-11-17  
状态：待用户审阅，尚未批准实施

## 一、目标与范围

将现有“模拟验证”和“场景导演台”整合为一个“导演台”，提供“场景演练／自由调试”两种互斥的操作方式。同一时间只允许一种方式存在活动轮次，以减少入口、数据范围和操作状态的理解成本。

本轮一次性完成页面迁移：只保留统一导演台入口和页面，移除旧入口、旧页面地址及其路由，不提供旧地址兼容跳转；同步更新项目内导航、链接、使用说明及测试。本阶段同时整合业务接入：能力中心以“情报接入”“态势接入”管理各自查询与通知接收能力，运行时通知来源收敛为情报、态势各一个。调用、规则、权限与凭证完成迁移后停用多余来源，历史不清除。

本方案独立于已上线的 R4 连接器兼容修复。R4 已保留四条入站来源及原凭证、处理配置和历史映射，用户测试验收仍待完成。本方案审阅通过前，不修改线上服务或实施整合功能。

## 二、现状与需要解决的问题

现有“模拟验证”已有可视化页面，可以从预置对象和报告中选择条目，修改道路通行状态、可用车辆数量、情报内容和时间，保存后单独发送通知。其基础对象和坐标由预置数据提供，部分字段仍需要填写 JSON，界面偏向技术测试工具。

现有场景导演台负责场景选择、演练轮次、事件推进、虚拟时间及任务相关操作。两者的控制接口与数据组织不同，但共用控制服务配置和通知目标。线上只读核查发现，当前通知目标为 `scenario-intel-source` 和 `scenario-situation-source`；普通模拟与演练均可能通过这两个目标发送通知，不能仅凭来源名称判断操作方式。

四条入站来源均有规则和授权依赖。核查时，`scenario-intel-source` 和 `scenario-situation-source` 分别存在 44 和 6 条历史事件；两条 `mock-*` 来源虽未在该统计中出现历史事件，但仍各有规则及授权，不能据此认定可以删除。

此外，当前查询在未明确限定轮次时可能读取活动演练。仅合并页面无法保证调试操作的数据范围正确，必须同时限定查询、修改、通知与结果归属。

## 三、统一入口与页面交互

侧边栏只保留“导演台”。页面上方提供操作方式选择，展示当前方式、当前轮次名称及运行状态。页面默认展示服务端确认的当前状态，刷新页面或重新登录不会自动切换、重置或启动。

```text
导演台     操作方式：[场景演练 ▾]     当前轮次及状态

场景演练：场景选择、启动、推进、虚拟时间、结束及历史
自由调试：预置测试数据、对象与情报编辑、修改记录、通知预览与发送
```

“自由调试”承接原模拟验证页面的操作，采用“选择对象 → 编辑表单 → 保存修改 → 按需发送测试通知”的流程：

| 内容 | 首版操作 |
| --- | --- |
| 道路 | 修改通行状态、限制说明及相关时间 |
| 资源 | 修改可用车辆数量及相关时间 |
| 情报 | 修改既有报告的标题、摘要、正文、关联对象和时间 |
| 修改记录 | 查看已保存的变化及其所属调试轮次 |
| 通知 | 预览内容，明确点击后发送，查看接收与处理结果 |

普通编辑流程不要求用户编写 JSON；关联对象和区域使用现有数据的选择控件，时间使用可读的输入方式。必要的技术标识放入详情，不作为主要操作信息。保存数据与发送通知始终是两个明确动作。

首版沿用预置测试资料，不新增自动生成数据、任意基础对象创建、地图几何编辑、复杂场景编辑器或从运行中演练复制数据等功能。

## 四、互斥模式与切换规则

操作方式是服务端共享的运行状态，不是每个浏览器自行保存的偏好。所有有权用户看到同一活动方式；多窗口或多人并发操作不能产生两个活动轮次。

### 4.1 从场景演练进入自由调试

有活动演练时，选择“自由调试”先弹出确认框：

> 切换将结束当前演练，并初始化自由调试数据。演练历史保留，结束后不能继续推进。已发送的通知不会撤回。
>
> 按钮：取消／结束演练并开始调试

取消后保留当前状态。确认后停止演练推进，核对正在执行的操作及通知状态；满足结束条件后，将演练轮次标记结束，再基于预置数据创建新的自由调试轮次。

暂停中的演练仍算活动轮次，同样需要明确结束。没有活动演练时，明确点击“开始自由调试”后才初始化数据。初始化不自动发送通知。

### 4.2 从自由调试进入场景演练

有活动调试轮次时，确认结束该轮调试后进入场景选择。选择场景并明确点击启动，才创建新的演练轮次；切换操作本身不自动启动演练。

### 4.3 自由调试重新开始

提供“重新开始”按钮，确认文案说明将结束当前调试轮次、恢复预置测试资料并开启新轮次。旧修改、通知和回执保留在旧轮次历史中，不混入新的调试列表。

重复选择当前方式、普通刷新、返回页面、浏览器重连均不会触发重新开始。

### 4.4 切换中与失败处理

切换采用受控的单次操作，重复点击或网络重试不能重复结束或创建轮次。切换进行中禁止新的推进、编辑及通知发送；旧页面发出的过期操作必须由服务端拒绝，不能只依靠按钮禁用。

对于正在执行的操作，先阻止新增工作，再使用原有停止、回执核对和结束检查机制。不能确认安全结束时，显示阻挡原因，不启动新模式、不强行清空状态。已经发出的通知不能撤回，其迟到结果仍归属原轮次。

若旧轮次已经结束而新轮次初始化失败，页面应如实显示“当前无活动轮次，初始化失败”，允许重试初始化；不得假装旧轮次仍在运行，也不得通过恢复旧状态重放通知。

## 五、权限、数据与历史边界

### 5.1 权限

统一导演台沿用现有场景导演授权：账号具有 `controlScenarios` 权限，并属于配置的 `directorSeatId`，同时满足相关来源及查询权限。任务准备等操作继续保留原有的额外权限检查。系统管理员身份本身不自动获得导演权限。

原普通模拟仅依据来源管理权等条件放行的操作，在整合后也纳入导演授权。后端接口必须同步约束，不能移除页面后留下绕过入口。普通业务席位原有的信息查看、任务参与和历史读取权限不因本次整合自动扩大或缩小。

### 5.2 数据与轮次

互斥运行不等于共用一份可覆盖的数据。两种方式均明确关联各自轮次：自由调试从预置数据初始化；演练按原场景规则启动。查询、保存、通知和回执必须绑定所属方式及轮次，不能在未找到调试数据时回退到活动演练数据。

保留现有演练虚拟时间机制，不因进入或退出调试重写旧演练时钟。自由调试首期沿用明确的观测时间、生效时间和有效时间编辑，不另建自动推进的调试时钟。

### 5.3 历史与异步结果

结束、切换和重新开始均保留原历史。历史轮次只读，不允许继续推进或通过旧编辑页写入。原业务任务、会话、文件和历史证据不被重置操作删除。

未发送的旧轮次通知不能在新轮次继续发送；已经发出的通知及后续处理、投递或回执保留原归属。无法确认接收状态时继续显示待核对，不伪装为失败或自动生成一条新的通知重发。

历史查看是只读视图，不改变活动方式，也不恢复旧轮次运行。

## 六、页面、接口与来源迁移

### 6.1 本轮完成的页面迁移

- 统一导演台内部容纳两种方式，迁入原编辑、保存、通知及回执操作。
- 移除旧模拟验证入口、独立页面及旧页面路由；统一导演台作为唯一页面地址。
- 更新内部导航、书签生成逻辑、帮助说明和测试，不保留旧地址别名或兼容跳转。
- 直接访问已移除地址时按应用的不存在页面处理，不触发任何模式操作。

具体统一页面路径在实现设计中沿用现有路由约定确定；页面地址清理不代表删除名称相似的后端 API。

### 6.2 后台接口与调用方

逐项核查普通模拟前端、场景导演台、探针脚本、示例配置、测试和控制服务调用。新界面复用现有业务操作及确认、回执机制，避免建立另一套控制平台。

仍需保留的接口必须执行统一导演授权、当前方式和轮次校验。对于原本没有轮次参数的写接口，明确升级调用方或拒绝旧式写请求，不能默认把它转发到当前活动轮次。需要停用的接口在调用迁移和回归完成后明确移除。

### 6.3 本阶段完成业务接入与通知来源整合

能力中心按业务呈现两个接入项，而不是让用户分别理解查询连接器和独立的“通知入站”连接器：

| 接入项 | 查询能力 | 通知接收能力 |
| --- | --- | --- |
| 情报接入 | 情报搜索、报告读取 | 情报事件接收、处理规则、接收席位与回执 |
| 态势接入 | 态势对象与变化查询 | 态势事件接收、处理规则、接收席位与回执 |

每项详情分别配置查询地址与查询凭证、通知接收地址与入站凭证，并展示各自状态。产品入口统一不意味着查询和通知共用密钥、权限或开关；原查询授权和通知管理授权继续分别核验。原独立“通知入站”卡片的管理功能迁入对应业务接入，不另保留一个需要用户配置的重复入口。

演练控制仍是导演台使用的控制能力，保留独立导演授权和控制凭证；此次情报、态势接入整合不把控制权合入业务查询权。通用 MCP 接入不受此调整影响。两个业务接入项也不代表必须部署两个进程或外部服务。

运行时只保留情报、态势各一个有效通知来源，两种操作方式通过服务端核验的模式与轮次区分，不再各设一组来源。四条原来源作为迁移输入，不作为最终运行目标。目标来源的具体标识在依赖核查后明确选定或复用，不能凭名称自动选择。这里的“两个”约束后续运行配置与新通知，不要求历史记录也只剩两个标识。

本轮迁移必须包含：

1. 形成四旧来源到两目标来源的对应表，逐项列出发送方、查询关联、凭证、处理流程、规则、接收席位、授权及历史引用。
2. 升级普通模拟、场景控制、探针、示例与测试的发送目标和模式／轮次参数，禁止调用方自行声明模式来扩大权限或跨轮次投递。
3. 按对应关系迁移处理规则与权限。同一目标下的旧配置不能简单取第一条或合并权限集合；需要不同处理流程或接收范围时保留明确条件，冲突在迁移报告中解决，不静默覆盖。
4. 明确目标入站凭证及其发送方更新方式，保留配对备份。完成迁移后撤销多余来源的写入资格，不长期兼容多个旧凭证或旧入口；查询凭证不因此合并。
5. 核对在途通知、去重标识及回执后切换。来源合并不能使旧消息被当作新事件重新处理，或让同名消息发生错误去重。完成回归后停用多余运行来源，并拒绝新事件写入旧来源。
6. 历史事件、任务、投递与回执保留实际出现过的原始来源标识、关联引用及授权语义，不批量改写为两个目标标识，也不人为补齐四个历史标识。历史中有几个不同标识取决于实际记录，与后续有效来源数量分别处理。
7. 历史列表、筛选与汇总统一按“情报／态势”归类；需要追溯时，在详情中显示原来源标识。归类映射不改写原事件、去重依据及回执关联，也不扩大历史查看权限。
8. 未被选为最终目标的旧来源不得继续接收新通知；其标识只在既有历史及必要的只读核对中使用。若复用某个已有标识作为目标，它作为两个有效来源之一继续使用。旧回执核对不能重新打开已停用来源的写入或自动重送。

后端复用 R4 的连接、秘密管理及原业务服务；根据上述业务关系完成必要的绑定和迁移，不仅把四张卡片在前端隐藏，也不借此重建通用路由平台。历史记录和不可变修订不直接重写。迁移失败按完整配对备份回退，不让部分迁移的来源配置对外运行。

## 七、实施顺序与验证

| 步骤 | 交付与退出条件 |
| --- | --- |
| 1. 依赖与状态设计 | 明确唯一活动轮次、切换结束条件、接口调用方及四来源到两来源映射；列清凭证、规则和权限处置 |
| 2. 服务端互斥与隔离 | 切换、结束、重新开始具有明确回执；防止并发双运行、跨轮次写入和异步结果串入 |
| 3. 页面整合 | 完成两种方式交互及情报／态势接入详情，迁入通知管理，移除旧页面和重复入口 |
| 4. 兼容迁移与回归 | 真实配置副本验证运行来源四转二、历史原标识及关联不变，核对凭证、规则、权限、在途事件与去重；完成业务及浏览器回归 |
| 5. 备份与测试环境发布 | 按届时明确授权发布；全量备份、可回退、核对原历史及业务；保持待用户验收 |

重点验收场景：

- 取消切换、重复选择、刷新、历史查看均无运行状态副作用。
- 从活动或暂停演练切入调试，确认前不变，确认后旧轮次结束、新调试轮次仅创建一次。
- 自由调试结束后进入场景选择，不自动启动演练。
- 重新开始恢复预置数据，但保留旧轮次历史、任务、通知和回执。
- 多窗口同时切换、网络中断后重试、结束或初始化失败，不产生双活动轮次或重复通知。
- 旧轮次编辑、迟到响应和通知回执不改变新轮次；已发通知仍可核对。
- 调试查询不读取活动演练作为默认替代；演练时间与旧证据保持原语义。
- 无导演授权的账号不能通过页面或直接调用 API 操作。
- 旧页面地址、入口及内部链接全部移除；需要保留的后台调用经过明确适配。
- 能力中心呈现情报、态势两项业务接入，各自包含查询与通知管理，查询及入站凭证和授权保持区分。
- 运行时仅两个有效入站来源，旧发送方已迁移，未保留为目标的旧来源拒绝新事件。
- 历史实际来源标识及事件、任务、投递、回执关联保持不变，不强行压缩为两个或补齐为四个；历史按情报／态势归类，原权限与去重依据不变。
- 旧规则、流程与接收范围按对应关系迁移，无隐式授权扩大、凭证混用、重复处理或错误去重；情报、态势独立查询正常。

部署前备份完整数据根、数据库、配置、外置凭证与密钥，并记录旧程序版本。失败时先停止新版本并保留失败现场，再按配对备份恢复，不能让旧程序直接打开已改变格式的活动数据。已经外发的通知不因程序回退而撤销，必须继续保留其回执核对依据。

## 八、本次审阅重点

请重点审阅以下方向是否符合预期：

1. 两种方式互斥，切换经确认后结束旧轮次；自由调试重新开始使用预置数据。
2. 自由调试采用可视化编辑与独立发送通知，不增加复杂数据创建功能。
3. 统一导演授权，结束和重置保留历史，切换失败不强行启动新模式。
4. 本轮完成旧页面、入口及地址移除，同时将查询与通知管理归入情报、态势两个业务接入；运行来源完成依赖迁移后收敛为两个；历史保留实际原始标识及关联，展示按情报／态势归类。

审阅确认后再进入具体实现设计与编码。本文形成不表示整合已实施、已上线或通过用户验收。
