### Shared capability center and administrator presentation

All identities use the Axon application chrome. `ApplicationSidebar` owns the shared brand, collapse controls and Settings footer. The root App narrows `AccountIdentity`: an independent administrator reuses the existing application with `personalOnly`, defaults to the capability center, and normalizes legacy `/admin` and business deep links to `/capabilities`. New Conversation, `useChat`, `useTasks` and private-space navigation remain available for this account's own private data. Business hooks, task-space group, work/information views, maps, annotations, context pickers and their API fetches remain disabled/unmounted. The local workspace adapter uses only server-returned `personalScopeId` for existing workspace controls; it does not create a fake business seat or grant overall-seat privileges. Pass the original administrator account to Settings so its role is shown accurately without model configuration or personal business preferences.

The New Conversation action occupies the same sidebar position and spacing as business accounts. When no personal space exists, keep the action enabled and open the existing private-space dialog with explicit “创建并开始对话” intent; create the space and then an empty conversation only after submit. Cancel, login, navigation and initial capability rendering perform no writes or model calls. A personal-space plus creates only the space; its conversation plus creates an empty conversation. Private space name entry opens its owned chat/workspace rather than a business task-information page; its description uses the private TaskPanel without business context/default controls. Files, fixed Skills, readonly Agents, native questions/confirmation and model choice continue through existing chat components.

`CapabilityCenter` provides one Expert/Skill/Connector tab row, context-specific search and a desktop card grid. Detail dialogs open on an explicit click; keep native Escape and focus restoration, including nested collaboration dialogs. Everyday cards omit release/revision identifiers. Ordinary catalogs remain authorization-filtered; administrator cards use the management catalog and can configure the exact selected expert. Only administrators see the explicit “创建专家” action. A create click uses the existing persistent action receipt and opens that draft in `CapabilityManagement(initialExpertId)`; rendering, changing tabs, reading details and opening management must not POST or invoke a model. Existing draft conflicts, trial/manual-confirmation/publication and seat-default behavior remain in the same services.

R2 retains `/api/capabilities/library` as the controlled metadata compatibility endpoint. R3 `SkillLibrary` uses the current authorization-filtered `/api/capabilities/skills` catalog for ordinary users and the administrator management catalog for shared asset editing; these routes do not grant workspace, business-tool or organization-skill use authority to a seatless administrator. Connector integration is deferred; show an honest empty state instead of invented services or unusable connection buttons. Use the actual content-container width for desktop grid columns and validate 1060/1440 layouts, keyboard tab navigation, search/empty states, selected-editor targeting, one create POST and absence of administrator business requests. `tests/e2e/administrator.spec.ts` also covers explicit first-space/new-conversation creation, cancellation without writes, private-only navigation, shared sidebar spacing and correct account role. `capabilities.spec.ts`, `capability-management.spec.ts` and the existing access regressions remain required.


### R3 skill package management and selection

The existing capability-center Skills tab owns creation, copying and import for current administrators. Import first previews Markdown or one bounded ZIP, then requires an explicit “确认导入草稿” action. Cancel/reading does not create an asset or call a model; ordinary chat uploads remain documents. Builtins are readonly and can be copied into an independent organization asset. Keep file paths relative and render text inertly; binary resources are preserved/replaced rather than executed or loaded as active browser content.

`SkillManagement` separates files, checks/publication, optional isolated trials, publication history and seat use policy. Draft saves carry expectedDraftRevision; stale saves preserve local files and offer a separately read latest draft with an explicit discard choice. Check/scan/trial results retain their content digest and old snapshots are labeled, never promoted into current evidence. Publish requires valid saved format/integrity, explicit policy, notes and human publication intent; it does not depend on zero findings, successful scanning or successful trials. R2 expert trials are also optional. Keep current saved-configuration validation, risk acknowledgements, scope, notes and explicit publication confirmation; no trial status or file-environment trial result disables publication. Label isolated expert trials as optional, preserve true result/confirmation states, and do not claim trial review in the publication checkbox. Associate a confirmed successful trial only when both draftDigest and validationId match the current checks; otherwise omit trialId. See [R2 Expert Management](../backend/capabilities-r2.md#optional-expert-trials).

Scan reports distinguish pending/running/completed/partial/failed/not-applicable, findings and actual coverage. Render fixed rule/scanner version, file/line, raw tool severity, skipped paths and actual errors; a completed zero-finding report says only that no problem was found within that rule scope. Source compatibility/dependency declarations are not environment-detection conclusions. Do not add preflight environment pages, automatic production probes or risk-approval flows. Trials start only on explicit administrator input and keep owner-scoped records/files in their existing isolated Pi runtime.

Ordinary skill details stage a method into an already authorized workspace/conversation. Cancel does not create a conversation, and staging preserves unsent text/files and never sends a model request. A selected active conversation must finish first. New package selections carry revisionId/packageDigest as well as method hash; selection is checked again before sending. Expert configuration chooses a fixed published skill revision, and a newer package cannot silently replace that dependency. Seatless administrators can stage published enabled organization skills into their own personal conversations. Managed cards retain the detail/edit entry and expose a separate use action only for available published skills. Reuse the ordinary detail/space picker and staging callback: preserve draft/files and never send automatically. The scope editor describes business-seat publication separately from administrator personal use; business navigation and ownership checks remain unchanged.

Targeted browser coverage is `tests/e2e/skills.spec.ts` at 1060/1440 desktop widths, plus existing login/capability/expert-management/reference regressions. Native API/Pi tests verify permission denial, immutable version conflicts, manual-only extension behavior, actual method delivery and history separately from UI staging.


R3 policy forms and publication actions retain their own viewed revision/pointer baselines with local inputs. Scan polling, validation reloads and other GET responses must not silently advance these baselines. Advance only after the caller's successful mutation or explicit adoption of separately read latest data. A409 preserves local choices; idempotent lost-response retries retain the original action inputs. Both formal and test-mode skill detail routes must satisfy the shared safe DTO, including trialSummary, so a compatibility route cannot crash the panel through a missing field.


### Skill creation and concise capability chrome (2026-11-16)

Opening skill creation is local UI state, not a POST that creates a placeholder asset. Show labeled name/description/instructions fields before confirmation; instructions may be empty under the package standard. Cancellation writes nothing. Confirm uses the existing create action with complete files in one atomic operation; pending identical retries retain the action ID and actual input. Invalid input preserves form values and creates no asset. Copy/import retain their explicit existing semantics.

Ordinary method editing presents form fields with advanced file/source editing still available. Both views use the same local file bytes and the existing draft CAS. Preserve unknown frontmatter, extension metadata and other resources; opening, no-op changes, switching views or scan polling must not reserialize untouched content. Unsupported/broken frontmatter remains repairable in source view. Do not drop metadata to make a simplified form work.

Capability chrome omits decorative subtitles and repeated process explanations. Keep actual expert/skill descriptions, actionable errors/status, empty-state titles, and relevant report coverage. Show detailed scan evidence through a disclosure instead of pushing the publication form off-screen. Prerequisites for publication need concise actionable feedback; scanning/trial success is still not required. Validate at desktop1060/1440 widths with keyboard/focus and manual screenshot inspection; no mobile work.


### Skill authoring step progression and archive grouping

The primary authoring order is content, business use scope, then checks/publication. Advance only after the caller's successful action, never from a GET/scan poll. A newly confirmed complete creation may open at scope; import/copy/existing content retains a review path and an explicit next action even when unchanged. Saved content advances to scope, saved scope advances to publication and ordinary format validation; partial failures must distinguish the already-saved scope from a failed check. Preserve input/current tab on conflicts and do not skip newer unsaved edits. Never auto-publish, auto-run trials or call a model as part of this progression. Publication remains explicit and optional trial/history pages stay outside the required chain.

For new creations, compare the receipt's draft digest with the first management detail before initializing at scope. A retried create can return its original receipt after another administrator has edited the asset; in that case initialize at content for review. This check initializes local navigation once, and later GET/scan updates must not navigate.

The Skills section header owns the title and import/create actions in one flex row; do not render the title in a parent row and the actions in a child row. Verify aligned bounds at desktop1060/1440. Default cards include actual active/draft assets; group actual archived assets in a collapsed archive section. Do not hide by name, empty body or other content guesses. Old untouched placeholders are handled through a separately verified existing lifecycle action after backup, not a hidden automatic data cleanup on page read.
