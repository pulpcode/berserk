> 历史评审，不作为当前实施依据。当前方案见 [设计](../design.md)，检查结果见 [文档检查](../planning-check.md)。

- Query: 复核当前 design.md 第 3／7 节的容量公式、摘要限制、用途计数、旧自定义配置和官方 1M 表述。
- Scope: internal / mixed（审阅待实施设计，对照已读取的锁定 Pi 0.85.1 与官方 DeepSeek 文档）

## Findings

### 复核结论

没有发现 `I = min(B, C − O − S)` 或 `J = min(4 × I, C − summaryOutput − S)` 的直接算术错误。摘要的容量没有被错误缩成普通回答软预算，输出有预留；官方 1M 的保守配置值与任意自定义端点也已分开。以下为建议在交付审阅前澄清的设计问题，不是已发生的产品缺陷。

### R1：压缩后 60% 目标与真正通过条件不够明确

- 位置：`design.md:40`、`:71`、`:74`、`:99`。
- 分类：P1／需要明确的设计契约。
- 已验证事实：方案规定始终保留最近一个完整请求、本次输入与当前系统规则，摘要 JSON 又有 16 KiB 上限；这些内容均需重建后检查。
- 问题：前文写目标 `E_after <= 0.6I`，流程只写“重建后预算”，未明确 60% 是优化目标还是保存摘要的硬门槛。若不可压缩部分已占 `0.7I`，还可以在 `I` 内继续回答，但永远达不到 60%。直接按硬门槛实现会把可继续的会话拒绝；按软目标实现又需要明确何时允许停止扩大覆盖范围。
- 数值例：`I=8192`，不可压缩部分估算 6000，候选摘要及宿主效果说明合计 1000，`E_after=7000` 可以满足发送预算，却不满足 4915.2 的 60% 目标。
- 建议：明确 `0.6I` 为切点选择的努力目标，最终合法条件至少为 `E_after <= I`，并要求摘要后的输入较压缩前缩小；当固定部分＋至少一个最小合法摘要已超 `I` 时，应在模型调用前说明无法整理。不能仅因为未到 60% 自动多次摘要。
- 还需明确摘要可用空间如何参与切点：16 KiB 是绝对结构上限，不能当作任何 `I` 都容纳得下的预留。用当前估算 `/2` 时，16 KiB 本身约占 8192 个估算单位，已经超过允许配置的最小 `I=4096`；应派生本请求剩余空间，最终测量的是 Pi 实际摘要包裹＋宿主说明＋保留消息的整体输入。

### R2：UTF-8 字节／2 仍可能低估，不应作为未知 tokenizer 的“保守”保证

- 位置：`design.md:37`、`:60`、`:62`。
- 分类：P1／需要显式选择的估算政策；并非声称已有真实溢出证据。
- 已验证事实：本地 Pi 只对消息正文做字符／4 估算；DeepSeek 官方列出的中英文比例也是经验值。OpenAI-compatible 只是协议兼容，不规定 tokenization。
- 问题：`bytes/2` 解决了部分中文低估，却不保证标点、数字、随机标识符、JSON、用户自定义 tokenizer 的安全上界。小模型 `C=8192`、`O=2048`、`S=1024` 时有 `I=5120`；若某端点对某输入恰好接近每 UTF-8 字节一个 token，8000 字节输入估为 4000 而通过，但实际输入加输出可超容量。此处是说明算法缺乏上界的反例假设，未进行真实 API 测量。
- 方案已经注明“不能保证均不超限”，因此文字没有虚假承诺；仍应确认是否接受这一级风险。建议对尚未核验 tokenizer 的组合使用完整字节计数＋协议余量，或在文档明确 `/2` 是实验折中，验收必须比较真实输入 usage 且允许服务商拒绝。不要把最终 wire 估算称为硬性证明“实际 token 不超 C”。
- S 按 C 取 2% 是项目提案，不是官方建议。对 DeepSeek 1M 有 20000 余量，对小容量只有 1024；固定百分比不能补偿任意倍数的估算误差。

### R3：新环境容量与已有本地 v1／v2 设置的优先级需要按模型身份定义

- 位置：`design.md:49`、`:52`、`:53`。
- 分类：P1／实现前补齐兼容契约。
- 已验证事实：现有 `ModelSettingsStore.open` 会用保存文件覆盖环境里的 provider/model/baseUrl/key；v1 文件没有容量，保存文件有严格字段检查。代码锚点：`src/server/model-settings.ts:44`、`:60`、`:65`。
- 问题：新增 `LLM_CONTEXT_WINDOW` 是数值而不携带独立身份；“网页保存后的模型字段优先关系与现状一致”未说明一个 v1 本地模型如何处理新环境容量。若环境默认仍为 DeepSeek、v1 本地已改成另一个提供方，简单合并会把 DeepSeek 的环境容量赋给另一模型。反之，如果用户特意为相同本地模型填写了环境容量，忽略它也可能造成意外的配置缺失。
- 建议选定一种有限规则并写清：只有无本地设置，或环境 provider/model/规范化端点与有效本地模型身份完全相同时，环境容量才可作为显式来源；本地 v2 明确容量优先。身份不匹配的 v1 仍按已核对 preset 或 unknown 解析，不能只因为环境键存在就补齐。另一可行的更简单政策是本地文件存在时完全不用环境容量，但必须告知使用者应在网页补填。
- PUT 还应明确：省略容量是“同身份保持／换身份重算”，不等同于 `null`；若允许用户恢复 preset／清除显式值，需明确额外语义。本期可以不提供清除操作。

### R4：摘要输出额度、重试与剩余空间应在两次尝试中一致校验

- 位置：`design.md:74`、`:95`、`:118`、`:120`。
- 分类：P2／预算行为精确化。
- 已验证事实：当前 `MAX_OUTPUT_TOKENS` 允许 64～8192。方案取 `summaryOutput=min(4096,O)`；用户把普通回复上限设为 64 时，摘要也最多 64 token。严格六字段 JSON 加上非空任务事实可能无法完成。
- 问题：没有模型级最大输出独立配置时使用普通输出上限是可行的保守选择，但不能保证所有合法 O 均能生成有用摘要。还需定义 length 是否允许按相同 token cap 再试一次，还是直接报输出额度不足；纯增加修复提示不增加输出空间。
- 建议：将“摘要输出额度太小”列为可识别失败原因，并提供模型设置／服务端限额指引；或者为启用压缩设置经过验收的最低 O（明确是项目支持范围，不能冒充官方最低值）。两次尝试都要重做最终摘要 payload 预算检查，修复提示也计入 J；不得在重试中临时提升额度越过 I/C/J 或重新开始 deadline。

### R5：累计调用次数的名称与占额时机需避免误称实际网络调用

- 位置：`design.md:120`；现有代码 `src/pi/lab.ts:308`。
- 分类：P2／可观测性契约。
- 已验证事实：现有 streamFunction 在建立上游调用之前增加计数；其后的 onPayload、SDK 构造或本地校验仍可能失败而没有实际 HTTP 请求。
- 建议：对限额采用“已准入的模型调用尝试数”语义，最终 payload 检查通过后、交给 transport 前占额，后续错误不退还。单独记录 reply／compaction；不要求凭一次 SDK 调用证明提供商已处理。若继续叫“实际调用数”，应定义为交付 transport 的尝试次数而非成功响应数，并将本地拒绝与未知是否到达提供商区别开。
- 上限本身一致：回答最多 `maxToolCalls+1`，摘要最多 2 次（本设计不是 Pi split-turn 两摘要，而是主摘要＋一次修复重试），总上限 `maxToolCalls+3`，默认 11。两类独立子额度与共享总额都要检查，不能让未用摘要额度变为额外回答轮次。

### R6：旧自定义配置的可用性变化已写出，但 UI 补救入口还可以明确

- 位置：`design.md:51`、`:54`、`:136`；`prd.md:29`、`:39`。
- 分类：P2／可审阅的兼容行为。
- 已验证事实：旧官方默认组合能推导容量；旧自定义模型容量未知时会停止新发送，但页面、项目与历史继续可用。这是已写明的产品行为变化，不是无条件向后兼容。
- 建议补一句：页面进入就读取 contextReady，并在模型设置入口提示“补充模型上下文容量”；填写同一提供方／端点时沿用现有密钥，不要求重新输入；当前草稿保留。容量配置保存成功后用户显式发送，不能自动重放先前被拒绝的消息。
- `MODEL_CONTEXT_UNCONFIGURED` 应在同步 start 准入阶段返回，避免明知无法运行仍占会话或写用户消息；若依现有 SSE 路径返回也必须确保草稿恢复与无重复消息，二者应选定其一。

## 已核对且可保留的表述

1. **1M → 1,000,000 保守预设**：`design.md:50` 没有声称精确二进制边界，且包含官方端点限制。它是依据规格的应用数值选择；官方文档可核对的是 1M 和最大输出 384K／393216。
2. **C/B 分开**：`design.md:34` 的模型容量与 `:35` 的项目软输入预算区分清楚，真实验收降低 B、不伪造 C 是正确安排。
3. **J 独立于 I**：`design.md:118` 允许摘要输入达到 4I，但始终预留摘要输出和 S；适合在较低 B 下触发验证。4 倍为项目边界，不能保证任何已有大历史都可整理。
4. **同请求预算**：摘要与回答共享取消和总期限，失败不返还次数且不循环整理，符合目前宿主控制方式。当前代码不能直接提供这些新行为，属于拟实施内容。
5. **不用原聊天 wrapper 原样摘要**：`design.md:22`、`:26` 与本地 Pi `_runDefaultCompaction` 证据一致；用 purpose 区分 reminder／工具／输出／阶段是必要改动。
6. **未知 usage 明确未知**：`design.md:120` 未把缺失用量和 SDK 零费用占位当作免费，也未恢复用户此前拒绝的“10条真实验收限制”。
