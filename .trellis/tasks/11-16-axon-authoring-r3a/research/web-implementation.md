# R3A 原工作台界面实施与验收

## 产品行为与边界

- 专家/技能主按钮进入原新建个人对话流程，带入按请求消费的创作方法；明确保留手动创建与技能导入，取消空间/会话弹窗零资产、零模型。未发送正文不会调用模型，原输入、附件和默认专家不被覆盖。
- 原输入工具区的“创作方法”可在本人既有对话选择专家/技能；发送后按现有选择恢复机制消费，不形成永久会话授权。详情“对话修改当前草稿”携带明确目标与已保存基线，脏输入先明确放弃或取消。当前草稿的措辞避免从历史比较页误以为覆盖旧发布修订。
- 原 ConfirmationDetails 显示实际目标/基线、计算出的字段/文件增删清单、可展开完整候选及完整保存前内容，UTF-8文本可读且不截断；没有独立创作页面或结果卡片。
- 真正执行成功的原确认历史提供主动详情按钮，普通 receipt-only read 工具结果也能打开详情；原聊天URL/正文保持。仅受控成功工具投影、严格共享回执 guard、真实session/request/tool关联形成定位，模型正文和普通工具不能造链接。新建技能打开原管理时核对真实回执摘要，变化退内容审阅，未变化可进入范围；没有自动配置/发布/试用。

## 首轮失败与修复

1. Vite本地监听被sandbox拒绝，后续按授权在escalated测试环境运行；非产品失败。
2. 原有app.inject会缓冲SSE，pending确认无法及时到达浏览器；改真实HTTP后尝试URL重写又触发Origin/Cookie测试适配问题。最终使用本地4310实际Fastify及Vite5193同源代理，完整原生SSE，auth/API/Pi均真实，仅模型provider transport为fake。每次结束关闭本地服务，未部署。
3. 测试折叠组动态索引选择器有失效，修正测试辅助定位。随后发现实际保存结果被既有ConversationItems合并到确认历史，普通ToolMessage中的按钮不可见；在原ConfirmationHistory实际成功回执处补同一按钮，仍复用原组件。最终闭环已证明可主动进入原管理。
