# 多源上下文最小模拟场景（待审）

状态：设计提案，未实施。本文只定义合成数据、接口能力和可观察结果，不代表现有接口已具备这些能力。

## 1. 验证目的与边界

用一份合成的园区物资运输方案验证：外部消息没有 Axon 任务 ID 时，特情更新和独立态势变化都能触发工作；Agent 能查询报告历史、对象当前状态与变化、获准的 Axon 任务，说明哪些任务受到影响以及依据是什么。

一个独立 HTTP mock 进程提供 `intel`、`situation` 两个业务 API，Axon 宿主通过各自的 HTTP adapter 查询；两者保留独立系统标识和入站事件去重空间。本期两个系统共享一个 `contextScope`，两类数据具有同一可见边界；不为它们新增独立细粒度授权或逐条报告权限。既有入站来源认证与查询资料范围分别校验。场景重置、推进和故障开关属于测试控制端，不作为 Agent 工具。

集成与真实模型验收必须实际经过 HTTP 请求、认证、参数编码和响应解析。Axon 应用及 adapter 不得直接 import mock fixtures、读取 mock 数据目录或调用绕过 HTTP 的内存数据访问器；Agent 也不挂载这些目录。测试控制端可以装载 fixture，不能把它作为宿主查询的替代路径。

预期答案仅保存在测试侧，不进入来源通知、查询数据、Profile、Skill 或任何 Agent 可读资料。本文包含预期结果，因此不得整体作为模型输入或挂载资源。外部 API 只提供来源事实，不替 Agent 计算 Axon 任务影响或比较任务需求；任务目标和车辆需求只通过 Axon 任务查询获得。

模拟服务本身不需要模型，也不需要消防业务系统、真实车辆、地图、GIS 服务或真实传感器；本阶段实施验收仍须使用当前配置的真实模型完成查询与综合研判验证。所有名称、数量、区域和时间均为软件验证数据；“影响”只表示合成方案中的条件发生变化，不产生真实运输指令。

Axon 沿用固定规则投递。候选任务及影响分析是查询和分析结果，不自动改变投递席位、任务状态、业务方案或任何外部对象，也不因此读取其他任务的私有工作区。

## 2. 数据归属与标识

| 数据 | 主责方 | 本场景用途 |
| --- | --- | --- |
| 特情报告及其修订、原文、观测时间 | `intel` | 读取同一报告的历史，判断新旧说法与有效时段 |
| 道路、车辆资源、区域及其状态变化 | `situation` | 查询对象快照和自指定游标以来的变化 |
| 任务目标、关注范围、业务引用 | Axon | 识别获准任务与来源对象、区域、时间的关系 |
| 任务 × 席位工作区、会话和分析 | Axon / Pi 原生机制 | 保存本席位工作结果、依据和后续对话 |

业务对象使用 `{systemId, objectType, objectId}` 三元组；表格中的 `situation:road:road-west-01` 是该三元组的简写，不能靠名称相似、ID 尾缀相同或区域相邻把两个对象视为同一对象。`intel` 可以在报告中引用 `situation` 已有对象，不复制其主数据，也无权更新其状态。

`systemId` 表示外部业务系统身份；`sourceId` 只表示 Axon 入站来源配置。本场景部署映射为 `sourceId=mock-intel-source → systemId=intel`、`sourceId=mock-situation-source → systemId=situation`。二者不能混用；更换入站接入配置不应改变业务对象身份。

| 标识 | 示例 | 含义 |
| --- | --- | --- |
| 消息去重键 | `(mock-intel-source, intel-msg-0001)` | 一次来源通知；重送同一通知沿用同一 `sourceMessageId` |
| 业务对象引用 | `situation:road:road-west-01` | 可跨多条消息、多次修订、多个 Axon 任务复用的对象 |
| 报告引用 | `intel:report:report-west-01` | 同一报告的业务身份，修订时保持不变 |
| 对象修订 | `revision=2` | 该对象在其来源内的版本，不与别的对象版本比较大小 |
| 态势变化游标 | `situation-seq-101` | `situation` 变化流中的位置，不是对象 ID 或业务时间 |
| 证据引用 | `intel:report:report-west-01@2` | 一次查询实际返回的具体版本；用于解释和追溯 |
| Axon 任务场景代号 | `task-west-supply` | 仅供 fixture 和文档引用；不是产品中的 taskId |
| Axon 真实任务 ID | 创建 API 返回的 UUID | 由测试脚本记录代号→UUID 映射，只存在于 Axon 数据及测试控制上下文中 |

沿用现有 `(sourceId, sourceMessageId)` 接入幂等语义：相同键与相同语义内容不新增初始处理作业；相同键但内容不同应冲突。新修订应发送新消息 ID。不能用道路对象 ID 去重，否则同一道路的后续变化会被吞掉。人工重新处理是新作业，不冒充来源重送。

## 3. 固定合成数据

### 3.1 时钟、区域与对象

固定业务日期为 `2026-10-01`，时区为 `+08:00`。文中简写的业务时刻均属于该日；所有接口返回完整 ISO 8601 时间。时间窗采用左闭右开区间 `[from, to)`。业务时间和 `asOf` 随选定 fixture 阶段固定；`queriedAt` 记录实际查询时刻，不伪装成模拟业务时钟，也不用于推断业务变化顺序。

区域使用稳定编码 `zone-west`、`zone-east`，分别表示叙述上相邻的西区和东区。adapter 只按固定编码及显式对象成员关系筛选，不设置矩形坐标，不进行相交、距离或其他地理计算。“相邻”只用于说明空间接近不能证明业务相关；测试的无关性由不同区域编码和独立道路、资源池确定。

| 来源对象 | 区域 | 基线 revision / 时间 | 合成内容 |
| --- | --- | --- | --- |
| `situation:road:road-west-01` | `zone-west` | `1` / 09:00 | 西区通道，属于合成方案路径；没有可供查询的实时通行状态字段 |
| `situation:resource:vehicles-west-01` | `zone-west` | `1` / 09:00 | 可用车辆数 `4` |
| `situation:road:road-east-01` | `zone-east` | `1` / 09:00 | 东区独立通道，与西区方案无共用路段 |
| `situation:resource:vehicles-east-01` | `zone-east` | `1` / 09:00 | 可用车辆数 `5`，与西区无共享资源池 |
| `situation:area:zone-west` | `zone-west` | `1` / 09:00 | 固定区域和成员关系 |
| `situation:area:zone-east` | `zone-east` | `1` / 09:00 | 固定区域和成员关系 |

基线变化流位置为 `situation-seq-100`，E2 对应 `situation-seq-101`，均不是分页游标。道路只提供稳定身份、区域和方案关联所需的信息；不能把“查到了道路”解释为“态势系统确认道路畅通”。

### 3.2 Axon 的三个任务

以下业务引用与关注范围是拟新增能力的样例，字段落点以待审 `design.md` 为准。场景通过现有 API 创建三个公共任务，由脚本记录 API 返回的真实 UUID；`task-west-*`、`task-east-*` 仅为场景代号，不把它们写成产品 taskId。它们的任务状态均可保持 active，以验证业务时间不是创建时间或任务状态的替代物。

| Axon 任务 | 目标与约束 | 关注对象 | 关注区域 / 业务时间 |
| --- | --- | --- | --- |
| A `task-west-supply` | 复核西区物资补给方案；计划 09:40 使用西区通道，方案要求至少 3 辆可用车辆 | `road-west-01`、`vehicles-west-01`（均属 situation 系统） | `zone-west` / `2026-10-01 09:00–11:00` |
| B `task-west-transfer` | 复核西区设备转移方案；计划 09:50 使用同一西区通道，方案要求至少 1 辆可用车辆 | `road-west-01`、`vehicles-west-01` | `zone-west` / `2026-10-01 09:00–11:00` |
| C `task-east-current` | 复核相邻东区运输方案；仅使用东区通道和东区独立车辆池 | `road-east-01`、`vehicles-east-01` | `zone-east` / `2026-10-01 09:00–11:00` |

对象 ID 在该表只为排版省略系统和类型，实际数据必须保存完整三元组。A/B 是两份待复核方案，未并发承诺资源；本例只验证各方案的数量条件，不做资源预占、排程或全局配给。计划时刻和车辆需求属于 Axon 任务上下文，外部源不保存这些任务、不接收这些任务 ID。读取任务元数据不创建它们的工作区，也不授权读取其会话或文件。

时间无关的独立测试变体：重置实例后，把 C 替换为 `task-west-history`，目标为“复盘前一日西区运输记录”，关注西区相同道路与车辆、时间窗为 `2026-09-30 09:00–11:00`。其状态仍为 active；这样每个实例仍只有三个任务，可单独验证同对象同区域但业务时间无关。正常演示保留东区 C，不同时增加第四个任务。

### 3.3 特情历史

| 报告及 revision | `observedAt` / `publishedAt` | 有效时间 | 内容与引用 |
| --- | --- | --- | --- |
| `report-west-01@1` | 08:50 / 08:55 | 09:00–11:00 | 截至观测时刻未报告西区通道限制；引用 `situation:road:road-west-01`，区域 `zone-west` |
| `report-west-01@2` | 09:18 / 09:20 | 09:20–10:10 | 新报告：西区通道在该时段临时受限；引用同一道路，并说明是对本报告的更新 |

revision 1 的“未报告”不是未来可通行保证。revision 2 也只支持其明确有效时段内的结论。历史查询须同时可见两个版本；只查最新版本不足以验证“相较前次发生了什么变化”。

## 4. 通知形状与查询能力提案

### 4.1 两个来源的通知

下表描述逻辑内容。HTTP 请求沿用现有 `sourceMessageId/title/text/subjectId/occurredAt`，不增加结构化引用字段；正文提供报告／对象及版本线索，查询响应返回三元组。完整字段和示例见 [交互契约](../integration-contract.md)，不能把 subjectId 当作跨来源通用关系图。

| 通知 | 入站 `sourceId` / 消息 ID | `occurredAt` | 提供给处理流程的线索 |
| --- | --- | --- | --- |
| E1 特情更新 | `mock-intel-source` / `intel-msg-0001` | 09:20 | `report-west-01` 更新到 revision 2；引用西区道路；有效时间 09:20–10:10；查询报告历史的线索 |
| E2 独立态势变化 | `mock-situation-source` / `situation-msg-0001` | 09:30 | `vehicles-west-01` revision 1→2，可用车辆 4→2；变化游标 100→101；有效时间 09:30–11:00 |
| E3 未知对象报告 | `mock-intel-source` / `intel-msg-0002` | 09:35 | 新报告 `report-unknown-01@1` 引用 `situation:road:road-unknown-99`；区域 `zone-west`；有效时间 09:35–10:10 |

所有来源通知都不含 `taskId`、`taskIds`、Axon 工作区 ID 或席位 ID。来源只负责描述自身变化；固定规则的投递配置属于 Axon。

`occurredAt` 是来源通知所描述事件的时间；`observedAt` 是业务事实观测时间；`publishedAt` 是来源发布时间；`queriedAt` 是本次查询时间。不能用接入或查询时间替代业务有效时间。E2 的变化可在没有新增特情报告时单独发送。

### 4.2 所需最小只读能力

以下是 adapter / Agent 工具需要表达的逻辑操作，名称仅为提案，不承诺已经存在这些 API。

| 能力 | 输入 | 返回与边界 |
| --- | --- | --- |
| 特情报告历史 | `reportRef`；可选时间窗 | 报告各修订、原文、业务引用、有效时间和证据引用；区分未知报告和服务不可用 |
| 特情按范围查询 | `objectRefs`、`areaIds`、时间窗 | 匹配报告及命中依据；对象组内任意命中、区域组内任意命中，各已提供条件组之间取交集；不能仅按关键词猜引用 |
| 态势对象快照 | 可选 `objectRefs`、`areaIds`、分页 `cursor` | 按同一组内 OR、组间 AND 规则筛选；返回当前可见对象、对象 revision、有效时间、`asOf`、`queriedAt` 和分页 `nextCursor`；未知对象单列 |
| 态势变化查询 | 变化位置 `after` 或 `from/to` 时间窗，二者互斥；可选对象/区域、分页 `cursor` | 对象与区域组采用同一交集规则；返回完整变化前后版本、有效时间、`nextCursor` 与 `nextAfter`；结果为空与查询失败不同；游标不识别应明确报错 |
| Axon 任务上下文查询 | 当前主体身份；`task_search` 可选业务引用、区域、文本；`task_read` 使用真实 taskId | `task_search` 将引用命中、区域命中、文本命中取并集作为候选并说明原因；返回任务时间供分析判断，不在初筛隐式过滤。仅获准元数据、目标、业务引用和关注范围，不读取跨任务文件 |

外部查询的 `from/to` 按主设计过滤报告观测时间或态势变化生效时间，本 fixture 使用左闭右开端点并在返回中说明。查询报告完整历史时不套用任务时间窗，避免把此前观测的 revision 1 排除。任务相关性由分析再比较任务时间与业务有效区间：四个端点均已知时为 `item.from < task.to && task.from < item.to`；明确的开放端点按无界处理。有效时段未知时不能套用公式，不能默认为当前有效或直接断言无关。

例如同时提供道路 `road-west-01` 与区域 `zone-east` 时，外部检索不得因仅命中道路就返回该西区条目；提供多条道路时任一条匹配即可满足对象组。`task_search` 则允许对象或区域任意一组命中，把结果保留为候选后再分析。两种语义不能混用。

范围查询可只对本场景固定数据使用枚举过滤；不需要通用搜索引擎、对象图谱或空间分析。分页使用 `cursor/nextCursor`，即便本 fixture 只有一页也须明确末页与完整性。变化流位置使用 `after/nextAfter`：非末页 `nextAfter=null`，末页才返回非 null 的推进位置；读完所有页后才能用它开始下一批变化查询。E2 后从 `after=situation-seq-100` 查询并读完，得到 `nextAfter=situation-seq-101`。分页位置、变化位置和来源消息去重键不能互换；具体 wire 以主契约为准。

每次成功工具查询至少给出：来源、请求的对象/范围、宿主记录的 `queriedAt`、返回数据的 `asOf` 或业务时间、各项标识与 `revision`、分页／完整性信息。`evidenceRef` 所指的可读引用由宿主按来源、标识与版本派生，不是模拟 HTTP 响应的必填字段；依据定位到原生工具调用及实际返回记录，不要求新增证据数据库。联调字段以 [交互契约](../integration-contract.md) 为准。

不同来源 revision 不能比较新旧，不宣称双源全局一致快照。分析记录各来源实际读取的时间和版本；若最新版本超出触发版本，明确区分“触发变化”与“查询时最新情况”。

## 5. 可重放步骤与预期依据

mock 测试控制端支持“重置到基线”“推进到指定阶段”和显式故障开关。推进是固定 fixture 的选择，不依赖实际墙钟、随机数或真实外部系统。重置只作用于独立测试实例；同一 Axon 测试数据根内重复运行可用 run 前缀隔离来源消息 ID，不能绕过既有幂等规则。

| 步骤 | mock 操作 / 输入 | 必须可观察的结果 |
| --- | --- | --- |
| S0 基线 | 建立 3 个 Axon 任务；报告仅有 revision 1；态势游标 100，西区车辆 4 辆 | 能查询到完整基线；不因数据可查询就自动创建来源事件或触发分析 |
| S1 特情触发 | 追加报告 revision 2，发送 E1；态势仍为游标 100 | 产生来源处理与固定规则投递；分析查询同报告历史、相关态势、获准任务 |
| S2 相同消息重送 | 原样再次发送 E1 | 返回同一接收记录；不新增初始处理作业，不生成第二份初始投递 |
| S3 独立态势触发 | 西区车辆 revision 2 生效；态势游标推进到 101，发送 E2；不新增特情 | 单独触发新的处理；不能依赖 E1 或“再次提交特情”才能执行 |
| S4 未知对象 | 追加 `report-unknown-01@1` 并发送 E3；快照中始终没有 `road-unknown-99` | 如实报告未知对象；不把它映射到 `road-west-01`；区域只支持候选相关性 |
| S5 查询不可用 | 从基线单独分支重放 E1，令 situation 快照/变化查询返回明确 unavailable | 能取得特情历史和任务数据；说明态势查询失败及尚未证实的事项，不把失败当作空列表或“无影响” |
| S6 时间无关变体 | 独立重置，将 C 换为前一日西区复盘，再执行 S1/S3 | A/B 按其条件研判；C 虽同对象同区域且 active，业务时间与变化不相交，不能声称其前一日运输受今天的变化影响 |
| S7 需求互换对照 | 从独立 S0 分支，经 Axon API 将 A/B 的车辆需求从 3/1 互换为 1/3；保留名称、引用、时间和 C，直接执行 S3，不执行 S1 | 外部 E2 和车辆 4→2 数据保持相同；应改为 A 的数量条件满足、B 数量不足；不能沿用主场景“A 不足”的答案 |

S1 的预期研判依据：

- 引用 `intel:report:report-west-01@1` 与 `@2`，说明新增的是 09:20–10:10 的通道限制；`@1` 是先前的观测背景。
- A 的关注道路完全匹配，计划 09:40 落入限制时段，因此其既有路径假设需要复核。资源快照 `situation:resource:vehicles-west-01@1` 显示 4 辆满足“至少 3 辆”的数量条件；它不能消除道路限制。
- B 的道路也完全匹配，计划 09:50 同样落入限制时段，因此同一条 E1 同时影响 A/B，但须分别引用两任务各自的目标和时刻；不能只返回一个“所属任务”。
- C 的道路和资源池均独立，区域仅相邻，在本 fixture 中没有受影响依据。S6 变体中 C 的关注时段是前一日，两个时间区间不相交，不能把今天的限制写成对前一日运输的事实结论。

S3 的预期研判依据：

- 使用变化游标 100→101，引用车辆 revision 1 和 2，说明 09:30 起可用数由 4 降至 2。
- A 的资源引用匹配、时间相交，`2 < 3`，原方案资源数量条件不再满足；特情历史中最新的道路限制仍与 09:40 相交，所以可以综合列出道路与车辆两个不同来源的依据。
- B 也关注该车辆池，但其独立方案的数量条件为至少 1 辆，`2 >= 1`；不能照抄 A 的“数量不足”结论。正常演示中 B 仍受到先前道路限制影响，且应区分这不是 E2 新增的道路事实。
- C 的排除理由仍成立。不能把来源仅报告西区资源变化扩展为整个园区资源短缺，也不能把当前可用数当成已为 A/B 分别预留的车辆。
- 单独验证分支：重置基线后直接执行 S3，仍应触发并识别 A 的资源条件变化；由于该分支未发生 S1，不得引用不存在的特情 revision 2。

S4 中可以说“A/B 的区域与该报告区域相同，需要确认未知对象与方案路径的关系”；不能说“该未知道路就是 A/B 的道路”，也不能给出已经证实的路径影响。若引用区域不可靠或时间未知，也须保留这些缺口。

S5 中特情足以支持其来源内的道路限制结论；车辆数量是否满足要求没有当次态势证据。允许得到正常完成但证据不完整的分析，执行成功与业务结论充分性分别判断。恢复服务后可显式重新处理；本场景不要求新增自动重试或自动重放机制。

S7 与“从 S0 直接执行 S3”的原需求分支对照：仅 Axon 任务需求和相应 revision 改变，外部通知、查询事实及通用 Profile 保持相同。使用独立 Axon 测试数据根及新作业／会话，不复用 E2 接收记录或携带旧分析；必须实际读取互换后的任务目标，并分别依据 `2 >= 1`、`2 < 3` 判断 A/B。该分支没有特情 revision 2，不得声称有道路限制。固定场景及这一对照只验证所列能力，不代表对任意真实业务资料均能正确研判。

## 6. 验收证据与可重复性

每次验证应能检查以下结果；不以固定措辞或一条模型最终回复作为全部证据：

1. **边界**：抓取通知及四个外部查询端点的原始响应，确认不含 Axon 任务／席位标识、任务目标、需求阈值或预期影响答案；外部 fixture 没有 Axon 任务表。检查 Profile、Skill 和模型可读目录均无评分答案，宿主与 Agent 均不能直接读取 mock fixtures。
2. **触发**：E1、E2 有独立接收记录和初始作业；直接执行 S3 的分支也成立；相同消息重送被既有幂等机制处理。
3. **查询**：同时记录 mock 收到的 HTTP 请求及实际工具调用的授权主体、范围、返回版本和证据引用；S1 读取报告历史和态势，S3 读取变化及相关特情。核对分页读完后才使用 `nextAfter`；接口返回值而非模型推测是数据依据。
4. **关系**：E1 同时关联 A/B 的同一道路和不同计划时刻；E2 对 A/B 依据各自数量条件给出不同判断；正常 C 按独立对象/区域排除，S6 的 C 按业务时间排除，S7 的数量不足结论随任务需求互换。候选命中不等于已经证实受影响。
5. **不确定性**：S4 保留未知对象，S5 保留服务不可用；空结果、未知对象、查询失败是三个不同结果。
6. **隔离**：只保存到被授权的本次作业、投递和任务 × 席位会话；不创建 B/C 的工作区，不读取它们的私有会话/文件，不写外部业务状态。
7. **版本**：依据可定位到具体 report/object revision、有效时间和本次读取时间；同一重放阶段的 fixture 固定，跨来源不伪造统一版本。

实施时先以确定性 adapter 和脚本化 provider 测试触发、权限、查询、幂等及证据传递；这只能证明软件链路，不证明真实模型会正确主动查询和综合分析。本阶段验收还必须按 [acceptance.md](../acceptance.md) 使用当前配置的真实模型，在合成数据上执行 E1、独立 E2、未知／缺失资料及 S7 对照，记录模型与配置、fixture 阶段、真实任务／作业 ID、实际查询结果和最终判断。模拟服务本身不调用模型；真实模型由 Axon 运行。本轮只修改设计文档，尚未实施或执行这些验收。

## 7. 官方模型作为设计参考

- OGC SensorThings API 1.1 区分观测、被观测对象、属性、时间和位置，并定义关联查询及过滤能力；这说明外部上下文可以围绕对象与时空提供。其 Sensing 模型不要求消费方业务任务 ID；其中 Tasking 指 IoT 设备参数化，不能等同 Axon 任务。[官方标准，第 8、9 章及 Preface](https://docs.ogc.org/is/18-088/18-088.html)
- FEMA ICS 204 的工作分派含事件、执行时段、资源和工作内容；ICS 209 的事件状态报告含事件编号、报告时段与位置，二者职责不同。这个区分支持我们分别处理业务任务与外部态势依据。[ICS 204](https://training.fema.gov/EMIWeb/IS/ICSResource/assets/ICS%20Forms//ICS%20Form%20204%2C%20Assignment%20List%20%28v3.1%29.pdf)、[ICS 209](https://training.fema.gov/EMIWeb/IS/ICSResource/assets/ICS%20Forms//ICS%20Form%20209%2C%20Incident%20Status%20Summary%20%28v3%29.pdf)

上述来源只支持设计的可行性和概念边界，不说明所有应急系统都采用同一模型，不把告警、事件或观测直接视为任务。本 mock 不实现 SensorThings 或 ICS 兼容协议，也不以这些资料声称现有 Axon 已具有相关能力。
