## 3. 基线验证

- [x] 先检查模型工具和页面中已有能力可用，不先修改提示词、席位配置模型或新增 Skill。
- [ ] 依 `design.md` 顺序完成 E1/E2 → 分派 → 初稿导入 → v1 编制提交。
- [ ] 保存 v1、查询版本、业务回执及两席待办状态，再允许推进 E4。
- [ ] 完成恢复通知 → 退回 → 原会话修订 → v2 提交 → 验收；核对 v1 固定副本仍可读取。
- [ ] 核对显式信息处理状态与工作验收分开，总览只展示授权摘要。
- [ ] 首轮完整记录，无无限重试；环境故障、产品缺陷、模型问题、人员补充材料分别说明。

基线发现阻断时，保留停在哪里及原因。可独立验证下游，但明确记录人工关联、投递调整或补文件等干预，不冒充全流程直接通过。

## 4. 缺陷处理

- [ ] 对可复现的既有行为错误，记录输入、期望、实际结果与具体证据，最小修复并补有意义的回归。
- [ ] 对模型问题，先查看真实系统上下文、已开放工具、实际返回和历史；没有依据不增加提示规则。
- [ ] 若必须新增产品机制或改变既有流程／权限，形成后续提案待审，本期不顺带实施。
- [ ] 修复后只重测受影响流程，并保留首轮失败与最终结果；不开展模型架构基线比较。

## 5. 检查与交付

命令在 `experiments/harness-lab` 下使用 Node 24 执行。先运行新模拟能力的定向测试：

```sh
npm run typecheck
npm run lint
npm test -- tests/context-http.test.ts tests/context-cli.test.ts
```

新增驱动涉及实际接口的部分补确定性检查。若修改产品代码，按涉及的查询、交接、待办或审批模块运行其测试；交付前依包约定运行 `npm test`、`npm run build` 和 `npm run test:e2e`。真实模型、沙盒及人工业务验证单列，不以自动化绿灯替代。

交付内容：

1. 可复用的材料和分步准备方式。
2. 简洁的用户测试指南：登录哪两个账号、打开哪条待办、输入什么、核对哪些结果；新增账号凭据走本地配置，不入 Git。
3. 基线与最终结果：对应 PRD V01～V08，列出通过、未通过、人工纠正和未覆盖项。
4. 产品变更清单；如无需产品改动，明确说明。提交时主体语言中文，发布与 push 按用户指令执行。

兼容与回退：不计划产品数据迁移；新增 mock 阶段不改变旧阶段。测试准备只创建本轮数据，清理由精确记录的 ID／目录执行，不批量删除用户任务、会话或文件。产品修复如改变了记录格式，先补充兼容方案再动代码。
