# Agent 与现有框架的端到端场景验证方案

日期：2026-10-13。状态：**用户已批准实施，验证已执行并发现问题，待审阅结果；整体业务验收未通过。** 详见 [验证报告](research/agent-framework-validation.md)。

本文保存本轮讨论形成的下一阶段规划，供用户审阅。它扩展了原有任务内综合研判验证范围，纳入已建设的会话标绘、固定版本引用与地图交互。本文件存放在相关任务目录中以便追溯；本轮执行依据为用户在审阅稿落盘后明确要求“开始实施”。仅在隔离环境中进行验证，保留此前记录；不修改线上业务数据，不发布线上服务。

## 1. 验证目标

通过一个完整、可复现的合成业务场景，验证用户能否在现有系统中完成：

**理解任务 → 查询资料 → 综合研判 → 形成地图标注和说明文件 → 应对信息变化 → 修订成果 → 跨席位交接。**

分别评价三个方面，避免把工具调用成功等同于场景成功：

| 评价对象 | 需要回答的问题 |
| --- | --- |
| Agent | 是否读取充分依据、识别约束、选择合适工具，并准确说明实际完成了什么？ |
| 现有框架 | 权限、任务与会话隔离、版本、保存、引用及交接是否符合既有契约？ |
| 用户操作 | 用户是否清楚正在查看和编辑什么，能否找到成果、核对依据并继续办理？ |

这一阶段以验证和发现问题为主。先保存可复现证据，再区分模型表现、既有实现错误和真实产品缺口，不预设需要建设新的 Agent 框架或业务机制。

## 2. 参与对象与隔离边界

| 对象 | 本次场景中的含义 |
| --- | --- |
| 用户 | 实际登录、发起操作的账号；权限和操作归属由宿主确认 |
| 席位 | 用户承担的业务职责和既有授权范围；主流程使用总体席、筹划席 |
| 任务 | 本轮业务与成果的归属；主任务为“西区补给任务”，另设“东区独立任务”作对照 |
| 会话 | 某一用户在任务、席位上下文中的独立讨论入口，可绑定自己的标绘草稿 |
| 草稿 | 会话拥有的可编辑标注集合；另一个会话不得直接修改它 |
| 固定版本 | 已保存的指定修订或发布版；引用后不能被后续变化悄悄替换 |
| 任务当前标注 | 有权限的人显式选定的发布版；发布本身不自动设为当前 |

本方案中的“同任务两个会话并行”，明确指：**同一用户、同一席位、同一任务，打开会话 A 和会话 B，各自讨论并修改自己的草稿。** 不要求两次模型调用必须同时执行；重点是两个会话可交错操作而互不改写。

需要区分以下情况：

| 情况 | 本次验证内容 |
| --- | --- |
| 同一账号、同一席位、同一任务，两个不同会话 | 草稿独立；A 修改、发布或设为任务当前后，B 的草稿及固定引用保持原版本 |
| 同一账号，两个页面打开同一个会话 | 两个页面操作同一草稿；验证版本冲突检测，不能作为草稿隔离用例 |
| 总体席与筹划席的不同账号 | 按任务、席位与来源权限读取和交接；任务管理权限不自动赋予其他席位私有草稿或文件权限 |
| 多个不同账号同时登录同一席位 | 不纳入本轮；当前账号模型按一个席位一个启用账号的边界准备材料，不据此扩展多人共席机制 |

还需区分数据类型：

- 来源态势是可更新的资料展示；它刷新不等于会话草稿发生了变化。
- 草稿的已保存修订、发布版及显式固定引用应保持稳定。
- 普通工作区文件按“任务 × 席位”共享，并非会话私有。修订文件使用明确的新文件名并保留上一版，不将标绘的隔离保证扩大解释为普通文件的隔离保证。
- 跨会话查看和引用继续遵循已有权限。查看其他版本不改变本会话的编辑目标。

## 3. 验证环境与材料

使用独立验证环境，基于执行时确认的代码、模型和配置准备独立数据库、数据目录、测试账号与模拟来源实例，不替换线上业务数据。全部业务材料均为虚构，不向实际业务人员分派工作。

| 材料 | 设定及用途 |
| --- | --- |
| 主任务 | 西区补给任务，计划 09:40 执行，需要 3 辆车 |
| 初始道路资料 | 必经道路在 09:20—09:50 不可通行，构成时间约束 |
| 初始车辆资料 | 可用车辆为 2 辆，构成资源缺口 |
| 后续道路资料 | 新报告明确道路于 09:35 恢复通行；车辆仍为 2 辆 |
| 空间资料 | 提供已知道路、资源点和区域的几何信息，供查询与标注，不要求模型推测坐标 |
| 初始说明文件 | 提供普通可编辑文件，验证读取、另存、修订与交接 |
| 对照任务 | 东区独立任务，包含可辨别的不同约束和资料，用于检查错误关联 |
| 权限对照 | 同席位不同会话、不同席位的私有内容，以及明确无权访问的任务或来源 |

预期结论与评分依据单独保存，不能注入模型提示词、工具返回或业务资料。业务材料可以包含正常事实，但不直接给出“必须发现两个问题”等验收答案。

执行时记录 Git 提交、运行配置、模型与提供方、材料版本、调用次数、用量和耗时。真实模型仅使用虚构场景材料和必要工具定义；不把此前某次线上版本或局部模型验证结果当成本轮执行基线。

## 4. 主场景步骤

以下是拟使用的业务指令示例。执行时记录实际输入；允许用户提供正常业务要求，不在提示词中指定答案或逐步指导工具调用。

| 步骤 | 用户操作或场景输入 | 预期行为及证据 |
| --- | --- | --- |
| S01 接收与分派 | 总体席将西区补给任务及初稿交给筹划席办理 | 任务、资料、附件与责任席位对应正确；收件和交接有真实记录；不混入东区任务 |
| S02 综合研判 | “结合任务要求和当前资料，分析有哪些执行障碍。” | 实际读取任务、道路和车辆依据；识别道路时间冲突与车辆不足；区分事实、推断和待确认事项 |
| S03 形成成果 | “把需要关注的位置标到本会话地图上，并整理一份说明文件。” | 在本会话草稿中保存标注；位置来自已知空间资料；说明与地图一致；保留初始文件；地图和文件均可打开核对 |
| S04 发布与提交 | 明确要求发布标注，并提交说明文件及该发布版引用 | 交接内容指向固定发布版和文件副本；接收席位在授权范围内可读取；发布不自动设为任务当前 |
| S05 资料变化 | 注入道路恢复报告，再要求重新评估 | 读取新资料并比较旧依据；判断道路时间约束已解除，同时保留车辆不足的结论；说明变化依据 |
| S06 修订成果 | “根据变化修订标注和说明，保留上一版。” | 形成可比较的新修订、新发布版及新文件；旧发布版、固定引用和旧文件不被覆盖；修订与新依据一致 |
| S07 跨席位复核 | 总体席复核、退回补充，筹划席再次提交，总体席验收；另由有权限的人明确设定任务当前标注 | 交接、退回、再次提交、验收状态与真实回执一致；任务当前指向明确选定的发布版；未获授权的席位不能采用版本 |

S07 复用已有工作交接与验收流程。**标注不新增审批流程**；设为任务当前仍是由有权限的人显式发起的操作，不能由“发布”“提交文件”或一般讨论隐式触发。

## 5. 并行与异常用例

| 编号 | 条件或操作 | 预期行为 |
| --- | --- | --- |
| E01 | 同一用户、席位、任务的 A/B 会话从同一个固定版本派生草稿，交错修改 | 两份草稿独立；A 发布并设为任务当前后，B 的草稿、讨论所引用的版本不变 |
| E02 | B 查看或引用 A 的可读固定版本，然后要求修改本会话标注 | 查看和引用不切换编辑归属；只修改 B 自己的草稿；无权内容不能通过引用读取 |
| E03 | 两个页面打开同一会话，或人工编辑与 Agent 保存交错发生 | 过期修订写入产生明确冲突，不静默覆盖；保留未成功编辑的内容，重新读取后再决定如何处理 |
| E04 | “把那个点挪一下”，但存在多个可能目标 | 能唯一确定时操作；否则澄清，不随意选择对象或编造目标位置 |
| E05 | 来源不可用、资料过期或缺失几何 | 如实说明缺口及资料时效；不编造事实、坐标或成功结果；必要操作不能完成时明确停在该步 |
| E06 | 保存或发布的响应丢失，页面刷新或请求被中断 | 先检查真实结果或操作回执，避免重复业务动作；已成功的前序步骤不能被描述为整体回滚 |
| E07 | 对无权访问的任务、席位私有内容或来源进行读取、写入、引用 | 由真实权限边界拒绝；提示词、对象 ID 或交接文字不能扩大权限，也不泄漏受限内容 |
| E08 | 来源图层刷新，另一个版本被选为任务当前 | 来源变化与标注版本变化分别可辨；不替换已保存草稿和固定引用；用户能确认当前正在编辑的草稿 |
| E09 | 同席位的两个会话各自形成说明文件 | 明确其共享工作区属性；使用不同文件名保存各次成果，不声称框架已经提供会话级文件隔离 |

异常用例分开执行，避免在一次主流程中叠加过多故障而无法定位原因。权限、版本冲突、回执等机制尽量用可控条件复现；涉及模型判断的部分另行保留真实调用记录。

## 6. Agent 上下文与查询观察

沿用当前“简要绑定信息随会话提供，详细内容按需获取”的机制，不为验收预先塞入整张地图、完整文件或标准答案。

重点观察：

- Agent 是否知道当前会话的草稿和固定修订，是否在必要时读取图层、对象属性、几何及来源依据。
- `annotationRefs` 是否保持用户选择的固定版本及对象范围；引用是否造成不必要的全文或几何加载。
- 对资料、任务和态势的查询是否符合实际问题；是否存在重复查询、无理由读取全图或遗漏关键依据。
- 历史变长或上下文压缩后，需要精确信息时是否重新读取固定版本，而不是靠印象操作。
- 是否把工具失败、部分完成或未知结果说成已经完成。

记录上下文大小、返回数据量、调用次数、模型用量与耗时。字节数不等同于 token 数；先收集基线，不先设没有依据的性能达标线。若未实际触发上下文压缩，应注明该项未覆盖。

## 7. 执行方式与通过标准

审阅通过后，先进行一次主流程基线验证，再从相同初始材料独立重复两次，共三次。每次使用独立会话及可辨认的成果，避免继承前一次答案。各并行或异常用例至少执行一次，失败记录不得用后续成功覆盖。

每次区分：

| 结果类型 | 定义 |
| --- | --- |
| 无纠正完成 | 仅使用正常业务指令完成，没有额外提示遗漏事实、标准答案或正确工具 |
| 人工纠正后完成 | 人工指出遗漏、补充工具指导或纠正错误后才完成；记录介入点及内容 |
| 未完成 | 在该次运行中未满足验收条件，或因错误停止 |
| 未覆盖／环境阻塞 | 未实际执行或缺少环境条件；不计为通过 |

通过要求：

1. **机制约束不得违反**：不存在越权操作、跨会话改写草稿、覆盖固定历史版本、静默冲突覆盖或重复业务动作。
2. **业务结论完整且有依据**：初次识别道路与车辆两项约束；更新后正确处理道路变化并保留车辆缺口；不混入对照任务。
3. **成果可核对**：地图、说明文件、固定版本及交接引用相互一致，接收方能按权限定位实际成果。
4. **状态可信**：成功、失败、冲突、部分完成和未覆盖均有真实证据；用户能够继续操作。

三次均无纠正完成，仅作为该合成场景的初步稳定性证据，不代表任意业务场景的可靠性。出现人工纠正时，分别报告纠正前后的结果，不将其并入无纠正完成率。

出现越权或数据破坏等关键失败时，暂停受影响的后续写入并保全证据。需要重跑时标明原因、环境或代码变化及新的运行编号，不反复重试到通过后只保留成功样本。

## 8. 问题分类与后续开发依据

| 问题类型 | 处理依据 |
| --- | --- |
| 模型行为问题 | 核对实际输入、读取结果、工具选择和结论；区分偶发遗漏、推理错误及表达失实 |
| 工具或框架实现错误 | 用实际输入、状态和回执复现既有契约偏差，提出最小修复及针对性验证 |
| 测试材料问题 | 检查事实是否矛盾、缺失或含糊；保留原失败材料与调整说明 |
| 产品能力缺口 | 给出无法完成的具体步骤、已有替代方式及影响，再提交建设建议供审阅 |

本方案不提前建设 MCP 服务、新 Agent 框架、固定业务 Skill、依赖追踪图、新审批机制或自动采用机制。也不引入真实路网优化、资源调度算法或真实外部业务系统。

验证面向桌面浏览器，覆盖正常窗口缩放、会话与地图分屏及桌面窄面板；不增加手机端设计、编码或验收。

## 9. 预期交付物

- 可复现的场景材料、初始化条件、用户指令和操作步骤。
- 三次主流程及各专项用例的结果矩阵，列明通过、失败、人工介入和未覆盖项。
- 实际查询与工具调用、修订和发布记录、各版说明文件、交接回执，以及必要的桌面操作截图。
- 带证据的问题清单和优先级，区分模型、框架、材料与产品能力问题。
- 下一阶段开发建议，说明应先修复什么、哪些能力已有足够证据暂不新增。

本轮将形成验证材料、实际运行记录和问题报告；具体通过、失败与环境阻塞以新增验证报告为准。
