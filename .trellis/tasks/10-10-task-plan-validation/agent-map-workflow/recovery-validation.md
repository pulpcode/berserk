# 地图读取依据与失败恢复：实施和原场景复测

日期：2026-10-14。结论：**恢复机制改造完成，确定性检查通过；三个真实模型案例均保存正确，原先的草稿/来源交替拒绝未复现。模型调用和正文表述仍有问题，不能称为全面业务验收通过。**

## 实现结果

- 创建空白或固定基线草稿无需先读空状态；服务仍在准备阶段及事务内提交前重检绑定、权限和草稿不存在。
- 普通参数错误、缺项和冲突保留已确认读取记录，只暂停同一模型输出的后续地图写入；下一轮推理修正参数或补读受影响资源即可。
- 新读取按调用隔离，真实结果进入下一轮推理才建立依据。错误、替换或原地修改后的结果不会建立依据，旧记录不连带删除。
- 提交信号在 SQLite 提交成功之后发出。保存结果不确定时持续阻断写入，须核对原回执并重新读取；没有回执不代表没有保存。
- 保留 Pi 原生循环、HTTP CAS、来源批量原子保存及既有权限；未新增数据库表、跨请求缓存或界面功能。

## 保留的失败与限制

### 三次实际工具错误

- main-1 S03：首次 `situation_query` 漏填顶层 `systemId`，原生 schema 校验拒绝。补全参数后查询成功。
- main-1 S03：随后直接刷新，当前请求尚未读草稿，返回 `ANNOTATION_READ_REQUIRED`，`resources` 仅列出 draft missing。模型补读草稿后刷新成功，**没有再次查询来源**。此步是新的请求，上一轮草稿依据不跨请求缓存，拒绝符合保留的设计边界。
- main-3 S03：同样漏填 `systemId` 一次，修正后成功。读取草稿的有效结果得以保留，未产生后续读取循环。

本批没有 `SOURCE_READ_REQUIRED` 交替拒绝或 `ANNOTATION_BATCH_PAUSED` 连续循环。两例仍会漏填来源参数，说明工具使用并非稳定到每次正确；本轮没有改动来源查询 schema 来掩盖该问题。

### 正文语义未全面达标

- main-1 S03 称“原第一版中‘通道关闭与 09:40 冲突’的研判”。检查发布内容只有几何及来源引用，没有保存这段研判；它来自之前对话正文，不能说已在发布版里。
- main-3 S03 称旧发布版道路标注“仍是 rev 2（closed）状态”，main-2 称“内容仍指向道路 r2 的 closed 状态”。旧发布版没有保存 closed 属性，只有 r2 来源引用；这些说法容易混淆查询得到的来源事实与版本实际保存字段。main-3 本次新草稿确实保存了 open 属性，但不能据此推断旧发布存过 closed。
- main-1 S03 把 effectiveAt 列在“归入 refresh 的来源信息”下，容易误解为已存入标注。实际 sourceRefs 保存完整来源 ID、revision、queriedAt；业务时间在工具回执/来源查询中，不是 sourceRefs 的字段。
- main-3 S01 把带毫秒的查询时间简写到秒，却称“UTC 原值”，措辞不严谨；没有出现改时区后缀导致时刻改变，实际存储时间正确。
- main-2 明确说明 refresh 不同步业务属性；main-3 则通过额外 apply 真正保存了属性。二者不要混为一项统一行为。

三例均实际加载了地图 Skill，但本轮没有 Skill 开关对照，不能证明效果来自 Skill。本批目标图层明确，未重测同名/未指定图层的澄清问题；也不验证复杂空间推理。既有这些质量问题仍保留。
