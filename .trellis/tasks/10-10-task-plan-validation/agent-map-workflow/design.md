代码与上一版设计已保存到 Git 基线 `e9a01b4`。本稿修订行为现已实施，验证边界以新报告为准；原 [验收报告](validation.md) 和 [独立审阅](review.md) 保持历史原貌。要求见 [PRD](prd.md)，参考来源见 [调研](research.md)。

## 0. 本次审阅要点

目标是修正已验证的“创建空草稿被拒绝后，来源与草稿依据交替丢失”问题，保留已有权限、并发检查和原子保存。

| 原基线行为 | 本次调整 |
| --- | --- |
| 创建前必须读取尚无草稿状态 | 明确基线，由服务检查不存在与绑定条件，允许直接创建 |
| 多处通用错误处理调用全量 invalidate | 普通失败保留记录；指出缺失、过期或结果不确定的具体资源 |
| 失败阻断与读取记录清除耦合 | 同输出剩余地图写入暂停，下一次推理按具体问题恢复，不强制全量补读 |
| 同请求补充输入一律清空依据 | 普通补充输入保留记录；意图变化交由下一次推理，权限与绑定仍由服务核对 |

Claude Code 参考仅限用户提供仓库的固定第三方快照，不代表当前官方版本。借鉴按文件记录、写前核对、成功后更新及新建/覆盖区别；地图资源分类、请求内作用域、同输出失败暂停、数据库事务与来源校验是本项目适配，不以 Claude Code 名义背书。

本期不扩展会话级缓存、不拆分整套工具、不引入对象级合并、自动重试或新的持久化记录。第 4、5 节为基线已有能力，保持兼容；本次仅同步其中与新前置条件冲突的工具说明和 Skill 文字，不扩展 Skill 发现策略或地图 UI。

## 2. 编辑依据：来自已读结果，不来自写入瞬间的最新值

### 2.1 两种版本

业务选择继续显式：`baseRef`、固定历史 `ref`、发布的 `revision`、采用的 `publicationId`。用户可以要求“看昨天发布版”，但它不改变当前可写草稿。

机械条件由宿主管理：本会话 apply/from_source 的 `expectedRevision`；来源导入所用 `expectedSourceRevision`（来自已经交给模型的实际查询结果）；设为当前的 `expectedCurrentSequence`。HTTP 及服务 DTO 保留这些字段，只有模型侧不再重复填写。

### 2.2 请求内状态

复用 AnnotationRequestState，作用域固定为 `{actor, taskId, sessionId, requestId}`，记录三类独立依据：

| 资源 | 必要记录 | 粒度 |
| --- | --- | --- |
| 本会话草稿 | 已读/本链已提交的 setId、revision、hash | 整份草稿；不因只改一个对象而绕过整体修订检查 |
| 来源对象 | 授权查询返回的完整 fullRef、revision | 每个来源对象，完整标识含 systemId/objectType/objectId |
| 任务当前设定 | annotation_list 返回的 sequence | 当前任务的采用指针；不等于采用权限 |

来源记录沿用最多 500 条的边界，不保存整图、报告正文或额外几何副本，不自动注入对话。超过限制应在修改记录前明确拒绝，不能清空已有条目。未建草稿的读取结果仍可展示给模型，但不再充当创建动作必需的凭据。

新读取先处于未确认状态：只有本次工具结果经过现有后置钩子、成功且未经破坏地交给下一次正常推理，才成为读取依据。若该次读取失败、被改写或结果不可信，只丢弃该调用新产生的观察，不删除其他已确认记录，也不把新值提升为已读事实。

版本冲突时可以保留旧记录，由服务下次继续核对；“保留记录”不等于“记录仍有效”。不把外部当前修订写回旧记录冒充重新读取。实际权限由服务逐次验证，任何缓存都不能授权。

### 2.3 获取依据与推进

扩展现有 annotation_read：

```text
mode: draft
layerIds? / objectIds? / fields? / offset? / limit?
```

它只读取宿主绑定会话的当前草稿，先捕获固定 ref 再复用现有有界 read，返回真实固定修订及所选内容。未建草稿时返回明确状态与当前固定 baseline，不能谎称读过 baseline 的内容。

本请求 `mode:draft` 的成功结果建立/重新建立已有草稿的读取依据。创建成功也可根据真实回执建立新草稿依据，无需先观察 empty。原 `mode:read` 仍用于固定历史与参考内容，不隐式切换编辑目标。

成功写入在普通回执中返回 beforeRef/afterRef（或明确等价字段）。宿主仅沿本执行链已经确认的提交立即推进写入条件，允许同一输出中的普通草稿写入按顺序继续。这个机械推进不代表模型看过新内容；后续业务决策依赖前一步实际结果时，必须等结果进入下一次推理。外部新版本不可吸收，旧幂等回执不可推进或倒退依据。

读后用户在地图保存、另一标签页写入或同一会话被其他合法客户端修改：服务按原依据返回草稿冲突，指出需要重读草稿，保留来源与任务当前记录；拒绝把 expectedRevision 偷换为当前 head。来源有变化时只指出对应来源；其他记录仍会在实际使用时重新检查。

按动作读取所需内容：结构或名称操作可使用有界摘要，修改多边形需按需读取目标几何。既有 read 的 selectors/fields/hasMore 仍表达实际读取范围；本期不另建字段级授权系统，也不把读过修订摘要包装成已经理解全部几何。工具说明与 Skill 指导读取方法，服务保证版本、目标与几何合法性，业务理解单独验收。

### 2.4 同一 assistant 工具批次

复用 Pi 原生 sequential 执行与公开 hooks：

- 普通草稿 apply/from_source 可在一个模型输出中顺序执行；不因多个写入就全部拒绝。每个调用都使用本执行链已读/已成功提交的条件，逐次经过服务 CAS。
- 同一输出中刚执行的 read/query 不能为已经预生成的修改建立新的读取依据；读取结果进入下一次模型推理后才可使用。
- 已确认的本链成功写入可以立即推进机械条件；外部写入不能推进。写入失败时暂停同一 assistant 输出中剩余地图写入，把失败交给模型后再决策。暂停是批次执行状态，不是删除读取记录。
- 下一次正常推理可解除普通失败的批次暂停；缺少或过期依据仍须补读相应资源。参数错误修正后不强制重读。涉及结果不确定的资源不能仅因进入下一次推理而解锁，须先核对原动作。
- 地图读取/来源查询失败或后置钩子把结果改坏时，不能提升该次观察；同输出尚未执行的地图写入暂停。已有其他依据保留。钩子异常导致无法确认执行链完整性时仍终止请求。
- 发布、采用仍需明确业务版本和用户意图；不从新 head 自动生成 publish revision 或 publicationId。
- 一次来源工具调用可含多个对象，一次 apply 可含多个 operations；这种批量提供整批原子性，而非版本管理的唯一途径。多个独立工具调用分别提交，不能声称整组原子。
- 幂等回执查询不计新写入；已提交动作的同调用 ID 核对与返回优先于再次执行，但不能用旧回执推进新的执行依据。

通过真实 Pi loop + 假 provider 验证：已读后连续写入、外部插入写入、同输出 read/write、失败后停止、取消及压缩。保留原 hooks，不修改 Pi 内核、provider 或自动重试。请求内状态为首期有意取舍，暂不引入会话缓存/恢复。

### 2.5 生命周期与用户补充输入

- 同一请求内普通工具失败，不清空全部记录。
- 同一请求原生 steer/follow-up 被消费后，不仅因收到新文字而清空记录。新的用户意图在下一次推理生效；已有批次暂停不能由补充消息提前解除。若实际身份、任务或会话边界变更，应结束原作用域；基线/草稿变化仍由服务检查，不能随浏览器导航切换写入目标。
- 请求结束、取消、停止和进程重启后丢弃请求内状态；新请求重新读取所需依据，不扫描旧聊天或摘要自动重建凭据。这是本期范围取舍，与参考快照的跨轮文件缓存不同。
- 压缩开始时不开展新地图写入；压缩成功且无法确认原始读取内容仍进入模型上下文时，清除本请求的读取依据，按需重读。当前集成采用保守全量重读，不新增自动回填机制。压缩失败/取消沿用现有停止路径，不把失败压缩当成已完成的新上下文。
- 销毁读取状态不会回滚已提交数据、删除回执或把结果不确定伪装为未执行。

## 3. 模型工具与底层服务的边界

### 3.1 来源导入/刷新

模型侧建议统一结构，单个对象也用 items：

```json
{
  "items": [
    {"mode":"add", "sourceRef":{"systemId":"...","objectType":"area","objectId":"..."}, "layerId":"...", "objectId":"..."},
    {"mode":"add", "sourceRef":{"systemId":"...","objectType":"road","objectId":"..."}, "layerId":"...", "objectId":"..."}
  ]
}
```

工具名称仍为 annotation_from_source；items 为 1～20 项，不接受 expectedRevision、expectedSourceRevision、geometry、queriedAt、actor 或 sessionId。标注 objectId 继续是 Agent 选择的逻辑身份，本期不再加入主键生成/结果占位符机制；刷新必须用真实原 ID。

宿主由已读/本链已提交的草稿依据及已观察来源修订构造服务输入。没有来源读取依据时返回 SOURCE_READ_REQUIRED，不能替模型查询最新 revision 后立即写入。在授权范围内，先一次列出已知缺失的草稿/来源依据，不通过额外外部查询凑齐错误详情。模型仍决定查询谁；第一次查询把事实交给模型，保存时再次查询并核对来源是否变化。若用户明确要求旧来源修订，当前来源 API 无法提供时应说明限制，或使用已有固定标注快照；不能用请求里最后查到的最新来源冒充用户指定旧版本。

服务执行：

1. 规范化请求，核对稳定动作 ID 的旧回执和内容摘要。
2. 在任何来源网络操作前，核对 actor、任务、草稿依据、图层和对象规则。
3. 对最多 20 项来源做有界查询，逐个完整 ref/期望来源修订匹配，复制实际几何及本次 UTC 查询时间。不同系统查询不宣称同一全局时刻。
4. 全部准备成功后重检授权、取消、草稿 CAS 与容量，在一次现有 SQLite 事务写入快照、head、回执。
5. 准备或事务校验失败整批不写；不自动跳过失败项、不分拆提交、不读锁覆盖网络等待。返回明确 itemIndex、相关资源和错误类别，但不得泄露未授权对象详情。提交后回执投递失败属于结果不确定，不能沿用“整批未写”的措辞。

refresh 延续前一阶段契约：同一 ID、恰有一个匹配来源、兼容几何；保留说明、样式、属性及其他引用。一个批次重复操作同一标注 ID 拒绝，避免隐含顺序依赖；不同标注可以引用同一来源。既有 sourceRefs 不升级成认证。

### 3.2 普通编辑、发布、采用

- annotation_action apply 保持既有 operations 结构，模型不再传 expectedRevision；宿主注入本请求已读依据。自定义几何仍需 Agent 提交用户要求的内容。
- create_draft 保留显式 baseRef:null 或固定引用，取消模型先读 empty 的要求。服务执行前捕获当前绑定，验证请求基线与绑定一致、无草稿、基线可访问；提交事务再次检查无草稿和绑定未变化，再原子保存草稿/head/回执。这里捕获绑定是执行条件，不声称模型已读过基线内容；已有绑定不匹配时要求显式处理，不能自动切换。
- 创建期间其他客户端先创建草稿或更改绑定，返回明确冲突，不转成向现有草稿追加/覆盖。根据固定版本创建副本不要求读取完整快照；如果附带 operations 要修改继承内容，Agent 应先读取相关固定内容。继承逻辑 ID 和来源访问限制保持原有规则。
- 创建成功且回执可信时立即记录实际 setId/revision/hash，允许继续新增对象；后续业务判断依赖新结果时等待下一次推理。新增对象不需读取尚不存在的对象，但向已有草稿追加仍需已有草稿依据、明确图层及唯一对象 ID。修改/删除已有对象使用原草稿 CAS；不新增整图覆盖入口。
- publish 保留明确 revision：发布哪个保存内容是业务选择，不能让宿主擅自改为最新。仍只有用户明确要求才执行。
- set_current 保留 publicationId，宿主使用本请求 annotation_list 已返回的 current.sequence；没有读取则要求先读，变化则拒绝，不自动批准/采用；已有任务当前版本时保留先比较再采用的要求。
- HTTP 手工编辑继续显式携带开始编辑时的修订；不能借本次 Agent 改造改变 UI 未保存表单的冲突保护。

### 3.3 幂等和可审计性

模型调用参数里移除机械字段后，不得让重复调用因为宿主状态推进产生不同摘要。复用现有 action 表：摘要以规范化 Agent 意图、捕获的 task/session 和稳定 actionId 计算；实际执行的草稿/来源修订作为同事务回执元信息保留。该分离只在受信任宿主内部使用，HTTP 不能提供自选 digest/依据。

同动作 ID、同意图返回原回执，不重新读取来源；同 ID 改 items/目标/内容拒绝。收到真实成功回执才报告成功；回执/原生历史写入出错或取消后结果不确定，停止推进并按现有 receipt 查询，不自动重放。普通回执读取本身不证明模型已看到所有对象字段。

结果不确定时保留原动作 ID 与相关目标，不删除无关来源记录。原回执确认成功后按原动作解释，再读取当前草稿恢复依据；旧回执本身不推进或倒退当前版本。暂时未查到回执不自动等于未执行，也不能更换 ID 再做一次。只有执行边界能够确认未提交时才允许重新决策；无法确认则报告未决并停止相关写入，不新增后台重试或持久操作账本。

### 3.4 错误反馈与恢复

复用普通 toolResult/error，不另建恢复工具或编排器。服务与适配层按错误类别提供足够的结构化信息，再生成简短说明；不能靠匹配中文错误字符串决定是否清空状态。模型侧信息包括错误类别、当前权限下可披露的相关资源/输入项、是否已提交或结果不确定、必要恢复动作。具体字段在实施时沿用现有错误 DTO 扩展，避免两套不一致协议。

| 情况 | 对记录的处理 | 恢复方式 |
| --- | --- | --- |
| Schema/参数错误，尚未执行 | 保留已确认依据，不产生新观察 | 修正参数，不要求全量补读 |
| 缺草稿或来源依据 | 保留已有记录，列出已知全部缺项 | 只补读缺少部分，结果进入下一次推理 |
| 草稿修订/绑定冲突 | 保留原依据用于区分“未读”和“已过期”，不吸收外部 head | 重读草稿/绑定，重新评估；来源记录保留 |
| 某个来源修订变化 | 保留各来源原记录，指出具体项 | 重查该来源并评估；再次保存仍检查所有实际依赖 |
| 任务当前指针变化 | 保留草稿与来源记录 | 重新读取/比较当前设定，不自动采用 |
| 来源缺几何、离线或查询失败 | 不提升该次失败查询，其他依据保留 | 说明真实原因，不估算几何，不伪装成未查询 |
| 提交后返回异常或执行结果未知 | 停止相关写入链，记录原动作待核对 | 查回执；未查到不能直接重放 |
| 失权、取消或执行环境异常 | 不以缓存继续操作 | 按现有停止/授权边界处理；已经提交的不回滚 |

相关集成点必须一并调整：`annotation-tools.ts` 通用 catch、`annotation-state.ts` 的 blocked/invalidate/committed、`lab.ts` 的 before/after hooks、tool_execution_end、input.consumed、compaction 和 abort。保留原钩子安全检查，仅删除一种错误影响全部资源的耦合；不能只改工具 catch 而被事件处理再次清空。

恢复示例：

```text
查询来源 A/B/C → 创建草稿成功 r1 → 批量导入发现 B 修订变化
                                      ↓
                         本次未保存；草稿与来源记录保留
                                      ↓
                         重查 B → Agent 评估 → 再次保存
                                      ↓
                         再核对草稿及 A/B/C → 成功 r2
```

如果重查期间草稿或 A/C 又变化，仍应准确拒绝；“减少无谓补读”不能变成放弃真实冲突检查。

## 4. 态势标绘 Skill

复用部署维护的受控 Skill 目录和 skill_read。建议 id `map-annotations`，简介说明“查询、创建、修改、比较、发布态势地图标注时使用”；普通聊天无需加载。正文控制在约 1,200 中文字以内且不超过现有 16 KiB 限制，本期单 SKILL.md，不新增多文件读取协议。

正文结构：

1. 概念：地图底图是展示载体；来源态势与会话标注是内容分组；草稿内业务图层承载对象。点/线/面/文字是对象，不是图层。来源事实与用户规划区分；草稿/发布/当前采用不编码进业务颜色。
2. 归属：同任务不同会话草稿独立；读取参考不切换可写目标；发布与采用分离。
3. 目标：解析用户指定已有图层并读取确认；增加对象优先使用明确目标；新图层是另一个结构操作。多个匹配先问。没有图层且用户要求开始标绘时可以按意图建层，须明确说明；不得把“已有层优先”变成一律禁止建层。
4. 方法：复用来源用授权查询+来源工具；自定义用普通 operations；移动同一对象保留 ID；一批独立对象合并为一次写入；内容存在依赖时读回再继续。
5. 时间与引用：queriedAt 是查询时间，effectiveAt/validTime 是业务时间；按结构化证据解释，不能更换时区后缀。地图入口由系统提供，正文不必拼地址。
6. 核对：确认对象数、图层归属、几何来源、实际修订、未要求的发布/采用是否发生。只按所需字段读取，不为了完成单个对象查询整图。

不写入西区、discussion、测试坐标、固定图层名称或特定标准答案。名称和对象变化必须不影响规则。

Skill 不强制替代工具描述：每个工具仍保留必要参数/前置条件/错误含义。自动加载采用现有简介匹配和 skill_read，显式选择使用既有 Skill picker。是否真实加载、漏触发或过度触发均需记录；不默认所有地图问句都成功加载。

### 4.1 旧工作区与历史兼容

当前 workspace-index 要求 skillIds 恰为 synthesis/review；直接加第三项会使旧校验或旧程序拒绝打开。建议保留磁盘旧 workspace-index 不变，将 map-annotations 作为部署级附加方法目录，通过一个确定性的有效 Skill 集合解析函数供资源接口、readSkill、请求快照和 picker 共用；不能只改某一入口。它不授予新工具能力。

请求资源和 Skill 选择仍使用现有记录结构，受控 ID 白名单扩为三个，资源数量上限相应为三；正文/hash/所属请求验证继续严格。保持既有 composer 文本生成与旧历史字节不变，不建立第二份历史。后台明确 profile、只读子 Agent 原工具边界不扩大；得到方法说明不意味着得到写能力。

新程序需能读取旧的两 Skill 记录和新的三 Skill 记录。旧二进制不能保证读取新 Skill ID，故后续部署前需明确兼容回退包，或在完全停止服务后恢复升级前独立备份；不得将旧程序直接指向已写新历史的数据目录。若实施发现不改变记录版本无法满足既有严格历史契约，应在兼容测试阶段回到设计审阅，不临时放宽任意 Skill ID。

## 5. 结构化地图入口

复用 MapReference、AnnotationSelection、EvidenceMapLinks 和现有地图打开接口。

- 来源查询结果：继续从实际 query payload 生成来源入口。点击重新查询当前授权态势，历史证据修订与当前修订分开显示；当前来源不支持任意历史几何，不能冒称打开了原时刻地图。
- 标注写入回执：从服务返回的固定 setId/revision、成功对象 ID 列表生成“查看本次标注”；发布回执使用 publicationId。新增批量回执给出有界对象列表，单项历史回执继续识别。
- 在已有工具结果及所属请求的最终答复旁展示去重后的入口；只取同 requestId 的成功结果，重复对象/版本合并。大列表折叠显示数量并可展开，避免遮挡对话，不改变三栏布局。
- 固定标注点击按既有只读参考方式打开，不切换编辑目标。新修订不会改写旧消息的链接。
- 不从助手自然语言中提取权限、ID 或已完成声明；缺少结果、错误工具、格式坏的数据不生成成功写入入口。重复读取旧 receipt 的入口如展示，必须标记为原动作结果，不能声称本请求刚完成了写入。
- 权限撤销或跨账号查看时，真正加载地图仍检查当前权限；前端按钮不是访问令牌。
- 正确的旧 Markdown 地图链接继续走证据匹配；不通过接纳任意 href= 错误格式来掩盖质量问题，也不要求模型为每个按钮再调用一个引用工具。

当前结构化入口仅表示“本请求查询/修改的对象”，不等于自动证明正文某句论断。句级来源注脚、本期未调用对象的任意引用编排暂缓。

## 6. 行为矩阵

| 情况 | 行为 |
| --- | --- |
| 请求开始仅有自动草稿版本摘要 | 先读草稿结构/所需字段，不把摘要当作已读内容 |
| 尚无草稿、请求基线明确 | 不要求先读 empty；服务原子检查创建条件并保存，成功回执建立草稿依据 |
| 创建时另一个客户端抢先创建 | 返回已存在/冲突，不覆盖、不追加；已查来源记录保留 |
| 三个已查来源对象一起上图 | 一次 items 批量、一个草稿新修订 |
| 一个 assistant 输出生成三个独立写入 | 普通草稿写入顺序执行，沿本链成功提交推进条件；遇失败停止后续，每个调用独立提交 |
| read/query 和依赖它的写入同一输出 | 新读结果尚未影响这次推理，不能作为本次写入依据 |
| 用户在 Agent 查询期间手工保存 | 保留用户新修订，返回冲突，不自动换基线 |
| 来源在查询和保存之间改变 | 整批拒绝，指出具体来源，保留其他记录；重查/评估后全部依赖仍检查 |
| 参数错误或缺一类依据 | 保留其他已确认记录，修正参数或补读缺项，不产生交替遗忘 |
| 查看另一个会话或旧发布 | 可读但不改变本会话写入依据 |
| 缺几何/撤权/某项失败 | 整批无新保存；原草稿和旧发布保持 |
| 模型坐标正确但放错层 | 可形成技术合法动作，但场景验收失败；不能宣称服务能理解所有自然语言约束 |
| Skill 未加载 | 核心权限和 CAS 仍有效；方法使用质量单独评分 |
| 回执丢失 | 停止相关写入，核对原动作，不能声称未保存或直接重放 |
| 同请求普通补充输入 | 下一次推理重新判断意图，保留读取记录，写入仍核对实际资源 |
| 新请求/重启/成功压缩后缺少原始读取上下文 | 重新取得所需依据，不从聊天或摘要恢复写能力 |

## 7. 替代方案与取舍

- 只加强“成功后 revision +1”：保留模型机械负担，且不能安全预测失败/并发结果，不采用。
- 每次写入取最新 head：把冲突保护变成静默覆盖，不采用。
- 永久 edit token/通用操作日志：现有请求作用域与回执足够，本期不新增。
- 对象级版本/自动合并：可能减少无关对象冲突，但扩展存储与合并规则，暂缓；保留整份草稿 CAS。
- 将一次错误统一转换为全量失效：固定 main-3 已出现恢复循环，不再采用。保留按动作的精确校验与独立的批次暂停。
- 直接拆成 edit/write 即视为解决：工具名字不决定是否覆盖已有内容，先明确现有动作的前置条件，不增加重复工具入口。
- 扩展跨请求读取缓存或自动恢复：可能减少跨轮读取，但不是本次已验证失败循环的必要修复，暂缓。
- 给每个小动作建 Skill：知识分散且加载成本高，本期只建一个领域 Skill。
- 自动把新对象挪回推测的目标图层：可能覆盖用户新分类意图，不采用；用清晰方法与结果核对验证。
