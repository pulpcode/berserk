# 验证设计

## 1. 复用关系

| 环节 | 继续使用 | 本期工作 |
| --- | --- | --- |
| 收到外部变化 | 来源认证、消息去重、Profile、Pi 后台作业 | 准备独立合成数据，真实 HTTP 接入 |
| 查询与关联 | 任务上下文、task_information_list/read、外部只读查询 | 核对实际读取与权限；不自动注入全部信息 |
| 投递 | 固定接收者、补充建议、总体席审批 | 用既有配置保证人员获得需要的资料，不新增路由 |
| 人员办理 | 工作待办 `/work`、任务对话、任务相关信息 | 按合并后的界面编写操作步骤 |
| 文件处理 | Pi 文件／脚本工具、file_output、工作交接 | 验证初稿、v1、v2 和固定提交副本 |
| 工作进展 | 现有 WorkItem、工作总览 `/overview` | 核对提交、退回和验收后的双方视角 |

新旧入口兼容沿现有实现。Git 合并不等于线上已部署；执行前核对实际构建和数据版本，不要求用户在旧页面上验收新交互。

## 2. 测试材料

所有时间都是 `2026-10-01 +08:00` 的模拟业务时间，与真实执行日期分开记录。每轮使用独立数据目录、模拟服务实例和测试标识，保留既有测试与用户数据。

| 材料 | 内容 |
| --- | --- |
| 主公共任务 | 西区补给方案：计划 09:40 使用西区通道，至少需要 3 辆车；目标是提出可供人员决策的方案，不直接下达执行 |
| 对照公共任务 | 东区方案使用独立道路和车辆池，不因区域相邻就认定受西区信息影响 |
| 初稿文件 | `补给方案_初稿.md`：仅含任务目标、计划时间、车辆需求、待完善章节及“合成验证材料”声明，不放正确答案 |
| 道路通知 E1 | 沿用 `report-west-01@2`：预计 09:20–10:10 受限；历史修订 1 可查 |
| 车辆通知 E2 | 沿用 `vehicles-west-01@2`：09:30 可用车辆从 4 辆降为 2 辆 |
| 新增恢复通知 E4 | 同一报告修订 3：09:35 新观测确认限制已解除，修正修订 2 对后续时段的预期；车辆资料不变 |

沿用 E1/E2/E3 的原定义，新增 E4，不将已有“未知道路”E3 改成恢复事件。拟在模拟控制中增加 `advance recovery` 和 `event E4`；只扩展测试服务、命令和事实数据，不增加 Axon 产品接口。重复推进同一阶段不重复追加修订。

E4 的通知携带报告标识、修订和发生时间，正文仍须经既有 REST 查询获取；新修订使用新的 `sourceMessageId`。报告历史保留 1/2/3，最新查询返回 3，`asOf` 与发布时间对应推进。道路对象当前没有通行状态字段，不能把空 properties 解释为畅通；恢复依据是新的特情报告，不虚构态势系统的确认。

数据只说明事实和任务约束。验收检查“2 辆不足 3 辆”“道路恢复不等于车辆补齐”，不指定唯一方案文本，也不编造备用道路、增援已获批或车辆实际分配。

## 3. 操作流程

### P1：收到信息并安排办理

测试来源绑定现有多源分析 Profile，启用已有查询、任务判断和补充投递能力。固定情报席，候选筹划席／态势席，由总体席按既有规则审批。总体席须有来源内容／管理、资料范围、公共任务管理及工作总览的实际授权；筹划席须有资料范围授权，并实际收到相应结果。

先更新模拟事实，再分别通过接入接口发送 E1、E2。核对后台结果、任务关联、固定投递和获批的补充投递。模型未建议筹划席或漏关联时记录原始结果；可由人员按现有权限纠正以继续下游验证，但不得将纠正后的整条链路记为无人干预通过。

总体席在主任务工作区上传初稿，并通过对话分派“完善补给方案”给筹划席，选择初稿作为交接附件。人员核对确认卡并批准。筹划席从工作待办进入该工作项，签收并进入关联会话。

### P2：综合资料并提交第一稿

筹划席可以使用这样的自然语言要求：

> 请结合本任务的相关信息和交接初稿，编制供审阅的补给方案。写清依据、约束、建议及待确认事项；保留初稿，另存为补给方案_v1.md。

Agent 自主决定查询和文件处理步骤，不在测试消息中给出工具名或标准结论。材料不足时允许提问或明确缺口，不要求为通过测试无条件出稿。

核对其通过交接导入初稿，读取本任务道路、车辆信息和任务条件，必要时查询外部最新资料。文件生成后，筹划席明确要求提交，并确认对应文件；总体席通过交接详情查看或导入 v1。此时保持待验收。

### P3：情况变化后修订并验收

仅在 v1 提交后推进恢复阶段并发送 E4；这保证第一稿不能提前看到恢复事实。待 E4 完成分析、关联和实际投递后，总体席退回 v1，说明“有新的道路信息，请核对变化并更新方案”。

筹划席从退回工作进入原办理会话，要求比较新的道路信息与 v1，保留原文件并另存 `补给方案_v2.md`。Agent 应读取修订 3、比较旧依据，并核对车辆仍为 2 辆，不因道路恢复就声称任务条件全部满足。

筹划席提交 v2，总体席审阅后验收。继续使用原工作项的“提交 → 退回 → 再提交 → 验收”；不新增完成后重新开启状态。若将来需要修改已验收成果，另行讨论业务要求，不用本测试暗含该能力。

### P4：查看办理进展

核对双方工作待办及总体席工作总览。筹划席提交后是跟进，总体席待验收；退回后筹划席待办理；最终验收后该工作已办。

人员单独决定是否将自己的外部信息标记已处理。阅读、AI 成功、投递审批和工作验收均不自动代替这一决定。可用情报席检查：筹划席标记后，情报席自己的信息仍保持原处理状态。

## 4. 文件与记录

- 初稿、v1、v2 是当前任务 × 席位工作区中的普通文件；不同席位不共享 `/workspace`。
- 跨席位使用现有附件固定副本及导入；文件下载使用既有 file_output，下载本身不等于正式提交。
- Pi JSONL 保留模型回复和实际工具依据；SQLite 保留原有任务、关联、投递、办理状态和交接回执。本期不新增产品表或第二份会话历史。
- 测试清单仅保存本轮 task/event/job/work/session/operation ID、版本和文件 hash，便于复查；不能参与产品状态判断，也不修改原历史来补成功结果。

## 5. 验证层次与修复边界

1. 确定性检查验证新模拟修订、真实 REST 返回、通知去重、文件内容与现有交接状态；不代替模型能力证明。
2. 真实模型完成编制和修订，按事实覆盖、时效、未决条件及文件一致性检查，不按固定话术或固定工具顺序评分。
3. 用户用桌面页面完成正式确认与最终验收，检查合并后的交互。测试脚本不替用户点击在线确认或标记已处理。

先保留基线证据，再修复具体缺陷并回归。若只是业务材料未说明清楚，补材料并标为新测试版本；若需新增工具、提示词、权限或流程，先写出缺口与依据供审阅。没有发现产品缺陷时，本期可以只有测试材料、脚本及验证记录变更。
