# 测试指引

2026-10-09 已更新线上，具体消息触发方式见 [线上验收指南](server-test-guide.md)。以下为通用验收步骤。

## 1. 验证准备

- 使用有工作任务管理权的席位 A，以及普通接收席位 B；两者都需有测试来源和资料范围的读取权限。
- 测试 Profile 启用 `task_search`、`task_read`、`information_record_task_assessment`，并写明需要判断任务关联或新建建议。示例为 `experiments/harness-lab/fixtures/background-context.example.json`。
- 沿用两个西区任务和一个东区任务，接入一条新的道路信息。新输入会冻结当前 Profile；旧作业不会自动补算，旧作业“重新处理”仍使用它原来的配置快照。
- 新建建议是模型判断，不能保证每次都出现；“未记录判断”“暂不归口”“建议新建”分别显示，不把执行成功当作判断正确。

## 2. 一份分析关联多个任务

1. A 在“收到的信息”打开完成的分析，查看“任务关联”。确认每项理由是否成立，是否误关联东区任务。
2. 从西区任务菜单进入“相关信息”，查看同一消息的原文、分析和来源依据；再到另一个相关任务核对。
3. 只查看页面时不应新增会话或复制附件。两个任务关联同一份分析，不会因此启动第二次后台分析。
4. 在任务详情填写问题，按需要选择附件，点击“进入对话”。对话归当前任务，输入内容仍是草稿，发送后才处理。
5. 也可选择“提交后台分析”，明确确认后执行。完成后可从本席位的后续分析记录进入会话。

## 3. 新建公共任务建议

输入一条现有任务无法承接、有明确交付目标的工作需求，例如另行编制一份文件。查看分析中是否出现名称、目标和理由完整的新建建议。

- 建议出现时，任务列表尚不应新增任务。
- A 点击“创建公共任务并关联”，检查并编辑名称、目标及关联理由，确认后只新增一项公共任务；该任务“相关信息”可查看原信息和指定分析。
- B 可以查看自己获准的建议，但没有任务管理权时没有创建入口。
- 不采纳建议可以不操作，也可用“关联已有任务或个人空间”收录；不会阻塞投递。
- 公共任务名称和目标按公共规则可见；原信息和分析没有因此向无权席位公开。

对照输入应包含：已有任务能承接的需求、仅供参考的信息、尚无明确交付目标的信息。不要只测“新建成功”一个样例。

## 4. 人员纠正与隔离

在关联区测试人工保留、移除、恢复自动和再次补充。多窗口同时修改时，冲突应保留当前输入，可读取最新决定后继续编辑。移除一项不影响其他任务；人工保留固定所选分析版本。

A、B 分别从任务进入处理，导入的文件是各自工作副本；A 的会话、草稿和编辑结果不会进入 B 的工作区。个人空间收录只对所属席位可见。

## 5. 隔离验证命令

在 `experiments/harness-lab` 运行：

```sh
npm run probe:context -- --task-linking
```

使用当前本地模型配置、独立临时数据库和 HTTP 模拟源，只发送合成资料，不更新线上。输出证据目录；其中 `evidence.json` 保存实际查询、模型答复、判断及作业。各场景的预期只用于测试对照，不发给模型。

工程回归命令见 [implement.md](implement.md)。实际结果与已知语义偏差见 [review.md](review.md) 及 `research/` 中的验证记录。
