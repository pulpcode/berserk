# 真实模型能力验证

验证时间：2026-10-09。使用当前配置的 DeepSeek `deepseek-flash`、Pi 原生工具循环，以及本机 HTTP 模拟特情／态势服务。

## 范围与执行方式

```sh
cd experiments/harness-lab
npm run probe:context -- --task-linking
```

每例使用独立临时 SQLite、Pi JSONL、来源配置、合成任务与测试席位。模型只收到合成通知和获准查询工具；未发送实际业务资料，未操作线上服务。任务创建仅用于隔离测试夹具，模型不能创建任务。本次没有测试文件执行环境或浏览器交互。

通过真实接入 API 发送通知并重复发送，经过 BackgroundService、Pi 查询与判断工具、正常完成和席位投递。预期答案只在测试脚本中比较，不放入模型提示。每组检查：同一信息仅有一个作业、关联多个任务不增加分析次数、任务元数据未被自动新增或修改。

Profile 目标在两批测试中保持一致：

> 根据收到的更新，自主查询报告正文与历史、当前态势和 Axon 活动公共任务，综合说明变化、可能影响哪些任务及依据，区分事实、建议和资料缺口。比较任务的目标、资源条件与有效时间。结论用中文，列出来源与版本；不要修改任务或自动分派。结合已查询的任务记录关联；若需独立开展工作且无合适任务承接，提出新建公共任务建议；否则说明暂不归口原因。

可用工具为 `information_search/read`、`situation_query`、`task_search/read`、`information_record_task_assessment`。未配置附加 instructions、Skill 或 Agents。

## 第一批：四个基础场景

| 场景 | 预期 | 实际判断 | 模型请求 / 工具调用 |
| --- | --- | --- | --- |
| existing：西区限制通知，仅一个相关任务 | 关联西区补给方案 | 符合 | 4 / 10 |
| multiple：同一通知，两个相关任务和一个无关任务 | 同一分析关联两个西区任务，排除东区任务 | 符合 | 4 / 12 |
| new-task：需交付访客接待须知，没有承接任务 | 提出新建公共任务建议 | **不符合：记录了暂不归口** | 8 / 16 |
| reference：公制长度单位换算资料 | 不关联、不建议新建，说明原因 | 符合 | 7 / 15 |

工程执行 4/4 成功；8 条席位投递成功；判断结果 3/4 符合预期。各例仅一个作业，任务元数据均未改变。累计 23 次模型请求、53 次工具调用、139,454 token（包括缓存读取，非费用）。

`new-task` 已成功查询三个现有任务，正确识别没有合适任务，但自行增加了“持续性目标”条件：它认为一次性文稿交付不足以建议建立公共任务。这一条件不在工具说明、Profile 目标或用户通知中。其原判断为：

> 该需求为一次性文稿交付……独立工作目标尚不成立……如后续明确对外接待流程规范这一持续性目标，可再评估新建。

该例首次工具调用还遗漏 `relations`，Pi 参数校验返回错误后，模型自行补为 `relations:[]`；宿主没有强制重跑或代写判断。Profile 偏重态势变化可能影响了模型理解，但本验证不能据此确定唯一原因。

## 第二批：一次限定澄清后的复验

仅将记录工具说明中的“新建建议须有独立工作目标及理由”补充为“新建建议须有独立工作目标及理由；任务可为一次性交付”。没有改变上述 Profile、原四例输入和断言，没有加入示例答案或强制工具调用。

再次完整执行原四例，并增加两项条件变体：

| 场景 | 实际判断 | 模型请求 / 工具调用 |
| --- | --- | --- |
| existing | 关联唯一相关西区任务 | 5 / 9 |
| multiple | 一次分析关联两个西区任务，排除东区任务 | 5 / 10 |
| new-task | 建议新建“编制访客接待须知”，保留一次性交付日期与目标；没有创建任务 | 6 / 16 |
| reference | 暂不归口，无新建建议 | 5 / 13 |
| existing-draft：相同编制通知，但已有目标一致的活动任务 | 关联已有编制任务，不重复建议新建 | 4 / 7 |
| insufficient：仅有“接待体验有改进空间”的交流片段，无明确问题或交付目标 | 暂不归口，说明需补充的信息 | 5 / 16 |

工程执行 6/6 成功；12 条席位投递成功；归口分支及任务 ID 6/6 符合预期。各例仍仅一个作业，任务元数据均未改变。累计 30 次模型请求、71 次工具调用、178,231 token（包括缓存读取，非费用）。

`multiple` 首次同时传入 relations 和 emptyReason，宿主互斥校验拒绝后，模型自然改为只提交 relations 并成功。`reference` 尝试读取不存在的报告，收到正常 NOT_FOUND 后继续完成。这些错误和恢复均保留在证据中。

## 实测暴露的限制

1. **收件正文缺前文的问题已修复。** 第二批 existing 和 multiple 把完整分析放在记录工具调用之前，最终 assistant 消息仅给归口结论或续写第七节。验证时服务端只取 `finalMessageId` 对应文字，收件正文因此缺少一至六节；Pi 历史没有丢失。随后宿主改为投影同请求的公开说明与最终答复，分开展示；10 份真实执行证据的离线核对及 8 项边界测试通过，没有追加模型调用。这里保留原实测行为，不把离线修复验证冒充新的真实模型结果。
2. **归口正确不代表全文准确。** 两批均出现“未报告限制”被简化为“无限制”、空态势属性被解释为已确认无限制或源间矛盾等表述。第二批 existing 前文误称限制时段“完全落在任务执行窗内”，实际是部分重叠；其记录的关联理由则正确写为重叠。第一批还把限制结束时点写成已经恢复，缺少恢复通报依据。
3. **通用资料仍可能触发过多查询。** 参考资料、编制需求、模糊线索均查询了无关道路态势；第二批 new-task 还讨论了未被需求提及的接待用车。当前 Profile 的通用性和分析效率仍需按后续真实业务需求验证，本次不继续叠加提示规则。
4. **建议仍需人员判断。** “任务可为一次性交付”的澄清改善了本次结果，但只完成一次复验，不能声称已消除同类误判或达到稳定成功率。

本次可确认的是：真实模型能够通过现有 Pi 循环查询候选任务、记录多任务关联／新建建议／暂不归口，宿主校验、去重和禁止自动创建任务的边界有效。不能据此将自由文本分析结论视为全部准确。
