# 地图操作结果说明一致性：修改设计与原场景复测

日期：2026-10-14。状态：**已实施并完成固定复测；结果见 validation.md，验收未全部通过。**

当前提交：`b201934a15f3cf35ba0b278fcd51c0840464560b`。需求与通过条件见 [prd.md](prd.md)，操作清单见 [implement.md](implement.md)。

## 1. 设计判断

当前保存回执整体方向正确：服务完成操作，返回真实版本、对象和时间，原生 Pi 把结果交给模型，界面从真实结果生成地图入口。本轮不重构这一链路。

需要修改的是：工具描述与实际能力的矛盾、模型对不同证据范围的误读、新输入中仍要求手写地图链接的指导。最终自然语言仍由模型生成，规则属于软约束；本轮以真实复测评估效果，不承诺消除所有解释错误。

保留现有业务分工：

| 事实 | 权威依据 | 不能替代它的内容 |
| --- | --- | --- |
| 本次修改是否成功、保存到哪一修订 | 该动作实际成功回执及固定修订 | 模型提出的计划、失败调用、另一请求的旧回执 |
| 任务目前采用哪一版 | 实际新查询返回的任务当前状态，或本次成功采用回执所证明的提交时状态 | 本会话草稿版本、早先的助手回答、未返回 current 的修改回执 |
| 标注实际保存了哪些字段 | 已确认的写入及实际固定文档；回执不足时按对象/字段读取 | 来源响应中存在该字段、正文中讨论过该判断 |
| 谁执行了采用、属于哪个会话 | 查询/回执实际公开的身份与归属字段 | 相邻草稿列表、发布人、用户 ID 与会话名称的猜测 |
| 地图打开对象或版本 | 已有经过证据匹配的结构化引用 | 模型自行拼出的 ID、URL 或占位 href |

“本次未设为任务当前”可以由本次操作范围确定；“任务没有当前版本”是共享状态断言，需要相应依据。查询只证明查询时所见状态，也不是永久实时保证。

## 2. 修改项与边界

### D1. 让工具说明与实际能力一致（R1、R2、R3）

落点：`experiments/harness-lab/src/pi/annotation-tools.ts`。

- 复用已有 `canSetCurrent` 条件，使 `annotation_action` 的说明与已经按权限裁剪的 schema 一致。具备采用能力时说明现有读取、比较、显式采用规则；无该能力时明确当前席位不能设为任务当前，不再指导调用不可用分支。
- 说明草稿修改、发布与任务采用各自的作用范围，修正“工具只操作本会话草稿”却又包含任务采用的表述歧义。保持服务端权限、操作分支和当前序列校验不变。
- `annotation_list` 说明当前设定来自本次读取；采用者字段只证明返回的身份，不证明其操作会话。`annotation_action`/`annotation_read` 说明动作回执、固定版本读取与任务当前状态的区别。
- `current` 字段未出现表示该结果未提供当前状态，不能解释为 `publication:null`；历史 receipt 是原动作结果。
- 仍使用 Pi 原生参数校验和错误文本。仅靠当前证据不增加统一错误翻译器，不为了避免一次拒绝开放被裁掉的操作。

这部分即便需要修改程序，其主要作用仍是提供准确上下文，不是新增自然语言事实校验。

### D2. 在现有 Skill 集中整理表达规则（R1、R2、R5）

落点：`experiments/harness-lab/fixtures/skills/map-annotations/SKILL.md`；改写现有完成核对段，合并重复表述，不另建 Skill。

规则控制在以下通用范围：

1. 先报告本请求实际完成的效果；请求未涉及的全局状态无需顺带总结。
2. 确实回答当前共享状态时，通过已有工具核实；历史对话只说明当时所知，不能充当实时状态。
3. 来源事实、对话中的判断、标注实际保存字段分开表达。确认字段时优先使用已有充分证据，确有缺口才定向读回；不要求每次成功保存后再读一次。
4. 操作归属不超出实际字段。没有会话归属时不推断；用户明确询问而数据不足时说明不能确认。也不把“发布者”当作“采用者”。
5. 正常成功明确说明，失败如实报告；无须给每句成功结果添加免责声明。正文、确认前说明、问题选项都适用。

不写入测试对象名、固定版本号、错误请求 ID 或标准工具调用顺序。Skill 仍按现有原生机制加载，未读 Skill 不能单独判业务失败；记录实际加载情况用于分析。

### D3. 消除新输入的地图链接歧义，保留历史（R4、R6）

落点：`src/pi/composer-input.ts`、`src/pi/history-evidence.ts`；必要时核对 `src/pi/lab.ts` 的现有分派入口。路径相对 `experiments/harness-lab`。

现状：v1 的 `composerInputText` 含 `[对象名称](href)` 指导，v2 又复用 v1；历史校验要求已保存正文与相应生成器逐字相等。直接修改现有函数会使旧会话被判为不一致。这里存在明确兼容性需求，不能以“只是改一句 prompt”为由跳过。

拟采用最小版本扩展：

- 保留 v1/v2 生成和校验行为原样，新地图输入使用 `berserk.composer-input.v3`。含 `context`、`annotationContext` 或 `annotationRefs` 的新输入走 v3；仅选择 Skill/子 Agent 的旧路径保持现状。
- v3 使用同一组已有数据字段、权限与体积限制，不增加状态快照或几何。方法说明改为：对象名称可在正文直接提及，地图入口由界面根据用户引用和真实工具结果生成，无需手写地图 URL。
- v3 不再调用带旧链接指导的整体 v1 模板。可复用必要的小段代码，但旧版本输出须逐字稳定，不趁机重构历史系统。
- `composerHistory` 与 `validateHistoryEvidence` 显式识别 v3；继续检查身份、requestId、顺序、重复、未知字段、正文一致性、只读子任务边界及 Skill 快照。未知版本不能被当作合法 v3。
- 旧原生消息、已记录的 Skill 正文和合法 Markdown 地图链接均不改写。新会话与旧会话的新请求获得新说明；旧历史仍可能含原指导，不能声称历史内容已被清理。

v3 仅是这次文案变化所需的持久记录兼容版本，不建立第二份会话历史、摘要缓存或动态模板注册框架。

### D4. 保留回执与地图展示（R4、R5、R6）

`AnnotationReceipt`、服务事务、HTTP DTO、来源复制逻辑、`AnnotationRequestState`、固定引用及现有地图结果入口均保持原契约。

- 不追加完整任务状态、完整对象属性、完整地图文档，也不追加模型生成的“执行事实”。
- 本次不新增操作结果卡片或用户名称解析服务；现有回执入口已足以支持审阅和验证。
- 本次不要求语义审核后才展示答案，不用 UI 隐藏错误文字。若界面已有入口出现回归，作为缺陷处理；不把按钮可用等同于正文正确。

### D5. 只补充必要的测试取证（R7）

复用原 `probe-desktop-map.ts` 与 `probe-map-workflow.ts --recovery`。不得在产品路径加入评分规则、自动纠错或测试专用上下文。

- 桌面驱动默认五环境与业务输入不变。新增一个测试专用的固定模式 `--reporting-recheck`：连续运行两个全新隔离环境的**完整既有 B01→B02→C01→C02 协同链**，复用同一执行函数、指令、交互规则；不提供任意场景选择或失败重试选项。
- 该模式可与 `--prepare-only` 组合做零模型准备；不与 `--prepare-case` 混用。报告明确标注为额外两次协同复测，不伪装成又两轮完整八场景验收。
- 全量保留每个 requestId 下用户实际可见的助手文字、问答内容、工具参数/结果、独立前后快照。尤其不能只抽取最终答复而漏掉 C02 确认前说明。
- 语义审阅结果另存为测试证据，绝不进入模型输入。正则可定位占位链接和疑似断言，不能替代人工语义判定或自动改写答案。

## 3. 兼容性、影响与回退

### 4.3 原来源刷新三例的步骤与判据

复用 `probe-map-workflow.ts --recovery`，每例均保留三个步骤：

1. S01：无草稿开始，查询已有区域、道路和车辆，向指定图层上图；核对来源几何、ID、修订、查询时间。

3. 来源由 closed r2 改为 open r3。S03 使用原文：“道路来源有新变化，请重新查询核对并更新本会话地图中已有的同一道路标注，保留对象编号。写清当前状态、来源版本与时间，保存草稿，不改动或重新发布第一版。”

逐项核对：

- refresh 自身更新几何和相应来源修订/查询时间，保留业务字段；若模型随后另行 apply 保存业务属性，该实际保存必须计入，不能误判为 refresh 自动复制了属性。

- 来源 `effectiveAt`、`validTime`、`queriedAt` 与标注实际字段分开；回执含某时间不等于该时间已存到标注 `sourceRefs`。
- 原来“r2（closed）”等有合理来源解释的措辞先判歧义，不直接判虚报。只有明确声称保存了某字段而固定内容没有，才判已证实错误。
- 三例的普通工具错误与自恢复成本仍单列，不把解释改进建立在新增重复读取或反复拒绝上。

## 5. 判定与报告

### 5.1 每条重要说明的核对格式

审阅记录至少包含：场景、requestId、消息位置（中途说明/问题/最终答复）、原句、它声称的对象/时间/范围、模型当时获得的实际证据、独立真实状态、判定及理由。

| 判定 | 含义与处理 |
| --- | --- |
| 有依据且正确 | 实际证据支持其范围；通过 |
| 已证实错误 | 明确断言与实际状态/保存内容冲突；本轮说明质量不通过，即使操作正确 |
| 无依据的确定性断言 | 尤其是未提供的操作会话归属；不能因猜测恰巧吻合就算通过 |
| 表述歧义 | 有合理解释，先保留上下文，不自动判虚报；报告可读性观察 |
| 明确信息不足 | 数据确实缺失时可接受；用户要求的事实可正常查到却始终不查，另判任务完成度 |

评估全部可见助手内容，不能因最终拒绝正确就忽略前面的错误。也不能因拒绝、重试或澄清本身存在而认定解释错误。

### 5.2 汇总方式

分别报告三列，不合成一个模糊“通过”：

1. **操作与边界**：沿用原场景确定性断言及独立快照。
2. **说明准确性**：按 R1/R2/R4/R5 分类，列出每次 C01/C02、三条主链和三例恢复结果。
3. **顺畅程度**：模型/工具调用、额外读取、正常交互、参数恢复、停滞、耗时、累计 token；累计 token 不冒称单次上下文长度。

重点比较普通备注修改是否新增任务全量查询或成功后重复读回，以及无权限采用是否仍反复尝试不可用分支。一次合理按需查询或一次自恢复不是自动失败；如出现一贯的多余调用或拒绝循环，记录为未达本轮顺畅目标。

通过本轮须满足 PRD 全部门槛，且三个 C01/C02 观察和三例恢复流程均完成。若操作通过但仍有明确说明错误，报告“操作通过，说明改进未通过”，不因只是自然语言就降级隐藏。仅复测未复现不能证明普遍稳定，历史错误也不删除。

## 6. 本期停止线

若最小改动后，模型拿到清楚、正确的证据仍反复作无依据断言，保留样本并报告，不继续堆砌场景特例 prompt，也不自动加第二模型或回答拦截器。模型/思考配置对照、回执新增字段、身份显示或结构化结果卡片须另提方案。

新输入版本、权限或历史兼容发生异常，先停止真实模型批次；修复本范围内明确问题后，以新冻结版本复测，不能关闭校验来凑通过。
