# 下一阶段方案：从外部来报到人员建任务

版本：v0.2｜2026-11-06 用户已批准实施｜方案提交 `6987d34`；当前实施与验收中。审阅阶段的原版保留在该提交中。

## 1. 本阶段做到哪里

让场景从“导演投放信息”走到“业务席收到分析、人员创建任务并开展协作”。建设顺序是：**有限编码 → 配置联调 → 工程验证 → 小批量真实模型测评**。

保留现有简洁导演台，继续使用特情系统、态势系统两个来源。这个阶段完成一次事实核实协作，不提前建设方案批准、调派及车辆执行。

**仓库火情是本阶段唯一完整业务测试主线**，覆盖来报、初析、总体席建任务、工作分派、接收、提交和审核。

交通救援、登高演练作为“开场已有任务”：演示从 09:10 开始，剧本设定这两项业务在 09:00 已经开展，所以启动演示时由系统自动创建相应任务空间，表示之前就在办理的工作。它们参与续报关联和车辆占用判断，不各自再走一遍完整业务流程。

| 时点 | 建议的演示行为 |
| --- | --- |
| 开始前 | 系统自动创建“城西交通救援”“临港登高演练”两个开场已有任务；仓库火情任务尚不存在。 |
| 首报位置待核实 | 导演投放来报；后台 Agent 核对报告、对象、业务时间和已有任务，把初析送给总体席。总体席可继续核实、关联已有任务，或决定新建。 |
| 人员决定建任务 | 总体席从这条信息的分析结果进入已有任务表单，填写或修改名称、目标和关联理由后确认。原信息、分析版本及新任务一并关联。 |
| 仓库位置核实、资源清单确认 | Agent 针对当时已有任务进行判断；人员核对续报与任务关系，按需要分派事实核实工作。 |
| 席位协作 | 业务席使用已有任务工作区接收、办理、提交，总体席审核；工作提交不代表车辆已经出动。 |
| 完整事件演示 | 前五步之后，由导演继续按顺序投放背景事件、道路变化和旧观测晚到等后续预设来报，验证事实与关联更新。 |
| 重新演示 | 结束本轮，建立新的演示和两个开场已有任务；仓库火情任务需要再次由人员决定创建。历史保留只读。 |

不规定“首报必须新建任务”这一标准答案。人员可以等待位置核实后再创建；Agent 暂不归口或建议新建，都要看业务依据。整轮业务闭环验收必须实际覆盖一次人员创建。

## 3. 任务如何创建和绑定

总体席从**某条来报的成功分析结果**中点击“新建任务”，复用现有任务表单，填写或修改名称、目标和关联理由后确认。该入口保留原来报与实际分析版本的关联。

| 字段 | 含义 |
| --- | --- |
| `eventId` | 系统接收一条外部来报后生成的记录编号，标识“哪条消息” |
| `jobId` | 针对该消息进行某一次后台 Agent 分析的作业编号，标识“哪次分析” |

**新任务继承原来报/分析记录所属的轮次**，由宿主读取并核验已有归属，在同一事务中保存任务、关联和创建回执；业务席不选择或填写轮次。例如，从 A 的分析结果创建的任务属于 A；若提交前 A 已结束，拒绝该旧提交，不改绑到 B。两个外部系统的身份仍跨轮复用。

- Agent 提出新任务建议时，可用作表单初值，由总体席修改、确认或放弃。Agent 没有提出新建建议时，总体席也可从该成功分析结果打开现有表单，自行填写后确认创建。这是本阶段拟补充的入口能力，创建仍须人员确认。
- 创建权限仍使用现有公共任务管理权、业务协作资格和来源内容权限；导演不能通过这个入口办理业务。
- 失败、取消、未完成的分析不开放此创建入口；结束轮次的旧分析及旧表单不能再创建，不转绑到新轮。
- 同一分析版本沿用已有的一次创建回执。并发点击、响应丢失后重试返回同一结果；相同操作标识改变内容报冲突。
- 同一条来报曾创建任务后，即使通过“重新预处理”得到新的分析结果，也应提示查看已有任务，不能再次创建；不同分析版本的并发提交也须在事务内核对。确需从同一来报另建多个任务的交互后延，不按名称判断重复。“重新预处理”含义见下节。
- 任务名称由人员决定，不要求叫 T01，不按作者任务代号反查归属。关注对象/区域沿用现有表单与校验，由人员确认实际业务引用；不把整套模板答案写入目标。
- 任务关联不自动授权其他席位读取原信息。协作所需来源读取权按现有配置安排，不能复制完整分析到公共任务目标来绕过权限。

无来源的全局“新建任务”仍属于 SIM-TASK-002，不以本方案决定其归属。本阶段不实现已撤回的隐藏浏览器上下文、不要求业务席选择轮次，也不隐藏或禁用原入口。

## 4. 来报怎样处理

两个外部系统跨场景、跨轮次继续复用原身份和凭据。仅为本部署实际投递到的两个 sourceId 配置规则，按配置映射连接，不写死开发样例 ID，不顺带改变其他独立接入通道。

**建议本阶段初析结果先固定投递总体席**，其他席位由总体席按需分派工作并通过原有授权查看资料；不默认四席广播。预处理仍是独立的原生 Pi 作业，不继承某个席位的私有聊天，不因投递自动启动席位会话。

复用已具备的报告查询、对象查询、任务搜索/读取及结构化任务判断工具。处理配置只明确核对目标和能力边界，不预写“这条消息属于哪项任务”的答案，不另加一套七系统提示词或 Skill。同来源本阶段只启用普通预处理，不叠加持续分析。

由 Agent 判断关联已有任务、建议新建或暂不归口。人的关联修正与建任务决定分别保留；后续来报不自动更改任务目标、批准方案或启动执行。未形成有效任务判断时如实展示，不能由宿主补成正确答案。

消息接收、分析成功、结果投递、人员查看、任务创建和工作完成分别核对。投递重试只重试发送已有结果，不重新调用模型。

本方案中的“重新分析”统一指当前信息中心已有的**“重新预处理”**功能：原处理已经结束后，有来源管理权限的人员可手动让后台 Agent 再处理同一条来报。例如，首次分析失败、中断，或人员希望再次核对结果时使用。它沿用原来报和原处理规则快照，保留历史记录；`eventId` 不变，新分析生成新的 `jobId`。新的续报则是另一条来报，有自己的 `eventId`。

本阶段复用该功能，只补充再次建任务的检查；不增加自动循环分析或无限重试。

## 5. 场景数据和界面怎么改

- 新增场景定义版本，建议为 v4；仍保留六站、二十四车、五十三个对象、十二步/十三条来报及两种模式。只调整任务初始化与本阶段必要的业务表述，不改造整套资源或道路数据。
- 新定义显式保存预建任务集合 T02/T03。主任务不在预建集合，也不靠“缺一个任务”表示故障；旧定义仍按原三任务集合校验。来源快照与宿主初始化映射均保存该版本的完整校验依据，缺失或不一致时拒绝启用。
- 两个开场已有任务的目标改用业务表述，保留占用、时间和引用；不把“模拟场景”“本实例”等控制解释写入业务任务目标。原 T01 的人员目标不再自动灌入新任务，后续资源需求由人员明确。
- 新主任务在导演事件列表中不显示成已经存在的模板任务。事件详情只提供能由实际关联确认的任务入口；未创建时不提供虚假跳转，不按名称自动匹配。
- 沿用已有信息详情、任务表单、任务首页及工作交接界面；仅补必要入口和真实状态，不增加独立任务控制块或重复说明。
- 两种模式统一称为“主线演示”（前五步）和“完整事件演示”（全部十二步），均由导演手动投放预设事件。“完整”指事件范围，不表示重播某次历史演示。实施时同步对应界面文案，保留 `source_replay` 等既有技术标识与历史数据兼容。
- 主线演示在前五步投放结束后等待人员继续研判/选择方案。本阶段不建设支援执行流程。
- 两种模式均区分事件投放进度与业务任务状态：投放进度反映消息发送情况，业务进展依据人员操作和业务记录判断。

## 6. 结束与重演

**轮次隔离已经实现，任务是否归档不决定它是否隔离。**已归属 A 的任务及其分析、会话，在 A 结束后仍属于 A，退出当前业务候选并受只读限制，不混入 B 的处理上下文。这里的归属针对每条来报及其关联对象，不是为特情系统、态势系统各复制一套来源身份。

本阶段要补齐的是**自动归档的任务范围**：当前代码只遍历开场自动创建的清单，后来由总体席从来报创建的主任务可能漏归档。应按本轮实际绑定的全部任务检查归档资格，不再只查模板清单。

符合条件的任务按原规则归档；仍有未完成工作、不能归档的任务保留原状态并只读。漏归档不等于串轮，不能为了统一状态而伪造完成、绕过归档条件或删除会话和工作记录。

结束与重演继续沿用已有结束门禁、排队取消、在途停止与实际终态核对，重点回归三个时机：后台正在分析；总体席正在提交新任务；业务席正在办理工作。A 中已提交成功的记录仍属于 A，A 结束后的旧提交被拒绝；均不迁移到 B。归属核验要在实际提交处生效，不能只靠页面刷新。

## 7. 实施分段与验收

| 阶段 | 工作类型 | 交付与退出条件 |
| --- | --- | --- |
| S1 任务起点 | 编码与场景样例 | 新版只自动创建两个开场已有任务；总体席从来报分析结果确认建主任务并继承轮次；实际任务入口与旧版兼容通过 |
| S2 来报与协作 | 配置联调，必要的小范围补码 | 两个来源进入原生初析，总体席收到结果；相关/无关判断、关联修正及一次工作分派到审核打通 |
| S3 工程验证 | 确定性集成与桌面浏览器测试 | 创建/重新预处理去重、归档范围、权限及三类中断重演回归通过；保存原回执与真实状态 |
| S4 模型测评与待测发布 | 有边界的真实模型测评、整理证据 | 工程验证通过后核对真实模型判断，列明通过项、失败项及限制，再按批准范围发布供人工检查 |

S4 首批建议只跑**一轮完整事件演示，十二步/十三条来报**，前五步同时覆盖人员建任务和主线协作。每条来报最多一次自动初析，不自动重跑失败批次。真实模型一次作业可能包含多次 API 调用；执行前须固定模型、参数、场景/配置版本，列明调用、token、费用上限和停止方式。仅配置过 Key 不计为效果通过。

测评时每步等待该步消息的接收、分析和投递完成，再推进下一步；在事先记录的节点由人员创建任务、办理工作。这样可区分当时事实与后续变化；这只是测评顺序，不给导演台增加强制等待 Agent 的操作限制。

测评同时看四类行为：位置不确定时是否说明缺口；占用、检修和未知是否被误判为可用；旧观测是否覆盖更新事实；已有任务与无关背景是否被正确区分。判断有合理业务依据可以接受不同结论，不用固定话术或预填任务编号给模型“喂答案”。工程测试使用确定性模型；真实模型问题和人工修正另列证据，不混为自动通过。

交通救援与演练的车辆占用是主任务需要考虑的相关约束，仅靠它们不能充分证明系统能排除真正无关的信息。进一步增加地点、对象、资源无已知关联的来报，已记入 [SIM-EVAL-001](../11-03-scenario-demo/issues.md)，留待后期丰富测试，不增加本期样例或验收要求。

SIM-TASK-002 尚未解决，因此本阶段验收与发布仍只承诺有可信来源链的业务闭环；不宣称普通全局创建、个人空间等无来源路径已全部隔离。

## 8. 兼容、发布与回退

旧演示的已保存任务定义、任务 ID、原始消息、hash、回执及 Pi JSONL 不追改；新规则只影响未来接收，不扫描旧消息批量重跑。新旧初始化格式须有显式版本和严格验证，不能把格式未知或映射残缺当成新版两个任务。

发布前列出实际规则/授权差异，备份宿主与来源数据，并按现有切换约束先结束或锁定旧活动演示。上线不自动触发新演示或模型分析，由导演明确开始新的版本。回退时先停止新投放和处理，再配对恢复兼容代码、配置及对应数据快照，保留升级后证据；不让旧代码直接读取新格式后猜测。
