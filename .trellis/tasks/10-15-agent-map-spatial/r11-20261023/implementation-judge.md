# R11 评分入口：实现与验证

`judge.ts`提供两步：先用24条人工标定的声明校准评分器，再对64项任务逐项评分。当前只完成代码和离线检查，未运行真实评分。人工标签已有23条确定、C25待定，入口会在调用服务商前拒绝启动；不修改标签凑齐4/4。

## 怎样避免误判

- 评分对象明确分为“一句声明”与“一项完整任务”。一句正确不代表整题正确，调用过工具也不代表任务完成。
- 任务分别检查完成、依据、过程事实、最终事实、实际效果、范围和必要答案覆盖。表达别扭另记；不能用它代替事实错误，也不能用“仅表达问题”掩盖关键答案不清楚。
- 传入评分器的是不含组别和建议标签的公开记录，保留工具参数、回执及前后状态。Skill正文和私有推理不作为任务事实依据；原始证据仍完整保留。
- 后来的保存成功不能给较早的“已经保存”补依据。完整任务应保存而没有保存，或发生未经授权的状态改变，由程序强制判失败；评分模型的通过不能覆盖它。
- 评分结果需按冻结的结构解析。整题六个核心维度不能填“不适用”跳过，未完成和未决不能从总分母消失。最终报告仍需人工复核失败、分歧及抽样通过，模型初评不是最终人工裁定。

## 计费和证据保护

真实入口只接受当前worktree的`.local/spatial-r11/ledger.json`。校准、Agent和后续评分共用该账本，绑定同一源码冻结值；校准原始响应的请求ID、哈希和用量必须能在账本逐项对应。不能通过换输出目录重评同一个输入，也不能重新开启已经启动过的Agent批次。

评分预算最多88次请求（24校准+64任务）。每次启动前检查预算和完整输入大小，不为省额静默截断证据。保留原始请求、响应、解析结果和哈希；评分前比对任务归档时的证据哈希。输入过长、响应截断、缺少用量、模型改变或HTTP错误均停止，不自动重试。请求禁止重定向到其他端点。

每条评分前保守检查请求不超过100 KB，以对应10万输入token预留；这是启动保护而非精确token计算，账单以提供商实际usage为准。无法容纳完整证据时停下复核，不删除上下文后硬评。

## 执行顺序（当前未执行）

从`experiments/harness-lab`运行。先完成人工标签与材料曝光审计，所有代码稳定后用`live.ts prepare`生成冻结文件。使用同一个冻结文件、配置和固定账本：

1. `judge.ts calibrate OUTPUT FREEZE LEDGER CONFIG`：先核验人工标签和配比，再发出最多24次校准请求；保存真实结果并验证8/8。
2. `live.ts run OUTPUT FREEZE LEDGER CONFIG CALIBRATION_RESULTS`：核验校准和同账本的实际计费记录，再执行四组64项。
3. `judge.ts grade OUTPUT FREEZE LEDGER CONFIG CALIBRATION_RESULTS BATCH`：核验封存证据，对可评分任务各调用一次。未完成/未执行单列，不补跑、不自动补评。

`OUTPUT`必须为新的`.local/spatial-r11/`子目录，`LEDGER`必须为上述固定账本绝对路径。配置示例在`calibration-v2/judge-config.example.json`；密钥沿用本地环境，不写入证据、代码或文档。
