# 业务席位与补充投递审批：实现设计

状态：**已批准并实现**。四席位和示例配置用于本阶段验证，已应用线上，测试账号及步骤见 [线上验收指南](server-test-guide.md)。

## 1. 职责与权限

| 部分 | 负责什么 |
| --- | --- |
| 席位目录 | 统一席位 ID、名称和职责；初步分工见 [PRD](prd.md#2-席位定位) |
| 来源配置 | 允许的 Profile、接收席位上限及来源认证 |
| 来源规则 | 选用 Profile、固定接收席位、是否提出补充建议及候选范围 |
| Profile | 处理目标、工具、Skill、Agents、服务指令和资料范围，不配置接收席位 |
| Pi 主 Agent | 自主查询分析，分别提出任务判断和补充接收建议 |
| 总体席 | 审阅建议，决定是否补充投递及实际名单 |
| 宿主 | 校验权限、保存审批、根据决定生成投递并记录送达情况 |

### 席位目录

沿用 SQLite 的 `seats` 表，补充 `responsibility` 和职责版本 `responsibilityRevision`。拟设 `seat-overall`、`seat-intelligence`、`seat-planning`、`seat-situation` 四个稳定 ID；显示名称分别为总体席、情报席、筹划席、态势席。

扩展现有离线 `access:admin` 脚本，以独立的席位维护子命令修改名称和职责，不要求重设账号密码。职责为 1～1,000 字符；旧席位缺省为空，补齐前不能成为智能补充候选。账号开通仍用现有入口。本期页面只展示职责，不新增组织与角色编辑器。

总体席使用现有公共任务管理、模型设置及对应来源管理权限；其他三席默认使用正常对话、资料查询和获准业务交接能力。来源与资料范围仍分别授权，总体席不因管理身份而获得其他席位私有会话。

服务端后台配置新增可选 `deliveryReviewSeatId`，启用补充建议时必须指定有效总体席。本阶段统一使用 `seat-overall`；服务端按 ID 判断审批资格，不按名称、权限大小或当前在线人员推断。审批还要求当前账号具有该来源管理权限及完整结果读取权限。

旧 A／B 账号及工作区保留原 ID。本期在隔离测试数据中建立四席位；上线时显式开通新席位、配置权限和规则，不自动把旧 A／B 的私有数据转给新席位，也不自动停用旧账号。

## 2. 规则与快照

保留 `recipientSeatIds` 的原义：**固定接收席位**，非空。新增可选字段：

```ts
supplementaryDelivery?: { candidateSeatIds: string[] }
```

未配置表示只进行固定投递。开启时候选非空，引用中央席位目录；不在规则中再写一套职责。

示例规则：

```json
{
  "name": "特情分析与补充通知",
  "sourceId": "mock-intel-source",
  "profileId": "context-analysis",
  "recipientSeatIds": ["seat-intelligence"],
  "supplementaryDelivery": {
    "candidateSeatIds": ["seat-planning", "seat-situation"]
  },
  "enabled": true
}
```

该规则表示：成功结果始终送情报席；Agent 可建议增加筹划席、态势席，总体席决定。总体席通过审批权限查看结果，不必先给自己建立普通收件。补充候选排除固定接收者及本次审批席位，避免重复审批已有接收或监督访问。

保存时核验：固定席位和候选均有效且位于来源 `allowedRecipientSeatIds` 内；候选去重、不重复固定名单，沿用现有最多 100 席位边界；职责完整；所有接收者及总体席有权读完整结果对应资料范围；总体席具有来源管理权限。Profile 必须允许 `information_suggest_recipients`。不符合时明确阻止启用，不自动退回其他审批人。

接入时将规则、Profile、候选的 ID／名称／职责／职责版本，以及 `reviewerSeatId` 保存为作业快照。职责或规则修改影响新接入；旧作业使用原快照，执行和批准时继续检查当前有效身份与权限。重处理沿用已有的原规则快照约定，不静默套用新配置。

## 3. Agent 接入

在后台上下文加入固定接收者、补充候选及职责，并说明：固定名单由系统执行；工具只记录补充建议，总体席批准后才增加投递。任务创建者不是任务办理责任人，不从 `ownerSeatId` 推断应通知谁。

新增工具 `information_suggest_recipients`，仅注册到开启该规则的后台预处理主 Agent；人员对话、人员发起的后台分析和只读子 Agent 不注册。

```ts
// 提交本次完整建议，或说明无需补充。
{ recipients: [
  { seatId: 'seat-planning', reason: '道路封闭影响两个任务的方案安排。' },
  { seatId: 'seat-situation', reason: '通行状态变化需要纳入当前态势核对。' }
] }
{ recipients: [], noAdditionalReason: '现有影响属于固定接收席位的职责，无需补充。' }
```

工具说明：“建议在固定接收席位之外补充通知哪些候选席位，并逐项说明原因；无需补充时说明理由。每次提交完整建议，分析成功结束后交总体席批准。”

理由为 1～1,500 字符；两种输入互斥，拒绝重复、越界或已失去读取权限的候选。宿主绑定作业，不让模型填写 jobId、审批人或来源。工具返回已记录内容，并明确“尚未批准或投递”；无需模型再调用 prepare／commit。

同一作业内允许修订，最后一次成功记录生效。无效调用返回普通 Pi 工具错误，保留上次有效建议，Agent 可自行修正；未调用或一直无效只表示未记录建议，不强制补调用。显式空建议会清除本作业先前建议。

继续使用 Pi 原生循环：一次后台作业可以多次调用模型和工具，任务影响与席位建议共用分析上下文，不要求在单次模型回复里全部完成。无需新 Skill、固定思考步骤或独立 Router。`information_record_task_assessment` 保持独立，宿主不从分析正文猜测接收者。

## 4. 记录与结束处理

继续使用同一 SQLite 与 Pi JSONL：

| 内容 | 保存及职责 |
| --- | --- |
| 分析正文、查询及工具结果 | Pi 原生 JSONL，继续作为对话内容依据 |
| 固定名单、候选职责、审批席位 | 既有作业规则快照 |
| 最后有效建议 | `BackgroundJob.recipientSuggestion`：建议、toolCallId、记录时间；作业结束后固定 |
| 待批准事项及最终决定 | 新增 `background_delivery_reviews`；每个 job 至多一条 |
| 是否实际送达 | 既有 `BackgroundDelivery`，保持 `(jobId, seatId)` 唯一 |

审批记录只保存 ID、jobId、reviewerSeatId、状态、revision、时间，以及决定后的操作人、名单与逐席位理由；分析版本和建议通过已结束的 job 引用，不复制正文或聊天历史。补充投递引用 reviewId，固定投递继续以规则名单为依据。

最小审批状态：`pending → approved / declined`。无需补充或未记录有效建议不创建审批。`approved` 表示决定已保存，不能代替各席位的 `delivered / failed` 状态。

作业结束时：

1. 沿用现有原生结束记录、文件与取消核验；没有完整成功证据，不生成本次固定投递或审批。
2. 将已记录建议与本次 Pi 工具成功结果对应；无法对应时不发布该建议，记录原因，固定投递照常。整体历史损坏仍按原有错误处理。
3. 在 `finishJob` 同一 SQLite 事务保存终态、固定席位的 pending 投递；有有效非空建议时，一并创建 pending 审批。
4. 释放后台执行资源；固定投递沿已有流程送达。建议本身不产生额外收件，也不授予新的读取权限；某席位已有的来源查看权限仍然有效。

这一步不改变 `BackgroundJob.status`：审批等待期间作业已经是 `succeeded`。待批准保存为业务记录，是为总体席离线后也能处理，不是新的持久 Agent 执行引擎，也不使用悬挂的 Pi 工具调用。

SQLite 和 JSONL 不承诺跨介质原子提交。结束事务前异常退出沿用中断识别，不自动重跑；事务后重启恢复 pending 投递和待批准查询。

## 5. 总体席批准与投递

拟增加总体席待批准查询接口和决定接口：

```text
GET  /api/information/delivery-reviews?status=pending
POST /api/information/delivery-reviews/:reviewId/decision
```

```ts
{ clientActionId, revision, decision: 'approve',
  recipients: [{ seatId, reason }] }
{ clientActionId, revision, decision: 'decline', reason }
```

批准可以保留建议、移除某个建议席位、或增加原候选中的漏选席位。至少选一席；名单为空时使用“不予补充”。对原建议可沿用理由，新增或修改接收理由时由人员填写。

处理顺序：

1. 校验登录、CSRF、身份视图、指定总体席、来源管理及结果读取权限。
2. 核验审批仍 pending 及 revision；批准时再核验结果证据、原候选与当前接收权限。任一选中席位不合法则整次批准不提交，保留编辑内容供调整；不予补充无需选择接收者。
3. 在同一 SQLite 事务保存批准决定、每个新接收席位的 pending 投递和幂等回执；不予补充只保存决定。复用 `background_actions`，增加 `delivery_review` 操作类型。
4. 沿用现有投递服务逐席位检查、送达。投递失败保留批准决定，修复条件后可重试发送原结果，不调用模型、不再次审批。

相同操作重试返回原回执；revision 使两个浏览器不能相互覆盖决定。读取和重试也检查当前权限。总体席下线不会自动通过、转交或阻止固定投递；审批身份或权限失效时说明不可处理，维护人员修复原配置，不按在线或最高权限自动换人。

每项作业只完成一次审批。本期不另设“绕过审批直接补发”入口，不支持已决定事项重新编辑或追加第二轮名单。人员明确重新分析会形成新作业和独立建议；旧决定和送达保留，页面标明分析时间及版本，不覆盖或假装是同一项决定。

## 6. 页面

保留现有侧边栏和信息中心；桌面交互为主，不新建管理门户。

- **处理与投递规则**：保留“固定接收席位”；增加“允许 Agent 建议补充接收席位”开关和候选选择。职责从席位目录只读展示；审批人显示“总体席”。不开关则沿用原表单。
- **信息中心**：总体席增加“待批准投递”入口及数量。列表展示来源、标题、分析时间、固定接收者、建议接收者；其他具有来源查看权限的人员可查看允许的记录，但没有批准按钮。
- **审批详情**：同页展示原信息、分析结果与查询依据；分别展示固定投递状态、Agent 建议和理由。总体席勾选候选，点击“批准补充投递”或“不予补充”。不再叠加第二张确认卡；错误保留草稿，版本冲突展示最新决定。
- **作业详情**：分别显示分析状态、补充审批状态、各席位送达状态。批准后仍可能存在发送失败；分析失败也不覆盖旧成功作业的投递。
- **普通收件**：可展开“为何收到”，说明固定投递，或总体席批准及本席位接收理由；沿用提问、后台分析、任务关联和文件导入。其他候选、审批草稿、服务配置和他人私有接续不下发。

收到的信息仍引用同一份结果和附件，不提前复制进所有席位目录；人员继续处理时才导入工作区。收件不表示已读、签收或接受 WorkItem。任务信息读取继续要求任务可见、信息可读及资料权限，不因关联而自动放开结果。

## 7. 异常与兼容

| 情况 | 处理 |
| --- | --- |
| 未记录有效建议／明确无需补充 | 固定投递正常；显示未记录建议／无需补充，不创建审批或强制重跑 |
| 结果保存、执行失败、取消、中断 | 沿现有终态处理，不将建议当成成功结果投递 |
| 候选在分析后失去权限 | 保留建议供审阅，标明不可选；批准时须移除，不能绕过权限 |
| 固定接收席位发送失败 | 单独显示投递失败；合法的其他固定投递及待批准事项仍可处理 |
| 批准已提交、响应丢失 | 相同 clientActionId 返回原决定，重开页面可查 |
| 批准后接收权限发生变化 | 该席位投递失败；决定仍保留，不自动改送其他席位 |
| 重送同一来源消息 | 沿既有去重返回原接入结果，不产生新作业或审批 |
| 更改规则或职责 | 新接入使用新快照；旧审批显示原快照，不被悄悄改写 |

历史规则缺新字段按固定投递解释；旧席位职责为空，历史收件及交接仍能读取，不回填新审批、不重送信息。拟由数据库 v4 升为 v5，添加席位字段、审批表及相应数据契约；所有应用和管理脚本读取入口同步支持迁移与完整性检查。

完整性约束：固定投递来自规则名单；补充投递必须有同一 job 的 approved 审批及批准名单依据；审批只引用核验成功的预处理作业。普通收件 DTO 显式投影新字段，不将整个审批或规则对象返回给收件人。

部署前备份；旧代码不能直接打开新数据库。回滚需匹配升级前代码、数据库和配置，并保留新数据供核对。本次设计不执行迁移或更改线上账号。
