# 实施与验证记录

日期：2026-10-09。实施前设计已提交：`4fd9565`（设计业务席位职责与总体席补充投递审批）。本文件记录本地验证；随后已按用户授权部署，实际线上准备见 [验收指南](../server-test-guide.md)。

## 实现内容

- 中央席位目录保存名称、职责和职责版本；提供总体、情报、筹划、态势四席位的配置与职责示例。管理脚本可独立更新职责，不重设密码，不迁移旧 A／B 工作区。
- 保留固定接收者；规则可开启补充建议并选择候选，候选职责只读展示。同一 Pi 作业使用 `information_suggest_recipients` 登记理由，不增加第二段 Router 模型调用。
- 成功分析按原规则固定投递；经原生记录核验的非空建议生成总体席待批准事项，后台资源随作业结束释放。
- 总体席查看原信息、分析、查询依据和建议，可调整名单后批准或不予补充。决定、幂等回执及待投递记录在一个 SQLite 事务内保存；批准复用原结果，投递失败可单独重试。
- 信息中心保留侧边栏，增加审批列表与详情；普通收件可查看自身接收原因。保存失败保留编辑，响应丢失后核对已存决定，审批和送达状态分开。
- SQLite 升级至 v5，Pi JSONL 继续保存分析正文和工具依据，未复制另一份聊天历史。

## 部署后如何人工测试

部署时先按 [README 的四席位配置步骤](../../../../experiments/harness-lab/README.md#四席位与补充投递审批) 开通四账号、加载职责、配置来源／资料授权及总体席 ID；先备份数据库和配置。不要隐式替换 A／B 的历史身份。这些步骤现已应用于独立四席位测试配置，旧 A／B 保留。

1. 总体席在“信息处理中心 → 处理与投递规则”选择情报席为固定接收者，开启补充建议，候选选筹划、态势席。
2. 使用既有模拟通知接入入口发送一条道路变化信息，等待处理成功。情报席应立即收件；总体席应出现待批准建议，候选席位此时没有新增收件。模型未登记有效建议时则只有固定投递，查看作业详情了解实际原因。
3. 总体席打开建议，核对分析和逐席位理由，可取消一个接收者、修改理由后批准。只给实际批准的席位补充投递，分析作业和模型调用数不增加。
4. 刷新或重新登录仍能查看决定及送达记录。收件人“为何收到”显示自己的理由。非指定总体席无法批准，即使有其他管理权限也不自动成为审批人。
5. 换一条消息测试“不予补充”：固定情报席收件保留，筹划、态势不增加收件。

以上是能力验证流程。若需要验证没有建议的情况，可发纯文字更正；模型是否确实判断无需补充须阅读实际结果，不预置成必然答案。
