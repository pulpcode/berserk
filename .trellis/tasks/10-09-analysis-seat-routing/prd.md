# 业务席位与补充投递审批

状态：**待审方案，未批准实施**。日期：2026-10-09。

## 1. 目标

建立总体席、情报席、筹划席、态势席的初步职责。在保留固定投递的基础上，由后台 Agent 根据分析提出补充接收建议，经总体席批准后发送。

来源规则负责明确常规接收方，Agent 帮助发现还需要知悉的席位，总体席决定是否扩大投递范围。本期仍是能力验证，初步席位划分不代表最终组织体系。

## 2. 席位定位

| 席位 | 初步职责 |
| --- | --- |
| 总体席（兼管理员席） | 公共任务管理、跨席位协调、工作分派与验收、补充投递审批；承担当前系统管理职责 |
| 情报席 | 信息来源、事实核实、可信性、矛盾和缺失信息、特情变化 |
| 筹划席 | 综合任务要求与情报、态势，编制和修订方案，提出处置建议 |
| 态势席 | 区域、对象、资源及行动的当前状态、变化和约束 |

职责不等于数据权限；管理员也不因此获得其他席位的私有工作区。席位不对应一名常驻 Agent，不要求某个外部系统只服务一个席位。工作区继续按“任务 × 席位”隔离。

## 3. 本期需求

| 编号 | 要求 | 验收 |
| --- | --- | --- |
| SR01 | 建立四类席位的统一名称和职责，规则引用席位目录；保留现有登录及工作区隔离 | RT01、RT02 |
| SR02 | 原有固定接收名单始终生效；规则可另开补充建议并限定候选范围 | RT03、RT04 |
| SR03 | 同一次 Pi 后台分析分别判断任务影响和补充接收席位，给出逐席位理由 | RT05、RT06 |
| SR04 | 成功分析的固定投递不等待审批；有效补充建议生成总体席的待批准事项 | RT05、RT07 |
| SR05 | 总体席查看原信息、分析、已固定投递对象及建议，批准、调整候选名单或不予补充 | RT07、RT08 |
| SR06 | 审批保存到数据库；离线及服务重启后可处理，不保持 Agent、容器或模型调用等待 | RT09 |
| SR07 | 批准后复用原结果和投递机制；不重复分析，不为每个接收席位复制分析会话 | RT10、RT11 |
| SR08 | 信息中心展示待批准事项、决定和逐席位送达情况；接收人能查看自身接收原因 | RT12、RT13 |
| SR09 | 未产生有效建议时，仅完成固定投递；不强制补调用、不自动重跑、不视为作业失败 | RT14 |
| SR10 | 失败、取消、中断、权限变化、重复操作及旧数据保持明确边界 | RT15、RT16 |

固定投递沿用现有条件：**后台作业成功且结果核验通过后**创建投递。这里不新增“原始消息先送达”或“失败也自动投递”的机制。

## 4. 审批的含义

批准的是“把这份分析补充提供给哪些席位”，不是为分析结论作正确性背书，也不是工作分派或任务执行批准。接收席位收到后可以查看、提问或使用既有办理流程，不自动启动该席位的 Agent。

审批人固定为本阶段配置的总体席，不由模型指定，不自动挑权限最高的账号，也不交给建议接收者自行批准。总体席可以调整名单，但只能选择该作业获准的候选席位。

一条信息可以关联多个任务并补充通知多个席位；任务关联不直接决定收件权限，也不要求分别分析多次。

## 5. 本期取舍

- 四类职责在席位目录统一维护；本期通过现有管理脚本扩展配置，页面展示和选择，不建设完整组织管理界面。
- Agent 使用同一后台作业的上下文和 Pi 多轮工具循环，不增加必经的独立 Router 模型请求。
- 所有收件人须有权读取同一份完整结果；不按席位生成不同正文。
- 每项成功分析最多形成一项补充投递审批；批准或不予补充后不重新打开。已送达内容不追溯撤回。
- 暂不开展单 Agent 与分阶段方案的对比实验；真实使用或验证发现分析效果不足后再研究拆分。

## 6. 边界与审阅

不建设完整组织权限平台、多级审批、审批自动转交、审批超时自动通过、任意后台暂停恢复、自动业务分派或接收方签收流程。模型判断仍可能漏选或误选，人工审批不能保证自动发现所有遗漏。
