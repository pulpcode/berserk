## BUG-001：跨席位分派没有实际交接附件

**现象与影响**

A 已读取初稿和修订要求。用户要求全部分派给 B 后，A 的分派说明引用了自己工作区中的文件路径，但 B 打开工作后无法读取原稿。分派本身成功，文件没有随工作交接，阻断后续修订。

**预期与复现路径**

1. A 在自己的任务工作区读取初稿和修订要求。
2. 下一轮用户只说“直接全部分派给 B 去执行”。
3. 核对实际工具参数、准备结果和确认卡片，再批准分派。
4. B 查看输入资料并导入文件。预期两份实际文件可用，内容与 A 交接的固定副本一致；无关文件不应随同交接。

这是自然语言失败样本，不保证模型每次都以相同方式遗漏参数。

**已确认原因**

- 实际 `work_item_prepare` 调用省略 `inputPaths`，文件路径只出现在 `goal` 中。
- 服务端只根据 `inputPaths` 保存交接文件，返回 `files: []`；正式工作中的 `inputFileIds`、`inputFiles` 也为空。
- A、B 的 `/workspace` 对应不同席位目录。分派目标中的路径不会自动传文件，单纯告知路径不能使 B 获得文件。
- 当时模型可见的工作区共享范围与交接参数说明不充分；确认页面也未明显显示零附件。
- 不能由单次轨迹断定模型内部究竟误解了目录关系，还是生成参数时遗漏。不能把 B 目录隔离本身记成故障。

**证据**

- A 会话：`df6de98a-982a-4b4c-8ab2-0ebedb06aed7`；B 会话：`01a0c7fa-c509-76f3-9b7e-73a8419c0ab5`。
- 分派操作：`3d5fdeec-3b91-4b42-83bc-8242da1a871a`；工作：`d8b1ac53-5bd8-44d2-bda5-62bb9bc9db15`。
- 详细调用与代码依据见 [原始核查](research/evidence.md)，已有修复及验证结果见 [实施与验收记录](verification.md)。

**当前处理与关闭条件**

已补充工作区隔离、交接参数和工具衔接说明，并展示实际附件。明确指定双附件的交接与回传已通过，但自然多轮验收仍未通过，不能记为彻底修复。后续新会话曾正确准备两份附件，但受 BUG-003 阻断，也不能替代完整交接验收。

- [ ] 原自然多轮与独立对照场景完成实际交接，B 导入的文件字节正确。
- [ ] 单附件、纯文字任务、无关文件排除及零附件展示符合既有验收要求。
- [ ] 保留全部真实评测结果，不以反复重试直至成功代替验收；确定性服务测试与真实模型评测分别记录。

原坏单保留；验证使用独立测试数据，避免旧工作和重复文件干扰新分派。不自动给历史工作补附件。

## BUG-002：文件检查命令使后台预处理因需要确认而失败

**现象与影响**

消息“【复测02】请修订值班交接说明（附初稿和修订要求）”的首次预处理读取资料后发起文件检查命令，命中人工确认规则。后台以 `HUMAN_ACTION_REQUIRED` 结束，该次作业没有产生可投递的成功结果。

**实际命令**

```bash
cd /workspace && ls -la && echo "---HASH---" && md5sum *.md && sha256sum *.md && echo "---WC---" && wc -l -c *.md
```

命令意图是列文件、计算校验值、统计行数和字节数，没有删除或覆盖操作。本次命令在执行前被拦截。

**已确认原因与复现路径**

- `evaluateCommand` 不跟踪 `cd` 后的目录状态，遇到 `cd` 返回待审；字面量解析不处理未引用的 `*.md` 通配符，也返回待审。
- 实际判定为 `decision: ask`、`ruleId: shell.review`、版本 `axon-bash-v1`，理由为“该命令含未支持或无法可靠分析的语法，需要人工检查。”
- Pi 宿主的 `beforeToolCall` 在后台请求遇到 `ask` 时直接终止请求，不创建可等待人员处理的前台确认流程。
- 给命令检查函数上述固定输入，并在后台执行适配中模拟同一调用，即可验证这条故障链，不需要依赖真实模型重新生成命令。

这是当前命令策略与后台文件处理需求的适配问题：代码按现有保守规则执行，不等于 Agent 发起了危险业务操作，也不是 Pi 原生强制要求确认。

**证据**

- 来源消息：`manual-document-revision-20260922-retest-02`；事件：`3064fba1-637a-45c4-b53a-d5c7d4353fcb`。
- 本次失败作业：`532e870b-8e32-458b-aebb-aeb1d78cfcc2`；会话：`47da015e-e2ef-4a0a-8ffb-bc93217aee5b`。
- 工具调用：`call_00_40aPtJjAgt789XPfpq1R6939`；原生会话位于 `LAB_DATA_DIR/background/jobs/<jobId>/sessions/`。
- 代码依据：[命令策略](../../../experiments/harness-lab/src/execution/command-policy.ts)中的 `literal`、`commandRule`、`evaluateCommand`；[Pi 宿主](../../../experiments/harness-lab/src/pi/lab.ts)中 `beforeToolCall` 的 `active.background` 分支。

**当前处理与关闭条件**

尚未修复。普通命令的可用范围及后台遇到待审操作时如何处理，需要先审定；不据此直接放行全部 `cd`、通配符或未知语法。上述“未投递”仅描述这次失败作业，不代表该消息后续其他作业的状态。

- [ ] 按审定策略覆盖该命令及相关文件检查场景，避免普通预处理无故被阻断。
- [ ] 确实需要确认或禁止的操作仍受控制，不因修复绕过权限边界。
- [ ] 后台仍需终止时，能够看出具体受阻操作和原因；失败作业不被当作成功结果投递。

## BUG-003：分派准备与确认跨轮衔接失败

**现象与影响**

席位 A 的新对话正确读取两份文件，并在分派准备中带上了两份实际附件。Agent 只调用 `work_item_prepare` 就结束回复，声称等待确认卡片；用户没有看到卡片。用户提醒后，Agent 在新一轮调用旧操作的 `work_item_commit`，卡片出现，用户批准后请求仍失败，新分派没有生效。

**已确认的调用顺序**

1. 17:56:07，`work_item_prepare` 返回准备结果，`files` 含两份文件；该轮没有调用 `work_item_commit` 就结束。
2. 用户说“你没有给我弹出卡片”，开始新一轮请求。
3. 17:56:34，新请求用上一轮的 `operationId` 调用 `work_item_commit`；系统创建确认卡片。
4. 17:56:42，用户批准，交互记录为 `approved`。
5. 后端校验准备操作与当前请求不一致，终止请求；最终提示“操作规则或交互记录不可用，已停止本次请求，未放行后续操作。”
6. 业务操作没有成功回执。数据库原始状态仍为 `prepared`，不代表它此时仍满足提交条件。

**原因**

- 模型漏掉第二个工具调用是触发因素。工具说明已要求继续调用 `commit`，但说明不能保证模型每次遵循；模型内部漏调用的原因未确定。
- 宿主将准备操作绑定到原请求，`checkAgent` 要求准备与批准提交的 `sessionId`、`requestId` 一致且原请求仍有效；跨轮补做不满足条件。
- 这项校验发生在 `waitForInteraction` 返回批准之后，而非展示卡片之前，使用户确认了当时已经不可提交的操作。
- 外层统一异常处理掩盖了“确认与当前请求不一致”的具体原因。

这是模型调用衔接与 Axon 宿主校验、错误处理共同暴露的问题，不是用户未批准，也不是本次附件再次漏传。

**证据与确定性复现**

- A 会话：`840eb803-147b-455f-941a-b53b5ad02f80`；操作：`b35a7754-1141-4ebb-b576-5f0ef554542e`。
- 准备请求：`87181f60-f6fe-4e4d-879f-2a73777b9ba2`；提交请求：`012af6a2-38a8-4dee-b421-2e2d082f8909`。
- 已批准交互：`1e862198-cec2-43e6-a7fa-1d9b8e686046`；原生会话位于 `LAB_DATA_DIR/sessions/`。
- 代码依据：[工具定义](../../../experiments/harness-lab/src/pi/collaboration-tools.ts)、[Pi 宿主](../../../experiments/harness-lab/src/pi/lab.ts)的 `beforeToolCall`、[交接服务](../../../experiments/harness-lab/src/collaboration/service.ts)的 `checkAgent`／`authorizeAgent`。
- 回归可固定模拟“请求一 prepare 后结束 → 请求二 commit 旧编号 → 批准”，不要求真实模型再次漏调用。

**当前处理与关闭条件**

尚未修复。“面向 Agent 合并准备与请求确认，由宿主完成内部衔接”是讨论中的修复方向，尚未批准或实施；本记录不放宽跨轮授权、不批准自动重试。

- [ ] 正常分派能够展示实际确认内容，批准后返回真实业务回执。
- [ ] 无效操作在展示卡片前被识别并给出明确后续处理方式；批准时仍检查可能变化的条件。
- [ ] 区分用户拒绝、操作失效和提交失败；拒绝或取消后不执行。
- [ ] 不复用旧批准、重复分派或通过伪造成功消除错误；两份附件随成功分派实际可交接。

旧工作仍存在、同一工作区有三组测试文件属于本次测试的干扰因素。后续回归使用隔离数据；这些因素不能代替上述已确认的请求校验原因。
