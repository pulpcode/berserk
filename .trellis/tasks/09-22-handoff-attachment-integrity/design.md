## 2. 工作区说明

在 `src/pi/lab.ts` 现有席位工作区说明处使用：

> 当前 `/workspace` 属于当前任务和当前席位。同一任务、同一席位的会话共享文件；不同席位的 `/workspace` 对应独立目录。

这段说明用于普通席位工作区。后台服务预处理继续使用既有的“仅属于本次服务预处理”说明，不把独立后台目录描述成共享席位目录，也不向只读 Agents 新增交接能力。

以下关系图供开发者理解，不作为额外模型提示：

```text
同一个业务任务
  A 工作区中的文件
      ↓ A 通过 inputPaths 选择
  准备时保存固定副本 → 用户确认后成为交接附件
      ↓ B 从实际 inputFiles 中选择，调用 handoff_import_file
  B 工作区中的普通文件，可用 read / bash 继续处理
```

共享目录规则集中放在工作区说明中；操作参数的含义放在对应工具及字段说明中，不将同一套规则重复追加到用户消息、AGENTS.md 或每轮提醒。

## 3. 工具说明

本次只调整现有说明及字段描述，不改变参数结构、必填性或执行逻辑。工作区范围在上一节说明一次；字段含义、调用衔接分别放在以下位置。

| 位置 | 拟用说明 |
| --- | --- |
| `assign.payload.goal` | 接收方需要完成的工作目标与交付要求。 |
| `assign.payload.inputPaths` | 随工作交接的当前工作区文件路径列表，准备时保存固定副本。无附件时可省略或传空数组。 |
| `handoff_import_file.fileId` | 已交接文件的编号，可从关联工作或工作详情取得，例如 `inputFiles[].fileId` 或 `submissions[].file.fileId`。 |

`work_item_prepare` 的工具说明改为：

> 准备分派（assign）、签收（claim）、提交文件（submit）或验收/退回（review）。assign/submit 的 workspaceId 使用当前工作区；claim/submit/review 的 expectedRevision 使用工作最新版本。保存准备内容，返回 operationId 和本次实际附件 files。核对交接内容后，用返回的 operationId 调用 work_item_commit 展示确认卡片并等待用户批准。对象或文件不明确时先澄清。

这段替换原说明，不追加在原来的“准备成功后立即 commit”等提醒之后。`work_item_commit` 的确认规则、`work_item_read` 的结果查询说明和导入工具的复制行为沿用现状。

开发约定：核对是阅读本次准备结果；正常路径不增加查询、重复读文件或再次询问用户的步骤。导入工具同时支持分派资料和提交成果，上下文已有有效文件引用时可直接使用。故障复现用语放在第 5 节，准备单失效及兼容边界放在第 6 节，均不展开成新的常驻模型提示。

## 4. 确认页面

聊天中的分派确认卡片和工作待办中的页面分派确认，都在长篇工作说明之前展示服务端 `files` 中的实际附件：

```text
本次附件：2 个
  值班交接说明_初稿.md    693 B    查看 / 下载
  修订要求.md             1 KB     查看 / 下载

工作说明
  ……
```

零附件时显示：

```text
本次附件：0 个
本次未附文件；在工作说明中写路径不会自动交接文件。
```

保留现有确认、拒绝／取消按钮，不增加第二次确认或强制勾选框。复用已有文件组件，不新增来源路径字段；源文件路径不代表 B 的导入路径。

B 的工作详情始终显示“输入资料（N 个）”，为空时显示“本次分派未附文件”。该提示针对分派资料，不根据签收、验收等操作自身的空 `files` 判断资料缺失。

## 5. 验证与后续判断

在隔离数据中保留修复前基线，再只修改工作区和工具说明，运行相同场景：A 先读取初稿和修订要求，下一轮仅说“直接全部分派给 B 去执行”。不在用户输入中提示 `inputPaths` 或解释内部交接方式。

工作区放入一份无关文件作对照。修改后使用三次独立会话，逐次核对实际调用、准备附件、用户批准后的工作输入和 B 导入字节；记录全部结果，失败轮次不能丢弃。另验证明确只交一份文件、纯文字分派及原有明确指定两份附件的场景。

对照场景使用不同文件名和任务要求，包含 B 提交成果后 A 导入的方向；不把原测试口语或文件名写入工具说明。效果以实际交接结果判断，不以模型复述规则或逐字匹配提示词判断。

| 结果 | 后续处理 |
| --- | --- |
| 原场景和对照通过 | 按此范围完成附件展示和既有机制回归，不追加参数约束。 |
| 仍漏选、少选或选错文件 | 记录实际请求上下文、调用参数及结果，分析是说明未生效、说明仍有歧义还是调用未遵循；提出最小补充方案供用户审阅后再扩展实现。 |

字段必填只能拦截省略字段，不能解决错误的 `[]`、少选或错选文件，因此不能代替上述验证。通过有限场景也不代表能够完全保证模型理解用户意图。

## 6. 执行边界与兼容

以下供实现与验证使用，不注入模型：

- 确认、文件访问权限和参数有效性仍由现有代码检查；正常流程沿用已有一次人工确认。
- 尚未提交的准备内容需要更正时，可按原机制重新准备；旧准备单沿用原有失效规则。
- 结果不确定时查询原操作回执。已提交的同一 `operationId` 只返回原回执，不能借重试修改附件；这一规则不禁止用户另行发起新的工作。
- 文件复制沿用现有“准备时保存副本、接收时按需导入”流程。页面查看和下载读取已有副本，不新增服务端复制环节。

现有 Agent／页面／存储共用的 `workPrepareSchema` 保持参数形状和可选性，仅可补充字段描述。旧准备记录允许省略附件参数，继续按原含义读取。Pi JSONL、准备单、业务回执和固定副本均不迁移。
