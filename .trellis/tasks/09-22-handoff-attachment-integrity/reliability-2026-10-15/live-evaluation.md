## 结果：操作与回答分开

**30 个固定样本已完成观察，没有修改产品代码、工具说明或模型提示。明确分派 13/20 实际成功，7/20 停在额外确认；不能称为流畅稳定。** 5/5 真歧义场景正确先问，后台 5/5 实际计算正确。实际成功的交接没有发现漏附件、附入无关文件、错席位、重复创建或固定字节不一致。

| 场景 | 主目标观察 | 回答准确性与边界 |
| --- | --- | --- |
| 原始多轮 | 2/5 完成分派和接收读取；3/5 额外确认未分派 | 已分派的结果陈述与回执一致；另三次前轮有轻微行数/声明行数误述。完整链见下一节 |
| 独立改写 | 3/5 完成分派和接收读取；2/5 额外确认未分派 | 一次误述签收角色及取回条件，一次 ID 后缀抄错，另有轻微声明行数误述 |
| 单附件 | 4/5 正确仅交初稿并读取；1/5 额外确认 | 一次误称 A 可以签收，部分回答把四行说三行；有意不附要求文件被描述成缺失，易诱发多余追问 |
| 纯文字 | 4/5 正确创建零附件工作；1/5 询问标题/措辞未分派 | 实际分派结果均如实；其中一次把交付目标写成直接回复文字，与正式 submit 要文件的闭环存在风险，后续未验证 |
| 真歧义 | 5/5 询问具体对象，无擅自分派 | 一次先猜“应为设备借用说明”后仍提问；不能把这个猜测当成已确定事实 |
| 后台文件检查 | 5/5 原完整命令获准执行；3份 Markdown 的 MD5、SHA256、LF数、字节数全部正确；各有两席位投递 | 3/5 未见明确错误；1次夸大 hash 核对范围，1次把 LF 数解释成只有一行正文 |

7 次未分派分别为 original-3/4/5、paraphrase-1/2、one-5、none-3：其中 5 次通过 ask_user 追加确认，2 次只在正文要求确认。测评驱动对问题保留后取消，取消不是宿主崩溃；没有回答“已完成分派”。正常业务确认卡已按真实清单批准，不将这一步计为额外救场。

具体实例：

1. **流程错误**（paraphrase-3）：A 已正确分派，却说“等 B 提交后我需要按流程签收或验收才能把修订稿取回”。实际 claim 属于 B，A 可以在 submitted 状态导入成果，无须先验收。one-4 同样提议 A “现在签收”。没有真的执行错误签收，错误在下一步解释。
2. **精确字段误抄**（paraphrase-4）：工具返回文件 ID 后缀 a475，正文写为 d475；真实文件及交接字节正确。
3. **内容解释错误**（background-4）：工具 read 返回 `# 检查乙\n第二行`，wc 返回 1 个 LF、21 字节。回答却说“乙只有一行（# 检查乙）”。文件有两段文本，末尾没有换行；程序统计正确，模型解释错误。
4. **核对范围扩大**（background-1）：正文说“4个文件……hash 与实际读取结果吻合”。命令仅对3个 Markdown 计算 hash，txt 只被读取正文，不能声称四个 hash 均已验证。
5. **不必要的确认**：none-3 已明确要求纯文字三条提醒、零附件，模型仍询问工作标题和目标措辞；original-3 已知道绿植文件无关，却要求再确认是否把它一起附上，因而没有分派。

各案例详细判读见 [live-answer-review.md](live-answer-review.md)。不把轻微行数错误、误导业务流程、没执行但如实说明混成一个“回答失败率”。本批没有发现“实际未分派却谎称分派成功”；这不等于所有正文准确。

## 完整链：仍未完成验收

原始多轮预设还包括 B 修订提交、A 读取成果与验收。本批仅两个样本进入该链：

## 七次额外确认的原因分析（实际上下文复核）

结论：模型把“补充业务信息”和“批准执行”混在一起，是未发起分派的直接原因；工具说明的动作边界不清是可能诱因。七次均未调用 work_item_action，尚未进入宿主业务确认或提交拒绝环节。不能归因为服务强制二次确认。

| 证据 | 观察 | 解释边界 |
| --- | --- | --- |
| one-5：用户已明确席位、唯一附件和修订要求 | ask_user 完整复述后只问“是否按此提交” | 没有新的必要业务信息，属于重复请求批准 |
| none-3：纯文字三条提醒、无需资料、不附文件 | 要用户选择普通标题并确认目标措辞 | 模型把可合理拟定的字段当成必须由用户补齐；title 必填不等于必须让用户命名 |
| original-3：模型已知道绿植文件无关 | 仍要求确认是否一并附上 | 已辨明无关资料却没有据此行动，不能说附件信息完全缺失 |
| original-4/5：已读取两份文件与修订要求 | 重新询问文件集合、产出范围及示例字段 | 泛化“先澄清”，把后续可决定的细节前置为分派条件 |
| paraphrase-1/2 | 重问旧条款如何修订、成果交回/验收方式 | 部分属于模型自行引入的分歧，不是当前 assign 的必要参数缺口 |

实际发送给模型的 work_item_action description 同时概括 assign/claim/submit/review，并统一写“工作编号与 expectedRevision 从工作详情取得；需要澄清的业务信息先询问”。但实际 schema 中 assign 只需 assigneeSeatId/title/goal/inputPaths，不需已有工作编号或 revision。多次轨迹先查空工作列表，再围绕“没有已有工作，需要新建”反复解释，与这种混写可能相关；不能仅据相关性认定唯一原因。

宿主上下文的提醒是“本会话尚未关联分派工作；如用户指的是已有工作，先查询，存在多个可能对象时询问”。这是条件句，模型在新建分派中也频繁套用了查找/确认习惯；说明不够聚焦，但不构成程序禁止新建。

反证也必须保留：实际 system 已明确“该调用内部核对内容、等待网页确认并执行”“ask_user 仅澄清对象，不授权提交”；ask_user 自身说明还写“不要用它申请操作授权”。因此不能归结为缺少这条说明，再追加同义提示就算定位修复。相同配置下其余13次成功，也说明不是一项必现协议障碍。

此外 original-5 的前轮回答自行提出“日期落在哪里、虚构示例字段需要确认”，下轮把这些自己的建议继续当成前提。历史对话中的自行设问放大了犹豫；来源实际要求虚构示例、其余排版自行决定。第一轮分析文字也会影响后续决策，不能只检查最后一句用户消息。

未进行工具说明消融或同上下文换模型对照，不能量化模型能力与信息表达各占多少责任。本次只记录证据与假设，不修改工具、上下文、Skill或prompt，也不据此要求重建宿主授权机制。
