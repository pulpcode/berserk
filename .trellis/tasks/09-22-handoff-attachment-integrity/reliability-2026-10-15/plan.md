## 2. D1：只修正工作交接异常结果的展示含义

证据：既有 Pi 故障测试中，commit 已保存 work/receipt，但返回时异常使 native tool execution=failed。当前折叠卡只写“执行失败”，详情标题“工具返回（未完成）”，容易把传输/工具失败当成业务未发生。

拟改动：

- 仅对 `handoff` 且已批准、工具 `failed` 的卡片，使用中性说明，例如“交接工具未正常返回，请查询原操作回执确认结果”。对应详情不再笼统称业务“未完成”。具体文案随 UI 审阅确定。
- 保留 succeeded/not_started/unknown 及批准状态的既有事实；不把所有失败改成成功，也不因查询结果改写原生 JSONL。
- 复用错误中已有 operationId、work_item_read 或页面已有查询路径。此次不新增自动回执查询、结果卡片、持久账本或补提交按钮。
- 不改 Bash 卡片，不让通用“已批准”承诺业务已提交。提交前失败和提交后返回异常都必须诚实展示。

预期文件：`src/web/InteractionCard.tsx`、现有 `tests/e2e/hitl.spec.ts` 与 `tests/e2e/handoff.spec.ts` 的最少新增断言；复用 `tests/pi/collaboration.test.ts` before/after 故障事实。先补业务已提交的真实本地服务故障与 UI 对照，再改文案；不能只用手造的成功卡片证明修复。

为什么仅写 prompt 不足：这是前端确定性标签，模型生成什么都不会改变该标签。为什么不做自动状态修复：当前问题是表达含义，不是缺失业务回执；自动改写原生失败将掩盖真实工具故障。

验收：提交前异常没有 work，提交后异常恰好一个 work，两者原生异常均保留；页面不声称已确认“未提交”，能看到具体工具信息；刷新/旧历史/其他动作标签无回归。无需数据迁移，回退只撤销展示和对应测试，不回滚业务数据。

## 3. D2：真实容器检查，先补证据

前置条件：一套可用且明确隔离的本地或获授权测试 Docker 环境。当前 daemon 不可用；不默认为生产服务器，也不把启动全局 Docker 服务或远程操作隐含在本轮授权里。

复用现有 execution/background fixtures 与原生 Pi；固定 provider 发出原问题中的命令，不调用付费模型，不增加产品工具。独立输入包括 Unicode/空格 Markdown 名、空文件、无末尾换行和无关 txt。命令不变，预期 hash 按 fixture 字节独立计算，`wc -l` 为 LF 数、`wc -c` 为字节数；核对原生返回、exitCode、每文件/total、job 与 delivery。另保留无匹配文件的非零结果和原有受限/解析错误边界。

不得拿 fake Docker 的 `OK` 当计算证据，不为 MD5/行数验收扩大生产能力。两后台模式分别核对；seat analysis 不应生成 preprocess delivery。若仍无法执行，保持“未执行”，不能关闭 BUG-002 的本轮真实计算验证项。

预期只改测试/探针入口，不改 policy/runtime。若固定命令确有执行缺陷，再凭失败提出单独最小修改，不先建设 inspect_files。

## 4. D3：自然场景评测；先冻结，不同时改 prompt 与模型

沿用 `scripts/probe-handoff.ts`、真实配置的目标模型和现有隔离文件流程。第一批保持当前产品工具/说明，以判断旧问题在当前版本的实际频率。默认候选目标为现有 DeepSeek Flash，最终以审阅时明确的实际模型与参数冻结；不默认切 Pro、升级 Pi 或开启另一种思考模式。

拟六类 × 五次 = 30 个独立场景：原始两轮、独立改写/不同文件名、仅单附件加无关文件、明确纯文字、真正有歧义资料指代、合法后台处理。每类保留 5 次全部结果；清晰交接场景要求 5/5，合理歧义要求澄清而非乱附。完整链与只检查主动作分开计数。

原始第二轮保留“直接全部分派给 B 去执行”。正常审批点击按实际准备内容核对，不算人工救场；“没弹卡片”“请用某工具”等额外提醒计失败。选错附件或收件人不得自动批准来凑完整链。后台与分派链是否关联以 fixture/现有能力为准，不自动投递工作或触发接收 Agent。

每次记录：首次有效工具、选片集合、准备/确认/批准、实际 receipt、receiver bytes、继续办理/提交/验收、工具自恢复、额外提醒、全部正文。接收方自动导入是宿主步骤，不强迫模型重复 import。成功写入与回答准确性分别评分。

**预算提议，尚未批准执行**：每场景最多 20 次 provider 调用、10 分钟；整批最多 600 次 provider 调用、累计 800 万输入 token / 30 万输出 token，任一上限达到即停止，未运行样本列未执行。限制仅属于隔离测评驱动，不改变产品默认参数；token 上限依实际 usage 到账后停止后续请求，单个在途调用可能越过阈值，费用也不能由 token 数直接保证。启动前需用户确认可接受的计费上限、凭据外发授权与隔离环境，再据此冻结最终预算；不重复索要 API key，不读取并打印密钥。

这批不承担“同时修 prompt”的效果归因。若失败，先按实际加载 context/schema/Skill 与回执定位，再另拟一项最小表达实验，保留本批为回归、独立新题不用于调优。不得一次改模型、工具、上下文再宣称单项有效。

- 两文件导入中第二份失败可能保留第一份正确文件，API 整体不返回成功；逐文件幂等仍是契约，不新增多文件回滚事务。

- 保留错误、取消、未知结果和没有发生的操作区别。无重复提交、越权或错误文件泄露是发布阻断条件。
