# Axon / berserk：可靠性修复任务书

编制日期：2026-10-15  
目标仓库：`pulpcode/berserk`  
用途：交给 Codex，在本地仓库完成证据核实、最小设计、实现与验收。  
状态：实施建议；不是当前 main 源码审计结论，也不是已经完成的修复。

## 0. 工作目标与执行方式

目标不是“让一次演示成功”，而是使分派、人工确认、文件交接及相关后台处理具有明确的成功条件和失败边界。

核心业务验收：发送席位先读取相关资料，用户在下一轮自然表达分派意图；系统产生真实、有效的确认交互；批准后创建正确工作；接收席位能读取选定的固定资料，继续办理并完成既有提交／验收流程。另行验证后台文件检查的合法路径。后台处理与主链路的关系以当前代码为准，不擅自增加自动执行或自动发送消息。

按两个审阅单元开展：

- **第一轮执行 P0—P1**：只做审计、基线检查、必要测试和最小设计；不修改业务实现，不部署，不执行付费模型评测。交付后形成一个设计审阅点。
- **第二轮按批准的 plan.md 执行 P2—P6**：逐项修改、验证、记录。遵循仓库已有审阅规则，不将本任务书视为放宽权限或扩大产品范围的授权。

本方案中的候选工具名、错误码、测试编号是设计建议，不是声称仓库已经存在。真实路径、函数和字段由 P0 核实。发现已有正确实现时复用；发现前提不成立时记录反证并调整方案，不为迎合本任务书修改正确代码。

## 1. 事实入口与范围

公开问题记录提供三条调查线索：附件参数遗漏、后台命令待审导致终止、准备与确认跨请求失配。它们可能是不同缺陷，也可能已被后续提交部分修复。Issue 状态不能代替对当前代码的判断。[S1—S3]

仓库约定要求优先复用 Pi，避免无依据地新增状态与恢复机制；阶段设计已描述固定文件副本、版本检查和操作回执，并明确后置完整 Run／恢复体系。[S4—S6]

### 必须阅读，但按关联范围展开

先读根目录及目标目录适用的 `AGENTS.md`、`.trellis/workflow.md`、相关 `.trellis/spec/`。不要假定某个 Trellis 命令在 Codex 中可用。

接着定位：

```text
.trellis/tasks/09-22-handoff-attachment-integrity/
.trellis/tasks/09-19-w01-8-task-handoff/
相关 Web 人工交互、后台执行和命令策略的任务／设计文档
experiments/harness-lab/ 的包配置、锁文件、测试入口和源码
```

这些是调查入口；若已迁移或归档，查找真实位置，不重新创建同名历史任务。

### 本轮不做

不更换 Pi，不升级模型／SDK／运行时作为默认修复，不建设第二套 Agent 循环、完整 Run 平台、通用操作账本、持久化恢复、消息队列或全局文件版本库。确有能力缺口时记录证据并单独提案。

不放宽跨请求授权，不复用旧批准，不自动给历史坏单补附件，不把未确认动作自动提交，不把未知执行结果自动重试成新的业务操作。不扩大 Bash 白名单以凑出通过结果。

不自动提交、推送、合并、部署或关闭线上 Issue；保留用户未提交修改，不执行破坏性 Git 清理，不修改生产业务记录。提交建议以中文为主体。仅覆盖桌面浏览器及其正常窄面板，不加入移动端改造。

不读取或输出密钥，不把原始用户资料和运行日志默认加入 Git。真实评测须有隔离环境、已授权凭据及明确预算；缺少条件时标记“未执行”，不能填“通过”。

## 2. P0：核实当前代码与故障链

### 2.1 固定真实基线

记录仓库根目录、当前分支、HEAD、main／origin/main 对应提交、工作区是否有未提交修改及其范围。允许联网且不影响现有工作的情况下更新远端引用；无法更新时注明引用的时效，不称为“最新 main”。不要直接切换或覆盖用户的工作分支。

检查最近约 60 次 main 提交，并向前追溯三类问题首次引入点；既看主线演进，也展开相关合并中的实际 diff。数量只是起点，不以固定数量替代相关性。记录：提交号、改动目的、真实改动、测试变化、缺陷关联，以及是否仅改了文档或提示词。

从包配置和仓库文档识别真实测试／构建命令，运行获准的本地基线检查，分别记录已有失败与本次新增失败。不要编造 `npm test` 等命令或在未了解副作用时启动脚本。

基线指纹至少包括：源码提交与工作区差异摘要、锁文件摘要、运行时和 Pi 版本、模型配置标识、权限策略版本。模型实际可见的 prompt／工具定义／Skill 加载情况按本地可获得证据记录；不为此次修复建设平台级快照系统。

### 2.2 建立三条真实调用链

定位工具 schema、注册入口、执行钩子、领域服务、持久化、确认卡片、后台调度适配、相关测试与错误映射。

检索线索可用 `work_item_prepare`、`work_item_commit`、`inputPaths`、`waitForInteraction`、`checkAgent`、`beforeToolCall`、`HUMAN_ACTION_REQUIRED`、`evaluateCommand`。名称变动时沿调用关系继续追踪。

每条链回答四个问题：

1. 模型实际上拿到什么工具和说明、传入了什么参数？
2. 哪个程序条件决定可执行、待审、失效或成功？
3. 真正业务效果和 UI／工具宣称是否一致？
4. 替换为固定工具调用脚本后，缺陷是否仍存在？

分别评估工具契约、宿主机制、运行环境／策略、运行时 prompt／Skill、开发流程／评测。区分“已经证实”“合理假设”“被反证”“证据缺失”，不能用模型主观动机解释所有故障。

输出一张证据表：`问题 → 历史修复 → 当前路径/函数/提交 → 复现 → 原因层级 → 最小改动 → 验证方法`。

### 2.3 检查已有保护为何没有生效

重点核实准备单、固定副本、revision、回执及失效条件是否已经实现；如果存在，优先追查校验时机、入口绕行、状态展示或覆盖缺失，不重复建设。

同时核对部署记录：只有源码 SHA、不含未提交差异时，不足以认定对应线上版本。此次仅据现有证据记录，不主动访问生产环境。

**P0 退出条件**：每个拟改动都有代码／测试依据；已明确当前哪些问题存在、哪些已修复、哪些无法复现。无法取得证据的部分保持待核实。

## 3. P1：先建立测试与最小设计

优先复用现有测试框架、交互替身、业务存储和文件测试夹具。新建隔离数据目录；不要复用历史坏单。

### 3.1 确定性测试

| 编号 | 场景 | 必须观察的结果 |
|---|---|---|
| C01 | 正常发起分派、批准 | 出现真实确认；生成一个正确工作及成功回执 |
| C02 | 请求 A 准备后结束，请求 B 使用旧编号 | 在展示可批准卡片前拒绝；不产生业务效果；原因明确 |
| C03 | 用户拒绝、取消或等待超时 | 不提交；等待和准备资源不被错误复用 |
| C04 | 请求停止／服务重启后处理旧批准 | 按现有失效规则拒绝；不恢复原写动作 |
| C05 | 双击批准、重复回调或提交响应丢失 | 同一已授权操作不产生重复效果；可按既有权限查询回执 |
| C06 | 两个操作基于同一旧业务版本提交 | 冲突明确，不能都覆盖成功 |
| C07 | 准备后源文件改变 | 执行对应已确认固定副本，不能静默换成新内容 |
| C08 | 固定副本缺失／损坏，或确认前后权限变化 | 不交付错误内容；分别在可发现的最早阶段拒绝 |
| A01 | 选定两份文件，目录另有无关文件 | 接收方实际字节一致；无关文件不交接 |
| A02 | 单附件、明确纯文字、遗漏附件字段 | 按批准的契约区分；不能把未表达选择静默当成已确认无附件 |
| A03 | 越界路径、符号链接逃逸、跨席位／项目读取 | 拒绝；不泄露对方路径或内容 |
| A04 | 接收方已有同名但不同内容文件 | 不静默覆盖；保留现有冲突处理 |
| B01 | 缺陷记录中的固定文件检查命令 | 判定及后台结果可重现；不依赖模型重新生成该命令 |
| B02 | 已批准的文件检查能力 | 计算结果正确，且可在目标后台模式中完成 |
| B03 | 仍需确认或禁止的后台动作 | 保持安全边界；失败不作为成功投递 |
| U01 | 桌面确认卡片、刷新、切席及结果展示 | UI 对应真实操作；其他席位不接收或批准该操作 |
| U02 | 页面直接确认与 Agent 确认入口 | 不相互借用准备单；页面不被迫多弹一次确认 |

这些编号用于覆盖追踪，不要求新增一套测试框架。先核实现有覆盖，再补缺口。已正确行为应作为保护测试，而非制造“红测”。

**重要区别**：服务测试能验证显式选定的附件如何传递，不能证明模型会从自然对话中选对附件。重放省略参数的轨迹是行为定位；若旧契约允许省略，不能假装旧服务违反了当时契约。新的拒绝规则须先在最小设计中明确。

### 3.2 最小设计审阅

在 `plan.md` 内对三个缺陷各写一个短决策：现有证据、复用机制、拟修改契约、为何更小方案不足、兼容处理、安全影响、测试与回退。

特别明确：是否增加 Agent 单次业务入口；附件字段怎样表达“明确不带资料”；后台哪些普通操作获准以及通过什么能力完成。不要只写“优化 prompt”“增强健壮性”。

**第一轮到此交付**：提交审计、基线测试结果、必要回归测试和最小设计供审阅。不能将“方案已写”记成缺陷已修复。

## 4. P2：先修确认生命周期与执行衔接

### 4.1 保留请求授权，修正校验时机

先修确定性的错误路径：操作在当前请求中已经失效，必须在展示确认前识别。用户批准之后仍复核可能变化的权限、业务 revision、取消状态与固定副本。

旧请求结束后，下一轮不得复用旧操作执行写动作。只能明确告知旧操作不可继续；确有新用户意图时重新准备、重新确认。不能为了消除 requestId 错误而删掉请求绑定。

错误采用现有错误结构表达可区分原因，例如“操作已失效”“业务版本冲突”“用户取消”。候选错误码可以映射到现有体系，不要求发明一套新框架。对未授权调用仍遵循既有防资源枚举规则，不能泄露对象是否存在。

### 4.2 优先方案：单次 Agent 业务入口

经审阅确认存在协议衔接缺口后，让 Agent 一次表达完整业务意图，由宿主在同一现有请求内串联：

```text
校验输入与身份
→ 复用现有准备服务与固定副本
→ 确认前检查
→ 复用现有 HITL 等待真实人工决定
→ 批准后复查
→ 既有业务事务与回执
→ 返回真实结果
```

候选名称如 `work_item_request`，以项目命名规范为准。内部 prepare／commit 可以保留；这不是自动批准，也不引入跨请求恢复。

接入前明确现有 Pi 工具钩子如何触发人工交互，保证真实 toolCallId、operationId、interactionId 和请求上下文一致。不能简单嵌套调用工具函数绕开钩子，也不能伪造一条旧 commit 调用记录。

新模型请求优先只暴露一种业务写入口，避免新旧协议同时竞争；历史 JSONL、页面接口和已提交回执的读取仍保持兼容。不通过给旧 prepare 隐式增加副作用来改变其原有含义。

先覆盖分派主问题。若共享入口同时服务签收、提交和验收／退回，必须补齐这些动作的兼容测试；不能只验证 assign 就发布共享修改。

### 4.3 成功、批准和未知结果分开

已有准备记录不等于当前可提交；用户批准不等于提交成功。UI 成功状态由宿主事实决定，而非助手文字决定。模型误称完成仍作为评测失败记录，不用关键词替换整段回复来掩盖。

同一 operationId 的去重、业务 revision 冲突、短事务和回执优先复用现有实现。返回已完成回执前同样先校验访问权限；返回回执不是授权重新执行旧操作。

业务已提交但 SSE／日志写入失败，不反向伪造“未发生”。结果不确定时查询既有回执；禁止生成新 operationId 自动补做。只对本轮宿主业务操作验证无重复效果，不宣称 Bash 或外部系统 exactly-once。

**P2 退出条件**：C01—C06、U01—U02 通过；已有跨请求及人工确认安全边界不变。无需让模型再次漏调工具即可证明旧故障路径已受控。

## 5. P3：修复附件选择契约与实际交接

### 5.1 显式表达选择，但不让宿主猜意图

优先复用现有 `inputPaths` 和固定副本，不新建文件注册平台。建议 Agent 新入口要求显式提供附件选择：非空列表表示选定文件；空列表明确表示不携带资料。是否需要额外判别字段，由真实工具 schema、模型提供方兼容性及现有页面接口决定，不盲目增加相互矛盾的字段。

“省略字段”和“明确无附件”不能静默等同。新契约应用于被批准修改的入口；老页面或历史格式通过清晰的兼容适配保留，不能全局改默认值导致其他路径退化。

但必填列表仍可能被模型填成空数组：这只能消除隐式默认，不能确定资料选择正确。系统没有可信的机器可读依据时，不凭正文出现文件名就武断拒绝，不扫描目录自动附全部文件，不假设前几轮读过的文件全部相关。

当存在明确的页面选择或已结构化业务输入时，可据此检查交接集合；仅有自然语言且对象不清时，使用现有澄清机制。清晰的原始复现场景不能靠追加一长串工具教学提示才能通过。

### 5.2 同一清单贯穿准备、确认与接收

确认卡片必须展示宿主实际选定的附件数和名称；零附件须明确可见，不能只复述模型写的 goal。服务端固定清单与执行引用一致，拒绝批准后替换接收方或文件集合。

准备后源文件改变时，继续使用已固定字节，或由用户取消后重新准备；不能静默换版本。传输／导入验收从接收席位出发，核对真正可读取的文件内容。

文件与数据库结果分开核实，不能拿“工作创建成功”代替附件可用。优先复用现有先完成副本、再提交业务引用的机制；不为此引入消息队列。部分副本失败不能留下对接收方可见的半成功工作。

导入保留既有授权、项目范围和同名冲突策略，不覆盖接收方已修改的文件，不把任何一方的 AGENTS.md、会话历史或无关资料随意复制过去。

**P3 退出条件**：C07—C08、A01—A04、确认卡片展示测试通过。语义选片是否可靠留待 P5—P6 真实评测，不能用服务层绿测关闭自然语言缺陷。

## 6. P4：给后台提供明确可用的文件处理路径

### 6.1 先判断是否真的需要新能力

复现 BUG-002 的原始命令和宿主拒绝分支，核实这些统计究竟是业务必需、既有元数据已可提供，还是 Agent 自发添加的非必要步骤。

优先复用交接／导入结果已有的大小、摘要和文件引用。确实缺少后台所需能力时，再增加或扩展一个范围受控的文件检查入口，而不是无证据增加整套工具。

### 6.2 优先采用受控检查，而非放宽自由 Shell

若有能力缺口，候选工具如 `inspect_files`，仅接收当前任务授权范围内的文件引用或经安全解析的路径，以及明确检查项目。可按实际需求提供大小、SHA-256、行数；不必实现全部。

实现复用安全文件访问原语，不在内部拼接并执行 Shell。限制文件数量、总字节、输出大小和运行时间。大小／hash 等应来自同一已打开文件对象或已固定字节；不能先检查路径再用未受控路径重开文件。

测试覆盖 Unicode／空格文件名、空文件、末尾无换行、缺失文件、超限、符号链接及跨范围访问。行数定义要固定并写测试，避免与已有工具语义不一致。

### 6.3 后台受阻必须是诚实的结果

运行时明确提供“前台可等待确认／后台不能等待确认”的能力信息，但不把能力描述当作权限执行器。

对明确允许的能力提供实际执行路径。对仍需人工决定的操作，保留拦截，并返回具体的操作、策略理由和合法后续方式。若现有 Pi 公开钩子能够安全返回工具级拒绝，可让模型在原有循环中选择允许的替代能力；若不支持，就保留明确失败。不能吞掉取消异常、伪造工具成功或另建循环来实现绕过。

不自动转前台审批，不自动恢复旧后台任务，不把失败作业当作成功投递。用户有新意图时如何重新发起，沿用已批准的当前产品流程。

### 6.4 对关闭条件必须诚实

“业务已能通过受控能力完成”不等于“原始复合 Bash 命令已获支持”。若仍保守拒绝原命令，应在审阅后的验收定义中明确这是替代能力方案；未经确认，不能偷偷改掉原 Issue 的验收目标。

若项目要求支持该类 Bash 语法，另列受限语法和安全验证方案，经审阅后实施；禁止用字符串白名单或整体放行未知语法代替安全分析。

**P4 退出条件**：B01—B03 通过；普通后台业务有获准路径；原命令是否支持、哪些操作仍受阻均明确记录。

## 7. P5：最后优化实际加载的 prompt、Skill 和工具描述

先区分开发用 Codex／Trellis Skill 与产品运行时 Skill。仓库里有文件，不代表故障那次模型实际加载了它。

采集最小必要的有效输入证据：系统指令来源、工具 schema、资源引用、实际加载 Skill 的标识及内容摘要、可见工具参数与结果。不采集或索要模型隐藏推理，不把日志变成业务状态源。

只针对证据显示的误解或遗漏修改：工作区隔离的含义、附件选择的语义、如何发起真实人工确认、工具状态与业务成功的区别、后台能使用的能力。协议已经合并时删除旧“先 prepare 再 commit”的冲突指引。

安全规则在运行机制里执行，提示词只解释。不要把数据库状态机、重试策略和授权恢复塞进 Skill；也不要把本任务书全文放进产品 prompt 或根 AGENTS.md。

机制修复完成后固定代码，比较描述／prompt 的变化；避免同时换模型、改工具、改上下文和改场景，导致无法归因。确需模型对照时单独实验，不能用新模型通过替代原目标模型的结果。

**P5 退出条件**：实际加载路径已核实，旧新说明无冲突，变更与失败轨迹有对应关系；不是仅凭“文字更严格”就声称提升可靠性。

## 8. P6：真实场景评测、独立审查与交付

### 8.1 预先固定场景和次数

复用已有评测脚手架。以下为建议验收集合，正式运行前写入 verification.md，不能看完结果后改规则。

| 场景 | 预期 |
|---|---|
| 原始多轮：先读两份资料，下一轮自然要求分派 | 正确携带相关资料，产生确认并完成真实交接 |
| 独立改写／不同文件名的对照 | 不依赖记住固定措辞或文件名 |
| 单附件，同时存在无关文件 | 仅交接指定资料 |
| 明确的纯文字任务 | 不附加无关文件，零附件展示清楚 |
| 资料指代确实不明确 | 适当澄清，不擅自附全部文件 |
| 合法后台文件处理 | 通过被批准的能力路径完成，真实产出可用 |

原始案例文字从仓库缺陷记录取得，不在调试后偷偷改成详细工具教程。另设不参与 prompt 调优的对照场景；调试集合与最终验收集合分开。

建议在获批预算内，每个场景独立运行 5 次；预算更低则执行批准次数并注明证据不足。每次使用隔离业务初态，保留全部轨迹。验收用例的次数上限和单次预算必须预先确定，禁止无限重试。

清晰主场景建议以 5/5 真实端到端完成作为本轮工程门槛；这是有限样本标准，不是统计意义上的可靠性保证。所有确定性安全测试必须通过，任何未授权动作、错误附件泄露或重复提交都阻止发布。

### 8.2 不只判断助手回复

分别记录：第一次有效工具选择、实际附件集合、确认是否产生、有效批准、业务回执、接收方可读取字节、后台实际结果，以及需要多少次额外人工提醒。

正常的审批点击是预期交互；“你没有弹卡片”之类额外提醒不能算无需救场的成功。模型在同一次运行内自行纠正参数可记录为最终成功，但必须同时记录首次失败与修正次数，不能只留下最后一次调用。

外部服务超时、配额和业务错误分别记录；不能把失败样本从总表里删除。未执行的真实模型／浏览器测试明确写“未执行”；只通过替身测试不等于真实模型通过。

每个缺陷独立给出结论：机制验证通过／自然场景通过／仍未解决／受阻待验证。BUG-003 修好，不自动关闭 BUG-001。

### 8.3 独立审查

在现有流程允许时另开审查会话或使用可用的审查能力，只读查看 diff、设计和测试证据；没有此能力时执行单独的审查步骤，不声称做过独立审核。

重点检查：越权路径、批准绑定、取消竞态、重复回调、成功后报告失败、附件清单替换、旧页面／历史兼容、后台失败投递、以修改断言代替修复，以及新增平台设施是否超出范围。

### 8.4 发布材料，不直接发布

交付精确测试命令及结果、改动清单、剩余风险、数据兼容性、回退步骤和建议提交拆分。数据库确需调整时，必须有备份及在副本上的兼容验证；不能删库重建换取测试通过。

建议按“确认机制”“附件契约”“后台能力”“运行时说明与最终验收”拆成可独立审阅的变更组。共享前提要注明；不要每组都混入所有层的改动。是否提交由用户决定，Trellis 自动提交保持关闭。

## 9. 过程文件与完成定义

遵循现有 Trellis 任务管理方式；能续用现有任务就续用，需要总任务时建立关联，不重复复制历史材料。

保留少量可续接文件，名称可按仓库规范调整：

```text
audit.md          基线、提交与故障证据链、已证实／假设／反证
plan.md           审阅后的最小设计、契约、范围与决策
progress.md       已完成、当前步骤、阻塞、下一条明确动作
verification.md   命令、固定场景、所有通过／失败／未执行结果
release-notes.md  兼容性、回退、剩余风险与发布前检查
```

原始评测日志按项目已有忽略／脱敏规则放在受控目录；报告只引用必要证据，不复制完整隐私资料。

会话变长时先更新 progress.md。下一会话以文件、实际 diff 和测试状态恢复工作，不凭聊天摘要猜测哪一步已完成。阶段报告简短说明“改了什么、怎样验证、哪里还未证实”，不要反复写长篇架构论证。

最终只有同时满足以下条件，才能建议进入发布审阅：

- 已批准范围内的确定性机制与安全回归通过。
- 目标自然场景按预定次数完成，或明确说明未达标并保持缺陷开放。
- 无自动补历史数据、复用旧批准、放宽权限或隐藏失败等旁路。
- 代码、实际加载的指令、工具定义与验证材料能够对应到同一基线。
- 原有页面、席位隔离、历史读取和相关业务动作未发生已知回归。

不能把“建议发布”写成“已经部署”，不能把“方案完成”写成“问题解决”。
