# 后台工具反馈与信息处理看板

状态：2026-09-23 用户已批准，实施中。

## 目标

修复普通文件检查命令的误拦；后台某次工具调用受阻时，允许 Pi 根据反馈继续处理。信息处理中心保留工作台侧边栏，用作业看板与详情展示收到的信息、执行经过和投递结果，支持有权限的人员核对原因并使用已有操作处理。

## 已确认问题

| 问题 | 依据 |
| --- | --- |
| `cd /workspace && ls -la` 等文件检查命令被判为待审，后台直接结束 | [BUG-002](../09-22-handoff-attachment-integrity/bugs.md)、[复测记录](../09-22-handoff-confirmation-flow/research/manual-retest-03.json) |

| 进入信息处理中心隐藏侧边栏，查看作业后还需返回工作台 | `web/main.tsx`、`web/InformationCenter.tsx` |

## 本期要求

| 编号 | 要求 |
| --- | --- |
| R1 | 在前台和后台共用的命令策略中修复已验证的误拦。普通文件检查可执行，其他命令仍按现有策略处理；区分已命中风险规则与语法无法判断，不把后者描述为已知危险。 |

## 使用过程

正常流程：收到初稿及要求 → 自动预处理 → 向规则指定席位投递答复 → A 在对话中分派 B → B 修订并提交。

工具受阻：某条命令未执行 → Pi 收到工具错误 → Agent 可使用获准方法继续。若模型或执行环境发生无法恢复的错误，作业按现有规则失败；人员在信息中心查看原因，在条件改变后明确重新处理。

**执行完成不代表业务目标已经达成。** Agent 正常结束但只说明资料不足、操作受限或部分完成时，本期仍按现有规则投递这份答复，由接收人员判断后续工作。页面不把它标成“任务完成”或“预处理成功”，也不根据正文关键词自动改判失败。

| 编号 | 可观察结果 | 对应要求 |

| A3 | 受阻后仅回复“无法完成”时，保留受阻记录与实际答复，状态显示“执行完成”，按原规则投递；不宣称受阻命令已执行或业务目标已达成。 | R3 |
| A4 | 技术失败、取消和中断保持对应状态；没有成功执行证据时不新增结果投递，不自动重跑。历史失败不改写。 | R3 |
| A5 | 修复环境后，管理人员重新预处理产生新作业，保留旧作业及其规则快照；投递重试不运行模型。 | R4 |
| A6 | 侧边栏常驻；可直接切换对话、收件与信息中心，草稿和流式执行不丢失。看板筛选、各列数量、分页与详情一致。 | R5、R6 |
| A7 | 同一信息先成功投递、后重新处理失败时，明确展示两次作业各自的执行和投递状态；不拼成一次“失败但投递成功”。 | R3、R5 |
| A8 | 刷新、深链和前进后退保留定位；关闭详情回到原卡片。无权人员不可管理来源或读取其他席位私有分析内容。 | R5、R6 |
| A9 | 独立测试数据完成“消息接入 → 预处理 → A 分派 → B 读取附件并修订 → 提交 A”，保留真实轨迹；不以反复重试代替失败分析。 | R1—R6 |

## 边界

本期不新增后台审批等待、`request_handoff` 工具、`blocked` 状态、接手投递或自动转为席位前台工作的流程；不恢复旧工具调用，不自动批准或重新处理。失败预处理仍需来源管理人员核对，不能直接通过新接手按钮取走输入。

不增加业务完成度模型判断、命令安全判断模型、业务流程提示、通用 Run 平台或新的固定调用限额。Pi、Docker 隔离、原生历史、文件副本及现有来源权限继续使用；后台仍不提供正式协作写工具、指令修改或交互式 ask_user。

命令检查不等于完整的操作效果控制。当前 Python／Node 文件脚本及可写文件工具仍可修改工作区，Docker 不保护可写目录免于这些修改；本期不承诺所有删除、覆盖行为都经过确认。权限体系的进一步完善单独记录为 [PERM-001](issues.md)，后续审定。
