# 信息处理页面设计依据

本文件记录当前代码证据和拟议交互，仅用于方案审阅，尚未实施。

## 当前导航与可用操作

- 信息处理中心仍在同一个 React App 中。`experiments/harness-lab/src/web/main.tsx:268` 主动隐藏左侧栏，`:283` 隐藏工作区，`:351` 单独渲染信息中心；`src/web/styles.css:678` 让信息中心占满两列。因此才需要 `src/web/InformationCenter.tsx:55` 的“返回工作台”。隐藏侧栏并非技术或权限要求。
- 中心保留“信息记录、后台作业、处理与投递规则”三个栏目，见 `src/web/InformationCenter.tsx:57`。入口按获准来源显示，见 `src/web/main.tsx:280`；服务端继续按来源检查查看、管理权限，见 `src/background/service.ts:76`。
- 失败预处理当前提供“重新预处理”；“进入关联对话”仅供席位分析使用，见 `src/web/InformationCenter.tsx:79`。本次保留这些已有人工操作，不增加从失败预处理转入新接手流程的按钮。
- “收到的信息”已有任务、目标、资料选择和“进入对话分析”，见 `src/web/Inbox.tsx:95`；创建会话后的草稿、文件引用和导航见 `src/web/main.tsx:228`。收件接口只接受本人已送达记录，见 `src/background/service.ts:180`；本次不为失败预处理新增收件记录或接手投递。

## 拟议页面关系

左侧导航在对话、收到的信息和信息处理中心之间保持常驻；点击导航只切换右侧内容，不再要求先“返回工作台”。继续使用既有登录、来源权限和路由，保留会话草稿及当前选择。

信息处理中心保留三个栏目：

| 栏目 | 展示与操作 |
| --- | --- |
| 信息记录 | 保留接收记录和原始附件；分别显示各次预处理及分席位投递结果，便于核对一条信息的处理经过 |
| 后台作业 | 增加按现有作业状态组织的看板，保留列表；卡片显示任务、来源、当前状态与异常原因。点击打开详情抽屉，查看过程、文件及已有获准操作 |
| 处理与投递规则 | 保留当前配置入口，不把配置表单混进作业卡片 |

看板每张卡对应一次后台作业，使用现有 queued、running、succeeded、failed、cancelled、interrupted 状态组织列；具体分组合并由主设计确定，**不增加“需人工接手”列或 blocked 状态**。各列按相同筛选条件独立分页并显示服务器计数，不把全局第一页拆成列后视为全部记录。

作业详情抽屉集中提供已有可用操作，处理人员不必为查看卡片详情离开看板。保留筛选、滚动位置、深链及返回焦点，不通过拖拽任意改写运行终态。异常详情展示实际原因，管理人员可明确发起已有的“重新预处理”；不会因打开详情自动重新执行。

## 状态与权限边界

- **执行完成不等于信息送达，也不代表业务目标达成。** 执行结果与各席位投递结果按具体 jobId 分别展示；前一次成功投递不能与后一次失败预处理混成同一次执行结果。
- 重新预处理沿用创建新作业的现有行为，旧状态、错误与记录保留；如实展示模型答复，包括部分完成或无法完成的说明；执行完成标签不评价目标达成。只重试投递仍不运行模型。
- 本期不增加 `request_handoff`、接手投递、新接手按钮或接手会话进度。后台审批受阻的执行反馈由主设计说明，页面不推测接手状态。
- 中心权限与席位会话权限继续分开。中心查看者可以观察获准来源的预处理，以及其他席位分析的办理状态；不能因此查看他人的 `seat_analysis` 私密正文、文件及会话。当前边界见 `src/background/service.ts:212` 至 `:224`，新的看板和抽屉应沿用。

命令误拦修复发生在前台、后台共用的命令策略中，不新增页面专用的放行或审批入口。
