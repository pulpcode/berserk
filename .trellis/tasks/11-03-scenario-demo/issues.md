# 后续 Issue

## SIM-DOMAIN-001：按管理域拆分模拟服务，明确权威数据与态势汇集职责

记录日期：2026-11-03。状态：待后续建设；本虚拟剧本演示阶段不实施完整拆分。

本项已记为仓库内 issue，尚未同步 GitHub。记录时 GitHub 连接请求失败，本机也无 gh 命令；未创建远程 issue 或虚构远程编号。

### 用户要求与背景

用户要求后续更贴近真实系统建设，服务按照管理域拆分。此前将车辆基础资料、位置和可用状态全部归入“态势系统”是演示上的简化；这会掩盖数据维护责任和跨系统融合过程。

现有模拟服务将 reportData、objectData、changes、actions 等共同保存为场景快照，见 experiments/harness-lab/scripts/mock-context/server.ts 与 persistence.ts。后续应从真实业务责任确定服务边界，再决定部署粒度。

### 拟拆分的管理域

| 管理域 | 权威数据/写入责任 | 对外协作 |
| --- | --- | --- |
| 装备资产与维保 | 车辆身份、归属、车型能力、故障检修及履历 | 提供资源能力与技术状态 |
| 车辆动态与定位 | 位置、速度、航向、轨迹、设备报告时间与在线情况 | 提供观测，不代替任务可用性判断 |
| 勤务与调度 | 值守/人员条件、任务占用、调派、出发、到场、归队、释放 | 维护执行和占用事实，校验资源争用 |
| 接报与情报 | 原始来报、核实报告、来源、修订、业务时间与接收时间 | 提供事实线索与相互矛盾的信息 |
| 地理与环境 | 道路、区域、水源及其状态 | 提供地理条件与变更 |
| 综合态势 | 汇集上述数据形成可查询、可追溯的视图 | 原始事实回到各自管理域维护；展示派生结论与依据 |

这是后续拆分的候选边界，不将本表当作所有消防系统的统一标准。尤其要再审阅资产/维保、勤务/调度是否分别形成独立服务。

### 后续建设要求

1. 明确每个字段的权威来源、责任主体、更新入口、时间语义和对外接口，允许按域独立对接、替换与演进。
2. 区分“车况正常”“定位在线”“未被占用”“满足本任务条件”；综合可用性保留判断依据和未知项。
3. 建立跨域实体标识映射与版本/时效规则，不凭名称、同坐标或相同字符串合并身份。
4. 态势汇集保留来源与修订；支持单域延迟、故障、权限变化时的诚实降级。
5. 提供从当前场景快照迁移的方案，保留旧场景、接口兼容和历史证据。
6. 按管理域拆分职责与服务接口；独立进程、数据库及部署方式在启动本 issue 时审阅，不以部署容器数量代替领域拆分。

### 关闭标准

- 各域权威数据、服务接口、依赖与写入权限有明确设计并经审阅。
- 修改维保记录、定位上报和调度占用分别只经过对应管理域；综合态势能正确汇集。
- 单域不可用时能指出缺失依据，不将状态未知变为可出动；同车跨域身份可追踪。
- 存量场景与跨域更新、延迟、冲突、重启和权限回归通过，迁移及回退可验证。

### 七类系统设计后延（2026-11-05，用户已明确）

七类模拟系统设计作为本 issue 的后续候选内容保留，**不列入本期目标**：警情信息、装备资产与维保、勤务调度、车辆定位、道路交通、基础地理与设施、综合态势。完整候选设计见 [后续七类系统资料](research/external-systems-domain-proposal.md)。系统职责、字段权威来源、跨域实体映射、聚合授权及来源能力描述/Agent 与 Skill 适配均随本 issue 后续审阅。

本期继续沿用 intel / situation 双系统、现有报告/对象查询能力和模拟接入设定。不扩为七类逻辑系统，也不做物理服务拆分；固定双来源限制、通用提示词及 Skill 不为本 issue 提前改造。

用户已确认的“来源身份跨场景复用”和“业务来报去除控场说明”由 [本期有限调整方案](external-systems-design.md) 承接。本 issue 仍待后续建设，不能以本期改名或清理文案宣称完成域拆分。

### 本期关系

本期场景建设先复用一个模拟服务，数据仍需保留身份、事实时间、来源和用途，执行占用与态势展示职责要明确。完整管理域服务拆分不作为演示前置条件，后续安排见 implement.md。


## SIM-NOTICE-001：外部模拟来报移除作者预设的任务编号提示

记录日期：2026-11-05。状态：本期有限调整已实现并通过本地验收，未上线，待部署验证；新版本报告/通知已清理，旧历史原文不追改。本项沿用仓库内issue记录，未同步GitHub。

### 问题与依据

当前发送的SimulationNotification不含Axon任务ID，但部分预设报告正文含“T02交通救援”“T03已批准演练”等作者任务编号，生成通知时会带入报告摘要。这会提前提示剧本预设的任务关系，削弱外部来源只提供业务事实、接收侧判断任务影响的演示真实性。

依据：`experiments/harness-lab/scripts/mock-context/scenarios/data.ts`中E02、E03、E11的文案，以及由报告摘要生成通知正文的逻辑。导演侧T01/T02/T03定义与每轮实际taskId映射属于控场与任务初始化，不等于外部来报内容。

### 目标确认（2026-11-05）

用户认可业务来报口吻，保留地点、车辆、观测时间及修订等事实，移除“模拟场景”“投放时”和作者任务编号等控场说明。沿用现有特情/态势双系统和事件来源分配，具体兼容方向见 external-systems-design.md；目标确认时仅更新方案；现已按后续“开始实施”授权修改新版本样例，历史证据未改动。

### 本期处理范围

- 将普通来源报告和通知中的作者预设任务编号改为自然业务描述，如“城西交通救援仍在处置，相关车辆尚未释放”。不直接塞入Axon taskId或剧本预设的关联答案。
- 保留地点、车辆标识、来源对象/报告引用、观测时间、修订和场景时间等事实与溯源信息，供接收侧依据实际资料判断任务关联。
- 区分作者内部编号与真实外部系统可能提供的业务编号；不一概删除合法外部业务引用。导演侧任务编号与每轮映射可继续保留。
- 不追改已接收通知或固定历史证据，不据此自动新增投放、分析规则或任务关联机制；历史兼容与新轮数据生效方式在实施时核对。

### 关闭标准

1. 普通来源可读的报告标题、摘要、正文及投放通知均不再含作者T01/T02/T03提示或预先填入的Axon任务关联。
2. 车辆占用、道路限制、位置及时间等事实保持完整；仍能依据这些事实核验一个事件对多个任务的影响。
3. 导演任务准备、逐条投放、来源查询和历史回读回归通过；不以文本移除代替任务关联能力验收。


## SIM-TASK-001：将总体席判断并新建任务纳入场景剧本与测试

记录日期：2026-11-05。状态：待后续修改场景剧本；用户要求先记issue。本项沿用仓库内issue记录，未同步GitHub；当前不修改剧本、任务初始化、处理规则、产品代码或线上服务。

### 问题与目标

当前导演准备演示时，由后台按模板预建T01/T02/T03。这样可以验证已有任务内的研判与协作，却跳过了“是否需要新建任务”的业务判断。用户要求将新建任务本身纳入测试。

目标流程：**突发消息进入 → 按已启用规则由后台Agent初步分析 → 总体席查看信息及处理结果 → 决定新建公共任务空间 → 关联原消息/分析结果，开展任务协作。**

### 后续剧本修改范围

- 至少设置一条目标任务尚不存在的突发消息；导演负责准备背景和投放事件，不替总体席提前创建该测试任务。背景业务和已有任务仍可保留，具体初始化安排后续审阅。
- 初步分析不以已有任务为前提；Agent可以建议新建任务，由有权限的总体席确认，不因收到一条消息就自动建任务。
- 保留“关联已有任务”或“无需新建”的判断空间，避免剧本把每条消息的任务归属或新建结论写成答案；与SIM-NOTICE-001协同。
- 任务创建后保留触发消息、处理结果及创建决定的关联，任务和后续会话/资料继承本轮归属；重复提交与重新演示不产生错误的重复任务或串轮关联。
- 手动创建不显示或选择轮次；无来源消息的直接新建任务如何取得归属，以及跨轮提交如何处理，待`SIM-TASK-002`后续确定。用户已撤回隐藏页面上下文方式，不以该方式作为剧本修改或测试的前提。
- 后续实施时再审阅自动处理规则、投递给总体席的配置与测试方式；本次记录不启用规则或执行模型测试。

### 关闭标准

1. 剧本至少完整覆盖一次“先收到消息和分析结果，再由总体席新建任务”，该目标任务在投放前未被导演预建。
2. 无既有任务时仍可接收、初步分析并展示信息；新建任务由人员确认，相关权限、重复提交和取消路径可验证。
3. 新建任务能回溯触发消息及处理结果，并可进入后续协作；任务关联与本轮隔离检查通过。
4. 更新剧本和验收记录，保留无关背景信息及原历史证据，不把模板预建任务当作新建任务流程已通过。

### 与当前建设的关系

本项后续安排，不改变当前待审阅轮次隔离方案的实施范围，也不在本轮替换既有三任务准备机制。未来调整须复用任务创建权限、原生工作区和轮次归属约束。
