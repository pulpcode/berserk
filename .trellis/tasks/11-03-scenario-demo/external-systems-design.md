# 双系统来源与业务来报调整方案

版本：v0.3｜2026-11-05｜已按用户“开始实施”完成本地实现与回归；尚未上线。

## 1. 本期目标

沿用现有特情系统（intel）与态势系统（situation），修正来源身份/名称与来报内容中的演示控制信息。七类系统、管理域拆分及配套 Agent 能力体系扩展移至 SIM-DOMAIN-001；后续设计资料见 [七类系统候选方案](research/external-systems-domain-proposal.md)。

本期约束：

- 同一外部系统跨场景/轮次复用身份；场景通过既有配置选用来源，不变成一个新来源。
- 来报使用业务口吻，保留事实、合法引用、观测/有效时间与报告修订，不预填任务关联答案。
- 控制用轮次归属与业务时间机制继续有效；不通过清理文字削弱隔离、溯源或去重。

用户已批准收敛后的有限范围实施；现仅新版本业务报告/通知和示例来源显示名称完成修改，旧历史不追改。下文保留需求与上线约束，验证记录见实施子任务。

## 2. 当前核对结果

| 项目 | 当前实现 | 本期处理 |
| --- | --- | --- |
| 系统身份 | intel / situation 固定；通知目标按 systemId 选择配置好的 sourceId | 复用并验证，不重新设计来源注册 |
| 消息接入 | sourceId 代表接入通道，sourceMessageId 代表单条投递；轮次单独核验 | 保留现有标识和受信任核验 |
| 显示名称 | 示例配置中有“临港场景接报来源”“场景态势通知”；线上列表也出现带场景名的来源 | 统一按外部系统命名 |
| 业务正文 | 报告/通知仍含 T02/T03、模拟场景编号、投放时刻及部分演示解释 | 在新版本样例的业务内容中清理 |
| Agent 使用 | 通用提示词和 Skills 主要依赖现有报告/对象查询工具，系统名单动态来自授权配置 | 沿用现有工具与方法，不新增七系统说明或工具 |

依据：fixtures/scenario-demo 三份 example.json；scripts/mock-context/scenarios/control.ts 的 targets 映射；data.ts 的报告/通知生成；store.ts 的稳定投递编号。当前没有每轮动态注册新来源的问题，不能把名称中的“场景”误判为身份注册机制需要重写。

## 3. 来源身份与名称

### 保留双系统

| 业务显示名称 | 现有 systemId | 本期仍承担的范围 |
| --- | --- | --- |
| 特情系统 | intel | 报告、现场来报、核实及续报 |
| 态势系统 | situation | 车辆/资源、位置、道路、区域及变化查询 |

暂时接受状态、档案和位置等集中在态势系统这一现有简化，不在本期拆分其权威数据职责。

### 有限改动

1. 来源列表、消息详情/待办、筛选、规则配置及查询目录中，对应系统统一使用“特情系统”“态势系统”。来源名称不含临港、某剧本、演示轮次或“场景通知”。
2. 场景名称仅保留在导演台、场景定义和控制记录中；报告渠道/报告人可以写在业务详情中，不替代外部系统身份。
3. 同一部署中的新场景和新轮继续复用已有 systemId → sourceId 映射及凭据。技术 sourceId 可保留历史命名，不做全局字符串改名、旧通道合并或接收记录迁移；既有隔离验证通道不据此自动合并。
4. 不因来源名称调整改变权限、后台处理规则或接收席位。不同环境可有不同接入配置，不把部署通道差异当成按故事注册来源。

## 4. 来报内容怎样调整

修改对象为新版本样例的业务报告标题、摘要、正文及投递通知。导演侧步骤名、控场描述、T01/T02/T03 模板编号和初始化映射可以保留，不做无差别替换。

| 当前表达类型 | 本期调整原则 |
| --- | --- |
| “模拟场景 run-…”“投放时场景时间…” | 从新业务正文去掉；轮次与时钟仍通过既有元数据、snapshotClock 和工具说明提供 |
| “T02交通救援仍在处置” | 改为“城西交通救援仍在处置”，保留原车辆、地点、占用与时间事实 |
| “T03已批准演练” | 使用具体演练名称和占用事实，去掉作者任务代号 |
| “本报告不证明本系统完成调派”“该记录不修改后续事实”等作者解释 | 用业务报告表达观测内容；事实解释与判断规则由已有工具/Skill 承担，不把剧本答案写进来报 |
| 地点、车号、来源报告/对象引用、修订、观测/发布时间、有效区间 | 保留；合法外部业务编号不等于作者任务编号，不能一概删除 |

例如：特情系统发送“临港仓库烟情首报”；正文描述烟情和位置待核实。仍可附已存在的报告引用、修订与观测时间，不能为了自然口吻失去可核对依据。

导演步骤“旧巡查报告晚到”可以保留作控场提示；业务报告可以使用“中轴桥巡查情况”，以原观测与发布时间体现先后，不用作者解释替 Agent 判断。具体改写须保持原事实与既有事件顺序。

不顺带改变事件归属：继续使用现有 intel/situation 分配，不按后续七类系统重排投放。维持六站二十四车、背景业务、十二步/十三条通知、旧观测晚到及两个演示模式；不新增剧情事件、调派或到场事实。

## 5. 保留的技术边界

- 不更换 sourceId、systemId、对象/报告 ID 或已保存消息 ID；每轮投递仍唯一、同一次重试仍稳定，去重仍按原协议工作。
- scenarioInstanceId、来源核验、工作区/任务继承、结束门禁、原生上下文及历史只读机制保持；去掉正文轮次字样不等于去掉归属。
- 业务观测/有效时间与真实接收/查询时间分别保留；不得删掉 snapshotClock，也不让 Agent 改用现实时间判断有效期。
- 已接收消息、回执、payloadHash、来源原始记录与 Pi JSONL 不追改；新内容走新场景版本。旧记录沿用现有兼容投影，不对冻结证据做全文替换。
- 本期不把列表技术编号隐藏、换新业务编号等额外 UI 建议一并实施；该建议不作为本次验收条件。
- 不改主 system prompt、Skill 方法或工具契约来介绍新领域系统；必要的名称变化由现有动态授权目录体现。

## 6. 拟实施与检查顺序

1. 核对仓库样例及实际部署中的双系统显示名称与固定映射，列出需要改名的配置，不动凭据和既有 ID。
2. 修订新版本报告/通知文案，区分导演说明和业务事实；核对合法引用、时间、未知与占用均未丢失。
3. 为内容变更更新场景版本/hash，验证原历史可读、新演示使用新文案，保持既有来源核验与回执契约。
4. 回归双系统查询、事件投递、原消息重试、旧消息晚到、轮次切换及业务显示。源码/契约未改动的部分不顺带重构，不开展付费模型验收。
5. 部署与新演示启用另按实际操作授权执行；不自动终止当前演示、重置数据、投放事件或启用后台规则。

## 7. 验收标准

- 新旧两个场景/轮次使用同一组预配置来源身份，来源显示为“特情系统”“态势系统”，不出现某场景名。
- 新报告标题、摘要、正文和通知不含演示控场说明、作者 T01/T02/T03 或预填的 Axon 任务关联；合法对象/报告引用保留。
- 业务口吻变化不改变原地点、车号、事实状态、观测/有效时间、修订、事件先后、数量和背景业务。
- 既有工具仍能查询同一双系统；不新增域系统、来源发现框架或模型工具。
- 同轮重试回原回执；新轮投递不碰撞；迟到记录与跨轮访问保持隔离，历史原始证据保持不变。
