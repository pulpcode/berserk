# 多轮演示隔离与重新演示方案

版本：v0.4｜2026-11-05｜**用户已授权提交并实施已明确范围；SIM-TASK-002继续待定**。

本文件承接[导演台查看与控场边界调整](../11-04-scenario-demo-m1/director-history-adjustment.md)。用户于2026-11-05要求“提交方案git，然后开始实施”；先提交本设计基线及issue，再实施已明确范围。SIM-TASK-002与已撤回的隐藏页面上下文方式继续不实施，不启用自动分析规则或执行付费模型批次。

## 1. 先看结论

本期聚焦**轮次隔离与重新演示**：A完整执行后，或在中途中断后，都可以结束A、创建新轮B，从所选场景的初始状态开始。

- 每次重新演示都创建新的轮次、任务和上下文，即使采用同一个剧本，也不复用旧轮身份。
- 导演发起一次重新演示，后台统一处理；各席位更新展示范围，旧记录保留，不逐席改写历史。
- 消息、任务、作业、会话和查询结果明确归属哪一轮；Agent只获得本轮需要的业务资料。
- **轮次仅在导演台和后台控制中体现**；业务席不选择、不填写轮次，也不因任务创建而看到演示/普通业务的选择。
- 无来源消息的手动任务如何确定归属尚未定案，见`SIM-TASK-002`；上一版“页面取得隐藏上下文、请求自动携带”的方式已撤回，不能据此实施。
- 历史轮次本期只读，不提供切回继续、从中断位置执行或根据历史记录再次执行的入口。
- 保留以后建设历史轮次执行的可能性，但不提前建设挂起状态、恢复专用快照、恢复接口或恢复按钮。

**“重新演示”保持结束旧轮、创建新轮的含义，不改为默认挂起旧轮。**

## 2. 本期范围

| 纳入本期 | 后续建设 |
| --- | --- |
| 消息、任务、作业、会话、查询及结果的轮次归属 | 历史轮次继续、恢复或重新执行，优先级较低 |
| A完整执行后→新建B；A中途中断→新建B | 可恢复挂起、跨场景版本恢复、历史快照执行 |
| 各席位按轮展示，旧页面防误操作，历史只读 | 多个演示同时运行、跨轮汇总与资料复制 |
| 既有普通后台分析、持续研判、前台对话的隔离适配 | 场景自动研判规则正式开通及模型语义验收 |
| 重新演示过程中丢响应、重启及未确认操作的核对 | 结构化方案卡、审批、车辆执行和移动 |
| 历史兼容及确定性联调验收 | 管理域拆分、真实外部调度接入 |

本期适配Agent通路，不因此创建处理规则或增加执行授权。原有场景模式和停止点保持，完整执行不代表新增后续方案审批、车辆到场能力；工程验收使用替身，不自动开展付费模型批次。

## 3. 现状与差距

| 当前已有 | 本期还缺什么 |
| --- | --- |
| 每轮有独立编号、场景时间、对象/报告/通知编号 | 消息接收、作业和会话的完整轮次绑定 |
| 单一活动演示、请求去重、旧任务归档及旧轮冻结 | 中途结束时对排队、在途和未完成业务的统一收束与隔离 |
| 历史独立只读、原请求回执恢复 | 所有席位列表、直接访问与写入的统一轮次检查 |
| 资源查询校验同一场景时钟 | 查询在执行前固定所属轮，避免重新演示后改读另一轮 |
| 普通作业有独立会话，持续研判按配置时期分会话 | 配置时期与演示轮次同时隔离，避免新轮复用旧历史和基线 |

代码依据见[现状核对](research/run-isolation-basis.md)。已有编号和任务归档不等于完整隔离；现有冻结语义继续用于历史只读。

## 4. 使用方式

### 4.1 状态与入口

| 状态 | 含义 | 可执行操作 |
| --- | --- | --- |
| 准备中 | 新轮已创建，尚未成为当前演示 | 继续准备；完成确认后启用 |
| 当前演示 | 当前可控场、可办理业务的一轮 | 按现有权限操作，或确认重新演示 |
| 已结束 | 本次演示结束，保留完成或中断时的历史 | 只读查看 |

不增加“已挂起”状态。重新演示进行中沿用操作进度/回执，不增加一套业务任务状态；仍只允许一个活动演示。

当前轮已有的手工锁定/解除锁定保留，它只控制本轮操作，不代表历史轮次的挂起或恢复。

| 使用情况 | 重新演示的结果 |
| --- | --- |
| A已完成当前模式的事件投放 | 确认结束A，创建B，从初始时间和第一个事件开始 |
| A只演到一半 | 确认中断并结束A，保留当时记录；创建B，从初始状态开始 |
| 在新轮选择同一或另一场景 | 始终创建新轮；名称相同也不沿用A的消息、任务、研判或会话 |
| 点击任何历史记录 | 打开只读详情，当前控场目标不变，不启动执行 |

导演台继续保留“重新演示”“演示记录”两个主要入口。确认界面写清“结束当前A，创建新轮B”，并列出在途处理、未投放通知等需要处理的项目。

“待完成准备”继续用于恢复**新轮创建/初始化/启用尚未完成的操作**；它不是恢复已结束A，也不是恢复中断的模型推理。页面只显示必要的场景名、创建时间、模式和状态，技术编号按需披露。

### 4.2 业务席如何在不感知轮次的情况下使用

轮次是演示环境的内部隔离机制，不是业务对象。业务席仍使用原有任务、消息、待办、研判和态势页面，不展示轮次名称/编号、演示选择器或“所属演示”字段。场景选择、轮次状态和历史轮次入口只出现在导演台。

目标是后台提交启用B的结果后，业务页面读取B的数据；视图同步及无已绑定来源请求的归属方式待后续定案，不预设页面取得标记、客户端自动携带的实现。业务页如需更新提示，应使用普通业务文案，不广播“切换到B”，也不把控制提示交给Agent。

已经打开的A任务、对话和地图保留原归属和草稿，按“已归档资料/只读”等业务状态呈现，不显示“演示已结束”或轮次号；不能原地变成B。写入受后台限制，过期页面只提示重新进入后提交。

业务席新建任务、个人空间及会话时，需要有明确的后台归属依据，但无已绑定来源/父对象时如何取得该依据尚未确定。不得将“自动绑定当前活动轮”“改为无归属记录”或“增加业务席选择器”作为默认替代方案，也不预设演示/正式部署的具体适配开关。该问题留待`SIM-TASK-002`审阅。

账号、权限、登录、模型配置、技能和底图属于公共平台配置，不随重新演示复制。原有非演示历史按原权限保留，不混入当前演示；轮次隔离不扩大任何席位权限，不应以业务席退出重登或选择轮次代替归属判断。

## 5. 信息和上下文如何隔离

### 5.1 消息在接收时确定归属

模拟来源发送通知时，在**接口元数据**中携带所属演示；这与业务正文、关联哪条任务是不同的信息。

后台依据已认证的来源身份及已保存通知核验归属，入库后固定。不能按正文里的编号、地区、任务名称，或接收时“当前是哪轮”猜测归属。非演示来源继续使用原协议；演示来源缺失或归属不符时明确拒绝，保留发送方原消息供重试，不悄悄放进当前轮。

接收和执行两处都检查归属。规则与持续配置按轮保留生效版本；A的记录不能因B正在活动就套用B的新配置。已停用配置不会因重新演示自动启用。

| 情况 | 处理结果 |
| --- | --- |
| A消息正常到达，A正在运行 | 进入A；按原有已授权规则处理 |
| B已开始，A消息晚到 | 仍保存到A，只读核对；不启动新的分析、不改变A场景事实，不进入B |
| 重复投放同一消息 | 返回原回执，不重复入队；同一消息编号改归属或改内容则报冲突 |
| A已接收但尚未开始处理 | 结束A时停止本轮调度，排队作业取消并记录原因，不转交B |
| A的Agent正在处理，导演确认结束A并重新演示 | 先关闭A的新写入/调度，请求停止Agent并等待终态确认；停止或完成已核实后才启用B。若停止前已完成，结果仍归A；无法确认时保持待核对，不先切到B |
| A已生成但尚未投放的通知 | 明确确认不再发送，保留原未投放记录；B采用自己的新通知 |
| 接收结果尚未确认 | 先查询原回执核清；不能靠新建B绕过不确定结果 |

接收成功、研判完成和演示结束分别记录。历史页面可追加接收/操作回执核对信息，但不开放新的场景投放或业务执行。

### 5.2 任务关联只在本轮内判断

先由程序限定本轮任务候选，再由Agent根据事实判断与其中哪些任务有关。一条消息可以关联本轮多个任务，也可以暂未关联；消息不需要预先写死T01/T02。

本期只建立演示归属，不处理已登记的消息正文真实性改进事项。既有正文中的演示编号不作为隔离依据。

任务改为总体席手动创建后，仍需满足“人员决定任务内容、业务席不感知轮次、后台明确记录归属”的目标。**无来源消息的直接新建入口，归属机制待解决**，本轮不选择新的替代实现。

| 创建入口 | 轮次如何确定 |
| --- | --- |
| 导演按模板准备任务 | 宿主绑定正在准备的目标实例；不误绑为此时仍活动的旧轮 |
| 从消息/分析结果创建任务 | 可依据已保存消息/作业的归属核验原权限、来源关联及该轮活动状态；多条来源须同轮；业务席不选择轮次 |
| 直接点击“新建工作任务”，没有来源消息 | 待`SIM-TASK-002`确定。需求保留，不采用上一版隐藏页面上下文方式，也不默认改为绑定提交时的当前轮或要求人员选择 |

例如，总体席在A消息上选择创建任务，宿主从该消息确定A，将新任务记录为`scenarioInstanceId=A`；随后各席位的工作区、会话和资料从该任务继承归属。任务编号、创建席位和演示归属分别记录：同一个总体席可在不同轮次创建不同任务，创建者身份不等于轮次身份。

直接新建时如何确定归属、跨轮时如何处理旧页面提交，均作为待解决问题，不沿用已撤回的“表单固定隐藏标记、由客户端自动携带”结论。防止误绑、业务席不出现轮次术语的目标保留，但具体交互和处理方式后续审阅。

任务创建与已确定的归属保存应保持一致，去重不能改变原归属；不能先生成任务再猜测补齐。无来源手动创建路径尚未收敛，不能宣称所有创建入口的隔离设计已完成。将“消息分析→总体席判断新建”替换进测试剧本仍按`SIM-TASK-001`后续安排，不在本期改变三任务预建机制。

### 5.3 Agent使用哪一轮，由宿主固定

宿主在建立一次处理请求时，固定该请求所属演示，并向它的工具、子任务及结果保存流程传递同一后台上下文。

例如：A的Agent调用“查询车辆”，工具后台自动限定A，只返回A的数据；如果A已进入结束流程，则明确停止当前调用。模型不能通过修改参数查询B，也不会因为页面启用B而自动改查B。

| 入口 | 隔离要求 |
| --- | --- |
| 普通后台分析 | 作业从原消息继承归属；结束轮次后不允许重试原轮分析或把作业改绑B |
| 持续研判 | B独立建立输入、原生会话、批次及已发布基线，不继承A；原配置时期机制继续保留 |
| 业务席前台对话 | 从所属任务/会话确定归属；B使用新任务/工作区/会话，A会话保留只读 |
| 查询与工具 | 任务、报告、对象、资源、空间结果及显式引用都检查同轮与原授权 |
| 文件与历史 | 由所属工作区/会话/作业继承归属；继续使用Pi原生历史及现有文件机制，不另存一套聊天 |

任务内对话可继承任务的已校验归属，消息驱动的初步分析可继承原消息归属。没有已绑定任务、消息或其他父对象时，如何确定归属仍待`SIM-TASK-002`明确，不使用已撤回的页面上下文方案补齐。工具不能临时改用另一轮数据，普通业务原有权限约束保留。

### 5.4 模型看到什么

模型主要看到业务任务、消息、事实、时间和必要引用，不反复追加轮次UUID或“切换到B”的提示词，不把多轮资料一起交给它筛选。

对象引用和`snapshotClock`中仍可保留编号，供精确引用和核对；不会为了隐藏编号破坏原始证据。场景时间必须继续向模型明示，真实接收/查询时间继续保留，两者用途不变。模型看见编号不等于由模型负责隔离。

控制用归属信息主要由后台校验，不作为新增业务表单字段或轮次切换提示词。业务席显示事实、业务时间和必要对象引用，不把控制用轮次标记呈现为业务正文；现有通知中的作者控制前缀须纳入接入/展示适配检查，原始冻结证据不追改，业务投影不冒充未经处理的原文。

## 6. 完整执行后与中途中断后的重新演示

### 6.1 一次重新演示的顺序

1. **预检及准备B**：确认导演权限、所选场景/模式、A当前状态及所有待核对请求；为B创建独立实例和任务。B在正式启用前不参与A的任务候选和处理。
2. **关闭A的新写入和新调度**：确认后保存操作记录，停止A的新模型请求、业务提交与投放。回执核对及晚到消息仍归A。
3. **收束在途处理**：请求停止可取消的Agent并等待确认；发送/工具写入等结果未知的动作先核对。尚未开始的A作业取消并保留原因。未能停止或核清时，不宣布B已启用。
4. **结束并封存A**：保留A当时的时间、步骤、事实、任务/工作状态、原生历史、草稿和分析结果；完成必要的任务归档/只读封存。
5. **启用B并核对**：来源服务在本地事务中将A冻结、B设为活动并增加活动版本；宿主核对回执后开放B，各席位刷新。B从初始业务时间、初始事实和第一个事件开始。

对于已经运行的Agent，“请求停止”不等于“已停止”。后台须核对原作业已经取消、中断或正常结束，并核清在途工具效果。若Agent恰好先完成，保留其原结果及真实终态，不伪装成取消。结束门禁关闭后，迟到的模型输出或工具回调不能再发布新判断、发起后续工具或写入B；已有证据仍归A。B使用独立新上下文，不接续A的处理请求。

这里只影响A的演示执行，不暂停全系统的非演示业务。导演权限仍只负责控场与协调停止，不增加业务办理、规则管理或付费模型批次授权。

### 6.2 中途结束不伪造业务完成

结束一轮演示不表示其中任务、工作或车辆行动已经完成。保留“演示完整执行后结束”或“演示中途中断”的原因及结束位置，供历史查看。

符合现有归档条件的任务沿用原归档流程；存在未完成工作的任务按已结束轮次只读封存，保留其真实状态及交接记录。它们退出当前轮的任务候选和待办范围，不能继续办理。**不强行把工作改成完成、不删除未完成记录，也不绕过通用任务归档检查。**

未完成工作本身不必被伪造完成才允许开始B；必须核清的是正在执行或结果未知的操作。轮次结束的执行限制、任务封存及通用任务归档是不同层次，实施时需要共同验证，避免只改来源活动指针。

### 6.3 防止旧请求误生效

本期每次重新演示都使用新轮编号，A不重新激活；即使再次选择同一剧本，也创建B或C。

后台校验**所属演示**与**活动版本**。A的旧页面、旧工具调用、迟到的模型输出或业务提交，不能作为B/C的新操作生效，也不能被自动改绑到新轮。人工提交需重新读取当前状态后明确发起；版本校验由程序完成，不交给LLM。

历史资料保留其原业务时间和版本，只读查看时按原归属读取，不自动将旧研判作为B的基线。

### 6.4 丢响应、重启和多人操作

沿用并扩展现有激活回执，保存操作编号、起止演示、预期版本和完成阶段，不建设通用工作流引擎。

- 来源活动指针是唯一活动演示依据；各席位不保存独立的“当前活动演示”。页面仅保存自己的浏览位置与草稿。
- 重新演示未核对完成时，相关轮次的新写入和新模型调度保持关闭。重启/刷新只查询状态，不自动发送、推进或重试模型。
- 来源已启用B但宿主尚未确认时，显示“启用结果待核对”；人员核对后继续同一准备/启用操作，不另建C、不恢复执行A。
- 多个导演窗口竞争时，活动版本校验只允许一个成功；另一个刷新后重新确认，不能静默重定向。
