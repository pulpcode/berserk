# 后续候选：七类模拟外部系统设计

版本：v0.1｜2026-11-05｜仅作 SIM-DOMAIN-001 的后续设计资料，本期不实施。

用户已明确：七类系统及管理域拆分不列为本期目标，保留为后续 issue。下文的“首批”“本次拟调整”“D0—D3”均属于该后续候选设计，不得用来扩大本期范围。当前仅保留特情/态势双系统，具体本期调整见 [双系统来源与来报方案](../external-systems-design.md)。本文不构成实施授权。

## 1. 目标与已确认约束

目标：使演示中的消息和查询数据来自有明确业务职责的外部系统，让场景组织事件，而不是把场景名称当成消息来源。

用户已确认：

1. 一个场景使用多个外部系统，同一个外部系统可以参与不同场景；不按场景或演示轮次创建新的来源身份。
2. 来报使用业务口吻，保留地点、车辆、观测时间、报告修订等事实，移除“模拟场景”“投放时”和作者预设的任务编号等控制说明。

来源系统、报告人/采集渠道、场景/轮次是三个不同概念。例如：“警情信息系统”是发送系统，“园区值班员”“无人机观测”是原始报告渠道，“临港仓储火情”是场景。业务列表的“来源”展示发送系统；报告详情可以展示渠道和原始业务依据。

## 2. 现状与建议改变

当前只有 intel 报告查询与 situation 对象/变化查询两类模拟接口，共用 mock-context 进程和场景持久快照。车辆基础资料、状态、位置和道路等集中在 situation；样例来源名称含“临港场景”。这只能作为当前实现说明，不作为未来系统边界。

本方案建议：**六类业务来源系统 + 一套综合态势系统**。先建立逻辑职责、来源身份、查询与写入边界，继续复用一个模拟进程和数据库。独立进程、独立数据库及跨服务部署后续安排。

## 3. 建议模拟的七类系统

| 系统 | 负责维护的事实 | 当前剧本需要模拟的最小内容 | 职责边界 |
| --- | --- | --- | --- |
| 警情信息系统 | 警情来报、现场核实、情况续报、报告渠道与修订 | 仓库烟情首报、位置待核实、园区与无人机两份核实报告、火势续报 | 外部警情记录与 Axon 任务空间分开；收到警情不自动创建或完成 Axon 任务 |
| 装备资产与维保系统 | 车辆/装备身份、所属单位、车型能力、技术状况、故障与检修记录 | 六站二十四车档案、车型能力、检修车及技术状态未知记录 | 不维护车辆当前任务占用或实时定位；预计检修结束不等于已修复 |
| 勤务调度系统 | 值守条件、既有业务行动、车辆占用、演练安排与释放确认 | 城西救援、登高演练、占用车辆、释放条件与已确认状态 | 本次拟调整只模拟既有占用事实；新支援的批准、下达、出发、到场仍属后续执行建设 |
| 车辆定位系统 | 定位观测、设备上报时间、最后位置、定位缺失/陈旧 | 已有车辆位置及时间，V24 的旧定位和待核实状态 | 定位在线不证明车辆可用；不凭站点归属生成当前位置，不提前建设移动轨迹 |
| 道路交通系统 | 道路通行、封闭、施工、巡查观测、有效时段及修订 | 北货运路施工、城北路巡查、中轴桥封闭、旧巡查晚到、东环线通行 | 旧观测作为历史报告保留，不按接收先后解除较新封闭；不替车辆作调派决定 |
| 基础地理与设施系统 | 区域边界、道路/桥梁基础几何、站点和水源设施的位置与基础属性 | 六区域、六站、道路/桥梁、八个消火栓的既有空间基础资料 | 基础地图不维护动态路况；设施故障/维保归设备责任域，其他环境数据有实际剧情需求再扩展 |
| 综合态势系统 | 汇集以上系统形成的当前视图、变化索引、字段溯源和缺口说明 | 车辆综合查询、道路和资源地图、跨域状态依据与更新时间 | 维护汇集结果，不成为全部原始事实的写入入口；结论须带来源，不覆盖原始记录 |

这些名称和边界按本演示需要提出，不要求外部真实组织恰好采用七个独立软件。装备资产/维保、勤务/调度首批各合并为一个逻辑系统；更细拆分留到确有独立对接需求时。

导演台是模拟控制入口，场景引擎是合成数据协调器，Axon 的任务/Agent/工作区是应用内部能力，均不列为上述外部业务来源。

## 4. 一辆车如何跨系统出现

以演练占用车辆为例，拟形成以下责任分工，数值与时间以原有数据核对后的版本为准：

| 需要回答的问题 | 应读取的系统 | 应得到的事实 |
| --- | --- | --- |
| 是什么车、属于哪个站、具备什么能力？ | 装备资产与维保系统 | 稳定车辆身份、归属、车型能力与技术状况 |
| 是否正被占用、由什么业务占用？ | 勤务调度系统 | 演练/救援安排、占用时窗、是否已有释放确认 |
| 现在能核实的位置在哪里？ | 车辆定位系统 | 最后观测位置、观测时间与陈旧/缺失状态 |
| 站点、区域、道路边界在哪里？ | 基础地理与设施系统 | 基础几何及固定空间引用 |
| 途经道路当时是否可通行？ | 道路交通系统 | 对应路段的限制及有效时间 |
| 能否在地图和资源清单里一起核对？ | 综合态势系统 | 合成视图，逐项保留上述依据及未知项 |

“技术正常”“没有已知占用”“位置可信”“满足本次任务要求”分别表达。综合态势/资源查询服务可以按明确规则整理这些事实，但不凭一个状态推断完整出动资格；首批不建设通用资格规则引擎。

同一车辆在多个系统中有不同记录，不是多辆车。通过明确的实体映射关联，保留各系统记录引用与版本；不靠同名、同坐标或车号字符串相等自行合并。组合资源统计不能把档案、勤务和定位记录重复计车。

## 5. 场景事件怎样归到这些系统

建议保持现有十二步顺序与至少十三条通知的规模，先调整事实归属和业务文案；不为凑齐来源而增加无意义通知。

| 现有事件 | 建议发送系统 | 数据调整原则 |
| --- | --- | --- |
| E01 烟情首报、位置待核实 | 警情信息系统 | 标题和正文描述烟情及待核实事项 |
| E02 城西交通救援进展 | 勤务调度系统 | 陈述既有救援及车辆占用，不写作者 T02 |
| E03 登高演练继续 | 勤务调度系统 | 陈述演练安排、车辆占用和释放依据，不写作者 T03 |
| E04 仓库位置核实（两份报告） | 警情信息系统 | 两份独立报告分别注明园区值班员、无人机观测渠道，不合并成一个消息编号 |
| E05 车辆档案清单确认 | 装备资产与维保系统 | 清单通知只证明档案/技术记录；需要占用、位置时查各自系统及态势汇集，不用一条清单冒充全部状态已确认 |
| E06 施工、E07 巡查、E08 桥梁封闭 | 道路交通系统 | 分别维护本路段事实、修订和时间 |
| E09 旧巡查报告晚到、E10 东环线通行 | 道路交通系统 | 明确旧观测与当前状态，保留原观测时间 |
| E11 交通救援继续占用 | 勤务调度系统 | 说明尚未释放，不预填 Axon 任务关联 |
| E12 火势续报 | 警情信息系统 | 陈述现场状态，不把续报写成 Axon 支援已完成 |

定位和基础地理系统首批可以主要提供查询与初始记录。综合态势随责任域数据变化更新视图，不再对同一原始事实重复发送一份来报；以后确有独立融合结果通知时，应明确它是综合态势系统发布的派生结果，并引用原始依据。

保留全市背景：六站二十四车及主线未使用的车辆、独立救援、演练、日常路况和未知记录继续存在。跨域拆分不把世界缩成只服务主线的七辆车。

## 6. 业务消息与来源显示

示例一：

- 来源：警情信息系统。
- 标题：临港仓库烟情首报。
- 内容：09:12 接园区报告，临港仓储区发现烟情，具体仓库位置待核实。
- 详情：原始报告渠道、观测/发生时间、发布时间、报告编号、修订、相关位置/对象引用。

示例二：

- 来源：勤务调度系统。
- 标题：城西救援车辆占用更新。
- 内容：城西交通救援仍在处置，相关两辆车尚未释放。具体车辆和占用记录可查。

原始内容不生成“模拟场景 run-…”“投放时场景时间…”或作者预设任务关联。业务编号、车辆编号、观测和有效时间保留；不能因为出现编号就一概删除。

场景业务时钟仍由宿主在查询返回/上下文中清楚提供，真实接收与查询时间仍保留。删除消息中的控场说明，不等于撤掉场景时间校验或让模型改用现实时间。

“来源”一律使用实际发送系统名称。经综合态势查询得到的数据，接口来源可以是综合态势系统，详情须能看出资产、勤务、定位等原始依据；不能把聚合接口名称冒充每条事实的原始维护者。报告人、无人机等放到渠道/原始来源说明，不把场景名称替换成另一个含糊标签。

建议将列表默认展示的 run-… 技术投递编号收进详情，以业务编号辅助识别。此项属于待审阅的展示建议，不以隐藏编号代替后台隔离。

## 7. 逻辑系统与物理部署分开

拟落地首批包括：

1. 七类逻辑系统有稳定身份、来源目录和能力声明；职责不同的事实分别经过所属域的写入和查询入口。
2. 仍可共用 mock-context 进程和数据库；按域组织数据与接口，再由综合态势读取这些域形成视图。不能只改七个名称，所有记录仍由同一个无边界对象表任意修改。
3. 导演一步可让多个域提交对应合成事实；共用存储阶段继续采用既有事务和快照机制，不新增消息总线、独立时间服务或分布式事务。
4. 不为每个域新增一套模型工具。先核对现有报告/对象查询适配是否能复用，缺少的只读能力按明确契约补齐；不把所有系统说明和资料无差别放进模型上下文。
5. 独立进程/数据库、真实系统接入、轨迹及完整调派反馈后续另行设计。

当前模拟配置校验、场景查询与通知生成仍固定 intel/situation，通知生成还有二选一来源分配；一个系统当前只选择一种查询适配器，而道路等责任域可能同时需要报告和对象能力，后续须明确能力组合与适配契约。因此这不是改配置名称即可完成的调整：后续实施需同步修改来源注册、按事件选择责任域、查询适配、来源凭据映射、权限、完整来源核验和综合查询溯源。

## 8. 身份、时间、权限与历史兼容

- 系统身份跨场景复用，控制用轮次归属继续保留在受信任元数据中。重复演示可以复用业务车号、报告业务编号，但技术投递身份必须满足现有全局去重契约；同轮重试稳定、新轮不碰撞。不能只去掉消息 ID 的 run 前缀。
- 各系统记录明确本域的实体引用、版本、观测/生效/发布时间。综合视图保留每项事实的原始依据、时效和缺口；来源失联/旧记录不自动变成“正常/可用”。
- 共用场景时钟和既有 snapshotClock 校验；每域观测时间可以不同，晚到报告不改变其观测时刻。以后物理拆分时再设计统一快照/延迟与故障规则，不能用现实时间兜底。
- 新域的查询、通知接入及聚合结果继续经过授权和轮次检查；聚合接口不授予未获准底层资料的读取权。导演控制权仍不等于业务办理权。
- 新来源目录与旧 intel/situation 接口的对应关系需明确兼容适配。旧 sourceId、对象/报告引用、认证及规则不能因改名隐式改绑到另一域；不直接重写已接收消息、原生 JSONL、固定结果或去重摘要。
- 新样例使用新场景版本；历史保持原记录与只读访问。上线时配套升级宿主、模拟服务与配置，保留完整备份及回退，不偷偷把活动演示替换为新样例。
- 默认处理规则不因新增系统自动启用；不在本方案里增加模型批次或真实执行授权。

## 10. 拟验收结果

1. 不同场景/多轮演示复用同一系统身份；消息列表、筛选、查询目录与规则配置使用一致系统名称。
2. 各事实确实由责任域维护；只改车辆检修不会修改定位或勤务记录，态势能说明变化来自哪里。
3. 首报、勤务、道路三类来报有不同发送系统，业务正文不含控制说明或作者任务编号；报告渠道、修订和时间仍可回溯。
4. 同一车辆跨域关联可验证，统计不重复计车；检修、占用、定位过旧和未知能区分，不凭预计结束时间自动恢复可用。
5. 旧巡查晚到不解除新封闭；一个域未覆盖/失败时能指出缺口，不把缺失当成正常。
6. 六站二十四车及无关背景保留；初始记录可查，不强迫每个系统都发通知。
7. 同轮重试、新轮重演、在途停止、来源核验、聚合授权和跨轮引用拒绝全部保持；业务席不显示或选择轮次。
8. 旧历史与原生证据不追改，处理规则不自动开启；工程回归与模型语义验收分别记录。
