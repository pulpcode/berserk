# W01-8 设计：任务分派与成果交接

日期：2026-09-19。状态：**待审，尚未实施**。

## 1. 对象与边界

| 对象 | 含义与归属 |
| --- | --- |
| 项目／任务空间 TaskSpace | 继续使用现有 taskSpaceId；前端仍叫“项目”，不新增项目状态机 |
| 席位工作区 Workspace | 同一任务 × 席位的目录、AGENTS.md 及会话集合；沿用现有 workspaceId |
| 分派工作 WorkItem | 一项具体目标，包含分派方、承办方、输入资料和办理状态；与 Subagent 委派不同 |
| 提交 Submission | 承办方向分派方提交的一份固定文件，以及该次提交的验收／退回结果 |
| 会话 Session | 继续使用 Pi 原生历史；可明确关联一个分派工作。新关联会话读取工作摘要，不自动共享其他聊天 |

```mermaid
flowchart LR
    A[席位 A：分派目标与资料] --> W[分派工作]
    W --> B[席位 B：独立工作区与对话]
    B --> P[固定方案文件并确认提交]
    P --> R[席位 A：查看提交版本]
    R -->|验收通过| D[工作完成]
    R -->|退回意见| B
```

Pi 仍负责模型、工具循环、上下文、压缩和子 Agent。宿主新增分派工作与提交记录，是为了保存“谁交给谁、交了什么、是否被接收”；不据此引入完整 Run 或另一套 Agent 循环。

## 2. 两个测试席位

同一服务、同一数据根、同一 WorkspaceStore 和 PiLab。不能动态改全局 config.seatId，也不能创建两个 PiLab 共用索引文件。

- 配置可选 `LAB_TEST_SEATS`：两项 `{id,name}` 的 JSON 数组，唯一、合法且包含现有 `LAB_SEAT_ID`。未配置保持现有单席位方式；配置后开启本期协作测试入口。原席位 ID 不改名，界面名称可以是“席位 A／B”。
- GET `/api/info` 提供模式与席位名称；测试模式请求统一使用 `/api/test-seats/:seatId/...`，服务端将白名单 ID 解析为不可变 ActorContext。其余业务参数不能另传发起席位或覆盖权限。
- 测试模式除启动信息外不接受无席位的旧 API 路径；单席位模式仍保留 `/api/...`。原有 Host／Origin 和本地监听约束保持。
- 这是允许操作者切换的测试身份，不是登录认证。后续认证仅替换入口解析，领域服务继续接收同一席位范围。
- 所有 API、SSE、上传 XHR、预览和下载链接捕获发起时的席位路径。下载沿用流式链接，不为了加 header 将大文件全部读入浏览器内存。
- 页面状态和 sessionStorage 按席位分区；切席不取消原工作，不自动确认。旧事件只更新原席位缓存，两个标签页可分别停留在不同席位。

服务端工作区、会话、停止、交互回答、资料、历史摘要、文件和交接接口均校验 ActorContext。PiLab 启动读取全部已登记会话，按会话工作区自身的席位校验历史；对外只能取得当前席位的数据。资源及文件服务使用范围已校验的工作区，不提供可被浏览器直接调用的跨席位通用读取口。

模型设置仍为服务共享配置，任一测试席位可在全服务空闲时配置；密钥不进入模型上下文或文件沙盒。两个测试席位不是两套模型或两个运行服务。

## 3. 分派与办理

在自己的项目里发起分派，填写标题、目标、接收席位，并选择可选输入文件。服务准备固定资料副本，确认页显示目标、接收人和本次交接清单。

确认后，为接收方确保同一 taskSpaceId 下的唯一工作区；保存 WorkItem，接收方待办出现“待签收”。只交接选定资料，不能复制源 AGENTS.md 或会话历史。工作区提前准备成功而业务保存失败时，空工作区可保留，但不显示虚构待办或触发 Agent。

承办方“开始办理”后进入本席位会话，可选已有同项目、同工作关联的会话或新建会话。新会话不会自动发送消息。会话关联保存到业务索引，已有无关联会话须显式绑定，已绑定到另一工作的会话不自动改绑。

绑定仅在会话无活动请求时执行，否则返回 409；绑定与请求启动沿用同一进程内的活动检查，新请求固定 workItemId。SessionSnapshot 增加可选 workItemId；工作详情只返回当前席位已关联会话，不暴露对方会话 ID、标题或原文。

任务资料先作为名称、说明、固定文件 ID 出现在工作详情和按需工具查询中。用户或 Agent 可将它们复制到自己工作区后，使用现有 Pi read／bash 等工具处理；不把附件正文或对方聊天整体塞入上下文。开始每轮时，仅装入关联工作的当前目标、状态、最近退回意见及资料引用；AGENTS.md 继续独立加载。该摘要是业务输入，不是恢复提示词或压缩定制。

## 4. 状态及操作权限

状态属于 WorkItem，文件和 Session 没有对应业务状态。

| 当前状态 | 谁做什么 | 结果 |
| --- | --- | --- |
| 无 | 分派方确认分派 | assigned：待签收 |
| assigned | 承办方确认开始办理 | working：办理中 |
| working／returned | 承办方确认提交文件 | submitted：待验收，产生下一次 Submission |
| submitted | 分派方对当前提交确认“验收通过” | completed：已完成 |
| submitted | 分派方填写原因并确认退回 | returned：已退回 |

退回后可直接继续修改和再次提交，不要求另办一次签收。分派目标和输入资料在本期保持不变，需求调整写入退回意见；已完成工作不提供重开。打开待办、下载文件、模型回复结束，都不改变这些状态。

提交成功后，工具返回结果，Agent 可正常结束本轮。等待对方验收只保存在 WorkItem 中，不保持 AgentSession 或沙盒运行；对方处理后，用户另发新消息继续。

工作项保存递增 revision。所有修改带准备时的 expectedRevision，并在提交事务内重新核验；两个不同操作基于同一旧版本，只有一个能成功。该检查不限制普通对话或文件编辑并发。

claim、submit、review 必须提供 expectedRevision；新建工作的 assign 无此字段。review 固定 submissionId、决定及意见，提交时核验它仍是当前待验收版本。

## 5. 固定版本与确认

每次成果提交先支持一份普通文件。指定 `方案.md` 是指定候选源文件，确认页对应的则是服务已复制保存的具体字节。

1. 校验操作者、工作归属、状态与源文件范围；复用受控文件复制原语保存副本，计算实际 hash／大小。
2. 保存准备单 operationId，绑定动作、双方席位、目标工作、revision 和副本。确认页显示文件名、准备时间及查看／下载；不让用户阅读内部 hash 或 JSON。
3. 用户确认后重新核验工作状态、准备单及副本的存在／hash，原子保存业务状态及回执。提交动作引用同一个副本，不重新读取工作目录。
4. 生成 Submission 编号和固定文件链接，接收方待办转为“待验收”。原文件可继续修改，旧提交保持可读。

确认期间原文件变化不更新准备单；希望提交新内容时应取消并重新准备。固定的是实际复制的文件字节，不保证复制时得到整个工作目录的一致时刻；复制失败或源文件不符合限制时不出现可批准的准备单。

现有 FileService.publish 的下载语义保留。新增交接文件复制／读取入口复用其安全文件原语，不拿同一个 toolCallId 循环 publish 多份输入。副本保存在宿主私有目录，不挂载进任一沙盒；承办方和分派方通过 WorkItem／Submission 范围校验读取。

本期建议将交接文件导入同一 taskSpaceId 下自己的普通目录，跨项目导入后置。Agent 使用本轮固定的会话工作区，页面目标按同一范围校验。默认目标使用“收到资料／工作编号／文件编号／原文件名”，已存在相同字节直接返回；已有同名但被修改的文件返回冲突，由用户选择另存位置，不覆盖。复制不会授予读取对方目录的能力，也不会同步后续源文件改动。

## 6. 自然语言与页面共用操作

建议工具名如下，Pi wire 名使用下划线：

| 工具 | 用途 |
| --- | --- |
| work_item.list／work_item.read | 查询当前席位可见工作及详情、输入引用、提交和意见 |
| work_item.prepare | 准备 assign／claim／submit／review，返回 operationId 和具体操作摘要；只准备，不交接 |
| work_item.commit | 仅接受 operationId。复用现有 HITL，用户批准后执行准备单；不接收替换文件、席位或参数 |
| handoff.import_file | 将获准交接的一个固定文件复制到当前会话工作区，返回普通文件路径供 Pi 工具使用 |

例如“上报方案.md”由 Agent 查询关联工作、准备提交，然后调用 commit 等待用户确认。对象不明确时使用现有 AskUser。Subagent 保持只读，不获准使用这些写工具；其结果仍只回父会话。

页面表单也调用同一 prepare／commit 服务，点击“确认分派／确认提交／确认退回”直接完成操作，无须为页面按钮再启动模型或追加一次确认弹窗。Agent 路径由现有 InteractionCard 承接；其工具校验及历史解析扩展为支持本期受控工具，不修改 Pi 源码。

准备单记录来源 page／agent 和创建席位。页面提交接口仅接受 page 准备单；Agent 准备单绑定原 sessionId／requestId，只能由该请求的 commit 工具经现有 HITL 批准后执行。内部提交校验 operationId、当前 toolCallId 和 interactionId 的关系，不接受浏览器或模型传入 approved 字段。两类入口不能借用对方准备单绕过确认。

确认卡片增加可选的受控交接摘要及预览引用，服务端从准备单生成；旧 bash／演示确认仍按原格式解析。刷新保留仍有效的等待；停止、请求结束和重启的失效规则见下一节，不凭普通聊天文字或旧批准调用提交。

## 7. 保存、重复请求与中断

保留 workspace-index v2、普通文件和 Pi JSONL。新增 `LAB_DATA_DIR/collaboration/`：

| 保存位置 | 内容 |
| --- | --- |
| collaboration.sqlite | WorkItem、会话关联、Submission、准备单及操作回执 |
| files/<fileId>/content | 输入或提交的固定文件字节；元数据由数据库保存 |

核心字段如下；ID 为不透明字符串，时间用 UTC，路径只在服务端使用。

| 记录 | 核心字段 |
| --- | --- |
| WorkItem | id、taskSpaceId、creatorSeatId、assigneeSeatId、title、goal、inputFileIds、state、revision、latestSubmissionId、时间 |
| Submission | id、workItemId、提交次数、fileId、提交席位及时间、验收决定／意见／席位／时间；验收结果可追加，文件内容固定 |
| WorkAction | operationId、source、创建席位、kind、固定参数及摘要、expectedRevision、去重键、创建进程标识、可选原会话／请求、是否放弃、成功回执 |
| 交接文件 | fileId、准备单及正式工作引用、原文件名、hash、大小、私有存储位置 |
| 会话关联 | sessionId、workItemId；会话所有者仍由原工作区确定，不复制聊天 |

建议使用 Node 24 自带 `node:sqlite`，只在具体协作存储模块使用，不增加 ORM 或独立数据库服务。当前 24.14.0 的 API 仍标为实验性；采用它是本期实现建议，需在 P1 验证事务和目标环境，不借此升级运行时。依据见 [存储说明](research/storage-and-interaction.md)。

工作状态、提交记录及同一次操作回执在一个短事务中提交；模型等待、文件复制及目录准备不放在事务内。副本须先完整落盘再被业务事务引用。两席位读取同一业务存储；待办由状态查询得到，不另建消息队列或通知回放系统。

- 页面创建准备单时保留 clientActionId；Agent 侧由 sessionId／requestId／toolCallId 建立准备请求关联。相同键和参数返回原准备单，参数不同返回冲突。
- 先校验访问权限；commit 对同一个 operationId 返回原成功回执，不重复提交。新 operationId 仍须校验当前状态和 revision。重新分派相同文字不作语义去重，它是需要再次确认的新工作。
- 成功业务事务不因 SSE／JSONL 结束保存失败而回滚。任务详情和 work_item.read 可查真实结果；旧工具缺结果仍按 W01-7 显示未知，不伪造 Pi 工具记录。
- 未提交准备单只在创建它的服务进程有效；Agent 的准备单还绑定原请求。重启、原请求结束／取消后不接受旧确认，须重新准备。已提交回执跨重启可查，不再触发动作。
- 页面“取消本次操作”将自己的 page 准备单标记为已放弃，之后不可提交；不撤回已经完成的业务。取消与提交在同一业务存储内校验，先完成的决定生效。仅关闭详情不会放弃准备单。
- Agent 取消在业务事务开始前已生效则不提交；事务已经开始则等待明确结果，成功提交后保留效果。结果不确定时先查 operationId，不自动生成新的提交动作。
- 孤立副本或未提交准备单不向另一席位公开。它们不是“已提交成果”，后续清理只处理无业务引用的副本，不删除业务历史。

这套回执仅保证本期宿主内的分派／提交动作，不承诺 Bash、任意脚本或外部系统恰好执行一次。

## 8. 网页交互

沿用现有项目和会话侧栏，新建会话仍可选择项目，项目栏加号保留。

- 增加“测试席位”切换和“工作待办”入口；待办按“待我办理／待我验收／我发起的”筛选，状态和所属项目可见。
- 项目页增加“分派工作”，打开目标、接收席位、输入文件表单；确认显示完整交接内容。
- 工作详情显示目标、输入资料、办理状态、提交次数、固定文件及退回意见，提供“开始办理／继续对话／提交文件／验收通过／退回”等当前有效动作。
- 会话只在关联工作时显示一个可打开详情的工作标题；不在每条回复或输入框下增加常驻业务提示。
- 准备提交可预览／下载；保留表单草稿，失败不清空，不确定结果提供“查询结果”，不自动重发。
- 待办数表示未处理事项，进入详情不自动清零。蓝点继续只表示未读助手回复，不混作业务待办。
- 手机详情单列；按钮可键盘操作，弹窗 Escape、焦点返回、长文件名换行及切席后的草稿保留纳入验收。

## 9. 接口与权限

下面路径相对当前席位 API 根；详情必须先校验当前席位是分派方或承办方。不存在和无权访问均返回 404。

| 接口 | 输入／结果 |
| --- | --- |
| GET /work-items | 当前席位待办／发起项摘要；不返回对方会话或目录内容 |
| GET /work-items/:id | 目标、状态、revision、输入元数据、提交与处理意见；仅本席位关联会话 |
| POST /work-items/prepare | `{clientActionId,kind,taskSpaceId或workItemId,expectedRevision?,payload}`；各 kind 使用严格独立字段定义 |
| GET /work-actions/:id | 自己准备的动作及回执；不执行动作 |
| POST /work-actions/:id/commit | `{confirm:true}`；仅执行自己的 page 准备单；Agent 走内部 HITL 批准钩子 |
| POST /work-actions/:id/cancel | 放弃自己的未提交 page 准备单；不撤销已提交业务 |
| GET /handoff-files/:id | 经工作／提交授权的固定文件预览或下载；未提交副本仅准备方可看 |
| POST /handoff-files/:id/import | 指定同任务下自己的 workspaceId 及可选另存位置；受控复制，不覆盖 |
| POST /sessions | 增加可选 workItemId；校验本席位工作区与项目归属 |
| POST /sessions/:id/work-item | 显式绑定原先无关联、无活动请求的同项目会话；不同工作禁止静默改绑 |

ActorContext 在服务入口生成，领域服务也复核角色、任务、会话及文件关系。浏览器字段和模型参数均不能改变发起身份，不能把接收席位 ID 当作源文件访问授权。切换测试席位本身是本期允许的测试功能。

## 10. 兼容与发布

旧任务空间、workspaceId、文件和会话 ID 保留；索引 v2 已支持多席位，不为本期重写 Pi 历史。新增接收工作区时使用现有初始化规则，独立 AGENTS.md 为空，不复制发送方规则。业务存储用独立 schemaVersion，缺失时仅在未初始化的新功能目录建立；已初始化但缺失／损坏时明确报错，不重建为空库。

实施先验证两个席位范围和存储边界，再接交接及网页。发布前停服备份数据，用副本完成旧记录和新业务读回；先在独立验收目录测试，最终只更新日常 4315，不长期恢复第二实例。

回退保留新增业务库和副本；旧程序不会管理新交接或识别新增业务确认。启用过协作的数据不能承诺直接由旧版无损续跑，应使用回退前备份在独立目录核对，新增数据保留等待恢复，不删除记录换取启动成功。
