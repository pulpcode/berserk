# 第二轮方案与批准：审阅入口

2026-11-06 · v0.1 · 设计草案，尚未开始实施。

基线：`codex/scenario-demo@5e88ca8`。独立分支：`codex/scenario-plans-design`。第一轮仍可在原 worktree 继续；本分支只新增设计资料和父子任务关联。

## 交付目标与演示终点

人员能从任务内提出 A/B/C 方向，比较确切版本，批准 A 的某一版；中轴桥封闭后，系统核对 A 的依赖，显示“原批准保留，当前条件不成立”；人员提交并批准 B 的新版本。**本轮止于固定版本的批准与复核，不产生车辆占用、下达、出发或到场。**

推荐路径只是验收样例，方案内容仍由人员和 Agent 根据实际查询形成。09:28、09:34 是故事中的筹划估计，不是现有来源已提供的路线计算或执行回报。

## 建议交付内容

| 交付 | 建议行为 |
| --- | --- |
| 方案卡及版本 | 可在公共任务下各席位自己的工作区/会话中起草，或在方案页编辑；人员显式提交任务内共享版本；共享后内容不可改，修订生成新版本 |
| 并排比较 | 一次选择 2—3 个固定版本，按车辆、路段、时窗、条件、依据与不确定性对齐；没有模型自动评分 |
| 人员决定 | 原建议由筹划席/总体席提交、总体席批准；此为新增权限建议，待 D02 审阅。作业审核沿用派工者审核，方案决定保留确切版本与内容 |
| 有效性复核 | 有限条件由宿主按当前来源核对；模型解释影响；历史批准不被后来的事实改写 |
| 后台共享读取 | 后台只读经人员提交且符合来源/共同受众授权的方案，发布研判时复核所读版本 |
| 兼容与接入 | 保留逐条初析旧路径；补齐持续结果的人工建任务、可信报告定位，再在独立场景验证持续模式 |

## 最需要你审阅的范围决策 D01

**建议将“从持续研判结果人工建任务”一并纳入本轮，以便演示双系统从首报开始使用现有持续研判。**

原因：现在人工建任务只接受成功的逐条初析结果。同一来源只能采用一种处理模式；直接切持续模式，会失去现有的来报建任务入口。另外，当前通知的 `subjectId` 是报告编号，而持续任务发现把它当报告主题或态势对象编号，不能直接可靠解析。两项都需要有界的兼容修补，详见 [研究依据](research/basis.md)。

若暂不纳入，备选范围是保留现有逐条初析，交付方案/比较/批准及**人员点击复核**；自动持续复核和对应验收后延。不能同时承诺不改入口又直接切换处理模式。本稿以下设计按建议方案展开，**D01 尚待确认，实施收敛门禁尚未通过**。

## 其他建议规则（均待审阅）

1. 原稿建议总体席拥有方案批准权、筹划席和总体席提交共享版本；这是新增限制，不是现有分派/审核权限。多筹划席的分工与最终批准边界按下文 D02 待决，不能先固定为产品角色权限。导演、后台和子 Agent 无新增业务决定权。
2. 每任务同一时刻只有一个当前批准版本；不同候选方案可以并存。批准新版本需明确替换当前批准；提交新候选不会自动替换旧批准。
3. 已声明必要条件存在不成立或未知项时，禁止批准。允许保存、比较和退回有缺口的候选，先补证或修改方案；不提供强行批准按钮。
4. 条件全部满足只表示所列条件已核对，不认证完整出动资格。到达时间保留筹划估计与假设，人员对方案取舍负责；第三轮下达前仍须再次核验。
5. 共享版本为新的、经人员确认的任务业务记录。私有对话、文件与工具结果不自动公开；引用原件仍需原权限。

## 权限审阅 D02：分工作业审核与最终采用

用户提出后续存在多个筹划席：筹划 A 将工作分给 B/C，B/C 交作业后由谁审核，以及本稿是否收窄现有权限。

已核对：现有工作交接按具体工作的参与关系授权，接收方签收/提交，派工方审核最新提交；审核通过才完成工作，退回则重新提交。因而 A 分给 B/C 的工作由 A 审核，不要求总体席逐项审核。各项工作可以放在同一公共任务下；现有记录没有父子工作依赖和自动汇总，不能宣称已有通用逐级审批引擎。

**待决：最终方案是否直接沿用派工者审核，明确采用一个方案版本；还是另设任务指定的最终批准资格。**建议先复用现有审核关系；确需独立的方案采用决定时再明确其责任人。不仅按“筹划/总体”名称固定资格，不默认增加“成果验收后再批准方案”的串行双重操作。若一次审核同时决定采用，必须明确指向确切方案版本；接受包含多个候选的文件不能自动视为批准其中某一个。

本例用于澄清权限语义，不提前建设席位层级、增加演示账号或实现父子工作自动流转。D02 未决，原权限矩阵及决定记录与既有审核的映射尚未冻结。

### 采用后的业务去向与重复审核问题

用户进一步追问：方案采用之后做什么，以及原稿是否将普通交付审核与方案审核分立。当前稿的确保留了现有作业验收，同时另设计方案批准；此前补充的“可合并”尚未落实为一套一致的最终设计，不能把原独立 API/决定表当作已经审定的必要机制。

现有审核对象是作业的某次提交，文件只是载体。建议收敛为同一条业务链：B/C 分项提交→派工者 A 验收→A 整合提交→最终派工者审核并明确采用某个方案版本→待下达→人员显式下达→模拟执行与反馈。如果某次审核已经明确采用一个版本，不再要求对同一决定重复审批；接受含多个候选的研究成果则仍不替人选择版本。此建议待 D02 确认。

“采用”应产生可供后续执行引用的明确版本及人员决定，但不自动占车或出发。第二轮交付到“已采用、待下达”及事实变化后的复核；第三轮实现下达前重查条件、发送指令、模拟服务受理/占用与逐车回报。方案卡可以作为作业成果/当前选用版本的结构化展示入口，其存在不必意味着另一套审核流程或另一组角色权限。

若按统一流程收敛，需要整体修订 PRD、技术设计、API/记录、权限与实施计划；补足现有审核对确切方案版本的关联，并评估复用已有提交/验收证据。当前仅记录待审建议，未把“采用后执行”提前纳入第二轮，也未将该建议视为用户已批准。
