# 态势查看与标绘编辑：产品范本及工作模式调研

调研日期：2026-10-24｜决策更新：2026-10-25｜任务：fire-situation-plotting

**当前结论：用户已选择单地图、按需展开标绘工具，首期不拆页面。** 第 1–8 节保留当时的产品调研及候选比较，其中“待讨论 / 待定”是历史状态；最新决策见第 9 节，执行依据为 V1.1 PRD、设计及实施清单。

用户重新提出：态势与标绘是否需要拆开、是否属于不同业务系统。V1.0 的双模式预览只证明一种交互可以表达需求，不能据此认定顶层“态势 / 标绘”切换已经定案。本记录用于重新评估该选择，不授权实现。

## 1. 结论与证据边界

公开产品同时存在三种组织方式：在事件地图内直接编辑；在同一解决方案内按岗位提供多个应用；将专业计算、资料管理与地图拆成独立应用并交换数据。因此，没有从这些范本中得到“态势与标绘必须分成两个页面或系统”的结论。

对本项目的当前建议是：**以事件/任务地图工作区为入口，按可写草稿进入局部编辑；保留明确的编辑状态，顶层不先固定为两个对等业务模块。** 只读展示入口是否首期单独提供，取决于实际岗位分工。

下面分别标注官方已说明的行为和对本项目的推论。证据来自公开官方文档、教程和建设材料；未登录这些产品的客户部署，也未实测其完整权限、协作或发布流程。研究产品组织方式，不建议本期迁移到这些商业平台。

## 2. 先分清四种“拆开”

| 层面 | 需要回答的问题 | 本项目建议 |
| --- | --- | --- |
| 业务与系统 | 是否建设两个独立业务系统 | 当前不因查看/编辑而拆系统；业务边界按事件管理、资源管理、调度等实际职责确定 |
| 页面与工作区 | 是否给制图人员和指挥人员不同入口 | 同岗优先同工作区；明确存在独立看图岗位时，再提供简化展示入口 |
| 文档与图层 | 实际信息、计划、研判、历史版本是否混写 | 保留独立身份、权限和修订；可叠加查看，不因同屏展示合并数据 |
| 交互状态 | 鼠标当前用于查看还是绘制/拖动对象 | 必须明确；工具、可写目标、未保存状态及结束编辑入口可见 |

态势是对事件情况和变化的综合理解与呈现，标绘是输入和表达地理信息的方法。手工画出的实际积水范围可以提供态势信息；画出的拟部署位置则表达计划。不能按“自动数据 / 手工绘制”替代“事实 / 方案”的判断。Esri 的架构指南将态势系统定位为汇聚业务流程与外部来源、按不同受众组织展示的能力，支持上述区分。[官方架构说明](https://architecture.arcgis.com/en/industry-and-tech-patterns/emergency-management-lens/systems/situational-awareness.html)

## 3. 可参考的真实范本

### 3.1 D4H Incident Management：事件地图内直接标绘

官方行为：Situation、Tasks 和 Status Boards 中的地理位置汇入事件主地图；地图本身提供绘图工具。绘制的几何可以作为 Map Note，也可以关联任务板或状态板条目。点击图形可继续编辑。[地图模块说明](https://help.d4h.com/article/511-map-overview)；[标绘图文操作](https://help.d4h.com/article/546-using-map-annotation-tools)

借鉴：标绘嵌入事件工作，而不要求用户先进入独立标绘系统。图形具有业务用途，不能只有形状与颜色。此文档并不证明所有编辑均有审核发布；不能把本项目的版本机制说成 D4H 的行为。

### 3.2 ArcGIS Mission：实时任务地图配合可编辑图层

官方行为：任务分析地图同时展示人员位置、任务、报告等图层；存在可编辑上下文图层时，分析人员可以启动 Add or Edit Feature 工具，再次点击结束编辑。另有供地图所有者/管理员使用的地图配置编辑界面。[任务地图及编辑工具](https://doc.esri.com/en/arcgis-mission/latest/manager/manager-mission-analyst-map-panel.html)；[地图配置编辑](https://doc.esri.com/en/arcgis-mission/latest/manager/manager-mission-details-mission-map.html)

借鉴：区分“编辑业务要素”和“配置地图”。前者可在态势上下文中完成；不应把底图、图层配置、现场记录、计划部署全部塞进一个含义不清的编辑模式。

### 3.3 CalTopo / SARTopo：同图协作，规模扩大后分工作图

官方行为：共享地图区分 Read、Update、Write；Update 可以新增并修改自己的对象，Write 可以修改地图中的所有对象。[权限说明](https://training.caltopo.com/all_users/share/permissions)

官方救援教程建议先做好分组、命名及地图内容管理；当事件很大或跨多个作业周期，再使用现场作业图、计划图和主图，并将清理后的作业数据汇入主图。[大型事件组织教程](https://training.caltopo.com/firstresponse/course/scale)

借鉴：拆图的理由是职责、周期和信息负荷。当前项目可以优先复用现有草稿与版本，不提前建设多地图同步机制。不能把 CalTopo 的直接共享编辑复制为本项目自动发布策略。

### 3.4 ArcGIS Emergency Management Operations：同一方案中的岗位应用

官方行为：Emergency Information Manager 用于记录事件、绘制影响区与理解影响；Incident Status Dashboard 用于指挥人员查看；另外提供面向公众的入口和专题录入表单。底层由地图、图层和视图支持。[产品组成](https://doc.arcgis.com/en/arcgis-solutions/latest/reference/introduction-to-emergency-management-operations.htm)；[完整图文教程](https://learn.arcgis.com/en/projects/manage-and-communicate-emergency-information/)

借鉴：参谋录入和指挥展示可以有不同界面，但仍围绕同一事件及共享数据。多个应用入口不等于两套互不相干的业务。官方工作流也说明人工绘制的事件与影响区可供后续展示使用。[业务流程](https://doc.arcgis.com/en/arcgis-solutions/latest/reference/use-emergency-management-operations.htm)

### 3.5 EPA / NOAA CAMEO：专业能力拆为独立应用

官方行为：CAMEO Data Manager 管资料，ALOHA 进行化学泄漏影响计算，MARPLOT 负责地图；应用可以独立使用或交换信息。MARPLOT 既能导入图层，也能绘制对象，并可显示 ALOHA 的影响范围。[EPA 官方软件套件说明](https://www.epa.gov/cameo/what-cameo-software-suite)

借鉴：确实可以存在多个业务/专业系统，但拆分依据是资料、模型与地图职责，并非查看与画图这两个操作。本期没有建设此类独立专业系统的需求。

### 3.6 国内森防建设材料：按部署与业务职责组织

北京市应急管理局 2021 年公布的建设方案，将火场标绘与火场/力量信息可视化一同放在应急地理信息系统，同时区分云端交换和现场指挥端。[北京市应急管理局原文](https://yjglj.beijing.gov.cn/art/2021/8/10/art_5618_682304.html)

借鉴：国内也有将标绘与态势展示放在同一业务能力中的设计。该来源是建设方案，不能用来证明当前产品具体有哪些按钮、标签页或已完成哪些部署。

## 4. 可采用的实践原则

以下是基于上述范本、项目现有契约与桌面交互约束的综合建议，不是消防规范对 UI 的强制规定。

1. **围绕事件和任务组织入口。** 用户先知道当前处理哪个事件，再选择查看、标绘、分析或引用；不必先理解两个抽象模块。
2. **先明确写入目标，再激活工具。** 显示草稿名和可写状态；来源与参考版本继续只读。工具关闭后回到查看，保持地图范围及图层。
3. **编辑中继续查看态势。** 可以看来源详情和刷新信息，但不能让来源变成可拖动对象。切换选中对象不应丢失表单；未保存退出沿用保存、放弃、取消。
4. **信息性质、来源和版本分别表达。** 现场记录、研判、拟定方案与草稿/发布状态是不同维度。人工记录并不天然不可信；外部来源也不能因显示在地图上就视为已核验。发布计划不代表行动已发生。
5. **展示采用明确版本。** 工作中的草稿不自动成为任务当前成果；保存、发布、采用保留已有服务和权限。这里没有新增强制审核环节，也不等于要求每次画点都审批。
6. **显示内容按用途裁剪。** 初始图层适量，必要时展开历史和参考成果；指挥展示入口可隐藏绘图工具及复杂属性，但不维护第二套事实数据。
7. **规模与分工明确后再分工作区。** 多人持续制图、独立指挥席位、跨多个作业周期、需要外部受众入口时，再考虑独立展示与方案工作区。独立业务系统还需明确的数据职责、集成或部署需求。

## 5. 本项目的三个候选方案

| 方案 | 体验 | 优点 | 代价与适用条件 |
| --- | --- | --- | --- |
| A：统一事件地图，按草稿进入编辑（当前推荐） | 默认查看；点击“编辑当前草稿/开始标绘”打开工具与属性；完成后收起 | 保留上下文，入口轻，适合同一批人边看边画 | 要把可写目标、选择规则、工具状态和未保存状态做清楚 |
| B：同一产品分“态势总览 / 方案工作区” | 总览面向指挥，工作区面向持续制图 | 适合固定岗位与大量方案编制 | 增加导航、版本关联和状态保留成本；两边仍应共享数据与符号 |
| C：态势展示与专业制图独立系统 | 专业系统产出受控成果，态势系统接入 | 适合已有 GIS/调度系统或独立部署责任 | 当前证据不足以支撑；增加身份、格式、同步、运维成本 |

V1.0 的“查看 / 编辑”在交互状态层面可以保留；本次重开的是其顶层入口和业务命名。A 不承诺一次实现任意多图层编辑、多人实时协作、方案对比或新的调度功能。

## 6. 推荐方案的具体操作示例（待确认）

以已有任务的水域救援方案为例：

1. 打开任务地图，查看已有来源、任务当前标绘和按需加载的参考版本。
2. 在本会话草稿旁点击“编辑”。进入工具状态，但地图范围、来源内容和参考版本继续保留。
3. 选择冲锋舟标号，在草稿里画拟部署点与拟接近路线，明确标注为计划；不能借此移动来源对象。
4. 完成编辑并保存草稿。按现有规则另行发布、采用；这些动作各自可辨。
5. 供查看的入口读取授权版本，隐藏工具，仍能打开对象的来源、信息性质和时间。

这里的冲锋舟属于标绘对象，未声称当前来源服务已经有真实单艇定位。现有车辆数量汇总、道路、区域来源继续保持原含义。

建议首轮验证三个任务：边查看来源边画方案；修改草稿时检查一条只读来源；发布后的查看者识别实际信息与计划。观察是否发生误拖来源、误认计划或丢失输入，再决定是否需要独立工作区。此次只做调研，没有执行可用性测试。

## 8. 实时态势与标绘的协同：追加验证（2026-10-24）

本轮问题：车辆等实时位置是否应与标绘同图，实际产品如何协调，何时需要分工作区。以下是公开官方教程的核验，不是客户部署实测；截图来自官方教程页面，在浏览器打开后截取显示区域保存。本轮没有新增实时定位功能或调整首期实施范围。

### 8.1 CalTopo：实时位置可跨地图复用，任务标绘与轨迹同屏

[Live Team Tracking](https://training.caltopo.com/all_users/team-accounts/team-tracking) 明确说明：

- 录制中的轨迹在有网络连接时近实时上传，可在同一地图中看到不同队伍的轨迹。
- Shared Locations 是独立于某一张地图的叠加层，因此切换团队地图仍可以查看相同的定位数据。
- 点击位置可看设备名称、坐标、最后更新时间，也可以查看轨迹或将该时刻位置复制为普通标记。
- 官网桌面示例同时显示 Team 1/2 assignment 与 Team 1/2 track；紫色和蓝色长线是任务路线，橙色和绿色线是实际录制中的轨迹。

这比简单的“查看 / 编辑互斥切换”更有参考价值：实时位置与工作图内容分别管理，展示时叠加。复制位置为标记不意味着该标记继续跟随定位更新。

[Scaling up for Large Incidents](https://training.caltopo.com/firstresponse/course/scale) 则建议：先用目录、命名和显隐管理内容；事件范围、人员或作业周期显著扩大后，才考虑现场作业图、计划图和主图。主图由整理后的数据周期性更新，并非所有工作图永远自动双向同步。

### 8.4 对本项目的协同建议（仍待审阅）

推荐沿用第 5 节的 A：统一事件作业地图，进入某一草稿的局部编辑；保留以后按岗位增加只读总览的能力。需要明确区分四件事：数据职责、地图呈现、编辑权限、成果采用。共享地图不等于所有对象都可编辑，也不要求所有岗位使用同一种界面。

| 内容 | 更新方式 | 协同规则 |
| --- | --- | --- |
| 实时车辆/船艇位置 | 定位平台更新 | 授权视图读取同一来源；只读，显示定位时间与过期状态；不随草稿保存/发布而冻结 |
| 人工现场信息，如实际积水范围 | 人工上报及核实 | 保留报告者、报告时间和核实状态；人工标绘也可成为态势信息，不能全部归为计划 |
| 拟部署点、拟行动路线 | 草稿编辑 | 与源对象通过完整身份关联；不覆盖实际位置；草稿可协作，但不默认成为指挥总览采用的方案 |
| 任务当前方案 | 沿用既有发布、采用流程 | 总览读取明确版本；新草稿不自动替换当前方案；已采用的计划仍然是计划 |

具体操作：操作者看消防车实际位置，同时编辑其拟待命点；真实位置继续更新，计划点保持固定。发布并采用新版本后，总览更新计划叠加层；人员上报到场或业务系统给出状态后，再更新行动状态，不能因为发布计划就显示“已到场”。

交互要求：默认查看；明确显示当前可写草稿；绘制时不让实时更新抢地图视角或重置工具；跟随某辆车需要主动开启；历史回放或固定时刻研判必须显示对应时间，不能伪装为实时状态。

拆分条件：同一批人员边看边画时优先一个工作区；参谋持续编制、指挥席只看当前成果、大屏或多周期方案并行时，增加独立入口。只有已有调度/GIS 平台、独立管理职责或明确部署边界时才进一步考虑独立系统；即使分系统，也应围绕同一事件、对象身份和明确成果版本协调，而不是靠截图或手工重复维护。

### 8.5 尚未定案
