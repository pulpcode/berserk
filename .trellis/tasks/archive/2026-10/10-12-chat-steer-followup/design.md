# 技术与交互设计：会话追加消息

状态：已获实施授权；先完成公开 SDK 技术验证，需求以 prd.md 为准。

## 交互结构

沿用现有聊天页面，输入框上方只出现紧凑待发送文字行。无边框卡片、独立标题栏、进度仪表或队列管理页。输入区下沿保留已有模型入口，右侧运行时同时保留停止方块、发送箭头与小菜单；空闲隐藏发送模式。菜单仅“引导 / 排队发送”，选项有一行解释。默认排队与 Ctrl/Cmd+Enter 引导已获用户确认；界面将 Steer 统一显示为“引导”。

输入右侧箭头与 Enter 采用当前模式；Ctrl/Cmd+Enter 在忙碌时补充当前回复；Shift+Enter 换行，Tab 移焦。关闭菜单恢复触发按钮焦点。只有超过三条时折叠其余。一次发送确认后恢复默认模式。发送期间锁住该提交动作，输入仍可继续编辑，晚到的回执不得清空新草稿。

用户新截图要求逐条 Queue 组件：每行“引导”/ 删除 / 更多，更多中提供取回编辑。原子操作按 submissionId 和当前队列 revision 校验，仅作用于尚未消费消息。Pi 未提供逐条修改的高层接口，必须先验证 public clearQueue / clearAllQueues 加原顺序重入与消费之间的原子边界；如不能仅靠公开 SDK 保证，则形成明确技术缺口并再审阅，不用私有队列字段。不能一边清队列一边允许异步消费，也不能把已消费消息重新入队。停止先关闭接收，再清队列、等待取消收敛，取回尚未消费内容；非空草稿保留并分隔合并。失败时也保留可取回内容，不自动续跑。

## 边界与标识

- sessionId：已有会话与席位范围。
- expectedRequestId：已有前台运行身份，覆盖整个 Pi 原生后续消息链；不等同 Codex turnId，也不承诺绑定每一条初始用户目标。
- submissionId：浏览器 random-uuid.ts 生成，唯一标识一次追加提交；同 ID 同内容重试返回已有回执，异内容拒绝。
- pendingRevision：用于单条 Steer/删除/取回检测列表已被消费/改变；不是多用户协作版本系统。

宿主仅增加接收台账/展示投影（内存），原生队列负责调度。台账记录提交内容、模式、目标执行、接收和消费关联；不建立第二个可执行队列，不复制整个聊天历史。

## 拟议接口

保留现有 POST /sessions/:id/messages 的普通启动与 SSE。

新增 POST /sessions/:id/inputs，JSON body 为 {submissionId, expectedRequestId, mode:'steer'|'followUp', text}。验证原席位权限、CSRF、长度、纯文本范围和状态；该端点只接收消息并返回回执，不启动新的 prompt、SSE 或执行环境。重试去重必须先于“目标已结束”判断，避免接受成功却因回执丢失再次提交。状态冲突与接收结果未知分别表达。

GET session snapshot 增加最小 pendingInputs/intakeReceipts 投影用于刷新、断连和回执核对；运行结束仍保留未消费的取回内容。GET submission receipt 按确切 ID 查询（可从 snapshot 派生或独立只读接口，实施时择一，不重复建设）。内存回执按会话/执行有界保留；过期/重启未知不能冒充“从未接收”，不自动重试执行。

新增原子队列操作（steer/delete/takeback），携带 submissionId、目标执行、pendingRevision 和操作去重标识。先返回过期状态再由客户端刷新，不在旧列表上静默修改。转换保持原提交身份，仅修改投递意图；取回内容必须尚未消费。删除可短暂撤销，服务端以原提交身份核对目标运行和未消费性后恢复，不因重复点击生成新提交。过期只能取回草稿，不能默默改投新执行。

现有 SSE 加入追加消息接收/消费/取回事件，所有事件仍带 host requestId。前端消费时插入实际用户条目并截断上一个助手片段，防止多次回复拼在一起。历史事实最终以 Pi SessionManager 为准；动态台账不作为已持久化聊天证据。

## 执行生命周期

1. 普通请求照旧创建 request-scoped AgentSession、资源快照与沙箱。
2. 主会话处于可接收阶段时，通过公开 Pi 队列接口加入纯文本。准备、压缩、人工交互等待、后台和停止阶段首期拒绝追加并保留输入。
3. 默认 one-at-a-time；Steer 高于 Follow-up，因此不承诺两种模式混合后的全局先来先执行。
4. Follow-up 继续同一个 requestId、模型配置、指令快照、权限和沙箱；总 deadline（若配置）不因追加而重置，使用量合并在现有请求结果中。
5. 接近结束时，接收操作与关闭接收标志需要串行化；Pi 已投递消息才能从待发送中移除。Pi 最后一次队列读取后迟到的已接收消息，若运行已结束则标记未处理可取回，不启动另一轮兜底执行。
6. 取消首先同步关闭接收并阻止后续消费，清理队列与运行取消按实际 SDK 行为串行化；必须用竞态测试证明取回不会与模型消费重复。
7. 原来一次 prompt 返回后保存结果/清沙箱/dispose 的边界保留，必须在此之前处理残留队列台账。

## 消息关联技术门槛

AgentSession 用于展示待发送状态的文字列表，通过文本 indexOf 匹配消费事件，未提供浏览器 submissionId 的一一关联。底层 Agent 队列存储独立消息对象，允许同文重复，不会按文本自动去重。这是精确关联 UI 操作时的接入限制，不是 Pi 无法执行同文消息。首先验证公开的 session.agent.steer/followUp + 唯一时间戳/宿主关联表是否可保留完整原生会话生命周期，并通过真实 Pi 测试证明消费关联；不用私有字段。若仍需要不可接受的二次状态机或 SDK 补丁，则停在技术验证阶段重新审阅；不得通过给用户文本插入隐藏 ID 污染模型输入。

接收与处理的保证必须由“入队—消费—终结核对”共同建立。expectedRequestId 只防止跨运行误投，不单独证明消息被模型读取。

## 首期兼容与范围限制

不改变空闲时附件/引用/Skill/角色选择，也不修改任务首页或业务工作任务。忙碌纯文本追加是新增能力。问答/审批仍走原交互响应端点，不能用 Steer 当批准。子 Agent 工作期间的补充只投给父 Agent，父工具链结束后读取，不承诺立即改变子 Agent。后台作业暂不接收。

服务端连续运行时刷新可取回内存投影；进程崩溃不承诺恢复未消费队列。浏览器保留未确认发送的草稿/标识直至核对，不对未知结果自动重发。

## 上线与回退

仅在用户批准实施后开发。上线前关闭追加入口并等待现有执行结束，避免发布时丢失内存待发送消息；与用户确认的发布窗口一致。新契约采用可选字段，旧会话历史仍可读，不做数据库迁移。回退前同样排空或取回队列，恢复旧前后端。本轮授权实施；部署与提交不在本轮明确请求内。
