# Research: R4 business integration and storage map

- Query: Map existing business configuration, query/control/ingress consumers, account boundaries and migration seams for R4-0; identify where one authoritative connection configuration must replace duplicated endpoint/credential reads without weakening domain checks.
- Scope: internal; source inspection only. No environment/secret files, deployed data, network, tests, migration or git operations were accessed/executed by this researcher.
- Date: 2026-11-17
- Baseline: task `research/baseline.json` records `a3b9b887ab7cb26a1212d7b8bd543fb0d83b02f0`, clean product tree before planning. This report relies on that root-owned baseline and inspects current files; it does not independently establish git status.
- Requirements: task `prd.md` and `research/Axon_R4_Connectors_MCP_Plan_v0.2.md`, especially sections 4, 7, 9 and 10. They are requirements inputs, not evidence of implementation or permission to migrate.

## Findings

### 1. Main conclusions

1. The existing lookup is explicit `systemId` matching, not a connection-target resolver: `ContextService.query` normalizes input, finds the system, then checks seat/service scope (`src/context/service.ts:46`). No `resolveTarget`/`resolve*System` business helper was found in the searched source. Preserve old source identities; map each to a stable connection internally rather than adding business target selection.
2. Configuration is currently split into context systems, simulation control and background ingress. Query credentials are copied once into `ContextService.tokens`; control and ingress credentials are read from an environment object on use. Updating only context query transport would leave commands, director, legacy controls and source authentication on independent old configuration paths.
3. Existing parsing permits extra systems and multiple same-adapter systems. Enabled simulation only requires its two mappings to be `intel` and `situation`; it does not restrict the whole systems array to those two. R4 must detect conflicting deployed configurations before apply, not silently choose the first. Test fixtures intentionally exercise two same-adapter sources.
4. The capability SQLite database is the smallest established durable owner for connection revisions, fixed mappings, management audit and action receipts. R3 already extends it with a separate module metadata version while leaving `PRAGMA user_version=2`. Existing migrations provide strong stopped-root backup/recovery patterns. There is no reusable persistent encrypted connector secret store in the inspected source.
5. System administration belongs to an account. Business authority belongs to enabled real seats plus task/source/scenario/tool checks. An independent administrator's `account-<UUID>` scope is private workspace storage, never a business seat. Personal credentials in public tasks remain an explicit unresolved user decision; this report does not choose that policy.

All code paths below are relative to `experiments/harness-lab/` unless prefixed with `.trellis/`.

### 4. Inbound, background configuration and fixed mappings

- `src/background/config.ts:7`: ingress source is `{sourceId,name,credentialRef,systemId?,allowedProfileIds,allowedRecipientSeatIds}`. `systemId` is optional, and source entries without a query system are a supported legacy path. This cannot be removed during migration merely because it has no intel/situation mapping.
- `src/background/config.ts:41`: strict parser supports up to 100 sources/profiles; sources have unique source IDs and unique credential references, but **does not require systemId uniqueness, adapter uniqueness, or a reference to an existing context system**. Profile scope linkage is checked later by `BackgroundService.configuredProfileScope` (`src/background/service.ts:216`).
- `src/background/config.ts:76`: `LAB_BACKGROUND_CONFIG` absolute JSON, up to 2MB, ingress token at least 24 chars. `authenticateSource` (`:87`) performs constant-time Bearer comparison using `credentialRef`; source authentication is separate from browser authentication.
- `src/server/background-routes.ts:38`: only marked `axonSource` upload/event routes receive source auth and bypass browser auth. `src/server/auth.ts:55` limits that bypass to this explicit route marker. Preserve source-specific credentials and upload ownership; do not make generic connector routes source-auth bypasses.
- `src/background/service.ts:317`: verifies scene provenance, resolves uploads, hashes semantic payload, serializes intake, reuses source+message receipt only for identical content/run, checks accepting/backlog, freezes rule/Profile, commits event/job/continuous input atomically (`:326`). Saved event `systemId` is taken from trusted configured source (`:332`). R4 session selection must have no effect on this mapping.
- Source/rule/Profile/recipient permissions remain owned by background service/store: `permission` (`:208`), exact captured query scope (`:216`), source accepting control (`:298`), current rule/run checks (`:304`) and run visibility (`:146`). Existing source/queue enable state and connector ordinary enable state need explicitly composed semantics, not two competing ingress routes.
- Run isolation uses system metadata at `src/background/service.ts:147,156,243,290,320`; fixed mapping reconciliation/verification at `src/scenario/scope.ts:33,46,75` and `src/server/scenario-routes.ts:45`. These consumers need the same effective business metadata projection as the query service after migration.
- Checked-in example topology is `intel -> mock-intel-source`, `situation -> mock-situation-source`, one separate simulation controller. See `fixtures/scenario-demo/context.example.json:3`, `:8`; `background.example.json:7`, `:23`; `notifications.example.json:2`. Query tokens may be shared between intel/situation; control and ingress are distinct. These are example reference names, not verified deployed names or secrets.
- `scripts/mock-context/main.ts:20` independently validates notification targets as intel/situation and rejects missing/query/control-shared notification credentials (`:22`). This belongs to the separate simulated source process. Axon-side management must not pretend it reconfigures that process or alter notification destinations automatically.

### 6. Existing permissiveness versus R4 single-instance requirement

- Context uniqueness is by `id` only (`src/context/config.ts:70`); there is no business-slot uniqueness constraint. Enabled simulation's `sources.length===2` does **not** forbid a third system, a second information/situation adapter under a new ID, or another ingress source mapped to that system.
- `tests/scenario-resource-clock.test.ts:38` intentionally constructs two situation adapters `source` and `second`, both scene-clocked, to verify cross-source clock conflict handling. Keep those decoder/clock regression cases via a lower-level test-only transport fixture if production R4 business assembly becomes single-instance; do not delete coverage or equate this historical fixture with deployed multi-instance support.
- `tests/context-http.test.ts:40` checks duplicate identical IDs and invalid config, not same-adapter uniqueness. Add explicit management/import/assembly tests for differently named second business bindings, including disabled existing binding, concurrent requests, copy and changed display name.
- `tests/context-background.test.ts:55` intentionally includes `legacy-source` without `systemId`. It must remain preserved/inventoried; do not silently coerce it to a known business slot or discard it.
- Migration dry-run must enumerate **all** systems and ingress sources, compare simulation mapping and persisted source references, and list unmapped/duplicate/contradictory entries. Report a conflict and stop related apply rather than selecting by array order. Existing IDs need not match example IDs except where current enabled simulation/command code expressly fixes intel/situation.

### 7. Account, role, workspace and capability boundaries

- `src/access/system-roles.ts:51`: `SystemRoles.has/requireAdministrator` checks explicit account role plus enabled account; no seat-name/task/model-management inference. `src/server/capability-authorization.ts:7` re-resolves current account and exact actor seat; administrator check is separate.
- `src/server/app.ts:94` registers formal administrator endpoints outside the business seat hook. Reuse that placement for organization connection management. Ordinary business use still needs its own current identity and allowed connection/tool checks.
- `src/server/auth.ts:115` has three distinct helpers: `accountIdentityOf` for authenticated management, `identityOf` for real business seats, `workspaceIdentityOf` for private workspace projection. `auth.ts:64` separately allowlists safe seatless-account routes; any new personally usable catalog/credential path must be intentionally routed/allowlisted without opening business context routes.
- `src/access/store.ts:44` projects command authority from configured seats + enabled account + director exclusion. `:81` owns the common director predicate, `:96` workspace eligibility, `:113` business identity, `:130` account union, `:139` private-owner projection. `:331` acquires actual task/workspace admission. Retain all these; a connection grant adds no fake business seat.
- `src/access/personal-scope.ts:4` reserves account storage namespace. Task records validate private ownership and forbid scenario/business context for that namespace (`src/access/store.ts:27`). It is not a scope/default inheritance platform to reuse for connector target selection.
- Pi omits business tools/principals from independent administrator personal requests: `src/pi/lab.ts:970,1019,1050,1078`. Generic MCP addition needs a separate authorized runtime tool path while preserving this omission. Runtime authorization rechecks already exist around native tool calls and model permits (`:1114`, `:1262`, `:1476`). Do not reuse R3's administrator-personal Skill policy as proof of connector personal-credential policy.
- **Public-task result visibility is task × seat, not user:** `src/workspaces/store.ts:89,94,102,112` lists/gets/binds/prepares workspaces by seat; `src/pi/lab.ts:675,709,722` lists and reads sessions by that workspace/seat, without a user-ownership read check. `src/files/service.ts:224,232,259` authorizes saved outputs by workspace/task/seat, not the invoking account. `ExpertBinding.userId` and request actor audit do not make stored conversation bytes private to that user.
- A unique partial index allows only one enabled account per seat (`src/access/store.ts:60`); multiple simultaneously enabled accounts on one seat are rejected. After disabling the old account and enabling a different account for that same seat, existing seat-scoped read checks allow the successor to read that seat's old conversations/files/outputs, subject to current task/source access. No transfer execution or user-private history mechanism is implied.
- **Disclosure required if personal credentials are approved in public tasks:** a secret remaining personal does not make returned data user-private. Once results enter native chat, workspace files or fixed outputs, they follow existing seat-space retention/visibility; future authorized operators of that seat can read them, and explicit existing handoff/publication actions can share derived content. Other seats do not gain the private conversation/files merely because task metadata is public. Credential revocation/replacement cannot be described as deleting already persisted results. This is a scope tradeoff to explain, not a recommendation to add a privacy platform or a choice of policy. Business-seat private TaskSpaces are likewise owned by seat; only the independent administrator account namespace is intrinsically user-owned.

### 9. Minimal proposed seams (research recommendation, not implemented design)

1. Add a narrow connector module with durable connections/revisions, a server-owned fixed business-slot mapping and credential resolver; extend capabilities DB with its own checked module metadata version using the R3 pattern. A unique durable mapping by controlled business-slot identity survives disable/rename, preventing a second binding under concurrent creates/imports. Generic MCP records do not receive these slots. No task binding/default tables.
2. Give old domain code a single effective business configuration/transport projection. Keep `systemId`, `sourceId`, scopes, adapter, clock, resource-capability and recipient/Profile metadata as business-owned facts; replace only endpoint/credential resolution with the mapped connection revision. Do not maintain independently editable copied endpoints or refresh old files over migrated rows.
3. Centralize legacy query, controller and ingress credential resolution behind that authority: `ContextService`, all three CommandService paths, `ScenarioScope`, both control route implementations and `authenticateSource`. Keep query/control/ingress credential roles separate even if they refer to one business integration. Snapshot actual revision/credential identity for admitted calls; use current state at the existing domain admission boundaries. Existing control maxBytes variants (2MiB/4MiB) remain intentional.
4. Initialize/gate connector storage before `createApp` assembles context/background/scenario/commands and before background starts. Explicitly distinguish absent legacy optional configuration from corrupt/incomplete R4 configuration; current context-error swallowing must not downgrade a prepared migration to an empty usable installation. Provide explicit isolated test configuration injection as existing `createApp` options do.
5. Add administrator routes using account identity and SystemRoles; preserve existing business routes/services and browser auth guards. Native Pi tools continue through existing confirmation and runtime guards; new MCP does not enter background registration or the old business adapter catalog.

Likely required touched files: new `src/connectors/*` and shared connector contracts; `src/server/app.ts`, `src/pi/lab.ts`; the production credential consumers listed in section 5; `src/background/config.ts` + `src/server/background-routes.ts` for source auth; migration script/package command; carefully selected fixtures/tests. Most query consumers in section 3 can stay unchanged if `ContextService.config` exposes authoritative immutable metadata and query resolves through the same connection projection. If metadata becomes dynamic, their current direct `.config.systems` reads must be made revision-consistent together, not patched one by one.

### 10. Dry-run / apply / recovery proposal

- Dry-run on a copy: inspect all legacy context systems/scopes; simulation URL role, sources, director and command grants; ingress sources, credential **references**, Profiles and recipient grants; current rules/source controls and pending background work; persisted original system/source IDs in tasks/events/streams/commands. Output planned stable mappings, IDs/counts/digests and conflicts without credentials or rewriting business/native bytes. No live external call is required to establish this inventory.
- Bind plan to canonical non-secret input digest and exact original configuration bytes/path identities. Legacy files can live outside dataDir (`loadContextConfig/loadBackgroundConfig`); unlike R3, **full data-root backup alone does not cover them**. Apply/rollback must explicitly pair those configs and usable secret/key versions with the full root. Avoid putting secret values or reusable secret fingerprints into a dry-run report.
- Apply only through explicit stopped migration with independent verified backup; persist prepared state before schema/mapping mutation; one durable action/migration identity reuses the same mapped connection IDs. Persist secret safely before committing its reference and make failures reconcilable; do not claim SQLite makes an external secret file/store atomic.
- Startup blocks prepared state, missing mappings, duplicate legacy slots, unknown policy shape or unavailable required keys. Re-entry uses original plan/backup/identity, verifies every unrelated file and the allowed logical capability DB transformation, then completes. Changed source files or different plan conflict. Migrated authority wins; old JSON is historical input/explicit compatibility read only.
- Rollback restores a **copy** of the matched full pre-R4 root and configs/keys with the matched old binary; preserve active R4 root and original backup. Do not run old code on new active state merely because business tables were unchanged. No runtime replay, event reroute or command resend belongs to migration.

## Caveats / Not Found

- No production/environment config or data inventory was read, so actual deployed extra systems, custom source IDs, pending jobs, external file paths and key availability remain unknown. Checked-in examples are not deployment facts.
- No connector database, target resolver, persistent encrypted secret backend, R4 migration or single-business-slot constraint exists in the inspected source. Proposed names/layout are minimal seams for root review, not an implementation claim.
- Personal-credential use in public tasks remains pending. No policy was inferred from current private workspace or Skill behavior.
- Existing R2/R3 migration helpers are examples, not directly reusable R4 routines: new external config/secret inputs and a new allowed database transformation require their own exact validation. Source/control and runtime snapshots currently have different lifetimes; hot configuration changes need one agreed snapshot/admission rule.
- No tests were executed or claimed passed, no code/spec/product/roadmap was changed, and no migration/apply/online request was performed by this researcher.
