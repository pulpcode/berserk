# 连接器随消息引用方案

状态 **待审阅** · 基线 `main` 的 `738dc29` · 分支 `codex/connector-message-references`

## 目标

把 Axon 聊天框中的显式连接器选择绑定到一条用户消息。用户可以从「+」指定这条消息要用的来源，同时也可以直接提问，由通用助手按当前权限和候选情况发起调用。界面分别呈现用户引用的来源与实际工具调用。

[Codex CLI 提交 App 引用](https://github.com/openai/codex/blob/3f65e9f13165d85d1b1fbe20ce06c55758f927b9/codex-rs/tui/src/chatwidget/input_submission.rs#L418-L453)时，为这条输入附上结构化 `Mention`。运行时处理[本次显式引用](https://github.com/openai/codex/blob/3f65e9f13165d85d1b1fbe20ce06c55758f927b9/codex-rs/core/src/plugins/mentions.rs#L41-L60)，下次用户发起新一轮时[清理上次的选择](https://github.com/openai/codex/blob/3f65e9f13165d85d1b1fbe20ce06c55758f927b9/codex-rs/core/src/session/turn_input.rs#L762-L777)。Axon 借鉴引用的作用范围，沿用自己的目标澄清和逐次确认流程。

## 用户交互

| 场景 | 预期行为 |
| --- | --- |
| 在「+ → 使用连接器」中选择来源 | 支持搜索、多选、取消勾选。输入框显示可移除的「本条消息引用」标签。关闭选择面板或刷新页面时，未发送的选择随原草稿保留。 |
| 发送带引用的消息 | 本次请求使用显式选择的来源。提交后，标签跟随原消息进入历史，下一条新草稿的选择为空。历史标签表示「已引用」，调用、拒绝和结果由工具记录展示。 |
| 继续讨论已有结果 | 用户可以直接发送「把刚才两条整理成表格」。助手可以使用历史结果完成这类追问。 |
| 继续获取新数据且本条未选来源 | 通用助手按当前账号和空间重新确定候选。唯一候选可在需要时发起调用。多个候选按现有规则询问目标，目录不足或无法在对话内澄清时提示从「+」明确选择。专业专家按其已发布的连接器引用工作。每次 MCP 工具调用沿用现有确认。 |
| 发送失败或连接中断 | 已确认原消息未写入时，把选择和正文、附件一起恢复。已有新草稿时提供原有的显式恢复操作。请求状态未知时先核对服务端。消息已写入时从历史读出引用和结果。 |

「+」的提示和无障碍名称采用「添加文件或能力」，菜单项采用「使用连接器」。允许在个人项目和可用的公共任务空间中选择符合现有权限条件的来源。范围限于桌面端聊天引用。连接器管理、`@` 自动完成、插件安装、任务默认设置与队列协议属于其他改动。

## 实现设计

1. **草稿与提交。** 沿用 `connectorIds` 发送字段，纳入 `useComposerSelections` 已有的随消息消费、提交和恢复流程。发送时固定 ID 列表，新建会话时将引用与原草稿一起转移。发送消费只清理已经提交的选择，保留并发形成的新草稿。活动请求中的选择保持固定，带连接器的下一条消息作为独立前台请求发送。现有普通文本排队继续走现有入口。
2. **本轮准入。** 继续使用通用助手候选解析、专业专家发布引用以及 `RequestMcpTools` 的当前账号、空间、凭证、工具版本和确认校验。仅从本次请求携带的 ID 确认显式引用。工具就绪后，取已验证的连接器 ID、名称和修订用于历史显示。实际调用仍有独立回执，旧消息的引用和确认均无新调用效力。
3. **消息历史。** 复用 Pi `SessionManager` 的请求级 MCP 准入记录。为有显式选择的请求新增准入记录版本，记录有序、去重的 `explicitConnectorIds`，并与已准入的工具来源校验一致。其余请求继续使用 v1。沿用现有对请求、会话、身份和执行清单的交叉校验，名称和修订从同一份已验证的来源快照投影。通过已有消息选择展示挂到请求的首条用户消息，发送中的标签从当前提交快照即时显示，重载后以服务端证据为准。该记录采用运行时元数据，模型输入和压缩上下文沿用现有的正文与工具结果。
4. **兼容与回退。** 旧浏览器缓存里会话级连接器 ID 的含义无法可靠区分。首次使用新版本时清理这些旧 ID，请用户重新选择；正文、附件和其他引用继续按已有机制恢复。旧 v1 记录按原规则读取，旧消息不回填显式引用标签。当前旧版的历史校验会拒绝未知的 `berserk.*` 记录，发布时需先验证双读能力，再启用新记录写入。写入后，回退目标必须保留新旧版本读兼容。

## 实施顺序与验收

1. 调整草稿的消费、恢复和旧缓存处理，使用现有发送和恢复入口覆盖新建对话、已有对话及切换空间。
2. 实现准入历史的双版本读取和显式引用投影。在 `mcp-runtime`、历史校验及消息展示测试中覆盖旧版读取、无工具调用但有显式引用、自动候选无引用标签、重载后的名称和修订一致性。
3. 更新「+」入口、选择面板和用户消息标签。复用连接器浏览器测试，验证在 1060px 和 1440px 桌面窗口可完成多选、移除、发送与重开。验证下一条无选中标签且请求无 `connectorIds`，仍能在唯一候选时发起确认，多候选时能澄清。验证显式选择不进入正在运行请求的文本队列。
4. 覆盖发送前拒绝、确认取消、发出后流中断、已有新草稿四种路径。预期分别为恢复未写入的草稿、保留已写入的引用、按服务端状态核对结果、保留新草稿并提供显式恢复。恢复过程不自动重发已接收的消息或外部调用。
5. 在 `experiments/harness-lab` 运行类型检查、lint、单测、构建和定向 Playwright 回归。审阅后如需线上验收，用 4316 的「模拟资料库」依次体验显式选择、无选择的历史追问，以及无选择的新查询和确认。
