# Axon 能力中心与专家协作
## 阶段需求与建设轮次调整方案

**版本：v0.1　｜　日期：2026-11-14　｜　状态：待审阅**

配套使用：《R2 专家管理与使用配置方案评审稿 v0.2》。本稿负责阶段调整；R2 稿负责本轮功能实施。本文提出具体建议，不代表已获批准、已修改仓库或已开工。

### 一、建议结论

**保留 R1—R6 原编号及其相对顺序；R3 后插入独立的 R3A“对话辅助能力创建”，R6 后新增 R7“能力安全治理”。R2 仍只建设专家管理与普通停用。**

| 变更 | 本次建议 | 本次不做 |
| --- | --- | --- |
| CR-01 能力安全治理 | 作为 R7 独立交付管理员封禁、紧急停止、处置结果及解除流程 | 不提前加入 R2；不删除 R1 安全守卫 |
| CR-02 对话辅助创建 | 作为 R3A 交付管理员通过对话创建、修改专家及方法型 Skill 草稿 | 不开放普通用户创作；不自动发布或授予权限 |

建议执行顺序：**R1 收口 → R2 → R3 → R3A → R4 → R5 → R6 → R7 → 阶段总验收。**

R3A 是独立建设轮次，不是 R3 或 R2 的隐藏工作包；这样增加两个可单独验收的交付，不重编号原 R4—R6。阶段总验收由原 R6 末尾移至 R7 之后，R6 仍有自身验收。

### 1.1 保持不变的产品约束

系统统一“管理员”；通用助手不进入专业专家列表；用户入口仍为“与专家协作”；保留 releaseVersion、revisionId 和不可变修订。普通用户个人创作、企业智能体部署不纳入本阶段。继续复用 Pi、现有业务服务与桌面 Web 工作台。[D1、D2]

### 1.2 本次核查边界

核查分支为 codex/axon-r1-experts，固定提交为 **eb87638f35f12fe91fea71c765a84fe148db49e7**。截至本次读取，分支头仍为该提交；仓库保留 R1 用户验收未完成的记录。[S1]

以下区分“代码已具备”与“下一步需要建设”，不把规划对象当作已实现功能。

### 2.1 两个容易误判的点

**封禁基础不等于完整安全治理。** 当前 banned 的有效状态还可能来自账号拒绝或修订缺失，不能都解释成管理员对资产的封禁；未来解除封禁也不能清除账号限制或掩盖内容损坏。[S2]

**对话创建不等于输出一段 Prompt。** 必须能够读取选定草稿、提出结构化差异、经确认保存，再进入原校验与发布流程。否则只是聊天生成文字，管理员仍需手工搬运。

### 2.2 复杂度判断（方案评估，不是工期承诺）

| 增量 | 判断 | 主要成本 |
| --- | --- | --- |
| 阶段文档调整 | 低 | 统一路线图、变更记录、任务依赖及验收归属 |
| R2 衔接要求 | 小幅增加 | 复用其原有业务服务、并发控制和审计，不建设助手或应急平台 |
| R3A 对话辅助创建 | 中等 | 草稿工具、差异确认、并发冲突、真实模型效果与权限验证 |
| R7 安全治理 | 中高 | 多模式覆盖、停止结果可观察、队列边界、外部结果不明及恢复一致性 |

详细接口和资源投入在对应轮次开工前基于届时代码细化；本稿不预填未经测量的工时或性能数字。

## 三、调整后的建设路线图

| 顺序／编号 | 建设主题 | 主要前置条件与交付 |
| --- | --- | --- |
| 1 · R1 | 统一专家基础 | 已提交实现；先完成最终验证与用户验收，不重做已完成底座 |
| 2 · R2 | 专家管理与使用配置 | 依照配套 v0.2：草稿、校验、试用、发布、普通停用、默认与使用范围 |
| 3 · R3 | Skill 管理与技能包 | 动态技能草稿、管理员创建／导入、扫描与隔离试用、版本及发布 |
| 4 · R3A（新增） | 对话辅助能力创建 | 依赖 R2、R3；管理员用对话生成／修改专家、方法型 Skill 草稿并保存 |
| 5 · R4 | 连接器规范化与 MCP | 保留原范围；让接入身份、调用、取消和回执边界可核查 |
| 6 · R5 | 后台 Agent 统一化 | 保留原顺序；后台引用统一专家，保留触发、来源、批次与投递 |
| 7 · R6 | 专家团与协作编排 | 保留原范围；顺序、有界并行、受控嵌套和执行关系 |
| 8 · R7（新增） | 能力安全治理 | 基于已落地的运行方式，完成管理员处置、影响分析、取消结果及恢复 |

### 3.1 为什么将对话创建放在 R3 后？

专家草稿服务来自 R2，技能草稿与安全准入来自 R3。此时可以复用同一管理流程，避免先做“聊天写文件”，后续再补管理契约。核心创建流程不需要等待 MCP、后台或专家团。

R3A 先使用已有获准能力目录；尚未实现的连接器或工具只能列为缺口，不能虚构可绑定对象。R4 以后扩展目录时复用同一选择契约，不要求 R3A 提前实现连接器。

### 3.2 为什么将完整安全治理放在 R6 后？

R4—R6 会新增外部调用、后台作业及并行委派场景。先形成真实执行边界，再统一管理处置，可避免提前建设抽象的全局调度／中断框架。

**后置的是统一管理与应急处置，不是基本鉴权。** 各轮新增执行入口，当轮就必须接入权限复核、用户取消及既有安全限制；不能等到 R7 才阻止越权。

### 3.3 排期取舍

本稿选择“保持旧编号、插入 R3A”。它会让 R4 的开始顺序后移，但能较早验证管理员建设能力的效率。若将对话创建全部放在 R6 之后，原路线更少受扰，但其价值反馈更晚；本稿不推荐该顺序。

安全治理无需技术上等待所有模块才能做局部版本；将完整交付安排在 R7，是为了统一验收范围，而非声称 R6 是一切封禁实现的硬依赖。

## 四、CR-02／R3A：对话辅助能力创建

### 4.1 产品定位与必交范围

在管理员的专家／技能管理页面提供“对话创建”“对话修改”入口，共用一个能力配置助手。它是管理员创作方式，不是普通专家卡片，也不改变普通用户不能创建资产的规则。

| 必须完成 | 明确不做 |
| --- | --- |
| 描述需求后生成专家名称、职责、专业指令和已有能力引用建议 | 自主授予权限、配置凭证、直接发布、停用或封禁 |
| 创建方法型 Skill 的 SKILL.md、文本参考资料和文本模板草稿 | 自动生成／调试可执行脚本、安装依赖、任意联网检索或批量自治创作 |
| 读取指定草稿或从已发布修订创建新草稿，展示逐项差异并确认保存 | 改写不可变修订、编辑系统内置核心配置或助手自身权限 |
| 解释校验／试用结果，辅助拟定代表性测试输入 | 由模型宣告试用通过或替代管理员确认 |

脚本型 Skill 仍可按 R3 由管理员导入并校验；本次新增轮次先不承担脚本自动生成。专家团与连接器的对话创建也不在 R3A 必交范围，后续可专项扩展。

### 4.2 目标流程

**管理员描述 → 助手澄清与生成建议 → 预览字段／文件差异 → 管理员确认采纳 → 保存草稿 → 原校验、试用、发布流程。**

修改场景必须显示目标专家／技能、基线草稿修订和被改字段。管理员可以拒绝或局部采纳；未采纳的字段不改。草稿被其他人修改时返回冲突，不用模型的新文本覆盖别人的变更。

### 4.3 实现原则

复用 Pi 会话执行与流式组件，增加受控管理上下文；管理工具调用 R2／R3 的同一业务服务，不直接写数据库、已发布内容目录或通过宿主 Shell 修改文件。名称和具体接口在 R3A 详细设计时确定。

会话绑定管理员身份及创作目标。工具仅允许读取获准目录、读取指定草稿、提出变更、校验，以及提交经宿主确认的草稿变更；不挂发布、授权、封禁和生产业务操作工具。保存时再次鉴权并使用草稿并发版本及幂等动作 ID。

可以用受控的管理 Skill 表达创作方法，但 Skill 本身不授予管理权限。外部资料和模型生成内容不作为确认凭证；管理聊天也不自动读取其他用户会话或任务文件。

### 4.4 独立验收

CA-01：对话创建一个专家和一个方法型 Skill，真正存为可编辑草稿；经原发布流程后可使用。

CA-02：对话修改只影响被确认的内容，旧会话和已发布修订不变；冲突、重复提交、撤权均有确定性验证。

CA-03：普通用户、伪造确认及资料中的越权指令不能执行管理写入；模型不伪造保存、校验或试用成功。

## 五、CR-01／R7：能力安全治理

### 5.1 交付定位

将既有状态守卫发展为管理员可使用、可追溯的应急处置流程。保留普通停用、用户“停止当前回复”的独立含义，不把三者合并成一个模糊的开关。

| 管理范围 | 要求 |
| --- | --- |
| 专家／技能 | 选择资产整体或具体修订，显示受影响会话、依赖和活跃执行；未加载的无关能力不连坐 |
| 专家团 | 识别成员与执行树关系；父任务停止向下传播，成员受禁后的团队结果不得伪报完整成功 |
| 连接实例 | 阻止本平台后续调用和新的自动任务准入；不把关闭连接等同于删除凭证或撤回远端操作 |
| 前台、试用、创作、后台 | 覆盖本阶段实际纳管的运行方式；保留服务身份、席位身份和管理员身份的区别 |

连接事件接收与自动处理分别设计：受影响来源默认阻止新自动执行，已接收事件仍保留；是否继续接收按来源接入策略明确设置，不静默丢弃、改投或恢复后自动重放。

### 5.2 处置过程与必要边界

**选择目标／原因 → 预览影响 → 确认并持久化禁用状态与审计 → 阻止新准入和后续调用 → 对在途执行请求取消 → 展示处置结果。**

影响预览是当时快照，不是未来请求的完整清单。状态提交后新请求仍须被守卫拦截；处置结果区分“已阻止、取消中、已停止、结果待核对”，不能只返回一个成功提示。

后台未领取任务应进入可解释的阻塞／暂停状态，保留输入、游标及原快照；在途任务尽力取消。解除封禁仅恢复之后的准入资格，不自动重放作业、消息或业务写入。

解除必须对应明确处置记录和当前状态，不能通过普通启用覆盖；专家整体、修订、主体授权等限制仍分别生效。当前代码将账号拒绝、修订缺失也投影为 banned，设计时须保留原因区别，不能一键清除所有拒绝。[S2]

### 5.3 范围控制与验收

以当前单服务进程部署为基线，不新增分布式广播、强杀宿主进程或通用事务补偿。已发出的外部操作可能继续执行；保留回执查询和结果不明提示，不保证瞬间停止、费用归零或自动回滚。

SG-01：同一受禁目标覆盖前台、试用、创作、委派和已纳管后台；无关用户／能力不受影响。

SG-02：等待人工确认、队列领取、并行子节点、外部调用在途、重启等边界可验证；旧确认不能绕过新限制。

SG-03：取消失败／效果未知如实呈现；解除不清除其他限制、不重放工作；审计与状态变更一致。

管理详情提供对象级处置记录，跨对象只增加必要查询；不顺带建设大型安全运营平台，也不授予管理员读取他人完整聊天内容的权限。

## 六、对 R2—R6 的影响与约束

### 6.1 R2 不扩容，只保留必要的服务边界

**R2 仍按配套 v0.2 实现：管理员网页创建／编辑、校验、隔离试用、发布、普通停用／恢复启用、归档、默认及使用范围。** 不增加对话助手页面、管理 Skill、模型管理工具或统一紧急处置。[D3]

R2 原已规划的草稿服务、draftRevision／draftDigest、clientActionId、管理员鉴权和操作记录，应由服务端独立于表单组织；后续对话入口复用该服务。这不是要求 R2 建设通用插件接口或预建全部未来数据表。

普通恢复只能解除 disabled，不能绕过既有 banned 或账号拒绝；普通停用允许已接受请求按原快照收尾，但拒绝新工作及追加输入。席位／账号撤权仍及时生效，不因延期封禁管理而放宽。[D3]

### 6.2 后续轮次只承担自身需要的衔接

| 轮次 | 当轮必须具备的边界 | 不提前建设 |
| --- | --- | --- |
| R2 | 草稿／发布服务与页面解耦；固定内容证据；鉴权、并发、幂等及审计 | 创作助手、封禁／解除界面 |
| R3 | 技能草稿文件与版本的受控读写；结构化校验结果；隔离试用和安全限制 | 自动生成脚本、绕过扫描的“AI 快速发布” |
| R4 | 明确连接、动作、执行身份、取消能力与结果不明语义；每次调用鉴权 | 全局紧急控制面、分布式取消 |
| R5 | 后台领取和执行时复核权限；可追踪作业与能力引用；保留暂停恢复与事件 | 重建后台调度、提前做统一处置 UI |
| R6 | 真实父子关系、活动节点、权限向下收窄、取消传播和部分失败 | 将新增编排变成不受守卫约束的第二条运行路径 |

上述要求落实到各轮详细设计和自身验收；不能只写“预留扩展”而没有调用边界，也不能提前实现整个 R7。

### 6.3 不变的约束

保留 R1 的修订摘要算法及历史解码、Pi 依赖边界、内容缓存与实时授权分离。R2 不批量重写旧版本，不把后台个人默认解析提前改造，不将“未来统一”作为删除现有业务校验的理由。

阶段总验收新增两条闭环：**管理员对话创作并经原流程发布能力；管理员对已纳管能力进行受控处置并核对结果。** 不用这两项后续验收阻塞 R2 独立交付。

### 6.4 风险控制

R3A 的主要返工风险是表单逻辑无法复用；R7 的主要返工风险是新增运行模式没有权限和取消边界。通过上表约束控制风险，不用预建微服务、消息总线或完整 Run 平台来解决尚未验证的问题。[S9]

## 七、Codex 先执行的“规划调整”工作

本节在用户确认两份方案后执行。**“先调整”指更新需求、路线图和任务上下文，不是先实现 R3A／R7，也不是先修改运行状态或生产数据。**

### 7.1 文档优先级与原文保留

经确认的本调整稿仅在 CR-01、CR-02、轮次和下表明确衔接事项上覆盖旧规划；R2 v0.2 规定本轮细节；0A／0B 未受影响的结论继续有效。代码是实现事实，不是推翻已确认需求的依据。
