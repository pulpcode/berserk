# Task and Seat Access Contract

## 1. Scope / Trigger

Read for authentication, task metadata, workspace access or account provisioning. This increment supersedes the anonymous entry assumptions in W01-8 for formal mode. Keep one PiLab/data root; no personnel handover or second chat store. Optional background intake/execution is specified separately in [Information Processing and Seat Delivery](background-execution.md).

## 2. Signatures

- `loadConfig`: defaults `LAB_AUTH_MODE=login`; requires `LAB_SESSION_SECRET` (32+ chars); `LAB_SESSION_HOURS` defaults 8. Explicit `test` permits legacy test routes on isolated data only; it cannot open a formal schema-v2 data root.
- `/api/auth/session` returns `AuthSession`; `/login {seatId,password}` resolves the enabled account for the selected seat and rotates cookie, CSRF and viewId; legacy `{username,password}` remains supported for scripts, but supplying both selectors is rejected; `/logout` revokes the authenticated session and rotates to one anonymous session before notifying other browser tabs, avoiding competing anonymous cookies.
- `/api/tasks` GET lists authorized metadata; `?clientActionId=uuid` queries this user's creation result. POST takes `{title,goal,visibility,clientActionId,context?}`. PUT `/:id` takes `{title,goal,revision,context?}`; optional metadata semantics are defined in [Multi-source Context Queries](context-analysis.md). POST `/:id/archive|reopen` takes `{revision}`; `/:id/workspace {}` lazily prepares this seat's workspace.
- `AccessStore` uses the collaboration SQLite connection. Schema v2 adds accounts, seats, auth_sessions, task_spaces, task_actions; Pi JSONL remains history authority. Missing v2 tables fail, never silently recreate them.
- `access:admin account|disable|reset --data-dir ABS --service-stopped`: offline only. `account --manage-tasks` grants public task metadata management; `--create-public` remains a compatibility alias for the same capability. Account passwords accept 10–256 characters. Password input is TTY-hidden, not argv. `reset --backup-dir ABS` moves the entire data root without overwriting a backup, copies only model settings to the new root.
- `account --control-scenarios` explicitly grants the independent `controlScenarios` seat capability; `--no-control-scenarios` revokes it. The flags are mutually exclusive. Omission preserves an existing grant during account maintenance, while newly created seats default to false. This capability does not imply task/source/model/work-overview permissions or business approval authority. Scenario routes must additionally check the configured director seat; seat names alone are not authority.

## 3. Contracts

Official `@fastify/cookie@11.1.2` / `@fastify/session@11.1.3`, opaque signed HttpOnly SameSite=strict cookie, SQLite store and absolute expiry. HTTP secure=false is used for loopback and explicitly authorized direct-HTTP demonstrations with a configured public Origin; this does not encrypt credentials or cookies. Retain exact Host/Origin enforcement, login, CSRF and seat permissions. Long-term public HTTPS deployment requires separate secure-cookie configuration. No public registration or default password. Node scrypt uses random salt, N=131072/r=8/p=1 and constant-time comparison. Login attempts are limited by source and account, with at most two concurrent password derivations. Reset/disable revokes existing sessions.

Anonymous `AuthSession.loginSeats` contains only `{id,name}` for seats with enabled accounts, including the anonymous response after logout. Never expose usernames, account display names, responsibilities, permissions or password metadata in these choices. Seat selection conveys no authority: resolve the enabled account server-side, apply the same account/IP throttling, and verify its existing password. Unknown/disabled seats and incorrect passwords return the same `INVALID_CREDENTIALS` response.

Only bootstrap/auth, static resources and minimal health are anonymous. Mutations require trusted Origin plus matching CSRF; business mutations also require `x-axon-view` matching the authenticated browser view. This marker conveys no authority. Read calls supplying it reject stale identities. SSE closes after login invalidation while accepted work continues under its captured seat. Invalid login does not cancel an Agent request.

Public TaskSpace metadata is visible to enabled business seats; business private metadata belongs to ownerSeatId. Independent administrators use the account-owned private scope below. The retained `createPublicTask` identity field and `seats.create_public` database column grant creation, editing, archiving and reopening of every public task's metadata (UI: 任务空间), regardless of owner. Public ownership alone grants no metadata-management authority. Private task metadata (UI: 个人空间) remains owner-only, including for public-task managers; every eligible business seat can create its own private spaces. `manageModelSettings` controls all shared model configuration reads and writes. Eligible workspace owners may list safe model choices and select a configured model for their own idle conversations; selection never grants configuration rights or reveals endpoints/keys. Ownership and public/private type are immutable. Existing WorkItem participant checks remain in force; cross-seat assignment requires an active public task and enabled business receiver.

WorkspaceStore retains task×storage-owner paths and native session bindings, reads current task titles from AccessStore and checks task visibility on get. The legacy `seatId` storage field may carry the reserved account scope below without creating a business seat. Empty formal indexes have no default workspace until explicit creation. Listing metadata or logging in creates no workspace. Workspaces are prepared idempotently after catalog creation; failures can be retried without another task. Creation and session binding recheck current workspace eligibility after asynchronous preparation and immediately before the index rename; revocation before rename must not publish new ownership.

Task archive uses synchronous admission counters for requests and writes, including upload, instructions, handoff copy/import and session preparation. Different sessions may run concurrently. Reject archive while any admission, live preparation or unfinished WorkItem remains. Archived history remains readable; reopening permits new work. Task metadata edits use revision CAS and record the last modifying user alongside the current result. Creation deduplicates userId+clientActionId; changed payload conflicts.

Resource snapshots/native resource records optionally include the current task id/title/goal/visibility, validated by the history decoder. Pi compaction, native history, tools and cancellation are unchanged. Task text never expands tool permission. Current model input is captured once per request.

Historical experiment projects need not be migrated. Formal startup rejects unregistered workspaces; it never publishes old data or assigns it to the first account. Backup and clean initialization are explicit, offline and tested. All persisted seat IDs (including disabled accounts) remain valid for historical handoff validation; only enabled seats are new recipients. The parent Agent receives current enabled seat id/name pairs from AccessStore on every request; testSeats is only the explicit test-mode fallback. Never derive the formal model-facing seat directory from disabled test configuration or existing work items.

The scenario capability adds `seats.control_scenarios` with a checked, denied-by-default value. Schema versions 13–18 preserve the six optional-module layouts formerly numbered 7–12; `access/schema.ts` owns their shared mapping. Background/continuous/annotation constructors preserve the capability generation while advancing their own layout. Migration retains accounts, sessions, tasks and existing capability values; existing seats receive no scenario grant. A missing capability column in a v13–v18 database is corruption and fails closed. Older binaries do not recognize the new version family; rollback requires a matching data backup. Do not infer installed modules from an unnormalized version comparison.

`Identity.canCollaborate?: boolean` is a server-computed business eligibility projection; authenticated responses always include a boolean. Old test fixtures without the field retain their prior allowed behavior. `AccessStore.isScenarioDirectorSeat(seatId)` identifies the configured director or a seat with the scene-control grant. `canCollaborate(seatId)`, `assertCanCollaborate(seatId)` and `businessSeats()` own current business eligibility: require an enabled account and exclude the configured scene director and seats granted `controlScenarios`. Runtime scene configuration supplies the reserved director ID without a new persistent role table. `seats()`/`allSeatIds()` retain real business-seat login/history semantics and never contain account storage scopes. Authenticated `AuthSession.seats` is the business candidate directory; unauthenticated `loginSeats` still includes the director. Do not filter the historical seat set to implement current eligibility. Use the shared director predicate when filtering historical supplementary candidates: a former candidate that is now a director must not remain a selectable receiver, while an ordinary disabled candidate keeps the existing unavailable/cancellable behavior. `canUseWorkspace`/`assertCanUseWorkspace` additionally admit a current independent administrator's private scope; this never grants business collaboration. `AccessStore.acquire` uses this workspace eligibility plus task ownership, while business endpoints retain `assertCanCollaborate`. Task-metadata create/update remains separate for director preparation and replay.

For each explicit login submit, read `/api/auth/session` immediately before the single login POST and use the CSRF token paired with the current Cookie. A second tab can replace the anonymous Cookie after logout while the first form still holds an old in-memory token. Do not automatically replay a login POST after failure. Cover Cookie replacement with a deterministic browser regression in addition to the two-tab logout flow.

## 4. Validation & Error Matrix

### Independent system administrators (R2 correction)

System administration belongs to an account, not to a business seat. The overall seat remains a business overview role and receives no implicit administrative grant. `access/system-roles.ts` owns denied-by-default `account_roles`; `CapabilityRoles` is a legacy compatibility export. Existing explicit legacy grants migrate without inferring additional roles. No future administration modules or general RBAC are included.

`Identity` remains the business actor with a required real seat. `AdministratorIdentity` has no seat and no business capabilities; it exposes `personalScopeId: account-<user UUID>`. `AccountIdentity` is their union. `AccessStore.identity` continues returning business actors, while `accountIdentity` owns authenticated account lookup. Fastify retains `request.identity`/`identityOf` exclusively for business code and `request.accountIdentity`/`accountIdentityOf` for authenticated account and management code. `identityOf` rejects a seatless account. Only private task/workspace/chat routes use `workspaceIdentityOf`, backed by an internal `AccessStore.workspaceIdentity(userId)` projection; its compatibility `seatId` is the account storage scope and must never enter business authorization. The authenticated union remains an administrator, not a fake business identity. Admin HTTP routes are registered outside the shared business seat hook and verify current system authority on every action and after awaited work.

Account personal spaces are existing private TaskSpaces with `ownerUserId` equal to the account UUID and legacy `ownerSeatId` equal to `personalScopeId`; createdBy/updatedBy must match that account. They reject public visibility, business context, scenario lineage and business origin records. `account-<UUID>` is a reserved storage namespace: business-seat provisioning rejects it and a persisted seat collision fails closed. Reads validate the owning seatless account and exact private ownership independently of its current enabled/role status, so disabling or revoking an administrator does not corrupt startup or rewrite history. New writes/execution require a currently enabled administrator. Public business metadata, foreign account/private business spaces, files and sessions remain invisible.

`AuthSession.identity` uses the account union. All accounts use one identity dropdown and password form. Existing `loginSeats` remains unchanged; optional `loginUsers` lists only enabled independent administrators as opaque account id plus display name, never username, grants or credential metadata. POST `/api/auth/login` accepts exactly one selector: seatId, accountId or the existing script-compatible username. Resolve accountId against current enabled seatless administrators before using the same password verification/throttling path; selecting an option conveys no authority. Seatless administrators enter the shared Axon application at `/capabilities`, with New Conversation and their own personal spaces; `/admin` and business deep links normalize to this view. Auth permits the task/workspace/session endpoint families and safe info/models/activity/capability catalogs, with exact ownership and private-only behavior enforced by services. Business context, information, work, scenario and model-configuration endpoints remain403. `/api/admin/access` reports current authority. Revocation or disabling removes the independent login identity and invalidates active access.

Personal Pi requests and readonly children register no real business query, information, work/command, annotation or spatial tools, and receive no business principal, work item or context references. They retain ordinary file tools, fixed Skills, native ask/confirmation, subagent execution and native JSONL history. Recheck the current actor/scope after preparation, after model-permit waiting, around awaited tool authorization and before subsequent model/tool calls; old confirmation cannot restore revoked authority. No new model loop or history schema is introduced.

Nullable `accounts.seat_id` requires explicit offline `migrate:access:administrators`, a verified full-root backup, and a migration record. Versions19–24 preserve the six optional business layouts formerly numbered13–18; older binaries reject them. Account IDs, passwords, existing seat links, indexes, child foreign keys, histories and grants must survive. Startup may migrate role metadata but never rebuild the accounts table. Provision with `access:admin administrator --username NAME --data-dir ABS --service-stopped`, using hidden TTY password input. It cannot convert an existing business account or create a fake seat. A new administrator-only installation may have zero business seats; historical business records still validate against the real seat set. Rollback pairs the previous binary with its corresponding complete data backup.

| Condition | Result |
| --- | --- |
| Anonymous business read/write | 401 AUTH_REQUIRED |
| Missing Origin/CSRF | 403 CSRF_REJECTED |
| Old browser view with a different login | 409 IDENTITY_CHANGED |
| Foreign private task/workspace/session | 404; no content |
| Missing public-task-management/model-write capability | 403 FORBIDDEN |
| Archived new work | 409 TASK_ARCHIVED |
| Revision/create payload mismatch, archive busy | 409 TASK_CONFLICT |
| Missing accounts, secret or catalog mapping | Explicit startup failure; no anonymous fallback |

## 5. Good / Base / Bad Cases

Base: login, create a private space, then create its first conversation.
Good: A establishes public metadata; B reads it and creates its own empty workspace. A task manager may edit this metadata without gaining access to A's or B's workspace contents; only explicit handoff shares fixed files.
Bad: treating public metadata as permission to read all workspace contents, or accepting a browser seatId as identity.

## 6. Tests Required

`tests/access.test.ts` covers login/CSRF/stale view, cross-owner public metadata management, denial after a creator loses that capability, manager isolation from foreign private spaces and workspace contents, private-owner updates, private IDs, lazy creation, native context, idempotency/CAS, archive admission, handoff participant rights, expiry/revocation, restart and backup initialization. Existing collaboration/Pi/file/HITL tests remain required. `tests/e2e/access.spec.ts` covers login/task navigation/independent identities and cross-tab logout. `probe:access` is separate live provider/Docker evidence.

`tests/admin-personal-access.test.ts` covers account scope/namespace collisions, exact private ownership, body/header spoofing, public/foreign denial and readable historical owners after disable/revoke. `tests/admin-personal-runtime.test.ts` covers the real Pi loop with replaced provider/Docker: file outputs, native ask/confirmation, readonly children, restart, queue waiting and current-role checks. `tests/admin-personal-workspace-commit.test.ts` withdraws the role after temporary-file preparation but before the index rename, for both workspace creation and session binding, and requires unchanged disk/in-memory ownership. These are deterministic evidence, not real-provider or real-container acceptance.

## 7. Wrong vs Correct

Wrong: keep an account's mounted App hidden after logout, or keep a unique enabled-seat list as the validity set for all historical business records.
Correct: unmount and abort the old client, reject stale writes on the host; preserve disabled seats as historical owners while preventing new login/assignment.
