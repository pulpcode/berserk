# Issue 管理规范

## 记录位置

- [GitHub Issues](https://github.com/pulpcode/berserk/issues) 是问题跟踪的唯一权威入口，在对应 Issue 维护编号、范围、当前状态、负责人、优先级和关闭结论。负责人和优先级按实际决定记录。
- 仓库保存版本化的技术设计、调查、实现说明、验证证据和历史记录。Issue 和相关仓库文档相互引用。引用某次复验或发布时，优先链接到固定提交及具体段落。
- Trellis 管理具体开发任务。一个任务可关联多个 Issue，一个 Issue 也可由多个任务分阶段推进。按实施范围判断任务完成和归档，按 Issue 自身的验收条件判断关闭。
- 新问题使用 GitHub 编号。旧本地编号通过 [迁移索引](../../.trellis/issues-index.md) 追溯。历史问题文件保留当时证据，本地索引只维护映射和证据入口。

## 新建与分类

1. 按现象、模块、关键词及旧编号搜索开放和已关闭的 Issue。找到同一问题时补充到原条目。一个 Issue 跟踪一个可独立判断是否完成的事项。
2. 正文记录背景和影响、预期结果、当前事实、剩余范围、可检查的完成条件和证据。缺陷写明实际与预期行为、最小复现和相关版本。改进写明要解决的现状及衡量方式。待设计事项写明待决定的问题、约束和预期决策。
3. 优先复用现有标签。公共 Issue 使用脱敏摘要或合成示例。凭据、用户原始数据和生产日志留在有权限的渠道。疑似安全漏洞通过 GitHub 私密安全渠道或维护者指定渠道报告。

## 进展与关闭

- 在原 Issue 补充有日期和来源的进展，分别记录实现、部署、技术验证和用户验收。覆盖不足时写清已验证的条件和仍需验证的场景。暂缓时写明原因及恢复条件，保持开放。
- 满足验收条件后，附相关提交、回归结果及适用的发布或用户验收记录，再以已完成关闭。取消或重复时写明理由或主 Issue，并使用对应的关闭原因。复发时可补充新证据并重新打开原 Issue。
