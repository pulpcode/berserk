# 模型平台凭证与添加流程修订方案

状态：已审阅并在当前分支实施，4316 暂缓更新 · 2026-11-19

管理员在「设置 → 模型 → 平台配置」为每个平台填写一次 API Key，平台下的模型共用该凭证。新部署可以先完成管理员初始化并进入设置，模型在补齐凭证及其他可用条件后才对业务席位开放。本稿修订[原多平台接入方案](model-provider-integration.md)中的凭证来源、平台添加流程和模型录入方式。

## 管理员怎么操作

平台页保留现有平台列表和编辑表单。新增和编辑的表单都显示一个固定名称的 **API Key** 输入框，删除「密钥环境变量」输入框。输入内容默认遮盖，已保存的密钥只显示状态。已配置的平台显示「留空保留当前密钥」，填写新值并保存即可轮换。表单在对应字段下显示校验错误，保存成功后清空输入框。`已保存` 表示后台已有密钥，实际连通性由真实模型调用验证。

| 管理员操作 | 页面与保存行为 |
| --- | --- |
| 添加平台 | 点击唯一的「添加平台」，在新增表单选择「内置平台」或「自定义 API」。添加表单和已有平台编辑分开，取消新增回到原平台。已有未保存修改时，沿用离开确认。 |
| 选择内置平台 → Kimi Code | 显示 Kimi Code 官方入口，预填 `https://api.kimi.com/coding/` 和 Anthropic Messages，API Key 始终可填。选择平台仅生成草稿，点击「保存平台」才创建。 |
| 选择自定义 API | 管理员填写平台名称、服务商标识、HTTPS 地址、协议和 API Key。协议兼容参数放在高级设置。 |
| 保存后配置模型 | 保留「模型目录」页。平台保存后可点「添加模型」，直接关联刚保存的平台，再从内置候选、在线列表或手动录入添加模型。 |

取消「使用 Kimi Code 预设」和全局「填入 Kimi Code 候选模型」两个快捷入口。平台可以先保存为草稿、以后补填 Key。编辑已有平台时，只要服务商、标准化地址和协议相同，留空就保留现有 Key；更换其中任一项且已有 Key 时，需重新填写适用于新目标的 Key，防止原凭证被发送到新目标。业务席位仍在对话中选择可用的「平台－模型」。

DSH Web 把内置提供商与自定义 API 放在同一个添加入口，内置目录提供地址、协议和模型候选。这里借用这套入口和单 Key 字段，沿用我们已有的两个管理页及平台、模型的启用规则。见 [DSH 提供商指南](https://github.com/deepseek-ai/deepseek-harness/blob/2e39e70496aa02986ca6a820c5d497e816b69d7e/docs/user/guide/providers.zh.md#L17-L31)和[添加表单源码](https://github.com/deepseek-ai/deepseek-harness/blob/2e39e70496aa02986ca6a820c5d497e816b69d7e/packages/client/ui-settings-models/src/client/ModelsSection.tsx#L589-L689)。

## 获取模型与手动录入

- **内置候选**：进入内置平台的「添加模型」表单即可看到已知候选，无需联网。Kimi Code 默认候选为 `kimi-for-coding`（K2.8 Preview），预设使用 `low` 思考。管理员选中候选后，可在模型表单补齐容量与用途确认，再决定是否启用。
- **获取模型**：已保存的平台若有明确的目录地址、鉴权方式和受支持的响应格式，且已配置 Key，管理员可以点击「获取模型」。服务端使用该平台已保存的 Key 请求目录。返回结果作为当前平台的候选，按模型 ID 去重，已在该平台登记的型号标为「已添加」。管理员勾选需要的模型并保存，只有选中的新模型写入配置。拉取本身不改变已有模型，也不自动启用新模型。
- **手动填写模型 ID**：始终保留这个入口。目录不受支持、请求失败、返回为空，或列表里没有目标模型时，管理员可以继续填写模型 ID 并完成保存。拉取失败时显示原因，保留当前草稿。

模型能否用于业务仍由现有的凭证、容量、用途确认和启用条件决定。目录返回型号只表示平台列出了该 ID，实际请求能否成功仍需验证。Kimi Code 的在线拉取以本项目所用的 API Key 和目录接口验证结果为准，首批可直接使用内置候选和手动录入。

## 后台如何保存和调用

平台写入接口统一接收可选的 `apiKey`，移除 `credentialEnv` 写入字段。后台按稳定的 `platformId` 生成内部 `credentialRef`。即使两个平台的服务商标识相同，只要平台 ID 不同，就各自维护凭证。管理员无需填写引用，读取接口只返回凭证配置状态。模型通过 `platformId` 关联平台，网页端只在平台页写入凭证。仍需兼容的旧模型保存接口也写入同一凭证存储。服务端调用前解析该平台凭证并显式交给 Pi。主对话、辅助调用和后台任务都遵守同一模型凭证来源，密钥缺失时在发出调用前提示未配置。

沿用现有 `LAB_DATA_DIR/model-settings.json`，在文件内部将平台元数据与 `credentials` 字典分开。平台记录写 `credentialRef`，字典按 `credentials[引用名]` 保存密钥。模型、平台、凭证和版本一次原子写入，复用受控文件及 `0600` 权限。这样一次保存失败或版本冲突时，现有凭证和运行时仍然配对。写入成功后更新受影响的平台模型，下次调用生效。凭证正文不回给浏览器，也不进入日志或会话记录。

## 新部署和已有环境升级

- **新部署**：完成现有账号初始化即可登录，模型 Key 可全部留空。可以保留预填的平台和模型信息。管理员为打算启用的每个平台录入自己的 Key，再根据启用状态、模型容量和用途确认开放给业务席位。
- **停止从环境加载模型 Key**：模型调用统一使用网页保存的凭证。`LLM_API_KEY`、`KIMI_API_KEY` 或旧平台指定的其他变量，即使已由 `.env` 文件或部署进程注入，也不会生效。本稿将停止读取的范围限定在模型 Key；登录签名的 `.env.auth.local`、服务端口和其他部署参数沿用现有配置方式。
- **已有网页保存的 Key**：兼容读取旧版本配置，将已保存的密钥按对应平台整理到内部字典，在首次成功保存时写入新格式。保留平台 ID、模型 ID、端点和会话的模型选择。
- **原先只靠环境提供 Key**：保留原平台和模型元数据，平台显示「未配置」；管理员在网页填入 Key 后恢复可用。如果旧部署连目录都只由部署参数生成，切换前先保存现用的平台与模型元数据，避免默认模型落回其他端点。以 4316 为例，若当前 DeepSeek 只有环境凭证，就把管理员补填及一次 DeepSeek 调用验证列为业务切换条件。上线前成对备份旧代码和模型配置，以便回退。

## 实施顺序与验收

1. 调整凭证存储、旧版本读取和运行时解析，保留版本冲突与忙态写保护。验证重启可恢复网页保存的 Key，旧本地 Key 可读，注入任何旧环境 Key 时缺失状态仍成立。
2. 收敛平台写入和读取接口，用两个相同服务商标识的平台验证凭证相互独立。覆盖留空保留、更新、更换目标必须重填、失败时旧配置仍有效，以及普通席位无法读写设置。检查响应和日志无密钥。
3. 用桌面浏览器走完「添加平台 → Kimi Code → 填 Key → 保存 → 添加模型」，并覆盖自定义 API、取消新增和已有平台编辑。检查未配置、已保存及模型可用三类状态能在各自位置看懂。
4. 用模拟目录和桌面浏览器验证三条录入路径。内置候选可离线展示，在线拉取使用当前平台的目录地址和凭证，仅保存勾选的新模型，重复 ID 只登记一次。无目录、失败或空列表时仍可手动填写。验证拉取和保存均不会绕过业务启用条件，普通席位无权拉取平台目录。
5. 用模拟传输核对每个平台的对话请求地址与鉴权。真实 Kimi Code 验收待管理员持 Key 后进行。真实调用验证通过后，按既有开放条件处理业务启用。

本次范围是凭证来源、存储、兼容迁移、平台添加和模型录入流程。原方案中的 Pi 协议适配、上下文组装、管理员权限及会话选模规则继续适用。实际操作见 [Web 模型设置说明](../../experiments/harness-lab/README.md#模型设置)。
