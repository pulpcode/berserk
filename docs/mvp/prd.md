# MVP 范围与需求

版本：v0.8；状态：总体需求修订稿；W01-1～W01-5 已实现，完整 MVP 未交付。来源和决策状态见 [decisions.md](decisions.md)。用户已明确面向垂直场景，以多轮对话交互和成熟 Harness 基础能力连接系统、处理任务与协同；先实现框架，再接入样板业务和模拟服务。MVP 业务闭环仍为多源研判与方案形成，调度实现后延。

## 1. 目标

建设面向垂直业务场景的 B/S Agent 作业与协同平台，以多轮对话为主要交互方式，依托具备 Tool、Memory、Skill、Subagent、上下文管理与压缩能力的统一 Harness，连接业务系统，完成信息处理、任务分派、协作与成果交付。

MVP 以消防救援为样板，在与生产业务隔离的模拟环境中，让不同预置席位在独立的会话和运行上下文中综合特情、态势等信息，形成有依据、可修改、可审核的方案。对标成熟 Harness 的能力机制与交互体验，不表示复制特定产品全部功能或承诺同等模型效果；垂直场景仍是产品定位。

MVP 应证明：

1. Agent 可以连续读取特情、态势和相关资料，综合不同来源的事实、变化与约束，生成和修改成果，并保留可继续工作的上下文。
2. 接收席位可以依据工作项、业务事实和指定成果版本继续作业，无需重新阅读发起席位的全部聊天历史。
3. 方案能够说明输入来源、态势判断、目标与约束、建议安排及待核实事项；输入更新后可追踪其影响，修订为新版本，最终完成审核和归档。
4. 用户可通过自然语言提出目标、追加约束、纠正信息和继续已有工作；Agent 根据目标与工具反馈组织步骤、选择并组合工具、调用 Skill 或子 Agent，处理过程不依赖唯一预编排脚本。
5. Agent 能加载 AGENTS.md／CLAUDE.md 这类持久指令文件中的约定、偏好与规则，并在获准修改后于后续运行使用更新内容；长对话接近预算时另行压缩历史，保留目标、约束、依据和未完成事项。

架构须兼容“先使用成熟内核，后续全部自研”的演进。全部自研指 Agent／Harness 能力最终由项目实现并移除原内核依赖，模型仍可使用外部 API；不要求自研基础模型、数据库或所有通用依赖。MVP 先落实可替换边界与数据保留，不承诺替换零成本或跨内核无损恢复。

MVP 完成需要 Harness 基础能力和方案成果／协同流程两部分均通过验收。方案中的人员、装备或其他资源建议只表达筹划意图，不产生资源占用或外部调度动作。业务工作分派、子 Agent 委派进入本阶段，调度系统操作继续后延。

交付先从基于 Pi 的多轮对话与最小只读工具开始：真实模型、流式回复、独立会话、基本停止／错误和原生历史，按 W01 C01～C06 独立验收。后续再完善 Memory、Skill、压缩与 Subagent，再按 W01-5 补齐 Web 上传、通用文件读写、隔离脚本执行和下载交付，之后建设完整 Run、确认恢复、业务成果版本和可替换边界，并工程化作业框架。固定资料只作工具验证，不要求首步先保存草稿 v1／v2。

框架通过后再接特情／态势、业务模板、席位规则和专业 Skill。第一增量通过不代替完整 Harness 或最终业务验收；本稿增加受控文件与脚本作业，保留下列 R01～R15；成果状态管理不作为 W01-5 的目标。

当前文件作业增量以 [W01-5](../../.trellis/tasks/09-17-w01-5-artifact-versions/review.md) 为准：按任务 × 席位划分工作区，上传成功即普通可写文件，复用 Pi 文件工具并落地最小执行沙盒及文件交付；同工作区的不同会话允许并行。专门的同文件冲突保护、独立工作副本与合并机制后置；成果业务状态、上报与版本库不在该阶段实现。

## 2. 范围基线

| 维度 | 本稿采用的建议范围 |
| --- | --- |
| 场景 | 一类代表性模拟场景，至少包含特情报告与态势快照两类输入；具体灾种和专业内容待业务确认 |
| 席位 | 信息态势席、筹划席、综合审核席；固定演示身份 |
| 任务 | 多任务空间，每空间多个会话；至少两个任务并行验证 |
| 协同 | 单层工作项；分派、签收、提交、退回、完成 |
| Agent | 前后台复用一套统一 Harness 引擎，会话与运行上下文隔离；1～2 个固定单层 SubAgent；一个后台特情处理 Agent |
| 交互 | 多轮对话作为主要工作入口；任务、工具进度、子运行、资料与成果面板辅助；标准业务动作仍有结构化入口 |
| 记忆与上下文 | Memory 指 AGENTS.md／CLAUDE.md 式持久指令文件，按工作区范围加载和受控编辑；会话历史、上下文预算与压缩另行管理 |
| 知识 | 一小批经确认资料，4～6 个版本化 Skill |
| 文件作业 | 上传、通用文件读写、隔离 Python／Shell 执行、中间产物与下载；不限定 Markdown |
| 业务成果 | 后续登记特情／态势简报、筹划方案两类；结构化数据与 Markdown 展示；不限制处理过程中的文件格式 |
| 集成 | 特情与态势信息模拟、只读信息查询及场景控制；一个地图／态势适配；资源概况、环境等输入按样板需要补充 |
| 运行 | Ubuntu 单机，服务端持久化；是否完全离线待确认 |

### 席位职责

| 席位 | 工作 | 主要交付 |
| --- | --- | --- |
| 信息态势席 | 接收分析、核实与整理信息、建立或关联任务、分派筹划、维护基础态势 | 简报、任务输入、候选标绘 |
| 筹划席 | 签收工作、综合特情与态势、检索依据、比较约束、草拟和修改方案 | 筹划方案及其依据 |
| 综合审核席 | 接收指定成果版本、检查依据、退回或确认 | 审核意见、版本确认记录 |

席位组合用于最终业务演示；具体动作权限在 M2 的 W00 形成静态矩阵，不扩展为组织和岗位管理平台。M1 先用固定测试身份和静态策略验证框架，不依赖业务席位命名与职责定案。

## 3. 样板业务流程

| 步骤 | 操作与交接 | 可观察结果 |
| --- | --- | --- |
| 1 | 场景控制注入特情消息、态势快照及样板所需参考信息 | 各来源、时间、版本已保存；特情处理作业可查询 |
| 2 | 后台特情 Agent 分析并投递提醒 | 候选摘要、来源、矛盾及待核实事项；信息席离线也保留待办 |
| 3 | 信息席核实、建立或关联任务 | 事件与任务关联，确认信息和模型分析分开 |
| 4 | 信息席分派筹划工作，筹划席签收 | 工作项包含目标、责任席位、输入和期望成果 |
| 5 | 筹划席读取特情、态势和知识依据，结合只读参考信息及专业 SubAgent 多轮研判 | 方案包含多源依据、目标、约束、建议安排、矛盾及待核实项；工具与子运行可追踪 |
| 6 | 筹划席正式提交，审核席退回 | 审核对象为具体版本，并记录退回意见 |
| 7 | 筹划席修改成新版本，再提交并获确认 | 历史保留，新版本不继承旧审批 |
| 8 | 需要时补充新信息，标识受影响成果并由人员发起方案修订 | 保留原输入快照及历史版本，新版本重新提交审核；不自动覆盖既有结论 |
| 9 | 完成方案交付并归档 | 可从任务查看输入依据、简报、方案版本、审核和运行记录 |

第二个任务复用同类场景，用于验证上下文隔离、不同输入版本和并发作业。多源报告可以存在刻意注入的矛盾；系统需保留来源并展示差异，不将矛盾静默消解为单一事实。

## 5. 不可混淆的业务规则

- 任务空间承载协作，WorkItem 承载分派，Session 承载对话，Run 承载一次执行。模型回复或 Run 结束不自动完成 WorkItem。
- 原始信息、模型候选分析与人员确认事实分层保存。缺失信息、矛盾和假设需显式标记。
- 正式成果独立于聊天存在。提交、退回和确认绑定具体版本；内容更新形成新版本。
- 方案类工作项以指定版本满足内容要求并通过审核为完成依据。方案确认只批准该成果；本阶段不触发外部调度或资源状态变更。
- 工具白名单不等于具体业务操作已获批准。成果正式提交、审核确认及共享态势发布需可追踪的服务端确认；普通检索、对话和草稿修改不因此一律挂起待确认。
- 成果共享以业务范围为边界，其他席位完整聊天历史不默认共享或注入。
- 停止运行不会撤销已经保存或提交的成果。保存、提交等操作结果不明时先查操作编号或幂等键，再决定是否重试。
- 服务常驻表示能够持续接收与消费作业；无事可做时不持续调用模型。分析完成、通知已保存、推送成功、人员已读、工作已签收分别记录。
- 模型不可用时，原始信息仍可查询；人员仍可使用结构化业务操作完成分派、审核等标准动作。
- 业务 WorkItem 分派改变责任和交付流程；Subagent 委派是一次作业内的计算分工；外部调度产生系统操作，三者不能复用同一完成状态或授权。
- 消息历史、文件式 Memory 与上下文压缩分别管理。Memory 是持续加载的规则／约定文件；压缩是历史上下文的有损整理，均不替代业务事实、成果或确认记录。
- 同任务同席位的获准会话可以加载同一份工作区指令文件，这不共享聊天历史；其他席位不默认读取该目录，共享指令按显式配置加载。更新／删除规则在下一 Run 生效，已有 Run 的输入快照不静默改写。文件中的指令不能扩大服务端权限，外部业务资料也不能自动变成指令文件。

| 用户与管理平台 | 注册、用户生命周期、组织树、岗位编排、轮班、SSO、复杂动态授权、通用审批设计器 |
| Agent 平台 | 整体规划／自主全局指挥 Agent、自由组队、递归委派、自主生成 Agent、自动修改正式 Skill |
| 持续自主执行 | 会话 Heartbeat、自主创建定时任务、Persistent Goals、无限续跑 |
| 执行控制 | 任意指令点自动恢复、复杂运行中改向；先停止再以新输入继续即可 |
| 自研内核与切换 | 本期仅落实 R15；自研第二套完整内核、多内核运营、旧会话完整迁移、运行中跨内核切换后续另行设计与实施 |
| 非受控执行与沙盒平台 | 宿主机任意命令与目录访问、未经配置的软件安装和执行联网、通用多租户沙盒运营；受控项目文件与隔离脚本执行进入 W01-5 |
| 高级交互 | 语音、视频、桌面控制、原生移动端、多人实时编辑、会话分支合并、通用即时通信 |
| 知识与成果平台 | 大规模治理、知识图谱、Skill 市场、任意格式解析、复杂 Office 排版 |
| 模拟与集成 | 生产业务接入、真实指令下发、多地图兼容、三维态势、灾情物理预测、跨区域全局优化 |
| 结构化长期记忆 | 自动抽取／召回事实、MemoryEntry 数据库、候选采纳工作流、语义／向量记忆检索、记忆置信度与失效管理；不属于本次文件式 Memory 要求 |
| 规模化设施 | 集群、高可用、多租户运营、完整运维平台、复杂消息治理 |

## 7. 验收和未决边界

M1 按 [acceptance.md](acceptance.md) 的 FG01～FG11 验证通用框架，包括记忆、压缩后连续作业和目标驱动的工具组合。完整 MVP 按 AC01～AC24 验收，覆盖业务闭环、Harness 能力与异常情况；框架通过后才推进样板业务与模拟服务。

调度扩展边界见 [design.md](design.md) 的“后续调度系统接入”。相关实现、外部接入调研和调度专用验收均放到后续阶段，不阻碍 MVP 方案交付。

用户已具备 DeepSeek、Kimi 等 API 和 Ubuntu 服务器；具体模型／协议、网络、机器资源和运行预算建设时补齐，凭证由用户写入本地且不跟踪进 Git 的配置。首步按 Pi 多轮对话路线设计；具体特情、知识样本、身份交互、动作矩阵、地图、M1 正式技术选型及质量阈值仍待确定，见 [decisions.md](decisions.md)。本稿不承诺灾情专业判断正确性、特定响应时延、准确率或任意执行点自动恢复。

这些决策按阶段解决：M0／M1 收敛模型访问、技术路线、记忆与压缩策略及运行预算；业务场景、模板、地图和质量阈值后移。工具、记忆、Skill、Subagent 和上下文压缩均为本 MVP 的基础能力，具体工程规模可以裁剪；通用工作流平台、动态插件市场和多内核运营体系仍不在范围内。
