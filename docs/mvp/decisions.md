分享页从总体立项答复开始，未显示更早的初始用户提问；B/S、Ubuntu、消防救援及与生产隔离等背景由 S1 的明确转述沿用。页面中可直接读取的用户补充为 U1、U2。

U3 的原意记录：“MVP阶段，先不加入调度相关的工作，实施延后……综合态势信息、特情信息等等多方面，形成方案等工作为最小实现目标，保留操作调度系统的设计和可能性，但是实现后延。”此项已明确，无需作为待定范围重新确认。

U4 的原意记录：“样板业务和模拟业务服务的实现顺序后移，先实现较为通用的harness和作业框架。”本次修改的是开发顺序和依赖，不取消最终的多源研判与方案交付。

本次未开展候选框架的独立源码和当前版本核验。因此，参考对象表是后续研究清单，不代表已验证其能力、许可或生产适用性。

| 恢复承诺 | 保存结果、识别中断、人工可从已有上下文继续；不做任意指令点自动续跑 | S2／S3 覆盖 S1 的宽泛恢复表述 |
| 通用代码执行 | 逻辑工作区必建；任意 Shell／代码执行及通用沙盒延后 | S2 覆盖 S1 的按需沙盒讨论 |

## 3. 待决策清单

这些事项不阻碍本次文档整理，但应在对应开发工作开始前收敛。建议仅用于比较，不视为用户已经选择。

| 编号 | 决策与待补输入 | 建议及取舍 | 最迟影响点 |
| --- | --- | --- | --- |
| D01 样板业务 | 具体特情类型、态势数据、其他来源、样本和专业审阅人 | 框架可演示后选择一类场景，至少特情与态势两类输入；不阻塞前期框架 | M2：W00、W03、W06 |
| D02 席位与身份 | 业务三席位、进入方式、动作权限和任务可见范围 | M1 先用固定测试身份／静态策略；业务矩阵在 W00 确认后配置，不等待业务定案才做身份接口 | M2：W00、W08-B；M1 基础在 W02 |
| D03 成果与确认 | 简报／方案字段、审核职责、输入更新或过期后的业务规则 | 先实现通用版本和固定确认机制；两类模板与业务规则后装配 | M2：W00、W07-B、W08-B |
| D04 模型与网络 | 首轮已确认使用现有 API；待补提供方／模型、接口协议、网络和运行预算；后续业务环境是否完全离线 | 先在允许的开发环境验证工具调用，业务数据和地图网络要求后补；不依赖样板业务 | M0：W01；业务环境在 W00／W13 前收敛 |
| D05 语言与 Harness | TypeScript 是否采纳；嵌入式核心还是包装已有运行时；选定内核与版本 | 优先验证 TypeScript＋可组合核心；包装运行时可减少部分内核工作，但需验证部署及协议约束 | W01、W02、W05 |
| D06 数据与框架 | 数据库、API／前端框架、检索方式、持久化作业实现 | 单机先减少基础设施种类；必须证明业务一致性、恢复和幂等，不以简化为由改用仅内存状态 | W01、W02 |
| D07 地图适配 | 既有框架、接口／图层／坐标、地图数据与网络约束 | 领域接入时选择单一薄适配，不作为通用作业台的启动依赖 | M2／M3：W00、W11 |
| D08 输入与文件 | 领域知识、附件格式、大小、业务成果和重置保留规则 | M1 先用文本／JSON 与 Markdown 测试成果验证保存、隔离和版本；业务格式随后确定 | M2：W00、W06、W07-B；通用机制在 W07-A |
| D09 规模与指标 | 开发机器与运行预算，后续业务并发／事件速率、质量样本和阈值 | 框架阶段测运行与成本，不等待领域准确率指标；样板确认后制定业务验收口径 | M0／M1：W01、W02；M2：W00；M4：W13 |
| D10 分工与工期 | 团队人员、可用时间、演示节点和交付形式 | 按工作包分责任，先完成 M0 再估算；当前没有人天或日期依据 | 开发排期前 |

当前优先收敛 D04～D06 中的开发模型、访问约束、技术路线和基础设施，先推进 W01。D01～D03 的样板业务、专业席位和成果规则，以及 D07～D09 的领域部分，在框架通过 FG 后再解决。调度接口、执行规则和外部系统选择仍在 MVP 之后，不作为本次交付阻塞项。

## 6. 参考对象与研究任务

以下“研究重点”归纳自原讨论，用于 W01 定向调研。只需最终采用一套内核；研究参考不等于集成依赖。

| 参考对象 | 研究重点 | MVP 的研究边界 |
| --- | --- | --- |
| [OpenAI Codex](https://github.com/openai/codex) | 会话／运行／执行事件分层、服务端状态、进度、确认及持久化 | 借鉴交互和运行协议，不复制全部 Coding Agent 产品功能 |
| [Claude 官方 Agent SDK 文档](https://code.claude.com/docs/en/agent-sdk/overview) | 多轮、工具循环、Skill、子 Agent 与人工确认的接入 | 评估模型、部署与依赖要求，再决定是否复用 |
| [pulpcode/claude-code](https://github.com/pulpcode/claude-code) | 保留用户给出的参考线索 | 原讨论提示其为非官方研究快照；使用前另查来源与许可，优先官方公开接口 |
| [Pi](https://github.com/earendil-works/pi) | 可组合核心、工具执行、上下文和事件流 | 作为嵌入候选，验证本项目需补齐的身份、文件和工具边界 |
| [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) | Agent Loop、会话记录、模块与插件边界 | 验证当前版本成熟度及兼容性，再考虑依赖 |
| [WorkBuddy](https://cloud.tencent.com/product/workbuddy) | 面向任务、角色和成果的作业台体验 | 作为交互参考，不由产品描述推断内部实现 |
| [Hermes Agent](https://github.com/NousResearch/Hermes-Agent) | 常驻服务、入口路由、独立作业、执行与结果投递、服务生命周期 | 本项目借鉴有界触发执行；不照搬全局记忆、持续目标和自动技能演化 |
| [OpenCode](https://github.com/anomalyco/opencode) | 服务端会话、异步执行、取消、事件流与程序化接入 | 验证真实持久化和中断行为；工具确认不替代业务版本审批 |

后续直接核验可从原讨论提供的 [Hermes 架构文档](https://hermes-agent.nousresearch.com/docs/developer-guide/architecture)、[OpenCode 服务端文档](https://opencode.ai/docs/server/) 和各项目官方仓库开始。验证结果应记录访问日期、依赖版本、实测场景和缺口，再更新 D05。

## 7. 文档更新规则

- 范围改变先更新 `prd.md`，再同步工作包和验收，不仅在实现备注中增加功能。
- 技术定案在本文件记录选择、依据、日期和影响，设计文档随后更新；候选方案不提前写成既定技术栈。
- 将 E1 细化建议提升为实现契约前，完成对应工作包的设计检查；存在用户产品决策的事项保留明确记录。
- 有业务代码和真实验证证据后再沉淀 Trellis 编码规范；当前占位规范不作为已实现架构的证据。
